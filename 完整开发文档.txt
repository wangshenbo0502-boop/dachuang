# 1. 文档维护规则

## 1.1 文档定位

本文档是 AI就业竞争力分析助手项目的唯一开发基准文档。

用于统一约束：

- 后端接口开发
- 前端页面开发
- 数据库设计
- AI模型调用
- RAG知识库建设
- 前后端联调
- AI辅助代码生成

项目开发过程中，所有新增功能、接口调整、数据库修改，都必须优先更新本文档，再进行代码实现。

禁止出现：

- 前端自行定义接口字段；
- 后端随意修改返回结构；
- AI生成代码脱离项目架构；
- 已规划但未完成的功能被描述为已实现。

---

## 1.2 实现事实优先级

项目开发过程中，以以下顺序作为真实依据：

```

>

```

其中：

- 已完成代码优先于规划；
- 接口实际返回优先于设计文档；
- 未实现功能不得提前宣传。

本项目面向高校学生就业能力提升场景，利用：

- RAG知识增强检索（Retrieval-Augmented Generation）

- 岗位智能匹配算法
- AI简历优化

构建一个能够帮助学生：

1. 分析自身就业竞争力；
2. 匹配目标岗位；
3. 发现技能差距；
4. 制定成长路径；
5. 优化求职材料；

的一体化 AI 就业辅助平台。

# 10. 后端 API 接口契约（API Contract）

## 10.1 API设计原则

所有后端接口必须遵循统一 RESTful 规范。

接口统一前缀：

```
/api/v1
```

完整格式：

```
HTTP方法 + /api/v1 + 业务路径
```


示例：

```
GET

/api/v1/jobs
```


---

# 10.2 通用请求规范


## Header要求


所有需要身份认证的接口：

```
Authorization:

Bearer {access_token}
```


示例：

```
Authorization:
Bearer eyJhbGciOiJIUzI1...
```


---

# 10.3 通用响应结构


所有接口必须返回统一结构：


```json
{
    "code":200,

    "message":"success",

    "data":{}
}
```


字段说明：


|字段|类型|说明|
|-|-|-|
|code|Integer|业务状态码|
|message|String|返回提示|
|data|Object|业务数据|


---

# 10.4 API状态码规范


## 系统级状态码


|状态码|含义|
|-|-|
|200|请求成功|
|201|创建成功|
|400|参数错误|
|401|身份认证失败|
|403|权限不足|
|404|资源不存在|
|500|服务器异常|


---

## 业务错误码


|错误码|说明|
|-|-|
|10001|用户不存在|
|10002|密码错误|
|10003|Token失效|
|20001|岗位不存在|
|20002|岗位匹配失败|

# 11. 用户认证模块 API


## 11.1 用户注册


### 功能说明

创建系统用户账号。

该接口只负责：

- 用户创建；
- 密码加密；
- 基础信息初始化。


不负责：

- 用户画像生成；
- 岗位匹配；
- AI分析。


---

## 接口信息


```
POST

/api/v1/auth/register
```


权限：

```
无需登录
```


---

## 请求参数


```json
{
    "username":"student001",

    "password":"123456",

    "email":"student@test.com"
}
```


字段说明：


|字段|类型|必填|说明|
|-|-|-|-|
|username|string|是|用户名|
|password|string|是|密码|
|email|string|否|邮箱|


---

## 后端处理流程


```
接收参数

↓

参数校验

↓

检查用户名是否存在

↓

密码Hash加密

↓

写入数据库

↓

返回用户ID
```


---

## 返回数据


```json
{
    "code":201,

    "message":"register success",

    "data":
    {
        "user_id":10001
    }
}
```

# 18. 数据库设计规范（Database Specification）

数据库主要负责：

- 用户基础数据存储；
- 学生能力数据管理；
- 岗位信息管理；
- AI分析结果保存；

数据库只负责：


# 27.2 开发顺序约束


所有功能必须按照以下顺序开发：


## 第一步：确定业务需求


明确：

- 用户需要完成什么操作；

系统输出：

开发前必须确定：

- URL路径；
- 请求方式；
- 请求参数；
- 返回结构；
- 错误处理。


禁止：

先写代码，再补接口。


---

## 第三步：数据库设计


根据接口确定：

- 数据表；
- 字段；
- 数据关系。


---

## 第四步：后端实现


开发顺序：


```text
Model

↓

Schema

↓

Repository

↓

Service

↓

API Router

↓

Test
```


---

## 第五步：前端接入


前端只根据：

API文档

进行调用。


禁止：

根据后端代码猜测字段。

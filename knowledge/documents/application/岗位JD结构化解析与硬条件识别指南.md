# 岗位 JD 结构化解析与硬条件识别指南

岗位描述不是一组等待做关键词计数的文本。它通常混合了准入条件、工作任务、能力要求、宣传话术、福利信息和合规风险。如果系统只计算“简历与 JD 的关键词相似度”，容易把不能投的岗位排到前面，也可能把具备可迁移能力的候选人错误判为不匹配。可靠的岗位解析应先识别约束，再理解能力，最后给出证据充分、可人工复核的结论。

## 一、六层岗位信息模型

第一层是**硬条件**。它决定候选人是否具备基本申请资格，包括毕业年份、学历层次、专业或学科门类、工作年限、身份要求、工作地点、到岗时间、实习时长、语言成绩、资格证书和是否接受出差等。只有原文出现明确限制时才标为硬条件；“优先”“更佳”“有经验者优先”不能直接升级为淘汰条件。

第二层是**必备能力**。它指完成核心工作不可缺少的知识和技能，如 Java 服务端开发、数据分析、用户研究、机械制图或英文书面沟通。必备能力不等于必须出现完全相同的工具名。例如“具备关系型数据库基础”可由 MySQL、PostgreSQL 等证据支撑，但“必须持有法律职业资格证”不能用相邻经验替代。

第三层是**加分项**。它提高竞争力但不应直接阻断投递，如开源贡献、竞赛经历、行业项目、多语言能力或特定云平台经验。系统应单独展示，不要和硬条件混成一个总分。

第四层是**工作职责**，描述入职后要完成的任务、对象、产出和协作关系。职责动词比宣传形容词更有价值，例如“设计、实现、分析、运营、维护、协同、交付”。

第五层是**候选人偏好**，包括城市、薪资区间、行业、企业规模、工作方式和成长方向。偏好不满足通常意味着“不推荐”，不等于“不合格”。

第六层是**风险信息**，包括主体不清、岗位职责与名称明显不一致、要求缴费或提供无关敏感信息、薪资描述异常、联系方式跳转到不明渠道等。风险信息必须单独提示，不能被高匹配分掩盖。

## 二、解析流程与字段规范

建议先保存岗位原始快照，包括页面地址、职位名称、企业名称、抓取时间和原始正文。之后进行版块识别、句子切分、条件抽取、术语归一化、冲突检测和置信度评估。任何后续摘要都应能回到原文片段，避免网页更新后无法解释历史推荐。

结构化结果至少包含以下字段：

| 字段 | 含义 | 示例 |
|---|---|---|
| `job_title` | 原始岗位名 | 后端开发实习生 |
| `eligibility` | 硬条件列表 | 2027届、每周到岗4天 |
| `required_skills` | 必备能力 | Java、SQL、计算机基础 |
| `preferred_skills` | 加分项 | 微服务项目、开源经历 |
| `responsibilities` | 任务与产出 | 开发接口、排查线上问题 |
| `preferences` | 用户侧偏好 | 城市、行业、薪资 |
| `risk_flags` | 风险及证据 | 要求先缴培训费 |
| `evidence_spans` | 对应原文片段 | 句子及字符位置 |
| `confidence` | 字段置信度 | high、medium、low |
| `unknowns` | 无法确定的信息 | 是否可转正 |

日期、薪资、学历和工作年限应保留单位及上下文。“本科及以上”和“本科优先”不是同一条件；“1—3 年”与“有项目经验”也不能互换。解析器无法判断时应输出“未知”或“待确认”，不要根据企业名、岗位名或历史岗位自行补齐。

## 三、硬条件判定规则

硬条件判定采用“原文强度 + 字段类型 + 排除语义”三步法。包含“必须、须、仅限、不接受、至少、不得、要求持有”等明确限制词，且对象属于资格字段时，可判为硬条件；包含“优先、加分、熟悉更佳、最好”时通常归为加分项。招聘文案中的“我们希望你”“期待你”需要结合完整句子判断，不应机械处理。

系统应识别条件组合。例如“2026年9月至2027年8月毕业的本科及以上学生”同时约束毕业时间和学历；“每周至少到岗四天，连续三个月”同时约束频率和周期。若用户档案没有毕业月份，结果应是“需补充信息”，而不是直接通过或淘汰。

对专业限制要保留原始范围。“计算机相关专业”可以建立专业同义词集合，但不能无限扩大到所有理工科。对证书、政治面貌、年龄、性别等字段还要进行合规和歧视风险提示，系统不应因为不合理要求而替招聘方强化自动筛选。

## 四、从岗位要求到能力证据

岗位匹配的最小解释单元是“要求—能力—证据”。每个必备要求都应指向用户档案中的课程、项目、实习、竞赛、作品、证书或可验证产出。例如 JD 要求“能够定位后端性能问题”，可引用压测报告、日志分析记录和优化前后结果；仅写“熟悉性能优化”属于弱证据。

匹配结果建议分为四类：已满足、有相邻能力可迁移、缺少证据、明确不满足。系统可以给出补证建议，如上传仓库链接、补充项目职责、说明到岗周期，但不得把“愿意学习”自动转换成“已掌握”。总分之外还应展示硬条件通过情况、核心能力覆盖率、证据强度和风险提示。

## 五、岗位风险与人工复核

教育部和人力资源社会保障部门持续提醒求职者防范虚假招聘、乱收费、培训贷、扣押证件、非法中介和以招聘名义收集银行卡等敏感信息。岗位解析模块可以识别风险信号，但不能直接断言企业违法。正确表述应为“检测到需要进一步核验的信号”，并引导用户到正规渠道验证招聘主体和职位。

以下情况必须进入人工复核：岗位正文过短；企业名称和页面主体不一致；薪资单位缺失；出现收费、押金、垫资或下载不明应用；要求提供身份证照片、银行卡、验证码等与当前申请阶段不相称的信息；解析结果存在互相冲突的毕业年份或地点。

## 六、验收清单

- 是否保存了原始 JD 快照和访问时间；
- 是否把硬条件、必备能力和加分项分开；
- 每个关键字段是否有原文证据位置；
- 未知信息是否明确标记，而不是由模型脑补；
- 是否允许用户修改错误解析并留下修订记录；
- 推荐理由是否能说明“为什么适合”和“为什么可能不适合”；
- 是否对收费、敏感信息和不明链接给出风险提示；
- 是否避免使用无法核验的“ATS 淘汰率”等营销数字。

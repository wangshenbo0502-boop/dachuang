# 数据分析看板（Dashboard）

## 项目概述

找一个公开数据集，完成数据清洗、分析和可视化，最终呈现为一个交互式的数据分析看板。面试中展示此项目非常有说服力。

## 核心功能

- 数据清洗流程（缺失值/异常值/格式统一）
- 多维度统计指标
- 交互式图表（折线/柱状/饼图/热力图）
- 数据筛选器（按时间/类别/地区）
- 数据导出（CSV/Excel）

## 技术收获

- 真实数据的清洗经验（数据质量从来不会完美）
- Pandas 高级操作（多级索引、透视表）
- 选择合适的图表类型表达数据
- 用 API 提供分析结果给前端

## 适合人群

有 Python 基础、想往数据分析方向发展的同学

## 前置技能

- Python
- Pandas 基础
- SQL基础

## 技术难点与面试展开点

BI 看板项目的深度在**数据链路**与**聚合查询性能**，而不是画图本身。**数据链路分层**要能画出来：业务库（OLTP，MySQL）→ 同步（CDC：Canal/Debezium 监听 binlog，或定时 ETL）→ 分析库（OLAP：ClickHouse/StarRocks/Doris 的选型理由——列存、预聚合、海量扫描快）→ API 层聚合 → 前端渲染。理解"为什么不用 MySQL 直接出报表"（大表聚合拖垮线上库）是数仓思维的第一课。

**聚合查询优化**：预聚合（按天/小时的汇总表，空间换时间）、物化视图、漏斗与留存类复杂指标的计算（留存矩阵的 SQL 实现是经典面试题）、大数据量分页导出的流式处理（避免 OOM）。

**前端可视化**：ECharts 图表选型（柱/线/饼/漏斗/热力的适用场景）、大数据量渲染性能（dataZoom、降采样）、看板布局（拖拽栅格）、权限（行级数据权限——不同部门看不同数据）。实时方向：WebSocket 推送 + 增量刷新，或 Flink 实时聚合后入库。

**面试高频**：OLTP 与 OLAP 区别、为什么列式存储适合分析、留存的 SQL 实现、看板大数据量卡顿怎么优化、实时链路（Flink + ClickHouse）的设计。

## 项目演进路线与推荐资源

**演进路线**：基础版（MySQL 聚合 + ECharts 静态看板）→ 进阶版（CDC/定时 ETL 到分析库、预聚合表、留存 SQL）→ 完整版（行级数据权限、WebSocket 实时刷新、大数据量导出流式优化）。附上一份"指标口径文档"（GMV/留存/漏斗的定义与计算 SQL），体现数据严谨性。

**推荐资源**：Apache ECharts 官方示例库；ClickHouse / Doris 官方文档（OLAP 选型对照）；《数据仓库工具箱》（Kimball，维度建模经典）；Canal 官方文档（MySQL binlog 同步）。

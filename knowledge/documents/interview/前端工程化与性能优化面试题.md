## Q1: 浏览器输入 URL 到页面渲染的全过程是什么？

**考察点**: 网络请求、DNS解析、TCP连接、HTTP请求、浏览器渲染等完整流程

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

从输入 URL 到页面显示的完整过程：

1. **URL 解析与 DNS 解析**
   - 浏览器解析 URL，确定协议、域名、路径等
   - 检查浏览器缓存 → 系统缓存 → hosts 文件
   - DNS 域名解析，将域名转换为 IP 地址

2. **TCP 连接（三次握手）**
   - 客户端发送 SYN 包
   - 服务器返回 SYN+ACK 包
   - 客户端发送 ACK 包，连接建立

3. **HTTPS 握手（如果是 HTTPS）**
   - 客户端发送支持的加密套件
   - 服务器返回证书
   - 客户端验证证书，生成会话密钥
   - 使用会话密钥进行加密通信

4. **发送 HTTP 请求**
   - 构建请求报文（请求行、请求头、请求体）
   - 发送请求到服务器

5. **服务器处理请求并响应**
   - 服务器处理请求
   - 返回响应报文（状态码、响应头、响应体）

6. **浏览器解析与渲染**
   - 解析 HTML 构建 DOM 树
   - 解析 CSS 构建 CSSOM 树
   - 合并构建渲染树（Render Tree）
   - 布局（Layout/Reflow）：计算元素位置和大小
   - 绘制（Paint）：将元素绘制到屏幕上
   - 合成（Composite）：将多个层合成显示

7. **断开连接（TCP 四次挥手）**

**答案解析**:

**DNS 解析过程**：
- 浏览器缓存 → 操作系统缓存 → hosts 文件 → 路由器缓存 → ISP DNS 缓存 → 根域名服务器 → 顶级域名服务器 → 权威域名服务器

**TCP 三次握手**：
```
客户端 → SYN → 服务器
客户端 ← SYN+ACK ← 服务器
客户端 → ACK → 服务器
```
为什么是三次？防止已失效的连接请求报文段突然又传到服务端，导致服务端一直等待。

**TCP 四次挥手**：
```
客户端 → FIN → 服务器
客户端 ← ACK ← 服务器
客户端 ← FIN ← 服务器
客户端 → ACK → 服务器
```
为什么是四次？因为 TCP 是全双工的，双方都需要单独关闭。

**浏览器渲染流程（关键）**：
```
HTML → DOM 树
CSS  → CSSOM 树
        ↓
    渲染树（Render Tree）
        ↓
    布局（Layout）
        ↓
    绘制（Paint）
        ↓
    合成（Composite）
```

**影响渲染的关键因素**：
- CSS 阻塞渲染（CSSOM 构建会阻塞渲染树构建）
- JS 阻塞解析（JS 可能修改 DOM 和 CSSOM）
- 优化策略：CSS 放头部，JS 放底部，使用 async/defer

**扩展问题**:
- DNS 预解析怎么做？
- 什么是 CDN？CDN 加速的原理是什么？
- CSS 为什么要放头部，JS 为什么要放底部？
- async 和 defer 的区别？
- 什么是关键渲染路径？如何优化？

## Q2: 浏览器的渲染流程是什么？（重绘、回流/重排）

**考察点**: 浏览器渲染机制、重绘回流的概念、优化策略

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**浏览器渲染流程**：
1. 解析 HTML 生成 DOM 树
2. 解析 CSS 生成 CSSOM 树
3. DOM + CSSOM 生成渲染树（Render Tree）
4. **布局（Layout / Reflow）**：计算元素的几何信息（位置、大小）
5. **绘制（Paint / Repaint）**：将元素绘制到像素点
6. **合成（Composite）**：将多个图层合成显示

**回流（Reflow / 重排）**：
当元素的几何属性（位置、大小）发生变化时，浏览器需要重新计算元素的几何属性，构建渲染树。

**重绘（Repaint）**：
当元素的外观（如颜色、背景）发生变化，但布局没有改变时，浏览器重新绘制元素。

**关系**：回流一定会触发重绘，重绘不一定触发回流。

**答案解析**:

**触发回流的操作**：
- 添加或删除可见的 DOM 元素
- 元素位置、尺寸、内容变化
- 页面渲染初始化
- 浏览器窗口尺寸变化
- 获取某些属性（offsetWidth、clientWidth、scrollTop 等）

**触发重绘的操作**：
- 颜色变化
- 背景变化
- 文本方向变化
- 阴影变化

**获取布局信息触发回流**：
浏览器为了保证获取的值是准确的，会强制刷新队列，触发回流。
```javascript
// 以下属性的读取会触发回流
element.offsetWidth
element.clientTop
element.scrollTop
getComputedStyle()
```

**优化策略**：
1. **减少回流次数**：
   - 批量修改 DOM（使用 DocumentFragment 或隐藏元素后修改）
   - 使用 class 批量修改样式
   - 避免频繁读取布局属性

2. **减少回流范围**：
   - 使用绝对定位脱离文档流
   - 局部修改只影响局部

3. **使用 CSS3 硬件加速**：
   - transform、opacity 不会触发回流，只触发合成
   - 使用 will-change 提示浏览器

```javascript
// 不好的写法（多次回流）
element.style.left = '10px';
console.log(element.offsetLeft); // 强制回流
element.style.top = '10px';
console.log(element.offsetTop); // 强制回流

// 好的写法（先读后写）
const left = element.offsetLeft;
const top = element.offsetTop;
element.style.left = left + 10 + 'px';
element.style.top = top + 10 + 'px';
```

**扩展问题**:
- 哪些 CSS 属性会触发回流/重绘/合成？
- 如何使用 Chrome DevTools 分析重绘回流？
- transform 为什么不会触发回流？
- 什么是合成层？如何创建合成层？
- 虚拟列表的原理是什么？

## Q3: 什么是跨域？如何解决跨域问题？

**考察点**: 同源策略、跨域概念、跨域解决方案

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**同源策略（Same-Origin Policy）**：
同源策略是浏览器的安全策略，协议、域名、端口三者完全相同才是同源。不同源的文档或脚本不能相互访问资源。

**跨域**：
当一个请求 URL 的协议、域名、端口三者之间任意一个与当前页面 URL 不同，即为跨域。

**跨域解决方案**：
1. **JSONP**：利用 script 标签不受同源策略限制的特性，只支持 GET
2. **CORS（跨域资源共享）**：服务端设置响应头，标准解决方案
3. **代理服务器**：Nginx 反向代理、Node.js 中间件代理
4. **postMessage**：窗口间通信
5. **WebSocket**：不受同源策略限制
6. **document.domain**：主域相同子域不同时使用
7. **location.hash + iframe**：利用 hash 变化传递数据
8. **window.name + iframe**：利用 name 属性持久化数据

**答案解析**:

**CORS 详解（最常用）**：
CORS 是 W3C 标准，通过服务端设置响应头实现跨域。

```javascript
// 服务端设置（Node.js 示例）
app.use((req, res, next) => {
  res.header('Access-Control-Allow-Origin', '*'); // 允许所有源
  res.header('Access-Control-Allow-Methods', 'GET,POST,PUT,DELETE,OPTIONS');
  res.header('Access-Control-Allow-Headers', 'Content-Type,Authorization');
  res.header('Access-Control-Allow-Credentials', 'true'); // 允许携带 Cookie
  if (req.method === 'OPTIONS') {
    return res.sendStatus(200);
  }
  next();
});
```

CORS 请求分为两种：
- **简单请求**：GET/HEAD/POST，Content-Type 为 application/x-www-form-urlencoded、multipart/form-data、text/plain
- **非简单请求**：先发送 OPTIONS 预检请求，服务器确认后才发送实际请求

**JSONP 实现**：
```html
<!-- 前端 -->
<script>
function callback(data) {
  console.log(data);
}
</script>
<script src="http://api.example.com/data?callback=callback"></script>
```

```javascript
// 服务端
app.get('/data', (req, res) => {
  const data = { name: 'test' };
  res.send(`${req.query.callback}(${JSON.stringify(data)})`);
});
```
JSONP 缺点：只支持 GET，不安全，容易被 XSS 攻击。

**Nginx 反向代理**：
```nginx
server {
  listen 80;
  server_name example.com;
  
  location /api/ {
    proxy_pass http://api.example.com/;
  }
}
```

**扩展问题**:
- CORS 中简单请求和复杂请求的区别？
- 携带 Cookie 的跨域请求需要注意什么？
- JSONP 的原理是什么？有什么缺点？
- postMessage 如何使用？有什么安全问题？
- 预检请求（OPTIONS）的作用是什么？

## Q4: HTTP 和 HTTPS 的区别是什么？

**考察点**: HTTP 与 HTTPS 的区别、HTTPS 加密原理、SSL/TLS 握手

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

| 特性 | HTTP | HTTPS |
|------|------|-------|
| 端口 | 80 | 443 |
| 安全性 | 明文传输，不安全 | SSL/TLS 加密，安全 |
| 证书 | 不需要 | 需要 CA 证书 |
| 速度 | 较快 | 略慢（加密解密开销） |
| 协议 | 应用层协议 | HTTP + SSL/TLS |
| SEO | 一般 | 搜索引擎更友好 |

**HTTPS 加密原理**：
HTTPS 采用混合加密机制：
1. **非对称加密**：用于交换会话密钥（RSA、ECDHE 等）
2. **对称加密**：用于加密传输的数据（AES 等）
3. **哈希算法**：用于验证数据完整性（SHA-256 等）

**SSL/TLS 握手过程**：
1. 客户端发送支持的加密套件和随机数
2. 服务器返回证书、选定的加密套件和随机数
3. 客户端验证证书，生成预主密钥，用公钥加密后发送
4. 双方用预主密钥和随机数生成会话密钥
5. 使用会话密钥进行对称加密通信

**答案解析**:

**HTTPS 握手详细过程**：

1. **Client Hello**：
   - 客户端支持的 TLS 版本
   - 随机数 random1
   - 支持的加密套件列表
   - 支持的压缩方法

2. **Server Hello**：
   - 确认 TLS 版本
   - 随机数 random2
   - 选定的加密套件
   - 选定的压缩方法

3. **Certificate**：服务器发送数字证书

4. **Server Key Exchange**（可选）：密钥交换相关信息

5. **Server Hello Done**：服务器握手结束

6. **Client Key Exchange**：
   - 客户端生成预主密钥（pre-master key）
   - 用服务器公钥加密后发送

7. **双方计算会话密钥**：
   - 用 random1 + random2 + pre-master key 生成会话密钥

8. **Change Cipher Spec & Finished**：
   - 双方确认密钥交换完成
   - 发送 Finished 消息验证握手

**证书验证**：
- 验证证书是否过期
- 验证证书是否被吊销
- 验证证书是否由可信 CA 签发
- 验证证书域名是否匹配

**HTTPS 的性能优化**：
- 会话复用（Session ID / Session Ticket）
- OCSP Stapling（证书状态装订）
- False Start（提早发送应用数据）
- HTTP/2 多路复用

**扩展问题**:
- HTTPS 的握手过程是怎样的？
- 什么是对称加密和非对称加密？
- 数字证书的作用是什么？如何验证证书？
- HTTPS 一定安全吗？有哪些攻击方式？
- HTTP/2 和 HTTP/1.1 的区别？

## Q5: HTTP 状态码及含义

**考察点**: 常见 HTTP 状态码的分类和含义

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

HTTP 状态码分为 5 类：
- **1xx**：信息性状态码，请求已接收，继续处理
- **2xx**：成功状态码，请求已成功处理
- **3xx**：重定向状态码，需要进一步操作完成请求
- **4xx**：客户端错误状态码，请求有错误
- **5xx**：服务端错误状态码，服务器处理请求出错

**常见状态码**：

**2xx 成功**：
- **200 OK**：请求成功
- **201 Created**：资源创建成功
- **204 No Content**：成功但无返回内容
- **206 Partial Content**：范围请求成功

**3xx 重定向**：
- **301 Moved Permanently**：永久重定向
- **302 Found**：临时重定向
- **304 Not Modified**：资源未修改，使用缓存
- **307 Temporary Redirect**：临时重定向（保持请求方法）
- **308 Permanent Redirect**：永久重定向（保持请求方法）

**4xx 客户端错误**：
- **400 Bad Request**：请求参数错误
- **401 Unauthorized**：未认证
- **403 Forbidden**：禁止访问（权限不足）
- **404 Not Found**：资源不存在
- **405 Method Not Allowed**：方法不允许
- **408 Request Timeout**：请求超时
- **409 Conflict**：资源冲突
- **413 Payload Too Large**：请求体过大
- **429 Too Many Requests**：请求过多（限流）

**5xx 服务端错误**：
- **500 Internal Server Error**：服务器内部错误
- **502 Bad Gateway**：网关错误（代理服务器收到无效响应）
- **503 Service Unavailable**：服务不可用（过载或维护）
- **504 Gateway Timeout**：网关超时（代理服务器超时）

**答案解析**:

**301 和 302 的区别**：
- 301：永久重定向，搜索引擎会更新索引，浏览器会缓存
- 302：临时重定向，搜索引擎不会更新索引

**302、307、308 的区别**：
- 302：临时重定向，可能改变请求方法（POST 可能变 GET）
- 307：临时重定向，保持请求方法不变
- 308：永久重定向，保持请求方法不变

**304 协商缓存**：
浏览器发送请求带 If-Modified-Since / If-None-Match 头，服务器判断资源未修改则返回 304，浏览器使用缓存。

**401 和 403 的区别**：
- 401：未认证（没有登录或 token 无效）
- 403：已认证但无权限访问

**502 和 504 的区别**：
- 502：网关/代理服务器从上游服务器收到了无效响应
- 504：网关/代理服务器等待上游服务器超时

**扩展问题**:
- 301 和 302 对 SEO 有什么影响？
- 304 的协商缓存流程是怎样的？
- 401 和 403 的区别是什么？
- 500 和 503 的区别是什么？
- 遇到 502/504 错误如何排查？

## Q6: GET 和 POST 的区别是什么？

**考察点**: GET 和 POST 请求的区别、HTTP 语义、安全性

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

| 特性 | GET | POST |
|------|-----|------|
| 作用 | 获取资源 | 提交资源 |
| 参数位置 | URL 中 | 请求体中 |
| 参数长度 | 受 URL 长度限制（浏览器限制，非 HTTP 标准限制） | 无限制（理论上） |
| 安全性 | 参数暴露在 URL 中，不安全 | 参数在请求体，相对安全 |
| 缓存 | 可以被缓存 | 一般不缓存 |
| 书签 | 可以收藏为书签 | 不可以 |
| 历史记录 | 保留在浏览器历史中 | 不保留 |
| 幂等性 | 幂等（多次请求结果相同） | 非幂等 |
| 编码类型 | application/x-www-form-urlencoded | 多种（form-data、json、x-www-form-urlencoded 等） |

**答案解析**:

**HTTP 语义上的区别**：
- GET：幂等、安全的方法，用于获取资源，不应该改变服务器状态
- POST：非幂等、非安全的方法，用于提交数据，可能改变服务器状态

**关于安全性**：
两者本质上都不安全，都是明文传输（HTTP 下）。
- GET 参数在 URL 中，更容易被看到
- POST 参数在 body 中，但抓包一样能看到
- 真正安全需要 HTTPS

**关于长度限制**：
- HTTP 协议本身没有限制 URL 长度
- 限制来自浏览器和服务器
  - IE：约 2048 字符
  - Chrome：约 8000 字符
  - 服务器（如 Apache）：约 8192 字节

**GET 请求可以带请求体吗？**：
HTTP 规范没有禁止 GET 请求带 body，但实际中很多浏览器和服务器不支持或不处理 GET 的 body，不推荐使用。

**POST 请求参数可以放在 URL 中吗？**：
可以，技术上没有限制，但不符合语义规范。

**其他 HTTP 方法**：
- PUT：更新资源（幂等）
- DELETE：删除资源（幂等）
- PATCH：部分更新资源
- HEAD：获取响应头
- OPTIONS：获取支持的方法

**扩展问题**:
- GET 和 POST 在 TCP 层面有什么区别？（是否两次发包）
- 什么是幂等性？哪些 HTTP 方法是幂等的？
- PUT 和 POST 的区别？
- GET 请求的参数能被缓存吗？
- 为什么 POST 请求会先发 OPTIONS？

## Q7: Cookie、Session、LocalStorage、SessionStorage 的区别？

**考察点**: 四种存储方式的区别、使用场景、安全性

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

| 特性 | Cookie | Session | LocalStorage | SessionStorage |
|------|--------|---------|--------------|----------------|
| 存储位置 | 客户端 | 服务端 | 客户端 | 客户端 |
| 存储大小 | 4KB 左右 | 无限制（服务端内存） | 5MB 左右 | 5MB 左右 |
| 生命周期 | 可设置过期时间 | 会话级别（默认） | 永久，需手动清除 | 会话级别（关闭标签页失效） |
| 与服务器通信 | 每次请求自动携带 | 通过 Cookie 传递 SessionID | 不自动发送 | 不自动发送 |
| 作用域 | 同源窗口共享 | 同源 | 同源窗口共享 | 仅当前标签页 |
| 安全性 | 有 XSS、CSRF 风险 | 相对安全 | 有 XSS 风险 | 有 XSS 风险 |

**答案解析**:

**Cookie**：
- 由服务端通过 Set-Cookie 响应头设置
- 每次请求自动携带在请求头中
- 可以设置 HttpOnly（防止 JS 读取，防 XSS）
- 可以设置 Secure（仅 HTTPS 下传输）
- 可以设置 SameSite（防止 CSRF）

```http
Set-Cookie: name=value; Path=/; Expires=Wed, 21 Oct 2026 07:28:00 GMT; HttpOnly; Secure; SameSite=Strict
```

**Session**：
- 存储在服务端（内存、数据库、Redis 等）
- 通过 Cookie 中的 SessionID 识别用户
- 默认关闭浏览器失效（可配置）
- 安全性较高，但有服务端开销

**LocalStorage**：
- HTML5 新增
- 持久化存储，除非手动清除否则一直存在
- 同源窗口共享
- 只能存字符串，需 JSON 序列化

```javascript
localStorage.setItem('key', 'value');
localStorage.getItem('key');
localStorage.removeItem('key');
localStorage.clear();
```

**SessionStorage**：
- HTML5 新增
- 会话级存储，关闭标签页或浏览器即失效
- 仅当前标签页可用，不同标签页不共享
- 刷新页面不会丢失

**使用场景建议**：
- Cookie：身份认证、会话管理（配合 Session）
- Session：用户登录状态、敏感数据
- LocalStorage：长期存储的用户偏好设置、缓存数据
- SessionStorage：临时存储、表单数据暂存

**安全问题**：
- XSS 攻击可以窃取 LocalStorage 和非 HttpOnly 的 Cookie
- CSRF 攻击利用 Cookie 自动发送的特性
- 敏感数据不应存在客户端

## Q9: 什么是 CDN？原理是什么？

**考察点**: CDN 的概念、工作原理、缓存策略、回源

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**CDN（Content Delivery Network，内容分发网络）**：
CDN 是构建在现有网络基础之上的智能虚拟网络，依靠部署在各地的边缘服务器，通过中心平台的负载均衡、内容分发、调度等功能模块，使用户就近获取所需内容，降低网络拥塞，提高用户访问响应速度和命中率。

**原理**：
1. 用户访问网站，DNS 解析时将域名解析到 CDN 节点
2. CDN 调度系统根据用户 IP 选择最近的节点
3. 如果节点缓存了资源，直接返回给用户
4. 如果没有缓存，CDN 节点回源到源站获取资源
5. CDN 节点缓存资源并返回给用户

**CDN 的核心功能**：
- 就近访问，降低延迟
- 减轻源站压力
- 隐藏源站 IP，提高安全性
- 抵御 DDoS 攻击

**答案解析**:

**CDN 工作流程**：
```
用户请求
  ↓
DNS 解析 → CDN 全局负载均衡（GSLB）
  ↓
选择最近的 CDN 节点
  ↓
缓存命中？
  ├─ 是 → 直接返回缓存内容
  └─ 否 → 回源到源站获取 → 缓存 → 返回给用户
```

**CDN 缓存策略**：
- **缓存时间**：通过 Cache-Control、Expires 设置
- **缓存刷新**：URL 刷新、目录刷新
- **缓存预热**：主动将资源推送到 CDN 节点
- **缓存键**：决定缓存的粒度（是否带参数等）

**CDN 回源**：
当 CDN 节点没有缓存或缓存过期时，需要回源站获取资源。
回源策略：
- 回源 HOST
- 回源鉴权
- Range 回源（大文件分片回源）

**CDN 加速的资源类型**：
- 静态资源：JS、CSS、图片、视频
- 静态页面
- 下载文件
- 流媒体

**CDN 的组成**：
- **分发服务系统**：边缘 Cache 节点
- **负载均衡系统**：GSLB（全局）、SLB（本地）
- **运营管理系统**：网管、计费、统计

## Q10: 什么是浏览器缓存？（强缓存/协商缓存）

**考察点**: 浏览器缓存机制、强缓存和协商缓存的原理、相关头部字段

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

浏览器缓存是浏览器将请求过的资源保存在本地，下次请求时直接使用缓存，减少网络请求。

**强缓存**：
不向服务器发送请求，直接使用缓存。
相关头部：
- **Expires**：HTTP/1.0，绝对时间
- **Cache-Control**：HTTP/1.1，相对时间，优先级更高
  - `max-age`：缓存最大时间（秒）
  - `no-cache`：不使用强缓存，需要协商缓存
  - `no-store`：不缓存
  - `public`：所有中间节点都可缓存
  - `private`：只有最终用户可缓存

**协商缓存**：
向服务器发送请求，服务器判断资源是否修改，未修改则返回 304 使用缓存，修改则返回新资源。
相关头部：
- **Last-Modified / If-Modified-Since**：基于修改时间
- **ETag / If-None-Match**：基于内容标识（优先级更高）

**答案解析**:

**完整缓存流程**：
```
浏览器请求资源
  ↓
检查是否有缓存
  ├─ 无缓存 → 请求服务器 → 存储缓存
  └─ 有缓存 → 检查强缓存是否过期
                ├─ 未过期 → 直接使用缓存（200 from disk cache）
                └─ 已过期 → 发送协商缓存请求
                              ↓
                        服务器判断资源是否修改
                              ├─ 未修改 → 返回 304，使用缓存
                              └─ 已修改 → 返回 200 和新资源，更新缓存
```

**强缓存相关头部**：
```http
Cache-Control: max-age=3600, public
Expires: Wed, 21 Oct 2026 07:28:00 GMT
```

Cache-Control 优先级高于 Expires。

**协商缓存相关头部**：

1. **Last-Modified / If-Modified-Since**：
```
第一次请求响应头：
Last-Modified: Wed, 21 Oct 2026 07:28:00 GMT

第二次请求请求头：
If-Modified-Since: Wed, 21 Oct 2026 07:28:00 GMT

服务器判断：未修改 → 304；修改了 → 200 + 新资源
```

2. **ETag / If-None-Match**：
```
第一次请求响应头：
ETag: "abc123"

第二次请求请求头：
If-None-Match: "abc123"

服务器判断：相同 → 304；不同 → 200 + 新资源
```

**ETag 相比 Last-Modified 的优势**：
- 精度更高（秒级以下修改也能检测）
- 文件内容不变但修改时间变了不会误判
- 服务器集群下更可靠

**缓存策略最佳实践**：
- HTML：协商缓存（no-cache）
- 静态资源（JS/CSS/图片）：强缓存 + 文件名 hash
- 频繁变化的资源：短缓存时间

## Q11: Webpack 的核心概念有哪些？（entry/output/loader/plugin）

**难度**: 中等

Webpack 是一个现代 JavaScript 应用程序的静态模块打包工具。核心概念：

   - 功能更强大，可以参与打包的各个阶段

5. **Mode（模式）**：

   - 不同模式有不同的内置优化

**答案解析**:

**基本配置示例**：
```javascript
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  mode: 'development',
  entry: './src/index.js',

    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash].js'
  },
  module: {
    rules: [
      {
        test: /\.js$/,
        use: 'babel-loader',
        exclude: /node_modules/
      },
      {
        test: /\.css$/,
        use: ['style-loader', 'css-loader'] // 从右到左执行
      }
    ]
  },
  plugins: [
    new HtmlWebpackPlugin({
      template: './index.html'
    })
  ]
};
```

**Loader 和 Plugin 的区别**：
- Loader：转换文件，处理特定类型的文件（如 CSS、TS 转 JS）
- Plugin：扩展功能，参与打包的整个生命周期，可以做更多事情

- **css-loader**：解析 CSS 文件

- **url-loader**：小图片转 base64
- **vue-loader**：处理 Vue 单文件组件
- **ts-loader**：TypeScript 转 JavaScript

**常见 Plugin**：
- **HtmlWebpackPlugin**：自动生成 HTML 文件
- **CleanWebpackPlugin**：清理输出目录
- **MiniCssExtractPlugin**：提取 CSS 为单独文件

## Q12: Webpack 的构建流程是什么？

**考察点**: Webpack 打包流程、各阶段作用、Compiler 和 Compilation

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

Webpack 的构建流程是一个串行的过程，从启动到结束依次执行：

1. **初始化阶段**：
   - 读取配置文件，合并参数
   - 创建 Compiler 实例
   - 加载所有配置的 Plugin
   - 调用 Compiler.run() 开始编译

2. **编译阶段**：
   - 从 Entry 入口文件出发
   - 调用对应 Loader 处理文件
   - 解析文件依赖，递归处理所有依赖模块
   - 构建模块依赖图（Module Graph）

3. **构建阶段**：
   - 根据 Entry 配置组装 Chunk
   - 每个 Chunk 包含多个模块
   - 生成最终资源（Asset）

4. **输出阶段**：
   - 根据 output 配置输出文件到指定目录

**核心对象**：
- **Compiler**：编译管理器，贯穿整个打包生命周期
- **Compilation**：每次构建的上下文，包含当前模块、依赖、产物

**答案解析**:

**详细构建流程**：

```
1. 初始化参数
   ↓
2. 开始编译（创建 Compiler 对象，加载 Plugin）
   ↓
3. 确定入口（Entry）
   ↓
4. 编译模块
   ├─ 从入口文件出发
   ├─ 调用对应 Loader 处理文件
   └─ 递归处理所有依赖模块
   ↓
5. 完成编译
   ├─ 得到所有模块内容
   └─ 得到依赖关系图
   ↓
6. 输出资源
   ├─ 根据 Entry 组装 Chunk
   ├─ Chunk 转换为 Asset
   └─ 确定输出内容
   ↓
7. 写入文件系统
```

**Compiler 和 Compilation**：
- **Compiler**：全局唯一，从启动到结束只有一个实例，包含完整的 Webpack 环境配置
- **Compilation**：每次文件变化都会创建新的 Compilation，代表一次构建过程

**Plugin 的作用时机**：
Webpack 在构建的各个阶段会广播事件，Plugin 监听这些事件来执行自定义逻辑。

关键事件钩子：
- `beforeRun`：开始编译前
- `compile`：创建新的 compilation 前
- `compilation`：compilation 对象创建后
- `emit`：生成资源到 output 目录之前
- `afterEmit`：生成资源之后
- `done`：编译完成

**Chunk 分类**：
- **Entry Chunk**：入口 Chunk
- **Normal Chunk**：异步加载的 Chunk（如动态 import）
- **Initial Chunk**：入口相关的初始 Chunk

## Q13: Vite 和 Webpack 的区别是什么？为什么 Vite 快？

**考察点**: Vite 和 Webpack 的区别、Vite 快的原理、Esbuild

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**核心区别**：

| 特性 | Webpack | Vite |
|------|---------|------|
| 开发模式 | 先打包再启动 | 按需编译，冷启动快 |
| 打包工具 | Webpack 自身 | 开发用 Esbuild，生产用 Rollup |
| 热更新 | 重新打包相关模块 | 精准更新，速度快 |
| 启动速度 | 慢（需要打包全部） | 快（按需加载） |
| 原生支持 | 基于打包 | 基于 ESM 原生模块 |
| 生态成熟度 | 非常成熟 | 快速发展中 |

**Vite 快的原因**：

1. **开发模式下使用原生 ESM**：
   - 浏览器原生支持 ES Module
   - 不需要打包，直接由浏览器处理依赖
   - Vite 只在请求时转换文件

2. **按需编译**：
   - 只编译当前页面需要的模块
   - Webpack 需要打包所有模块才能启动

3. **Esbuild 预构建**：
   - 使用 Go 语言编写的 Esbuild 预构建依赖
   - 速度比 JavaScript 编写的打包工具快 10-100 倍
   - 将 CommonJS/UMD 转换为 ESM

4. **高效的 HMR**：
   - 热更新只需要重新请求单个模块
   - 不需要重新构建整个 Chunk
   - 利用浏览器缓存策略

**答案解析**:

**开发模式对比**：

Webpack 开发模式：
```
启动 Dev Server
  ↓
打包所有模块（需要时间）
  ↓
服务器就绪
  ↓
浏览器加载打包后的文件
```

Vite 开发模式：
```
启动 Dev Server（几乎瞬间）
  ↓
预构建依赖（Esbuild）
  ↓
浏览器请求入口文件
  ↓
Vite 按需转换文件并返回
  ↓
浏览器处理 ESM 依赖
```

**生产构建对比**：
- Webpack：使用自身打包
- Vite：使用 Rollup 打包（更成熟的 ESM 打包工具）

**Esbuild 为什么快**：
1. 用 Go 语言编写，编译为原生代码
2. 并行化处理
3. 从零开始编写，不使用 JavaScript 的性能瓶颈
4. 内存使用高效

**Vite 的缺点**：
- 开发和生产环境构建不一致（Esbuild vs Rollup）
- 生态不如 Webpack 完善
- 对 CommonJS 支持需要预构建

**选择建议**：
- 新项目推荐 Vite，开发体验好
- 复杂项目、需要丰富插件生态用 Webpack
- Vite 正在快速发展，差距在缩小

**考察点**: Tree Shaking 的概念、原理、条件、实现

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**Tree Shaking（摇树优化）**：
Tree Shaking 是一种通过消除未使用代码（dead code）来减少打包体积的优化技术。它的名字来源于"摇晃树，掉下枯叶"的比喻。

**原理**：
基于 ES Module 的静态结构特性（import/export 在编译时确定，不能动态改变），在编译时进行静态分析，找出没有被使用的模块和导出，将其删除。

**实现条件**：
1. 必须使用 ES Module（import/export）
2. 生产模式下自动开启
3. package.json 中配置 sideEffects 标记副作用

**CommonJS 不支持 Tree Shaking**：
因为 CommonJS 的 require 是动态的，运行时才能确定导入的内容，无法在编译时静态分析。

**答案解析**:

**Tree Shaking 示例**：

```javascript
// utils.js
export function a() {
  return 'a';
}
export function b() {
  return 'b';
}

// main.js
import { a } from './utils.js';
console.log(a());

// 打包后，b 函数会被删除（Tree Shaking）
```

**sideEffects 的作用**：
有些模块虽然没有被导入，但有副作用（如修改全局变量、注入样式），不能随便删除。

```json
// package.json
{
  "sideEffects": false // 所有文件都没有副作用，可以安全 Tree Shaking
}

// 或
{
  "sideEffects": [
    "*.css",
    "*.scss",
    "./src/polyfill.js"
  ]
}
```

**Webpack 中 Tree Shaking 的条件**：
1. 使用 ES2015 模块语法（import/export）
2. mode 设置为 production（自动启用压缩）
3. 在 package.json 中添加 sideEffects 字段
4. 确保没有被 babel 转换为 CommonJS

**Tree Shaking 的局限性**：
1. 只能消除模块级别的未使用导出
2. 函数内部的未使用代码由压缩工具（Terser）处理
3. 有副作用的代码不能被消除
4. 动态导入无法 Tree Shaking

**CSS 的 Tree Shaking**：
CSS 也可以做 Tree Shaking，常用工具：
- PurgeCSS
- UnCSS
- Tailwind CSS 自带 JIT 模式

## Q15: 代码分割（Code Splitting）的实现方式有哪些？

**考察点**: 代码分割的概念、实现方式、配置方法

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**代码分割（Code Splitting）**：
代码分割是将代码分割成多个块（chunk），按需加载，而不是打包成一个文件，从而减少首屏加载时间。

**实现方式**：

1. **入口起点（Entry Points）**：
   - 配置多个 entry 入口
   - 手动分割，适合多页面应用

2. **动态导入（Dynamic Imports）**：
   - 使用 `import()` 语法
   - 按需加载，最常用的方式
   - 路由懒加载、组件懒加载

3. **提取公共代码（SplitChunksPlugin）**：
   - Webpack 内置插件
   - 提取第三方库和公共模块
   - 避免重复打包

**答案解析**:

**1. 入口起点分割**：
```javascript
// webpack.config.js
module.exports = {
  entry: {
    main: './src/main.js',
    admin: './src/admin.js'
  },
  output: {
    filename: '[name].bundle.js'
  }
};
```
缺点：手动配置，共享代码可能重复打包。

**2. 动态导入**：
```javascript
// 按需加载模块
button.addEventListener('click', async () => {
  const { calculate } = await import('./math.js');
  console.log(calculate(1, 2));
});

// 路由懒加载（Vue）
const Home = () => import('./views/Home.vue');
const routes = [
  { path: '/home', component: Home }
];

// React 路由懒加载
const Home = React.lazy(() => import('./Home'));
```

动态导入生成的 chunk 命名：
```javascript
import(/* webpackChunkName: "math" */ './math.js');
```

**3. SplitChunksPlugin**：
```javascript
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'all', // all / async / initial
      minSize: 20000, // 最小体积
      minChunks: 1, // 最少被引用次数
      maxAsyncRequests: 30, // 最大异步请求数
      maxInitialRequests: 30, // 最大初始请求数
      cacheGroups: {
        vendors: {
          test: /[\\/]node_modules[\\/]/,
          priority: -10,
          filename: 'vendors.js'
        },
        common: {
          minChunks: 2,
          priority: -20,
          reuseExistingChunk: true
        }
      }
    }
  }
};
```

**代码分割的好处**：
- 减少首屏加载时间
- 按需加载，节省流量
- 并行加载，提高速度
- 更好的缓存利用率（公共代码单独缓存）

**代码分割的代价**：
- 增加网络请求次数
- 需要处理加载状态（loading）
- 增加代码复杂度

## Q16: 前端安全问题有哪些？（XSS/CSRF/点击劫持）

**考察点**: 常见前端安全问题、原理、防御措施

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**1. XSS（跨站脚本攻击）**：
攻击者在网页中注入恶意脚本，当用户浏览时执行，窃取用户信息或进行恶意操作。

**类型**：
- **存储型 XSS**：恶意脚本存储在数据库，用户访问时执行
- **反射型 XSS**：恶意脚本在 URL 中，服务端反射到页面
- **DOM 型 XSS**：前端 JS 处理不当，直接使用输入内容

**防御措施**：
- 输入过滤和输出转义
- 使用 HttpOnly Cookie
- CSP（内容安全策略）
- 避免使用 innerHTML、document.write 等

**2. CSRF（跨站请求伪造）**：
攻击者诱导用户访问恶意网站，利用用户已登录的身份，发起跨站请求。

**防御措施**：
- CSRF Token 验证
- SameSite Cookie
- 验证 Referer
- 关键操作使用验证码

**3. 点击劫持（Clickjacking）**：
攻击者将目标网站通过 iframe 嵌入自己的页面，设置透明，诱导用户点击。

**防御措施**：
- X-Frame-Options 响应头
- CSP frame-ancestors 指令
- JS 顶层判断

**答案解析**:

**XSS 示例**：
```javascript
// 危险：直接使用用户输入
document.getElementById('content').innerHTML = userInput;

// 安全：转义后再插入
function escape(str) {
  return str.replace(/[&<>"']/g, m => ({
    '&': '&amp;', '<': '&lt;', '>': '&gt;',
    '"': '&quot;', "'": '&#39;'
  }[m]));
}
```

**CSP（内容安全策略）**：
```http
Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.com
```
限制资源加载来源，防止 XSS。

**CSRF 示例**：
用户在 A 网站已登录，访问 B 网站，B 网站中：
```html
<img src="http://bank.com/transfer?to=hacker&amount=10000" />
```
浏览器会自动携带 cookie 发起请求。

**CSRF Token 防御**：
- 服务端生成 token 存在 session 中
- 页面中携带 token（隐藏字段或请求头）
- 服务端验证 token 是否匹配

**点击劫持防御**：
```http
X-Frame-Options: DENY           # 不允许被 iframe 嵌入
X-Frame-Options: SAMEORIGIN     # 只允许同域名嵌入
```

**其他安全问题**：
- SQL 注入（后端为主）
- 文件上传漏洞
- 中间人攻击（使用 HTTPS）
- 密码安全（加密存储、加盐）

- 如何防御 XSS？有哪些层级？

## Q17: 什么是 PWA？

**考察点**: PWA 的概念、核心特性、技术组成

**难度**: 中等

**频率**: ⭐⭐⭐

**标准答案**:

**PWA（Progressive Web App，渐进式 Web 应用）**：
PWA 是一种 Web 应用，使用现代 Web API 以及传统的渐进式增强策略来创建跨平台 Web 应用程序。它兼具 Web 和原生应用的优点。

**核心特性**：
1. **可靠（Reliable）**：即使在网络不稳定或离线情况下也能快速加载
2. **快速（Fast）**：对用户交互响应迅速
3. **沉浸式（Engaging）**：可以添加到主屏幕，全屏运行，推送通知

**核心技术**：
- **Service Worker**：离线缓存、后台同步、推送通知
- **Web App Manifest**：应用清单，定义应用名称、图标、启动方式
- **HTTPS**：PWA 必须在 HTTPS 环境下运行
- **App Shell**：应用壳架构

**答案解析**:

**Service Worker**：
Service Worker 是 PWA 的核心，是运行在浏览器后台的脚本，独立于网页。

功能：
- 拦截网络请求，实现离线缓存
- 后台数据同步
- 接收推送通知

生命周期：
- Register（注册）
- Install（安装）
- Activate（激活）
- Fetch（拦截请求）

```javascript
// 注册 Service Worker
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}

// sw.js - 缓存文件
const CACHE_NAME = 'v1';
const urlsToCache = ['/', '/index.html', '/styles.css'];

self.addEventListener('install', event => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(urlsToCache))
  );
});

self.addEventListener('fetch', event => {
  event.respondWith(
    caches.match(event.request).then(response => {
      return response || fetch(event.request);
    })
  );
});
```

**Web App Manifest**：
```json
{
  "name": "My PWA",
  "short_name": "PWA",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#4285f4",
  "icons": [
    {
      "src": "icon.png",
      "sizes": "192x192",
      "type": "image/png"
    }
  ]
}
```

**缓存策略**：
- Cache First：缓存优先（静态资源）
- Network First：网络优先（动态数据）
- Stale-While-Revalidate：缓存先返回，后台更新

**PWA 的优势**：
- 无需安装，直接使用
- 可以添加到主屏幕
- 离线可用
- 推送通知
- 跨平台，开发成本低

## Q18: 什么是 SSR（服务端渲染）？有什么优缺点？

**考察点**: SSR 概念、优缺点、适用场景、与 CSR 的区别

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**SSR（Server-Side Rendering，服务端渲染）**：
SSR 是指在服务器端完成页面的 HTML 渲染，将渲染好的 HTML 发送给浏览器。

**CSR（Client-Side Rendering，客户端渲染）**：
传统的单页应用（SPA）采用客户端渲染，服务器返回空 HTML，由 JS 在客户端渲染页面。

**SSR 的优点**：
1. **首屏加载快**：HTML 直接渲染，不需要等 JS 下载执行
2. **SEO 友好**：搜索引擎爬虫能直接获取完整内容
3. **弱网环境体验好**：即使 JS 加载慢，也能先看到内容

**SSR 的缺点**：
1. **服务端压力大**：每次请求都要渲染
2. **开发复杂度高**：需要考虑服务端和客户端差异
3. **部署要求高**：需要 Node.js 服务
4. ** hydration 耗性能**：客户端需要激活交互

**适用场景**：
- 对首屏加载速度要求高
- 需要 SEO 优化
- 内容型网站（新闻、博客、电商详情页）

**答案解析**:

**CSR 流程**：
```
浏览器请求
  ↓
服务器返回空 HTML
  ↓
浏览器下载 JS/CSS
  ↓
JS 执行，请求数据
  ↓
渲染页面
```

**SSR 流程**：
```
浏览器请求
  ↓
服务器获取数据
  ↓
服务器渲染 HTML
  ↓
返回渲染好的 HTML
  ↓
浏览器直接显示内容
  ↓
下载 JS（hydration）
  ↓
页面可交互
```

**hydration（水合）**：
SSR 返回的 HTML 是静态的，客户端需要将其变成可交互的过程叫 hydration。
- 绑定事件
- 建立响应式
- 接管页面

**主流 SSR 框架**：
- React：Next.js
- Vue：Nuxt.js
- 通用：Remix、SvelteKit

**SSR 相关概念**：
- **SSG（Static Site Generation）**：静态站点生成，构建时生成 HTML
- **ISR（Incremental Static Regeneration）**：增量静态再生成
- **SSR vs SSG**：
  - SSR：每次请求动态渲染，数据实时
  - SSG：构建时生成，速度快，但数据不实时

**SSR 性能优化**：
- 流式渲染（Streaming SSR）
- 选择性 hydration
- 组件级缓存
- 数据预取

- SSR 和预渲染（Prerendering）的区别？

- SSR 中的 hydration 是什么？

## Q19: 前端模块化有哪些？（CommonJS/ES Module/AMD/CMD）

**考察点**: 模块化方案、区别、演进历史

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**前端模块化的发展历程**：

| 方案 | 出现时间 | 代表 | 特点 |
|------|----------|------|------|
| CommonJS | 2009 | Node.js | 同步加载，服务端 |
| AMD | 2010 | RequireJS | 异步加载，浏览器 |
| CMD | 2011 | SeaJS | 按需加载，浏览器 |
| ES Module | 2015 | ES6 | 标准方案，静态分析 |

**CommonJS**：
- 用于 Node.js，同步加载模块
- `require()` 导入，`module.exports` 导出
- 运行时加载，值拷贝
- 动态导入（可以在条件语句中 require）

**ES Module（ESM）**：
- ES6 官方标准
- `import` 导入，`export` 导出
- 编译时加载（静态分析），支持 Tree Shaking
- 输出值的引用（实时绑定）
- 浏览器原生支持

**AMD（Asynchronous Module Definition）**：
- 异步模块定义，浏览器端使用
- 代表：RequireJS
- 依赖前置，提前执行
- `define(['dep1', 'dep2'], function(dep1, dep2) {})`

**CMD（Common Module Definition）**：
- 通用模块定义，浏览器端使用
- 代表：SeaJS（玉伯）
- 依赖就近，延迟执行
- `define(function(require, exports, module) {})`

**答案解析**:

**CommonJS 示例**：
```javascript
// a.js
module.exports = { name: 'module a' };

// b.js
const a = require('./a.js');
console.log(a.name);
```

**ES Module 示例**：
```javascript
// a.js
export const name = 'module a';
export default function() {}

// b.js
import a, { name } from './a.js';
```

**CommonJS 和 ES Module 的区别**：

| 特性 | CommonJS | ES Module |
|------|----------|-----------|
| 加载时机 | 运行时 | 编译时 |
| 输出方式 | 值拷贝 | 值引用（实时绑定） |
| 动态性 | 可以动态 require | import 只能在顶层 |
| this | 指向模块本身 | 指向 undefined |
| Tree Shaking | 不支持 | 支持 |
| 浏览器支持 | 不支持（需打包） | 原生支持（现代浏览器） |

**值拷贝 vs 值引用**：
```javascript
// CommonJS - 值拷贝
// a.js
let count = 1;
function add() { count++; }
module.exports = { count, add };

// b.js
const { count, add } = require('./a.js');
add();
console.log(count); // 1，值拷贝，不会变

// ES Module - 值引用
// a.js
export let count = 1;
export function add() { count++; }

// b.js
import { count, add } from './a.js';
add();
console.log(count); // 2，引用，会实时更新
```

**循环引用**：
- CommonJS：输出已经执行的部分，未执行的不输出
- ES Module：输出引用，运行时取值

## Q20: 什么是 TypeScript？和 JavaScript 的区别是什么？

**标准答案**:

**TypeScript 是什么**：
TypeScript 是 JavaScript 的超集，添加了可选的静态类型和基于类的面向对象编程。它可以编译为纯 JavaScript，运行在任何浏览器、Node.js 环境中。

```

6. **联合类型和交叉类型**：

type B = { b: number };
type C = A & B; // 交叉类型
```

### MySQL 部分

### Q1: 索引底层数据结构？为什么用 B+ 树不用 B 树 / 红黑树 / Hash？

- **类别**: MySQL基础
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

**MySQL 索引底层使用 B+ 树**（InnoDB 引擎）。

**为什么不用其他数据结构？**

| 数据结构 | 缺点 | 为什么不选 |
|----------|------|-----------|
| **Hash** | 只支持等值查询，不支持范围查询和排序 | 数据库大量场景是范围查询和 ORDER BY |
| **红黑树** | 树的高度太高（数据量大时层数多），磁盘 IO 次数多 | 红黑树是二叉树，百万级数据高度约20层 |
| **B 树** | 每个节点都存数据，导致每个节点能存的索引键少，树更高；范围查询需要中序遍历 | B+ 树非叶子节点只存索引键，同样大小的节点能存更多键，树更矮（通常3-4层就能存千万级数据） |

**B+ 树相比 B 树的优势：**
1. **磁盘读写代价更低** — 非叶子节点不存数据，同样大小可容纳更多索引键，IO 次数少
2. **查询效率更稳定** — 任何关键字查询都要走到叶子节点，路径长度相同
3. **范围查询更高效** — 叶子节点形成有序链表，范围查询只需遍历链表即可，不需要中序遍历

</details>

### Q2: 事务隔离级别？MySQL 默认是哪个？MVCC 原理？

- **类别**: MySQL事务
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

**四个隔离级别（从低到高）：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 不会 | 可能 | 可能 |
| **可重复读（Repeatable Read）** | 不会 | 不会 | 可能（MySQL通过Next-Key Lock基本解决） |
| 串行化（Serializable） | 不会 | 不会 | 不会 |

**MySQL InnoDB 默认是可重复读（RR）**。

**MVCC（多版本并发控制）原理：**
- 每行数据隐藏两个字段：`DB_TRX_ID`（创建/最后修改事务ID）、`DB_ROLL_PTR`（回滚指针，指向 undo log）
- **Read View**：事务启动时生成的读视图，记录当前活跃事务ID列表
- **可见性规则**：
  1. 数据行的 trx_id < Read View 中最小事务ID → 可见（已提交）
  2. 数据行的 trx_id > Read View 中最大事务ID → 不可见（未开始）
  3. 在中间的话，看 trx_id 是否在活跃列表中：在则不可见，不在则可见
- **RC 和 RR 的区别**：RC 每次 SELECT 都生成新的 Read View，RR 只在第一次 SELECT 时生成

</details>

### Q3: 索引失效的常见场景？最左前缀原则？

- **类别**: MySQL索引
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

**最左前缀原则**：联合索引遵循最左前缀匹配，查询从索引的最左列开始，且不能跳过中间的列。

例如有联合索引 `(a, b, c)`：
- ✅ `where a = 1` — 走索引
- ✅ `where a = 1 and b = 2` — 走索引
- ✅ `where a = 1 and b = 2 and c = 3` — 走索引
- ❌ `where b = 2 and c = 3` — 不走索引（跳过了a）
- ⚠️ `where a = 1 and c = 3` — a走索引，c不走（跳过了b）

**索引失效的常见场景：**
1. 联合索引不满足最左前缀原则
2. **在索引列上做运算**（函数、计算、类型转换）：`where year(create_time) = 2024`
3. **隐式类型转换**：字符串字段用数字查询 `where phone = 13800138000`
4. **LIKE 以 % 开头**：`where name like '%abc'`
5. **OR 条件中有非索引列**：`where a = 1 or b = 2`（b无索引）
6. **!= 或 <> 操作符**（有时会失效，取决于数据量）
7. **IS NOT NULL**（IS NULL 可以走索引）
8. 优化器判断全表扫描更快时（比如小表或查询数据占比高）

</details>

### Q4: MySQL 锁机制？行锁 / 表锁 / 间隙锁 / Next-Key Lock？

- **类别**: MySQL锁
- **难度**: 困难
- **频率**: 高

<details>
<summary>答题要点</summary>

**锁的粒度分类：**

| 锁类型 | 粒度 | 引擎 | 说明 |
|--------|------|------|------|
| 表锁 | 整表 | MyISAM/InnoDB | 开销小，加锁快，冲突概率高 |
| 行锁 | 行级 | InnoDB | 开销大，加锁慢，冲突概率低，并发度高 |
| 间隙锁 | 区间 | InnoDB | 锁定一个范围的间隙，防止幻读 |
| Next-Key Lock | 行+间隙 | InnoDB | 行锁 + 间隙锁，左开右闭区间 |

**InnoDB 行锁的实现：**
- 通过给索引上的记录加锁实现，不是锁数据行本身
- 如果没有索引，会升级为表锁（全表扫描逐行加锁）

**三种行锁算法：**
1. **Record Lock**：记录锁，锁定单条索引记录
2. **Gap Lock**：间隙锁，锁定索引记录之间的间隙（开区间），防止其他事务插入
3. **Next-Key Lock**：Record Lock + Gap Lock，锁定左开右闭区间，**RR 隔离级别下默认使用**，用于解决幻读问题

**注意**：当查询条件是唯一索引且精确匹配时，Next-Key Lock 会退化为 Record Lock。

</details>

### Q5: 分库分表怎么设计？垂直拆分和水平拆分？

- **类别**: MySQL架构
- **难度**: 困难
- **频率**: 高

<details>
<summary>答题要点</summary>

**垂直拆分 vs 水平拆分：**

| 拆分方式 | 说明 | 优点 | 缺点 |
|----------|------|------|------|
| **垂直分库** | 按业务模块拆到不同数据库 | 业务解耦，便于分团队维护 | 跨库 JOIN 复杂 |
| **垂直分表** | 把大表按列拆分（冷热分离） | 减少单表列数，热点数据访问更快 | 应用层需要 JOIN |
| **水平分库** | 同一张表按行拆到不同库 | 解决单库容量和性能瓶颈 | 路由复杂，跨库操作麻烦 |
| **水平分表** | 同一张表按行拆成多张表 | 解决单表数据量过大问题 | 分页、排序、聚合复杂 |

**分片策略：**
1. **Range 范围分片**：按时间、ID范围分片 — 扩容方便，但可能数据倾斜
2. **Hash 取模分片**：`hash(userId) % N` — 数据均匀，但扩容麻烦（要迁移数据）
3. **一致性 Hash**：虚拟节点 + Hash 环 — 扩容时只需迁移少量数据
4. **按日期分片**：日志、订单等有时效性的数据

**分库分表带来的问题：**
- 跨库 JOIN → 应用层做 JOIN 或 冗余字段
- 分布式事务 → 最终一致性、TCC、SAGA
- 排序分页 → 需要各分片排序再归并
- 全局唯一 ID → 雪花算法、号段模式、UUID

</details>

### Q7: Redis 持久化机制？RDB 和 AOF 区别？

- **类别**: Redis持久化
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

| 对比维度 | RDB（快照） | AOF（追加日志） |
|----------|-------------|----------------|
| **原理** | 保存某一时刻的内存数据快照 | 保存所有写命令 |
| **恢复速度** | 快（直接加载二进制文件） | 慢（需要逐条执行命令） |
| **数据完整性** | 差，会丢失最后一次快照后的数据 | 好，最多丢失1秒数据 |
| **文件大小** | 小（压缩的二进制） | 大（文本格式，写命令多） |
| **对性能影响** | fork子进程，大数据量时会卡一下 | 每次写都追加，影响小但持续 |
| **默认开启** | 是 | 否（Redis 7.0后默认开启？需确认，实际很多场景会开启） |

**RDB 触发方式：**
- `save`：阻塞式，主线程执行，会阻塞
- `bgsave`：fork子进程执行，不阻塞（默认）
- 自动触发：配置 `save 900 1` 等

**AOF 刷盘策略：**
- `always`：每次写都刷盘 — 最安全，性能最差
- `everysec`：每秒刷盘一次 — 折中，推荐（最多丢1秒数据）
- `no`：由操作系统决定 — 性能最好，最不安全

**AOF 重写**：AOF文件越来越大时，Redis会fork子进程进行重写，生成最小化的AOF文件。

**Redis 4.0+ 混合持久化**：RDB + AOF 混合，文件前半部分是RDB格式的快照，后半部分是AOF格式的增量命令。兼顾了恢复速度和数据安全性。

</details>

### Q8: 缓存穿透 / 击穿 / 雪崩的区别和解决方案？

- **类别**: Redis缓存问题
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

| 问题 | 定义 | 原因 | 解决方案 |
|------|------|------|---------|
| **缓存穿透** | 查询不存在的数据，请求直接打到数据库 | 恶意攻击、数据不存在 | 1. 布隆过滤器<br>2. 缓存空值（设短过期时间） |
| **缓存击穿** | 热点key过期瞬间，大量并发请求打到数据库 | 热点key过期 | 1. 互斥锁（分布式锁）<br>2. 热点数据永不过期（逻辑过期） |
| **缓存雪崩** | 大量key同时过期，或Redis宕机，数据库压力骤增 | 缓存集中失效 / Redis故障 | 1. 过期时间加随机值<br>2. 多级缓存<br>3. 服务熔断/降级<br>4. Redis集群高可用 |

**一句话区分：**
- 穿透：查的是**不存在的数据**（缓存和数据库都没有）
- 击穿：**单个热点key**过期了
- 雪崩：**大量key同时**过期 或 Redis挂了

**布隆过滤器原理**：一个很长的二进制向量 + 多个哈希函数。添加元素时，用k个哈希函数算出k个位置，置为1。查询时，如果k个位置都是1则可能存在，有一个为0则一定不存在。有一定误判率（可能把不存在的判断为存在），但不会漏判。

</details>

### Q9: Redis 集群模式？哨兵和 Cluster 的区别？

- **类别**: Redis集群
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

| 模式 | 定位 | 节点数 | 数据分布 | 高可用 | 适用场景 |
|------|------|--------|---------|-------|---------|
| **主从复制** | 数据备份、读写分离 | 1主N从 | 全量复制（每个节点数据一样） | 不能自动故障转移 | 读多写少，需要数据备份 |
| **哨兵（Sentinel）** | 主从的高可用方案 | 至少3个哨兵节点 | 全量复制 | 自动故障转移（哨兵监控+选举） | 中小规模，数据量不大，需要高可用 |
| **Cluster** | 分布式集群方案 | 至少6节点（3主3从） | 16384个槽位，按哈希分片 | 主从+自动故障转移 | 大规模，数据量大，需要水平扩展 |

**哨兵核心功能：**
1. **监控**：持续监控主从节点是否正常
2. **通知**：节点故障时通知管理员和应用
3. **自动故障转移**：主节点挂了，选举新的主节点
4. **配置提供者**：客户端连接哨兵获取主节点地址

**Cluster 核心原理：**
- 16384 个哈希槽，每个节点负责一部分槽
- `CRC16(key) % 16384` 计算key属于哪个槽
- 客户端重定向：`MOVED` 永久重定向，`ASK` 临时重定向（扩容迁移中）
- 每个主节点有从节点做备份，主挂了自动切换

</details>

### Q10: Redis 为什么快？单线程为什么性能高？

- **类别**: Redis原理
- **难度**: 简单
- **频率**: 高

<details>
<summary>答题要点</summary>

**Redis 快的原因：**

1. **纯内存操作** — 数据存在内存中，读写都是内存级别的速度，ns 级别
2. **单线程模型** — 避免了多线程的上下文切换和锁竞争开销
3. **IO 多路复用** — 用 epoll/kqueue 等实现非阻塞 IO，单线程处理大量并发连接
4. **高效的数据结构** — 底层用跳表、压缩列表、SDS 等优化的数据结构
5. **简单的通信协议** — RESP（Redis Serialization Protocol），简单易解析

**为什么单线程还这么快？**
- Redis 是**内存数据库**，瓶颈不在CPU，而在内存和网络带宽
- 单线程避免了多线程的**上下文切换**和**锁竞争**开销
- 通过**IO 多路复用**（epoll），单线程可以同时处理成千上万个并发连接
- 核心命令都是 O(1) 或 O(logN) 的高效操作

**注意**：Redis 6.0 引入了多线程，但只是**网络IO多线程**（读写网络数据用多线程），命令执行仍然是单线程。核心原因是命令执行才是主要的逻辑处理部分，保持单线程可以避免并发问题。

</details>

### Q11: Kafka 和 RocketMQ 的区别？选型考虑？

- **类别**: 消息队列
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

| 对比维度 | Kafka | RocketMQ |
|----------|-------|----------|
| **开发语言** | Scala/Java | Java |
| **吞吐量** | 极高（百万级/s） | 高（十万级/s） |

| **消息回溯** | 支持（按offset/timestamp） | 支持（按时间戳） |
| **死信队列** | 需要自己实现 | 原生支持 |
| **运维复杂度** | 高（依赖ZooKeeper/KRaft） | 中等 |
| **生态** | 大数据生态完善（Flink/Spark集成好） | 阿里系生态完善 |

**选型建议：**
- **大数据场景、日志采集** → 选 Kafka（吞吐量最高，生态最完善）
- **业务系统、电商/金融** → 选 RocketMQ（功能丰富，事务消息/定时消息/死信队列开箱即用）
- **中小团队、简单场景** → 两者都可以，看团队技术栈

</details>

### Q12: 如何保证消息不丢失？如何保证消息顺序性？

- **类别**: 消息队列
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

**如何保证消息不丢失（三个环节）：**

| 环节 | 丢失原因 | 解决方案 |
|------|---------|---------|
| **生产阶段** | 网络抖动、Broker挂了 | 1. 同步发送 + 重试机制<br>2. 确认机制（Kafka acks=all, RocketMQ 同步刷盘+同步复制） |
| **存储阶段** | Broker 宕机、磁盘故障 | 1. 同步刷盘（RocketMQ 同步刷盘，Kafka 多副本）<br>2. 多副本机制（至少2副本，ISR同步） |
| **消费阶段** | 消费失败但先提交了offset | 1. 关闭自动提交，手动提交offset<br>2. 确保业务处理成功后再ack<br>3. 消费失败重试 + 死信队列 |

**如何保证消息顺序性：**

**全局有序**：一个Topic一个分区，一个消费者单线程消费 — 吞吐量极低，基本不用

**局部有序**（推荐）：
- **生产端**：相同业务ID的消息发到同一个分区（队列）—— 例如同一个订单的消息都发到同一个队列
- **消费端**：同一个队列的消息由同一个消费者有序消费
- Kafka：按 key 哈希选择分区，同一 key 的消息在同一分区
- RocketMQ：用 MessageQueueSelector 选择队列

**注意事项**：
- 消费失败重试时要注意不能打乱顺序
- 避免消费超时导致消息重新投递
- 业务层面也要考虑幂等（消息可能重复投递）

</details>

### Q13: 消息队列的应用场景？

- **类别**: 消息队列
- **难度**: 简单
- **频率**: 中

<details>
<summary>答题要点</summary>

**三大核心作用：异步、解耦、削峰**

| 场景 | 说明 | 举例 |
|------|------|------|
| **异步处理** | 把不需要同步处理的操作异步化，降低接口响应时间 | 下单后发短信/邮件、用户注册后发优惠券 |
| **系统解耦** | 系统之间通过消息队列通信，不直接依赖 | 订单系统 → MQ → 库存系统/物流系统/积分系统 |
| **削峰填谷** | 把突发流量暂存到MQ，下游系统按自己的速度消费 | 秒杀场景、大促订单、抢红包 |

**其他常见场景：**
- **分布式事务消息**：保证多个系统间的数据一致性
- **事件驱动架构**：各系统通过事件通信，松耦合
- **日志收集**：ELK架构中用Kafka做日志缓冲
- **数据流处理**：配合Flink/Spark Streaming做实时计算

> **什么时候不该用MQ？**
> - 对延迟要求极高的场景（MQ本身有毫秒级延迟）
> - 系统复杂度不高、同步调用足够的场景
> - 引入MQ会增加运维成本和系统复杂度，需要权衡

</details>

### Q14: Elasticsearch 倒排索引原理？

- **类别**: Elasticsearch
- **难度**: 中等
- **频率**: 中

<details>
<summary>答题要点</summary>

**正排索引 vs 倒排索引：**
- **正排索引**：文档ID → 文档内容（找某篇文档里有什么词）
- **倒排索引**：关键词 → 文档ID列表（找某个词在哪些文档里出现）

**倒排索引结构：**

```
单词词典（Term Dictionary）     倒排列表（Posting List）
     "apple"        →        [doc1, doc5, doc12, ...]
     "banana"       →        [doc2, doc3, doc8, ...]
     "cherry"       →        [doc1, doc7, ...]
```

**核心组件：**
1. **Term Dictionary（单词词典）**：存储所有Term，用B+树或跳表实现，支持快速查找
2. **Posting List（倒排列表）**：每个Term对应的文档ID列表，还包含词频（TF）、位置、偏移量等
3. **Term Index（单词索引）**：Term Dictionary的索引，用FST（Finite State Transducer）压缩存储，加速Term查找

**为什么 ES 查询快？**
- 倒排索引直接通过Term找到文档，不需要全表扫描
- Term Index（FST）存在内存中，查找Term非常快
- 倒排列表用压缩算法（FOR、RLE）存储，节省空间
- 分片机制，分布式并行查询

**相关度评分（TF-IDF / BM25）：**
- **TF**（词频）：词在文档中出现的次数，越高越相关
- **IDF**（逆文档频率）：词在所有文档中出现的频率，越低越有区分度
- **BM25**：ES默认的评分算法，是TF-IDF的优化版，考虑了词频饱和度和文档长度归一化

</details>

### Q15: 分布式事务解决方案？2PC / TCC / SAGA / 本地消息表？

- **类别**: 分布式一致性
- **难度**: 困难
- **频率**: 高

<details>
<summary>答题要点</summary>

| 方案 | 原理 | 一致性 | 侵入性 | 适用场景 |
|------|------|--------|--------|---------|
| **2PC（两阶段提交）** | 协调者+参与者，准备阶段+提交阶段 | 强一致 | 低（数据库支持XA） | 传统企业应用，并发不高 |
| **TCC（Try-Confirm-Cancel）** | 业务层面的两阶段，预留资源→确认/取消 | 最终一致 | 高（每个服务要写3个接口） | 资金类、对一致性要求高的场景 |
| **SAGA** | 长事务拆分为多个本地事务，失败时反向补偿 | 最终一致 | 中（需要写补偿逻辑） | 长流程业务（订单→支付→库存→物流） |
| **本地消息表** | 本地事务+消息表，定时扫描重试 | 最终一致 | 中 | 大部分业务场景（最常用） |
| **事务消息** | RocketMQ事务消息，半消息+回查 | 最终一致 | 低 | 有RocketMQ基础设施的场景 |

**各方案详解：**

**2PC**：
- 阶段一（Prepare）：协调者问所有参与者"能不能提交"，参与者执行事务但不提交，返回Yes/No
- 阶段二（Commit/Rollback）：全Yes则提交，有一个No则回滚
- 缺点：同步阻塞、单点故障、可能数据不一致（第二阶段协调者挂了）

**TCC**：
- Try：预留资源（比如冻结库存）
- Confirm：确认执行（扣减库存）
- Cancel：取消执行（释放库存）
- 缺点：业务侵入性大，每个服务都要实现三个接口

**SAGA**：
- 正向流程：T1 → T2 → T3 → ...
- 反向补偿：... → C3 → C2 → C1
- 两种实现：编排式（协调者统一调度）、协同式（各服务自己触发下一个）

**本地消息表（最常用）：**
1. 业务操作和消息记录在同一个本地事务中
2. 定时任务扫描消息表，发送未成功的消息
3. 消费方幂等处理，成功后ack
4. 简单可靠，大部分场景都适用

</details>

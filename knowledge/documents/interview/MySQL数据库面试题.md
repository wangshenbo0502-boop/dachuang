## Q1: MySQL的存储引擎（InnoDB和MyISAM的区别）

**考察点**: 存储引擎对比、InnoDB特性、适用场景

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

MySQL存储引擎是插件式的，不同的存储引擎有不同的特性。InnoDB是MySQL 5.5以后的默认存储引擎。

**InnoDB vs MyISAM对比**：

| 维度 | InnoDB | MyISAM |
|------|--------|--------|
| 事务支持 | 支持ACID事务 | 不支持事务 |
| 锁粒度 | 行级锁 | 表级锁 |
| 外键 | 支持外键 | 不支持外键 |
| 崩溃恢复 | 支持（redo log） | 不支持，容易损坏 |
| MVCC | 支持 | 不支持 |
| 全文索引 | 5.6+支持 | 支持 |
| 缓存 | 缓存数据和索引 | 只缓存索引 |
| 存储空间 | 较大（事务、MVCC等开销） | 较小 |
| 主键 | 必须有主键（没有会自动生成） | 可以没有 |
| 计数 | count(*)需要扫描（可优化） | count(*)直接返回（维护了计数器） |
| 适用场景 | 事务、并发写、数据一致性要求高 | 读多写少、不需要事务、计数多 |

**其他常见存储引擎**：
- **Memory**：内存存储，数据存在内存中，速度快，重启丢失
- **Archive**：归档存储，压缩比高，只支持插入和查询
- **CSV**：CSV文件格式，便于数据交换

**答案解析**:

深入理解InnoDB和MyISAM：

1. **为什么InnoDB成为默认引擎**：
   - 事务支持：保证数据一致性和可靠性
   - 行级锁：高并发场景下性能更好
   - 崩溃恢复：数据库异常重启后能恢复到一致状态
   - 外键支持：保证数据完整性

2. **MyISAM的优势场景**：
   - 读密集型应用，且写入很少
   - 需要快速count(*)统计的场景
   - 对数据可靠性要求不高的场景（如日志、缓存）
   - 全文搜索（虽然InnoDB 5.6+也支持，但MyISAM的全文索引更成熟）

3. **InnoDB的关键特性**：
   - **聚簇索引**：数据和主键索引存在一起
   - **事务**：支持ACID，四个隔离级别
   - **MVCC**：多版本并发控制，读写不阻塞
   - **行锁**：支持行级锁和间隙锁
   - **外键**：保证引用完整性
   - **change buffer**：减少随机IO

4. **如何选择存储引擎**：
   - 99%的场景用InnoDB就对了
   - 除非有特殊需求（如极致的读性能、全文搜索等）
   - MySQL 8.0中MyISAM已经基本被淘汰，系统表也改用InnoDB了

**扩展问题**:
- InnoDB为什么推荐使用自增主键？
- MyISAM的count(*)为什么快？有什么限制？
- Memory引擎和Redis有什么区别？
- MySQL 8.0在存储引擎方面有什么新特性？

## Q2: MySQL的索引类型和底层结构（B+树）

**考察点**: 索引分类、B+树结构、为什么用B+树

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**索引类型（按数据结构分）**：
1. **B+树索引**：最常用的索引类型，InnoDB和MyISAM默认使用
2. **哈希索引**：Memory引擎支持，InnoDB的自适应哈希索引
3. **全文索引**：用于全文搜索，MyISAM和InnoDB 5.6+支持
4. **R树索引**：空间数据索引

**索引类型（按功能分）**：
1. **普通索引**：最基本的索引
2. **唯一索引**：索引列的值必须唯一
3. **主键索引**：特殊的唯一索引，一个表只能有一个
4. **联合索引**：多个字段组成的索引
5. **全文索引**：用于全文搜索
6. **空间索引**：用于地理空间数据

**B+树结构**：
- 一种多路平衡查找树
- 非叶子节点只存储索引键（不存储数据）
- 叶子节点存储所有数据，且通过链表连接
- 所有叶子节点在同一层

**B+树的优点**：
1. **磁盘IO少**：树的高度低（通常3-4层就能存千万级数据）
2. **范围查询高效**：叶子节点形成链表，范围遍历只需找到起点然后沿链表走
3. **查询性能稳定**：所有查询都走到叶子节点，路径长度相同
4. **支持排序**：叶子节点有序，天然支持order by

**答案解析**:

深入理解B+树索引：

1. **为什么不用二叉查找树**：
   - 二叉树高度太高，磁盘IO次数多
   - 数据库索引存在磁盘上，每次访问节点都是一次磁盘IO
   - B+树是多路的，一个节点可以存很多key，树更矮

2. **为什么不用B树**：
   - B树每个节点都存数据，非叶子节点也存
   - B+树非叶子节点只存索引键，同样大小的节点能存更多key
   - B+树叶子节点用链表连接，范围查询更高效
   - B+树查询必须走到叶子节点，性能更稳定

3. **B+树的高度计算**：
   - 假设一页16KB，每个key+指针占16字节
   - 非叶子节点一页能存约1000个key（16KB/16B）
   - 三层B+树：1000 × 1000 × 1000 = 10亿条记录
   - 实际上叶子节点存数据，一页存不了那么多，但千万级数据3层足够

4. **InnoDB和MyISAM的B+树索引区别**：
   - **InnoDB**：聚簇索引，叶子节点存完整数据行
   - **MyISAM**：非聚簇索引，叶子节点存数据的地址指针
   - InnoDB的二级索引叶子节点存主键值，需要回表
   - MyISAM的二级索引叶子节点存数据地址，不需要回表

5. **哈希索引的特点**：
   - 等值查询非常快（O(1)）
   - 不支持范围查询、排序、最左前缀匹配
   - 有哈希冲突问题
   - InnoDB的自适应哈希索引是自动维护的，不能手动创建

**扩展问题**:
- B+树索引和哈希索引各适用于什么场景？
- 为什么InnoDB的页大小是16KB？可以改吗？
- B+树的插入和删除过程是怎样的？如何保持平衡？
- 什么是自适应哈希索引（AHI）？

## Q3: MySQL的索引失效场景

**考察点**: 索引使用规则、SQL优化、explain分析

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**常见索引失效场景**：

1. **违反最左前缀匹配原则**：
```sql
-- 联合索引 (a, b, c)
SELECT * FROM t WHERE b = 1 AND c = 2;  -- 索引失效
SELECT * FROM t WHERE a = 1 AND c = 2;  -- 只用a的索引
```

2. **在索引列上做运算或函数操作**：
```sql
SELECT * FROM t WHERE YEAR(create_time) = 2023;  -- 索引失效
SELECT * FROM t WHERE id + 1 = 10;               -- 索引失效
```

3. **隐式类型转换**：
```sql
-- phone是varchar类型
SELECT * FROM t WHERE phone = 13800138000;  -- 索引失效（字符串转数字）
```

4. **使用不等于（!= 或 <>）**：
```sql
SELECT * FROM t WHERE status != 1;  -- 可能索引失效（取决于数据分布）
```

5. **is null / is not null**：
```sql
SELECT * FROM t WHERE name IS NULL;     -- 可能失效
SELECT * FROM t WHERE name IS NOT NULL; -- 通常失效
```

6. **like以通配符开头**：
```sql
SELECT * FROM t WHERE name LIKE '%abc';   -- 索引失效
SELECT * FROM t WHERE name LIKE 'abc%';   -- 索引有效（前缀匹配）
```

7. **or连接的条件中有非索引列**：
```sql
-- name有索引，age没有索引
SELECT * FROM t WHERE name = 'a' OR age = 18;  -- 索引失效
```

8. **使用NOT IN / NOT EXISTS**：
```sql
SELECT * FROM t WHERE id NOT IN (1, 2, 3);  -- 可能失效
```

9. **全表扫描比索引更快时**：
   - 当查询返回的数据量很大（如超过表的20-30%）
   - 优化器可能选择全表扫描而非索引
   - 因为回表的随机IO比顺序扫描更慢

**答案解析**:

深入理解索引失效：

1. **最左前缀匹配原则**：
   - 联合索引是按索引列从左到右排序的
   - 跳过左边的列，右边的列就无法利用索引
   - 这就像查字典，只知道第二个字不知道第一个字，没法用拼音索引
   - 范围查询之后的列会失效：`WHERE a = 1 AND b > 2 AND c = 3` → a和b有效，c无效

2. **为什么函数/运算会导致索引失效**：
   - 索引存储的是原始值，不是计算后的值
   - MySQL无法通过计算后的值定位索引
   - 可以使用函数索引（MySQL 5.7+支持生成列，8.0支持函数索引）

3. **隐式类型转换的原理**：
   - 当比较的两边类型不同时，MySQL会做隐式转换
   - 规则是：将字符串转换为数字（方便比较）
   - 如果索引列是字符串，而查询条件是数字，就会对索引列做转换
   - 相当于在索引列上用了函数，导致索引失效

4. **如何判断索引是否失效**：
   - 使用`EXPLAIN`命令查看执行计划
   - `type`列：ALL表示全表扫描，index/range/ref等表示用了索引
   - `key`列：实际使用的索引
   - `rows`列：预计扫描的行数
   - `Extra`列：Using index表示覆盖索引，Using where表示回表过滤

5. **优化建议**：
   - 遵守最左前缀原则
   - 避免在索引列上使用函数和运算
   - 注意类型匹配，避免隐式转换
   - like查询尽量用前缀匹配
   - 用union代替or（两边都有索引时）
   - 用覆盖索引避免回表

**扩展问题**:
- 什么是索引下推（ICP）？它能解决什么问题？
- 联合索引的列顺序如何选择？有什么原则？
- 如何分析一条SQL的索引使用情况？
- MySQL优化器是如何选择索引的？

## Q4: MySQL的事务四大特性（ACID）

**考察点**: ACID概念、实现原理、事务基础

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**ACID是事务的四大特性**：

**1. 原子性（Atomicity）**：
- 事务是一个不可分割的最小工作单元
- 事务中的所有操作要么全部成功，要么全部失败回滚
- 不会出现部分成功部分失败的中间状态
- **实现**：undo log（回滚日志），记录修改前的数据，回滚时逆向操作

**2. 一致性（Consistency）**：
- 事务执行前后，数据库从一个一致性状态转换到另一个一致性状态
- 数据完整性约束（主键、外键、唯一约束等）不被破坏
- 业务规则也应该保持一致（如转账前后总金额不变）
- **实现**：主要由应用层保证，数据库保证约束层面的一致性

**3. 隔离性（Isolation）**：
- 多个事务并发执行时，事务之间相互隔离，互不干扰
- 一个事务在提交前，对其他事务是不可见的
- 隔离性分为四个隔离级别
- **实现**：锁机制 + MVCC（多版本并发控制）

**4. 持久性（Durability）**：
- 事务一旦提交，对数据的修改就是永久性的
- 即使系统崩溃，提交的数据也不会丢失
- **实现**：redo log（重做日志），写入磁盘后即使宕机也能恢复

**ACID之间的关系**：
- 原子性、隔离性、持久性都是为了保证一致性
- 一致性是最终目标，其他三个是手段

**答案解析**:

深入理解ACID：

1. **原子性详解**：
   - 不是说事务不能被打断，而是说即使被打断（如崩溃），也能回滚到事务开始前的状态
   - undo log记录了数据修改前的状态，回滚时执行反向操作
   - 注意：原子性是逻辑上的原子，不是物理上的不可中断

2. **一致性详解**：
   - 一致性是事务的最终目的
   - 数据库层面保证的是数据约束的一致性（主键、外键、唯一索引、check约束等）
   - 业务一致性需要应用层保证（如转账时总金额不变需要应用逻辑保证）
   - 一致性是结果，原子性、隔离性、持久性是达到一致性的手段

3. **隔离性详解**：
   - 隔离性是相对的，有不同的隔离级别
   - 隔离级别越高，并发性能越差，数据一致性越好
   - 需要在性能和一致性之间做权衡

4. **持久性详解**：
   - redo log是保证持久性的关键
   - 事务提交时，先写redo log，再修改内存中的数据
   - 即使宕机，重启后可以通过redo log恢复未刷盘的数据
   - WAL（Write-Ahead Logging）：先写日志，再写数据

5. **CAP定理与ACID**：
   - ACID是关系型数据库事务的特性
   - CAP是分布式系统的定理（一致性、可用性、分区容错性三者不可兼得）
   - 两者讨论的不是同一个层面的问题
   - 分布式事务中需要在ACID和CAP之间做权衡

**扩展问题**:
- 原子性和持久性都是通过日志实现的，undo log和redo log有什么区别？
- 一致性具体指什么？数据库能保证业务一致性吗？
- 为什么需要隔离级别？隔离级别是对隔离性的妥协吗？
- MySQL的崩溃恢复过程是怎样的？

## Q5: MySQL的事务隔离级别

**考察点**: 四个隔离级别、解决的问题、默认级别

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**SQL标准定义了四个隔离级别**，从低到高：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| 读未提交（Read Uncommitted） | 可能 | 可能 | 可能 |
| 读已提交（Read Committed） | 不会 | 可能 | 可能 |
| 可重复读（Repeatable Read） | 不会 | 不会 | 可能（MySQL基本解决） |
| 串行化（Serializable） | 不会 | 不会 | 不会 |

**各问题定义**：
1. **脏读**：一个事务读取到了另一个事务未提交的数据
2. **不可重复读**：同一个事务中，两次读取同一行数据，结果不一致（因为其他事务修改并提交了）
3. **幻读**：同一个事务中，两次同样的范围查询，结果行数不一样（因为其他事务插入/删除了记录）

**MySQL的默认隔离级别**：
- **InnoDB默认是可重复读（RR）**
- 但InnoDB在RR级别下，通过Next-Key Lock（间隙锁+行锁）基本解决了幻读问题
- 注意是"基本解决"，不是完全解决（快照读不会有幻读，当前读可能有）

**设置隔离级别**：
```sql
SET [SESSION|GLOBAL] TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

**答案解析**:

深入理解隔离级别：

1. **不可重复读 vs 幻读**：
   - 不可重复读：针对的是同一行数据的修改（update）
   - 幻读：针对的是行数的变化（insert/delete）
   - 不可重复读是"同一行数据前后不一样"
   - 幻读是"同样的条件查询，前后行数不一样"

2. **各隔离级别的实现方式**：
   - **读未提交**：基本不加锁，直接读最新数据
   - **读已提交**：每次select都生成新的ReadView（快照）
   - **可重复读**：事务开始时生成ReadView，整个事务使用同一个快照
   - **串行化**：所有select都加共享锁，读写互相阻塞

3. **为什么MySQL默认是RR而不是RC**：
   - 历史原因：MySQL早期的binlog是statement格式
   - RC级别下，主从不一致的风险更高
   - InnoDB的RR通过MVCC+间隙锁，性能和一致性平衡得很好
   - 现在row格式的binlog下，RC也没问题，但默认还是RR

4. **隔离级别和性能的关系**：
   - 隔离级别越低，并发性能越好，但数据一致性越差
   - 隔离级别越高，数据一致性越好，但并发性能越差
   - 需要根据业务场景选择合适的隔离级别
   - 大多数互联网应用使用RC级别（性能更好，且大多数业务能接受不可重复读）

5. **查看隔离级别**：
```sql
SELECT @@transaction_isolation;  -- MySQL 8.0
SELECT @@tx_isolation;           -- MySQL 5.x
```

- 实际项目中你选择什么隔离级别？为什么？

## Q6: MySQL的MVCC（多版本并发控制）

**考察点**: MVCC原理、ReadView、快照读与当前读

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**定义**：MVCC（Multi-Version Concurrency Control，多版本并发控制）是一种通过保存数据的历史版本来实现读写不冲突的并发控制机制。

**核心思想**：
- 读操作读取数据的历史版本（快照），不需要加锁
- 写操作创建新版本，不影响读操作
- 读写不阻塞，大大提高并发性能

**实现基础**：
1. **隐式字段**：每行数据都有隐藏字段
   - `DB_TRX_ID`：最近修改该记录的事务ID
   - `DB_ROLL_PTR`：回滚指针，指向undo log中的旧版本
   - `DB_ROW_ID`：隐藏主键（如果没有显式主键）

2. **undo log（回滚日志）**：
   - 保存数据的历史版本
   - 同一行的多个版本通过回滚指针形成链表（版本链）

3. **ReadView（读视图）**：
   - 事务进行快照读时生成的读视图
   - 决定了当前事务能看到哪些版本的数据
   - 包含：
     - `m_ids`：生成ReadView时活跃的事务ID列表
     - `min_trx_id`：活跃事务中的最小ID
     - `max_trx_id`：下一个要分配的事务ID
     - `creator_trx_id`：创建该ReadView的事务ID

**可见性规则**：
- 如果版本的trx_id < min_trx_id → 可见（事务在ReadView生成前已提交）
- 如果版本的trx_id >= max_trx_id → 不可见（事务在ReadView生成后才开始）
- 如果版本的trx_id在m_ids中 → 不可见（事务还活跃）
- 否则 → 可见

**答案解析**:

深入理解MVCC：

1. **快照读 vs 当前读**：
   - **快照读**：普通的select语句，读取的是快照版本，不加锁
   - **当前读**：读取最新版本，需要加锁
     - `SELECT ... FOR UPDATE`
     - `SELECT ... LOCK IN SHARE MODE`
     - `INSERT`、`UPDATE`、`DELETE`
   - MVCC只在快照读时生效，当前读需要靠锁来保证并发

2. **RC和RR级别的MVCC区别**：
   - **RC**：每次快照读都生成新的ReadView → 能看到其他事务刚提交的修改 → 不可重复读
   - **RR**：事务中第一次快照读时生成ReadView，后续复用 → 看不到其他事务的新提交 → 可重复读

3. **版本链的查找过程**：
   - 从最新版本开始，沿着undo log链表向前找
   - 对每个版本，用ReadView判断是否可见
   - 找到第一个可见的版本就返回
   - 如果所有版本都不可见，说明行已被删除，返回空

4. **MVCC的优势**：
   - 读写不冲突，读不加锁，写不加读锁
   - 大大提高了并发读的性能
   - 是InnoDB高并发的基石

5. **MVCC的局限性**：
   - 只解决了读-写冲突，写-写冲突还是要靠锁
   - 快照读看到的是历史数据，不是最新数据
   - 需要维护多个版本，有一定的空间和性能开销

6. **purge线程**：
   - 旧版本的undo log不会永远保留
   - purge线程定期清理不再需要的undo log
   - 当没有任何事务需要某个旧版本时，它就可以被清理了

- undo log和redo log有什么区别和联系？
- MVCC能解决幻读吗？为什么？

## Q7: MySQL的锁机制（行锁/表锁/间隙锁/Next-Key Lock）

**考察点**: 锁的分类、加锁规则、死锁

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**锁的分类**：

**按粒度分**：
1. **表级锁**：锁定整个表，开销小，加锁快，冲突概率高，并发度低
   - 表读锁（共享锁）：多个事务可以同时加读锁
   - 表写锁（排他锁）：只有一个事务能加写锁
   - 元数据锁（MDL）：保护表结构

2. **行级锁**：锁定行，开销大，加锁慢，冲突概率低，并发度高
   - InnoDB支持行锁，MyISAM不支持
   - 共享锁（S锁）：读锁
   - 排他锁（X锁）：写锁

3. **页级锁**：介于表锁和行锁之间（BDB引擎）

**按类型分**：
1. **共享锁（S锁/读锁）**：
   - 一个事务加了S锁，其他事务可以加S锁，但不能加X锁
   - `SELECT ... LOCK IN SHARE MODE`

2. **排他锁（X锁/写锁）**：
   - 一个事务加了X锁，其他事务既不能加S锁也不能加X锁
   - `UPDATE`、`DELETE`、`INSERT`自动加X锁
   - `SELECT ... FOR UPDATE`

3. **意向锁**：
   - 表级别的锁，用于表明某个事务将要对表中的行加什么锁
   - 意向共享锁（IS）：事务打算给行加S锁
   - 意向排他锁（IX）：事务打算给行加X锁
   - 提高表锁的判断效率（不需要逐行检查）

**InnoDB的行锁算法**：
1. **Record Lock（记录锁）**：锁定索引记录
2. **Gap Lock（间隙锁）**：锁定索引之间的间隙，防止插入
3. **Next-Key Lock（临键锁）**：记录锁 + 间隙锁，锁定左开右闭区间
   - 是InnoDB默认的行锁算法
   - 用于解决幻读问题

**答案解析**:

深入理解锁机制：

1. **行锁的加锁规则（RR级别下）**：
   - 唯一索引等值查询：命中记录 → Record Lock（退化为记录锁）
   - 唯一索引等值查询：未命中 → Gap Lock（锁定间隙）
   - 普通索引等值查询：命中 → Next-Key Lock + 下一个间隙锁
   - 范围查询：Next-Key Lock
   - 无索引：全表扫描，表锁（实际上是逐行加锁，效果类似表锁）

2. **间隙锁的作用**：
   - 防止其他事务在间隙中插入新记录
   - 解决幻读问题（当前读场景下）
   - 间隙锁之间不冲突（两个事务可以同时持有同一间隙的gap锁）
   - 只有插入操作会和间隙锁冲突

3. **Next-Key Lock**：
   - 是记录锁和间隙锁的组合
   - 锁定范围是左开右闭区间 (prev, current]
   - 例如索引值有10, 20, 30，那么：
     - (负无穷, 10]、(10, 20]、(20, 30]、(30, 正无穷)
   - 默认情况下，InnoDB的当前读使用Next-Key Lock

4. **加锁行为总结**：
   - 行锁是加在索引上的，没有索引就无法加行锁
   - 加锁的范围取决于索引和查询条件
   - 唯一索引比普通索引加锁范围更小
   - 等值查询比范围查询加锁范围更小

5. **MDL（元数据锁）**：
   - 访问表时自动加MDL读锁
   - 修改表结构时加MDL写锁
   - MDL读写互斥
   - 注意：长事务持有MDL读锁会阻塞DDL，进而阻塞后续所有操作

**扩展问题**:

- 意向锁和行锁是什么关系？
- 如何查看当前数据库中的锁等待情况？

## Q8: MySQL的死锁及解决方法

**考察点**: 死锁产生条件、检测与避免、解决方案

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**死锁定义**：
两个或多个事务互相等待对方释放锁，导致都无法继续执行的现象。

**死锁产生的四个必要条件**：
1. **互斥条件**：锁是排他的，一个资源只能被一个事务持有
2. **请求与保持条件**：事务持有锁的同时，又请求新的锁
3. **不可剥夺条件**：已持有的锁不能被强制剥夺，只能自己释放
4. **循环等待条件**：事务之间形成循环等待链

**InnoDB的死锁检测**：
- InnoDB有死锁检测机制（wait-for graph等待图）
- 检测到死锁后，回滚代价最小的事务（通常是影响行数少的）
- 可以通过`SHOW ENGINE INNODB STATUS`查看最近的死锁信息

**死锁的常见场景**：
1. **不同表相同顺序**：
   - 事务1：先锁A，再锁B
   - 事务2：先锁B，再锁A

2. **同一张表的不同行**：
   - 事务1：UPDATE ... WHERE id = 1
   - 事务2：UPDATE ... WHERE id = 2
   - 然后事务1又要锁id=2，事务2又要锁id=1

3. **间隙锁导致的死锁**：
   - 两个事务同时在同一个间隙加gap锁（gap锁不互斥）
   - 然后两个事务都尝试插入，就会互相等待对方释放gap锁

**解决和避免死锁的方法**：
1. **固定加锁顺序**：所有事务按相同顺序加锁
2. **缩短事务时间**：减少锁持有时间
3. **降低隔离级别**：RC级别下间隙锁更少
4. **使用更细粒度的索引**：减少加锁范围
5. **合理设计SQL**：避免大事务、复杂查询
6. **重试机制**：捕获死锁异常后重试
7. **使用锁超时**：`innodb_lock_wait_timeout`控制锁等待超时

**答案解析**:

深入理解死锁：

1. **死锁检测的原理**：
   - InnoDB维护一个等待图（wait-for graph）
   - 每个事务是一个节点
   - 如果事务A等待事务B持有的锁，就有一条A→B的边
   - 检测图中是否有环，有环就表示有死锁
   - 死锁检测的时间复杂度是O(n)，n是等待的事务数

2. **死锁检测的代价**：
   - 每次加锁都要检测是否形成死锁
   - 高并发下，死锁检测的CPU开销很大
   - 可以通过`innodb_deadlock_detect = OFF`关闭死锁检测
   - 关闭后靠锁超时来处理死锁

3. **间隙锁导致死锁的典型场景**：
```sql
-- 表t有索引idx_a，a的值有1,3,5
-- 事务1
SELECT * FROM t WHERE a = 2 FOR UPDATE;  -- 加间隙锁(1,3)
INSERT INTO t(a) VALUES(2);               -- 等待事务2的gap锁？

-- 事务2
SELECT * FROM t WHERE a = 2 FOR UPDATE;  -- 也加间隙锁(1,3)（gap锁不互斥）
INSERT INTO t(a) VALUES(2);               -- 等待事务1的gap锁 → 死锁！
```
这是因为gap锁之间是共享的，但插入操作和gap锁是互斥的。

4. **线上死锁排查步骤**：
   - 查看死锁日志：`SHOW ENGINE INNODB STATUS`
   - 分析死锁的两个事务分别在做什么
   - 找出加锁顺序不一致的原因
   - 修改SQL或业务逻辑，统一加锁顺序

5. **锁等待 vs 死锁**：
   - 锁等待：一个事务等另一个事务释放锁，最终能等到
   - 死锁：两个事务互相等待，永远等不到
   - 锁等待超时时间由`innodb_lock_wait_timeout`控制（默认50秒）

**扩展问题**:

- 死锁检测关闭后有什么影响？什么时候考虑关闭？
- 分布式系统中的死锁和单机数据库的死锁有什么区别？
- 如何监控数据库的死锁情况？

## Q9: MySQL的分页查询优化

**考察点**: 分页性能、深度分页、优化方案

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**传统分页的问题**：
```sql
SELECT * FROM table LIMIT 10000, 20;
```
当offset很大时（深度分页），性能会急剧下降。

**为什么慢**：
- LIMIT M, N需要扫描前M+N条记录，然后丢弃前M条
- M越大，扫描的行数越多，性能越差
- 即使有索引，也需要扫描M条索引记录

**优化方案**：

**1. 基于索引的延迟关联**：
```sql
-- 优化前
SELECT * FROM t WHERE status = 1 LIMIT 10000, 20;

-- 优化后
SELECT t.* FROM t 
INNER JOIN (SELECT id FROM t WHERE status = 1 LIMIT 10000, 20) AS tmp 
ON t.id = tmp.id;
```
- 先利用覆盖索引查出需要的id，再回表查完整数据
- 减少回表次数（从M+N次降到N次）

**2. 基于主键的范围查询**（知道上一页的最后一个id时）：
```sql
-- 上一页最后一条的id是10020
SELECT * FROM t WHERE id > 10020 LIMIT 20;
```
- 利用主键索引直接定位，跳过前M条
- 性能最好，但只能用于"上一页/下一页"的场景
- 不支持跳页

**3. 使用覆盖索引**：
```sql
-- 如果只需要id和name，且有联合索引(status, name)
SELECT id, name FROM t WHERE status = 1 LIMIT 10000, 20;
```
- 不需要回表，直接从索引中取数据
- 性能大幅提升

**4. 使用书签/游标方式**：
- 记录上一页最后一条的位置（如id、时间等）
- 下一页查询时从这个位置开始
- 适用于无限滚动的场景

**答案解析**:

深入理解分页优化：

1. **深度分页性能差的根本原因**：
   - MySQL的LIMIT offset, size是先扫描offset+size行
   - 不是直接跳到第offset行
   - 因为InnoDB的索引是B+树，只能顺序遍历，不能随机定位到第N条

2. **各种方案的适用场景**：
   - **延迟关联**：适用于有where条件且需要返回全字段的情况
   - **主键范围**：适用于顺序翻页（上一页/下一页），性能最好
   - **覆盖索引**：适用于只需要索引中字段的场景
   - **游标分页**：适用于移动端无限滚动的场景
   - **搜索引擎**：数据量大且有搜索需求时，考虑ES等搜索引擎

3. **为什么延迟关联能优化**：
   - 普通写法：扫描10020行 → 回表10020次 → 丢弃前10000行
   - 延迟关联：扫描10020行索引（不需要回表）→ 回表20次
   - 把大量的回表操作省去了，只回表需要的20行

4. **业务层面的优化**：
   - 限制最大翻页深度（如最多100页）
   - 用"上一页/下一页"代替页码跳转
   - 用搜索/筛选代替翻页找数据
   - 对于总数统计，可以用近似值（如ES的approximate）

5. **count(*)的优化**：
   - 分页通常还需要总数
   - InnoDB的count(*)需要扫描，性能差
   - 可以用缓存（Redis）存总数
   - 或者用近似值，不需要精确总数

**扩展问题**:
- 为什么MySQL不直接跳到offset的位置？
- 游标分页和普通分页各有什么优缺点？
- 大数据量下，如何实现高效的分页查询？
- 联合索引下，LIMIT的性能如何？能用到索引吗？

## Q10: MySQL的SQL语句优化方法

**考察点**: SQL优化思路、索引优化、查询优化

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**SQL优化的一般思路**：

**1. 慢查询定位**：
- 开启慢查询日志：`slow_query_log = ON`
- 设置慢查询阈值：`long_query_time = 1`（秒）
- 使用`explain`分析执行计划
- 使用`show profile`分析执行耗时
- 使用`performance_schema`分析性能

**2. 索引优化**：
- 为WHERE、JOIN、ORDER BY、GROUP BY的列建立索引
- 使用联合索引，遵守最左前缀原则
- 使用覆盖索引，避免回表
- 删除重复和无用的索引
- 避免索引失效（见Q3）

**3. 查询语句优化**：
- **避免SELECT ***：只查询需要的字段，减少数据传输和回表
- **小表驱动大表**：JOIN时小表在前，大表在后
- **用JOIN代替子查询**：MySQL优化器对JOIN优化更好
- **用UNION ALL代替UNION**：不需要去重时用UNION ALL
- **LIMIT限制结果集**：不需要全部数据时加LIMIT
- **避免在列上做运算**：防止索引失效
- **批量操作**：批量INSERT/UPDATE比循环单条快

**4. 表结构优化**：
- 选择合适的数据类型（越小越好）
- 避免使用NULL（NOT NULL + 默认值）
- 适当的冗余（反范式，减少JOIN）
- 大表拆分（垂直拆分、水平拆分）

**5. 数据库配置优化**：
- `innodb_buffer_pool_size`：缓冲池大小（建议物理内存的50-75%）
- `innodb_log_file_size`：redo log大小
- `max_connections`：最大连接数
- `tmp_table_size` / `max_heap_table_size`：临时表大小

**答案解析**:

深入理解SQL优化：

1. **EXPLAIN的使用**：
   - `type`：访问类型（ALL < index < range < ref < eq_ref < const/system）
   - `key`：实际使用的索引
   - `rows`：预计扫描的行数
   - `Extra`：额外信息
     - Using index：覆盖索引
     - Using where：回表后过滤
     - Using index condition：索引下推
     - Using temporary：使用临时表
     - Using filesort：文件排序

2. **JOIN优化**：
   - MySQL使用嵌套循环连接（Nested-Loop Join）
   - 驱动表（外层表）越小越好
   - 被驱动表的JOIN字段要有索引
   - 小表驱动大表：减少循环次数
   - 避免超过3个表的JOIN

3. **ORDER BY优化**：
   - 尽量利用索引排序（索引本身有序）
   - 无法利用索引时，MySQL会做filesort
   - filesort有两种算法：
     - 两次传输：先排序再回表（旧版）
     - 一次传输：把需要的字段都取出来排序（新版，内存占用大）
   - 优化：增加sort_buffer_size、减少排序字段、用覆盖索引

4. **GROUP BY优化**：
   - 默认会排序，可用ORDER BY NULL禁止排序
   - 利用索引分组
   - 用SUM(CASE WHEN)代替多个GROUP BY

5. **子查询优化**：
   - 尽量改成JOIN
   - 特别注意IN子查询，MySQL优化器可能处理得不好
   - 用EXISTS代替IN（取决于数据量）

6. **优化的一般步骤**：
   1. 找出慢SQL（慢查询日志）
   2. EXPLAIN分析执行计划
   3. 看type、key、rows、Extra
   4. 针对性优化（加索引、改写SQL）
   5. 验证优化效果

- filesort一定慢吗？什么是filesort？
- 如何优化GROUP BY查询？
- JOIN查询的执行原理是什么？

## Q11: MySQL的Explain执行计划分析

**考察点**: Explain输出含义、性能分析

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**Explain命令**：
```sql
EXPLAIN SELECT * FROM t WHERE id = 1;
```

**输出列的含义**：

| 列名 | 含义 |
|------|------|
| id | 查询中SELECT的序号，id越大越先执行，相同则从上到下 |
| select_type | 查询类型（SIMPLE/PRIMARY/SUBQUERY/DERIVED/UNION等） |
| table | 输出行对应的表 |
| partitions | 匹配的分区 |
| type | 访问类型（性能从差到好：ALL→index→range→ref→eq_ref→const/system） |
| possible_keys | 可能使用的索引 |
| key | 实际使用的索引 |
| key_len | 使用的索引长度（字节），越短越好 |
| ref | 与索引比较的列或常量 |
| rows | 预估要扫描的行数（越少越好） |
| filtered | 按表条件过滤的行百分比 |
| Extra | 额外信息 |

**type列详解**（性能从差到好）：
1. **ALL**：全表扫描，最差
2. **index**：全索引扫描，比ALL略好（只扫索引树）
3. **range**：索引范围扫描（BETWEEN、>、<、IN等）
4. **ref**：非唯一索引的等值查询
5. **eq_ref**：唯一索引的等值查询（JOIN场景）
6. **const/system**：主键或唯一索引等值查询，最多一行结果
7. **NULL**：不用访问表/索引，直接返回结果

**Extra列常见值**：
- **Using index**：覆盖索引，不需要回表
- **Using where**：存储引擎返回后，在Server层过滤
- **Using index condition**：索引下推（ICP），在索引层面先过滤
- **Using temporary**：使用临时表（GROUP BY、DISTINCT等）
- **Using filesort**：文件排序（ORDER BY无法利用索引）
- **Using join buffer**：被驱动表没索引，用连接缓存
- **Impossible WHERE**：WHERE条件永远不成立

**答案解析**:

深入理解Explain：

1. **id列的执行顺序**：
   - id相同：从上到下执行
   - id不同：id越大越先执行（子查询）
   - 有NULL：UNION的结果集，最后执行

2. **select_type详解**：
   - **SIMPLE**：简单查询，不包含子查询和UNION
   - **PRIMARY**：最外层查询
   - **SUBQUERY**：子查询（非FROM子句中）
   - **DERIVED**：派生表（FROM子句中的子查询）
   - **UNION**：UNION中的第二个及以后的查询
   - **UNION RESULT**：UNION的结果

3. **key_len的计算**：
   - 用于判断联合索引中实际使用了多少列
   - 计算方式：
     - char(n)：n × 字符集字节数（utf8mb4是4，utf8是3）
     - varchar(n)：n × 字符集字节数 + 2（长度）
     - int：4字节
     - bigint：8字节
     - datetime：5字节（5.6+）
     - 允许NULL：+1字节

4. **如何通过Explain优化SQL**：
   - 看type：至少要达到range级别，最好是ref或eq_ref
   - 看key：是否用上了合适的索引
   - 看rows：扫描行数是否过多
   - 看Extra：
     - Using filesort → 优化ORDER BY，加索引
     - Using temporary → 优化GROUP BY或DISTINCT
     - Using where → 考虑加索引或改写条件
     - Using index → 好现象，覆盖索引

5. **Explain的局限性**：
   - rows是估算值，不一定准确
   - 看不到内存使用、执行时间等
   - 不会告诉你触发器、存储过程的影响
   - 不一定能准确反映真实执行情况（优化器可能动态调整）

- Using filesort是在文件中排序吗？一定慢吗？
- 什么是索引下推（ICP）？Extra中的Using index condition是什么意思？
- EXPLAIN ANALYZE是什么？和普通EXPLAIN有什么区别？

## Q12: MySQL的聚簇索引和非聚簇索引

**考察点**: 聚簇索引结构、回表、二级索引

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**聚簇索引（Clustered Index）**：
- 索引和数据存在一起，叶子节点就是数据行
- 一个表只能有一个聚簇索引（因为数据只能按一种方式排序）
- InnoDB的主键索引就是聚簇索引
- 如果没有主键，InnoDB会选择唯一非空索引作为聚簇索引
- 如果也没有，InnoDB会隐式创建一个row_id作为聚簇索引

**非聚簇索引（Non-Clustered Index / 二级索引）**：
- 索引和数据分开存储，叶子节点存储主键值
- 一个表可以有多个非聚簇索引
- 通过非聚簇索引查找数据，需要先找到主键，再通过主键索引找数据（回表）
- MyISAM的索引都是非聚簇索引（叶子节点存数据地址）

**回表（Back to Table）**：
- 通过二级索引查到主键值后，再到聚簇索引中查找完整数据行的过程
- 回表需要多访问一次B+树
- 回表是随机IO，性能较差

**覆盖索引（Covering Index）**：
- 索引中包含了查询需要的所有字段，不需要回表
- EXPLAIN的Extra列会显示"Using index"
- 是重要的优化手段

**答案解析**:

深入理解聚簇索引：

1. **聚簇索引的优缺点**：
   - **优点**：
     - 查询速度快（索引和数据在一起，少一次IO）
     - 主键范围查询效率高（数据按主键排序，局部性好）
   - **缺点**：
     - 插入新数据可能导致页分裂（影响性能）
     - 二级索引需要回表
     - 主键最好用自增ID，随机主键会导致频繁页分裂

2. **为什么推荐自增主键**：
   - 自增主键是顺序插入的，不会频繁导致页分裂
   - 主键越小，二级索引的叶子节点越小，同样大小的页能存更多索引项
   - UUID作为主键会导致随机插入，页分裂频繁，性能差，索引体积大

3. **回表的过程**：
   - 第一步：在二级索引B+树中找到对应的叶子节点，获取主键值
   - 第二步：用主键值在聚簇索引B+树中找到完整的数据行
   - 两次B+树查找，所以比直接查主键索引慢

4. **如何减少回表**：
   - 使用覆盖索引：把查询需要的字段都放到联合索引中
   - 尽量用主键查询
   - 只查询需要的字段，避免SELECT *

5. **InnoDB vs MyISAM的索引结构对比**：
   - **InnoDB**：
     - 主键索引（聚簇）：叶子节点 = 完整数据行
     - 二级索引：叶子节点 = 主键值
     - 数据文件就是索引文件（.ibd）
   - **MyISAM**：
     - 主键索引：叶子节点 = 数据行地址
     - 二级索引：叶子节点 = 数据行地址
     - 数据文件（.MYD）和索引文件（.MYI）分开

**扩展问题**:
- 为什么InnoDB必须有聚簇索引？
- 聚簇索引的页分裂是怎么回事？如何避免？
- 覆盖索引和联合索引是什么关系？
- 为什么二级索引的叶子节点存的是主键值而不是数据地址？

## Q13: MySQL的覆盖索引和最左前缀匹配

**考察点**: 覆盖索引、最左前缀、联合索引

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**最左前缀匹配原则**：
联合索引按照索引列的顺序从左到右进行匹配，查询条件中必须包含左边的列，才能利用索引。

**示例**：联合索引 `idx(a, b, c)`

| 查询条件 | 索引使用情况 |
|---------|-------------|
| WHERE a = 1 | 用到a |
| WHERE a = 1 AND b = 2 | 用到a, b |
| WHERE a = 1 AND b = 2 AND c = 3 | 用到a, b, c |
| WHERE b = 2 AND c = 3 | 用不到索引（跳过了a） |
| WHERE a = 1 AND c = 3 | 只用到a（跳过了b） |
| WHERE a = 1 AND b > 2 AND c = 3 | 用到a, b（范围查询后失效） |

**原理**：
- 联合索引是按多列排序的：先按第一列排，第一列相同再按第二列排，以此类推
- 跳过左边的列，右边的列就无法有序，也就无法利用索引
- 范围查询（>、<、BETWEEN、LIKE前缀等）之后的列无法利用索引

**覆盖索引（Covering Index）**：
- 查询需要的所有字段都能从索引中获取，不需要回表
- EXPLAIN中Extra显示"Using index"
- 是重要的性能优化手段

```sql
-- 联合索引 idx(name, age)
SELECT name, age FROM t WHERE name = 'abc';  -- 覆盖索引，不需要回表
SELECT name, age, id FROM t WHERE name = 'abc';  -- 也是覆盖索引（主键天然在二级索引中）
SELECT * FROM t WHERE name = 'abc';  -- 需要回表，不是覆盖索引
```

**答案解析**:

深入理解联合索引：

1. **联合索引的列顺序选择原则**：
   - **等值查询优先**：等值查询的列放在左边
   - **区分度高的优先**：区分度高的列放在左边
   - **使用频率高的优先**：经常单独使用的列放在左边
   - **范围查询放右边**：范围查询的列尽量放在右边
   - 核心原则：让索引能被更多的查询复用

2. **最左前缀匹配的延伸**：
   - **字符串最左前缀**：`WHERE name LIKE 'abc%'`可以用到索引
   - **范围查询后失效**：范围列之后的索引列用不到
   - **IN不算范围查询**：`WHERE a IN (1,2,3) AND b = 4` 可以用到a和b的索引
   - 注意：MySQL优化器可能会调整条件顺序以匹配索引，但不应该依赖这个

3. **覆盖索引的好处**：
   - 减少回表次数，减少IO
   - 索引通常比数据小，缓存命中率更高
   - 避免随机IO（回表是随机IO）
   - 可以减少filesort（索引本身有序）

4. **索引下推（ICP, Index Condition Pushdown）**：
   - MySQL 5.6引入的优化
   - 将WHERE条件下推到存储引擎层
   - 在索引层面先过滤，减少回表次数
   - EXPLAIN的Extra显示"Using index condition"
   - 例如索引(a, b)，WHERE a = 1 AND b = 2 → 之前只能用a的索引，现在可以在索引中直接过滤b

5. **索引设计的一般步骤**：
   - 找出所有查询SQL
   - 分析WHERE、JOIN、ORDER BY、GROUP BY的列
   - 设计联合索引，尽量让更多查询复用
   - 验证执行计划

**扩展问题**:
- 联合索引的列顺序如何确定？有哪些原则？
- 范围查询为什么会导致后面的索引列失效？
- 索引下推（ICP）是什么？它和覆盖索引有什么区别？
- 为什么不建议建太多索引？

## Q14: MySQL的主从复制原理

**考察点**: 主从复制流程、binlog、复制模式

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**主从复制（Replication）**：
将一台MySQL服务器（Master）的数据复制到另一台或多台MySQL服务器（Slave）。

**作用**：
1. **读写分离**：主库写，从库读，提高性能
2. **数据备份**：从库作为备份，提高可靠性
3. **高可用**：主库故障时切换到从库
4. **负载均衡**：读请求分散到多个从库

**复制原理（三个线程）**：
1. **Binlog Dump线程（主库）**：
   - 主库的线程，负责将binlog发送给从库
   - 从库连接主库时，主库创建此线程

2. **IO线程（从库）**：
   - 从库的线程，负责读取主库的binlog
   - 写入到本地的relay log（中继日志）

3. **SQL线程（从库）**：
   - 从库的线程，负责读取relay log并执行
   - 将数据变更应用到从库

**复制流程**：
1. 主库将数据变更记录到binlog
2. 从库IO线程连接主库，请求binlog
3. 主库Binlog Dump线程读取binlog并发送给从库
4. 从库IO线程接收binlog，写入relay log
5. 从库SQL线程读取relay log，执行SQL，更新数据

**binlog的三种格式**：
1. **Statement**：记录SQL语句
   - 优点：日志文件小
   - 缺点：可能导致主从不一致（如UUID()、NOW()等函数）
2. **Row**：记录行的变更（MySQL 5.7默认）
   - 优点：不会有主从不一致问题
   - 缺点：日志文件大（批量更新会记录每一行）
3. **Mixed**：混合模式，自动选择Statement或Row
   - 一般操作用Statement，不安全的操作用Row

**答案解析**:

深入理解主从复制：

1. **异步复制 vs 半同步复制 vs 全同步复制**：
   - **异步复制**：主库执行完事务后，写binlog，立即返回成功。不关心从库是否收到。性能最好，但可能丢数据。
   - **半同步复制**：主库执行完事务后，等待至少一个从库收到binlog并ACK，才返回成功。性能和一致性的折中。
   - **全同步复制**：主库等待所有从库都执行完事务才返回。最安全，但性能最差。

2. **主从延迟（Replication Lag）**：
   - 从库数据落后于主库的时间
   - 常见原因：
     - 从库性能差
     - 大事务（执行时间长，回放也慢）
     - 网络延迟
     - 从库SQL线程单线程回放（MySQL 5.6之前）
   - 优化：并行复制（MySQL 5.6库级并行，5.7组提交级并行，8.0基于writeset）

3. **GTID（全局事务ID）**：
   - MySQL 5.6引入
   - 每个事务有一个全局唯一的ID
   - 简化主从切换，不需要找binlog文件名和position
   - 自动找同步点

4. **复制的局限性**：
   - 有延迟，不是实时同步
   - 异步复制可能丢数据
   - 主库写压力大时，从库可能追不上
   - 只能一主多从，不能多主（多主会有冲突问题）

5. **主从复制中的数据一致性问题**：
   - 为什么会不一致：网络问题、从库执行错误、bug等
   - 如何校验：pt-table-checksum
   - 如何修复：pt-table-sync

**扩展问题**:
- 主从延迟怎么解决？有哪些优化方法？
- 半同步复制能保证数据不丢吗？
- MySQL 8.0在主从复制方面有什么新特性？
- 如何搭建MySQL主从复制？简述步骤

## Q15: MySQL的读写分离

**考察点**: 读写分离方案、实现方式、一致性问题

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**定义**：
主库处理写操作（INSERT、UPDATE、DELETE），从库处理读操作（SELECT），以提高系统的整体性能和吞吐量。

**为什么需要读写分离**：
- 大多数系统都是读多写少
- 读是性能瓶颈
- 主从复制提供了从库可以读
- 将读请求分散到从库，减轻主库压力

**实现方式**：

**1. 应用层实现**：
- 代码中区分读写，选择不同的数据源
- 框架：Sharding-JDBC、MyCat中间件的客户端模式
- 优点：性能好，不需要额外组件
- 缺点：代码侵入性强，语言绑定

**2. 中间件实现**：
- 在应用和数据库之间加一层代理
- 中间件负责路由SQL到正确的数据库
- 常见中间件：MyCat、ProxySQL、MaxScale、Atlas
- 优点：对应用透明，无代码侵入
- 缺点：多了一层网络开销，中间件本身可能成为瓶颈

**3. 数据库驱动层实现**：
- MySQL Connector/J的ReplicationDriver
- JDBC URL中配置主从地址
- 通过Connection的readOnly属性控制路由
- 优点：简单
- 缺点：功能有限

**一致性问题**：
- 主从复制有延迟，写完立即读可能读不到最新数据
- 解决方案：
  1. **强制主库读**：写后的读强制走主库
  2. **延迟等待**：写后等一下再读（不推荐，不准确）
  3. **读半同步**：等从库同步完成再返回（影响写性能）
  4. **业务接受**：大多数业务能接受短暂延迟

**答案解析**:

深入理解读写分离：

1. **读写分离的适用场景**：
   - 读多写少（读请求远多于写请求）
   - 读是性能瓶颈
   - 业务能接受一定的主从延迟
   - 读请求可以横向扩展

2. **中间件方案对比**：
   - **MyCat**：功能丰富，分库分表+读写分离，国内用得多
   - **ProxySQL**：高性能，Query Routing灵活，支持查询缓存
   - **MaxScale**：MariaDB开发的，功能全面
   - **ShardingSphere-Proxy**：Apache项目，生态好

3. **主从延迟的解决方案**：
   - **关键业务读主库**：如支付、订单等强一致性场景
   - **写后读主库**：用户自己修改的数据，短时间内读主库
   - **根据延迟判断**：监控延迟，延迟小读从库，延迟大读主库
   - **半同步复制**：牺牲部分写性能，保证至少一个从库同步
   - **组复制（MGR）**：MySQL Group Replication，Paxos协议

4. **读写分离的注意事项**：
   - 事务内的读走主库（事务内可能有写）
   - 实时性要求高的读走主库
   - 从库挂了怎么办？故障转移
   - 从库负载均衡：轮询、权重、随机等

5. **扩展：读多了怎么办**：
   - 加缓存（Redis）：热点数据读缓存
   - 读写分离：非热点数据读从库
   - 搜索引擎：复杂查询走ES
   - 分库分表：数据量大到从库也扛不住

- 中间件方案和客户端方案各有什么优缺点？
- 主从延迟很高时，读写分离还有意义吗？
- 什么是强制读主库？哪些场景需要？

## Q16: MySQL的分库分表策略

**考察点**: 分库分表方案、分片策略、常见问题

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

**为什么需要分库分表**：
- 单表数据量太大，查询性能下降
- 单库连接数、IOPS有上限
- 单库数据量太大，备份恢复困难

**分库分表的方式**：

**1. 垂直拆分**：
- **垂直分库**：按业务模块将不同的表分到不同的库
  - 如：用户库、订单库、商品库
  - 解决业务层面的耦合和连接数问题
- **垂直分表**：将一张表的字段拆到多张表
  - 如：用户基本信息表、用户扩展信息表
  - 解决单表字段过多、大字段问题

**2. 水平拆分**：
- **水平分库**：将同一张表的数据按某种规则分散到多个库
- **水平分表**：将同一张表的数据按某种规则分散到多个表
- 核心问题：分片规则（路由规则）

**分片策略**：

1. **范围分片**：按时间、ID范围分片
   - 优点：扩容方便，范围查询高效
   - 缺点：数据热点（新数据集中在一个分片）

2. **哈希分片**：对分片键取模
   - 优点：数据分布均匀
   - 缺点：扩容麻烦（需要迁移数据），范围查询要查所有分片

3. **一致性哈希**：
   - 优点：扩容时只迁移少量数据
   - 缺点：实现复杂，数据分布可能不均匀

4. **查表法**：维护一张路由表
   - 优点：灵活
   - 缺点：路由表可能成为瓶颈

**答案解析**:

深入理解分库分表：

1. **什么时候需要分库分表**：
   - 单表数据量超过5000万或20GB（经验值，因场景而异）
   - 单库QPS超过瓶颈
   - 单库连接数不够
   - 注意：不要过早分库分表，增加复杂度

2. **分库分表带来的问题**：
   - **分布式事务**：跨库事务如何保证一致性
   - **跨库JOIN**：不能直接JOIN，需要业务层组装
   - **跨库排序分页**：需要在各分片查询，然后汇总排序
   - **全局唯一ID**：自增ID不再适用，需要分布式ID
   - **扩容困难**：数据迁移复杂
   - **运维复杂度高**：

3. **常见的分库分表中间件**：
   - **客户端模式**：Sharding-JDBC（ShardingSphere），TSharding
     - 性能好，语言绑定
   - **代理模式**：MyCat，Sharding-Proxy，Atlas
     - 对应用透明，多语言支持，有额外网络开销

4. **分布式ID方案**：
   - **UUID**：简单，但无序，长度长，不适合做主键
   - **雪花算法（Snowflake）**：64位，时间戳+机器ID+序列号
     - 趋势递增，性能好
     - 需要解决时钟回拨问题
   - **号段模式**：每次从数据库取一批ID
   - **Redis自增**：利用Redis的INCR生成ID

5. **分库分表的最佳实践**：
   - 能不分就不分，能用缓存、读写分离解决就不要分
   - 先垂直后水平
   - 分片键选择很重要：尽量让查询路由到少量分片
   - 选择成熟的中间件，不要自己造轮子
   - 提前考虑扩容、迁移、数据一致性问题

**扩展问题**:
- 分库分表后，如何实现分页查询？
- 分布式事务有哪些解决方案？
- 分片键（Sharding Key）如何选择？
- 分库分表后，如何做数据迁移和扩容？

## Q17: MySQL的数据类型选择

**考察点**: 数据类型、存储优化、性能影响

**难度**: 简单

**频率**: ⭐⭐⭐⭐

**标准答案**:

**选择原则**：
1. **更小通常更好**：能用小类型就不用大类型（占用更少的磁盘、内存、CPU缓存）
2. **简单就好**：简单数据类型的操作开销更小
3. **尽量避免NULL**：NULL的列使索引、索引统计、值比较都更复杂

**整数类型**：
| 类型 | 字节 | 有符号范围 | 无符号范围 |
|------|------|-----------|-----------|
| TINYINT | 1 | -128~127 | 0~255 |
| SMALLINT | 2 | -32768~32767 | 0~65535 |
| MEDIUMINT | 3 | -8388608~8388607 | 0~16777215 |
| INT | 4 | -21亿~21亿 | 0~42亿 |
| BIGINT | 8 | -922亿亿~922亿亿 | 0~1844亿亿 |

**实数类型**：
- **FLOAT/DOUBLE**：浮点类型，近似值，计算有精度误差
- **DECIMAL**：精确小数，用于金融等需要精确计算的场景
  - DECIMAL(M, D)，M是总位数，D是小数位数
  - 底层是字符串存储，计算开销大

**字符串类型**：
- **CHAR**：定长字符串，最大255字符
  - 适合长度固定的字符串（如MD5、手机号）
  - 查询效率比VARCHAR高
- **VARCHAR**：变长字符串，最大65535字节
  - 节省空间
  - 需要额外1-2字节存储长度
- **TEXT/BLOB**：大文本/大二进制
  - 不能有默认值
  - 排序时只取前max_sort_length字节
  - 会导致临时表用磁盘表

**日期时间类型**：
- **DATETIME**：8字节，范围1000-9999年，与时区无关
- **TIMESTAMP**：4字节，范围1970-2038年，与时区有关
- **DATE**：3字节，只存日期
- **TIME**：3字节，只存时间
- 优先使用DATETIME（TIMESTAMP的2038问题）

**答案解析**:

深入理解数据类型选择：

1. **整数类型的选择建议**：
   - 确定不会为负的用UNSIGNED（如ID、年龄）
   - 能用TINYINT就不用SMALLINT，能用SMALLINT就不用INT
   - 主键一般用BIGINT（防止溢出，虽然INT也够大多数场景）
   - 状态、类型用TINYINT

2. **VARCHAR vs CHAR**：
   - CHAR适合长度固定或很短的字符串
   - VARCHAR适合长度变化大的字符串
   - VARCHAR(5)和VARCHAR(255)存储"hello"空间一样，但排序时不一样
   - 不要随意给很大的长度（影响临时表、排序等）

3. **为什么避免NULL**：
   - NULL的列需要额外的存储空间（1bit per column）
   - 索引NULL列需要额外空间
   - NULL值的比较复杂（IS NULL、IS NOT NULL）
   - NULL值会影响聚合函数（COUNT(col)会忽略NULL）
   - 建议用默认值（如0、''）代替NULL

4. **ENUM类型**：
   - 枚举类型，内部用整数存储
   - 优点：紧凑、可以限制取值
   - 缺点：添加枚举值需要ALTER TABLE
   - 适用于状态、类型等几乎不变的枚举值

5. **IP地址的存储**：
   - 不要用VARCHAR存IP
   - 用INT UNSIGNED存（INET_ATON/INET_NTOA转换）
   - 或用VARBINARY(16)存IPv6

6. **主键选择**：
   - 自增主键：性能好，顺序插入
   - UUID：不推荐（随机插入、空间大）
   - 雪花算法ID：分布式系统推荐

**扩展问题**:
- 为什么推荐用BIGINT做主键？INT不够用吗？
- DATETIME和TIMESTAMP有什么区别？选哪个？
- 大字段（TEXT/BLOB）有什么性能问题？
- 为什么说ENUM是"魔鬼"？有什么坑？

## Q18: MySQL的redo log和undo log和binlog

**考察点**: 三种日志的作用、区别、两阶段提交

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**三种日志对比**：

| 维度 | redo log | undo log | binlog |
|------|----------|----------|--------|
| 作用 | 崩溃恢复、保证持久性 | 回滚、MVCC | 主从复制、数据恢复 |
| 层面 | InnoDB存储引擎层 | InnoDB存储引擎层 | MySQL Server层 |
| 内容 | 物理日志（页的修改） | 逻辑日志（反向操作） | 逻辑日志（SQL或行变更） |
| 写入时机 | 事务执行中持续写入 | 事务执行前写入 | 事务提交时写入 |
| 循环写 | 是（固定大小，循环覆盖） | 是（定期purge清理） | 否（追加写） |
| 崩溃恢复 | 前滚已提交的事务 | 回滚未提交的事务 | 不用于崩溃恢复 |

**redo log（重做日志）**：
- 保证事务的持久性
- WAL（Write-Ahead Logging）：先写日志，再写数据
- 事务提交时，先写redo log，再修改内存中的数据页
- 崩溃后重启，通过redo log恢复已提交但未刷盘的数据
- 由两部分组成：redo log buffer（内存）和 redo log file（磁盘）

**undo log（回滚日志）**：
- 保证事务的原子性（回滚）
- 记录数据修改前的状态，回滚时执行逆向操作
- 是MVCC的基础（保存历史版本）
- 存在于undo表空间中

**binlog（归档日志/二进制日志）**：
- Server层的日志，所有引擎都有
- 记录所有DDL和DML语句
- 用于主从复制和数据恢复
- 三种格式：STATEMENT、ROW、MIXED

**两阶段提交（2PC）**：
为了保证redo log和binlog的一致性，MySQL使用两阶段提交：
1. **Prepare阶段**：写redo log，标记为prepare状态
2. **Commit阶段**：写binlog，然后将redo log标记为commit

崩溃恢复时：
- 如果redo log是commit状态 → 直接提交
- 如果redo log是prepare状态且binlog完整 → 提交事务
- 如果redo log是prepare状态且binlog不完整 → 回滚事务

**答案解析**:

深入理解三种日志：

1. **为什么需要两种日志（redo log + binlog）**：
   - redo log是InnoDB特有的，用于崩溃恢复
   - binlog是Server层的，用于主从复制和归档
   - 两者功能不同，缺一不可
   - 两阶段提交保证两者的一致性

2. **WAL机制详解**：
   - Write-Ahead Logging：先写日志，再写数据
   - 为什么不直接写数据？
     - 数据是随机写（修改不同的页）
     - 日志是顺序写（追加写，速度快）
     - 先写日志，即使崩溃也能恢复
   - 数据页可以缓存在内存中，积累到一定程度再批量刷盘

3. **redo log的刷盘时机**：
   - redo log buffer → redo log file
   - 刷盘策略由`innodb_flush_log_at_trx_commit`控制：
     - 0：每秒刷盘（事务提交不刷盘）→ 性能最好，可能丢1秒数据
     - 1：每次提交都刷盘（默认）→ 最安全，性能较差
     - 2：每次提交写到OS buffer，每秒刷盘 → 折中
   - 还有`innodb_flush_log_at_timeout`控制刷盘频率

4. **binlog的刷盘策略**：
   - 由`sync_binlog`控制：
     - 0：由OS决定何时刷盘
     - 1：每次提交都刷盘（最安全）
     - N：每N次提交刷一次盘
   - 双1配置：`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`

5. **undo log和MVCC**：
   - undo log保存了数据的历史版本
   - 版本链就是通过undo log和回滚指针形成的
   - 不同事务根据ReadView选择不同的版本读取

**扩展问题**:

- 如何理解WAL机制？为什么要先写日志再写数据？
- MySQL崩溃恢复的完整过程是怎样的？

## Q19: MySQL的脏读/不可重复读/幻读

**考察点**: 并发事务问题、隔离级别关系

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**三个读问题**（按严重程度从高到低）：

**1. 脏读（Dirty Read）**：
- **定义**：一个事务读取到了另一个事务未提交的数据
- **场景**：
  - 事务A修改了某行数据，但还没提交
  - 事务B读取了这行数据
  - 如果事务A回滚，事务B读到的就是"脏"数据
- **举例**：A给B转100元，A扣了钱但还没提交，B看到余额增加了，然后A回滚，B的钱又没了

**2. 不可重复读（Non-Repeatable Read）**：
- **定义**：同一事务中，两次读取同一行数据，结果不一致
- **场景**：
  - 事务A第一次读取某行数据
  - 事务B修改并提交了这行数据
  - 事务A第二次读取同一行数据，发现变了
- **举例**：事务中第一次读用户余额是100，中间其他事务修改为200，第二次读变成200

**3. 幻读（Phantom Read）**：
- **定义**：同一事务中，两次同样的范围查询，结果行数不一样
- **场景**：
  - 事务A按条件查询一批数据
  - 事务B插入了符合条件的新数据并提交
  - 事务A再次按同样条件查询，发现多了一行（幻影行）
- **举例**：查询年龄>20的用户有10个，过了一会儿再查有11个

**与隔离级别的对应关系**：
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---------|------|-----------|------|
| 读未提交 | ✅ 有 | ✅ 有 | ✅ 有 |
| 读已提交 | ❌ 无 | ✅ 有 | ✅ 有 |
| 可重复读 | ❌ 无 | ❌ 无 | ✅ 有（MySQL基本解决） |
| 串行化 | ❌ 无 | ❌ 无 | ❌ 无 |

**答案解析**:

深入理解三个读问题：

1. **不可重复读 vs 幻读的区别**：
   - 不可重复读：**同一行**数据的内容变了（UPDATE）
   - 幻读：**行数**变了（INSERT/DELETE）
   - 不可重复读的重点是"修改"
   - 幻读的重点是"新增/删除"
   - 解决不可重复读：行锁
   - 解决幻读：间隙锁（Next-Key Lock）

2. **MySQL RR级别的幻读问题**：
   - 标准的RR级别是不能解决幻读的
   - 但InnoDB的RR级别下，**快照读**不会有幻读（MVCC保证）
   - **当前读**（SELECT ... FOR UPDATE等）通过Next-Key Lock基本解决幻读
   - 为什么说"基本解决"而不是完全解决？
     - 因为Next-Key Lock是加锁读，不是所有场景都用加锁读
     - 如果事务中先快照读，再当前读，可能出现不一致

3. **幻读的例子**：
```sql
-- 表t(id主键), 数据：id=1, id=5
-- 事务A（RR级别）
BEGIN;
SELECT * FROM t WHERE id > 3;  -- 快照读，结果：id=5（1行）
-- 此时事务B插入id=3并提交
SELECT * FROM t WHERE id > 3;  -- 快照读，结果：id=5（还是1行，没有幻读）
SELECT * FROM t WHERE id > 3 FOR UPDATE;  -- 当前读，结果：id=3, id=5（2行！出现幻读）
COMMIT;
```

4. **如何选择隔离级别**：
   - 大多数业务能接受不可重复读（两次读取之间数据变了很正常）
   - 互联网公司常用RC级别（性能更好，锁范围更小）
   - 金融等对一致性要求高的业务用RR或串行化
   - 选择隔离级别是性能和一致性的权衡

**扩展问题**:

- 幻读和不可重复读有什么本质区别？

## Q20: MySQL的慢查询优化

**考察点**: 慢查询定位、分析方法、优化思路

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**慢查询优化的整体流程**：
1. 开启慢查询日志，捕获慢SQL
2. 分析慢SQL（explain、profile等）
3. 针对性优化（索引、SQL改写、架构优化）
4. 验证优化效果

**第一步：开启慢查询日志**：
```sql
-- 临时开启（重启失效）
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 超过1秒的记录
SET GLOBAL log_queries_not_using_indexes = ON;  -- 没走索引的也记录

-- 永久配置（my.cnf）
slow_query_log = ON
slow_query_log_file = /var/log/mysql/slow.log
long_query_time = 1
log_queries_not_using_indexes = ON
```

**第二步：分析慢查询**：
- **mysqldumpslow**：MySQL自带的慢查询分析工具
  - `mysqldumpslow -s c -t 10 slow.log`：按次数排序，取前10
- **pt-query-digest**：Percona工具，功能更强大
- **EXPLAIN**：分析执行计划
- **SHOW PROFILE**：分析SQL各阶段耗时
- **Performance Schema**：更详细的性能分析

**第三步：优化方法**：

**1. 索引优化**（最常见）：
- 为WHERE、JOIN、ORDER BY、GROUP BY加索引
- 使用联合索引、覆盖索引
- 避免索引失效场景

**2. SQL改写**：
- 避免SELECT *
- 用UNION ALL代替UNION
- 大事务拆小事务
- 用JOIN代替子查询
- 批量操作代替循环单条

**3. 表结构优化**：
- 选择合适的数据类型
- 适当的反范式（冗余字段减少JOIN）
- 大字段拆表

**4. 架构优化**：
- 读写分离
- 加缓存（Redis）
- 分库分表
- 引入搜索引擎（ES）

**答案解析**:

深入理解慢查询优化：

1. **常见的慢查询原因**：
   - 没有索引或索引失效（最常见）
   - 全表扫描、全索引扫描
   - 大量的回表操作
   - filesort（文件排序）
   - 临时表
   - 大表JOIN
   - 深分页
   - 锁等待

2. **优化的优先级**：
   - 优先优化频率高、影响大的SQL
   - 优先加索引（成本低、见效快）
   - 然后改写SQL
   - 最后考虑架构层面的优化
   - 注意：不要过度优化，够用就好

3. **性能分析工具**：
   - **explain**：看执行计划
   - **show profile**：看各阶段耗时（CPU、IO等）
   - **performance_schema**：MySQL内置的性能监控
   - **show processlist**：查看当前连接和执行状态
   - **information_schema**：查看锁、事务等信息

4. **索引优化的经验法则**：
   - 等值查询列放在联合索引左边
   - 区分度高的列放在左边
   - ORDER BY的列尽量放到索引中
   - GROUP BY的列尽量放到索引中
   - 尽量使用覆盖索引

5. **慢查询治理的最佳实践**：
   - 开发阶段：SQL Review，检查索引
   - 测试阶段：压测，发现慢SQL
   - 上线初期：观察慢查询日志
   - 线上运行：监控告警，及时处理
   - 定期复盘：每周/每月分析慢查询，持续优化

**扩展问题**:
- 如何定位线上的慢查询？有哪些工具？
- 一条SQL执行很慢，你会怎么排查？
- 如何做SQL审核？有哪些工具？

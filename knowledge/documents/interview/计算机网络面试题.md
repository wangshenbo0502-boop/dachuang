## Q1: OSI七层模型和TCP/IP四层模型

**考察点**: 网络分层模型、各层功能、协议对应关系

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**OSI七层模型**（从下到上）：

| 层级 | 名称 | 功能 | 典型协议/设备 |
|------|------|------|-------------|
| 第7层 | 应用层 | 为应用程序提供网络服务 | HTTP、FTP、SMTP、DNS、Telnet |
| 第6层 | 表示层 | 数据格式转换、加密解密、压缩 | SSL/TLS、ASCII、JPEG、MIME |
| 第5层 | 会话层 | 建立、管理、终止会话 | RPC、NetBIOS、PPTP |
| 第4层 | 传输层 | 端到端的可靠/不可靠传输 | TCP、UDP |
| 第3层 | 网络层 | 路由选择、分组转发、IP寻址 | IP、ICMP、ARP、路由器 |
| 第2层 | 数据链路层 | 帧的封装、MAC寻址、差错检测 | Ethernet、PPP、交换机 |
| 第1层 | 物理层 | 比特流传输、物理介质 | 光纤、双绞线、集线器、中继器 |

**TCP/IP四层模型**：

| 层级 | 名称 | 对应OSI层 | 典型协议 |
|------|------|----------|---------|
| 第4层 | 应用层 | 应用层+表示层+会话层 | HTTP、FTP、DNS、SMTP |
| 第3层 | 传输层 | 传输层 | TCP、UDP |
| 第2层 | 网际层（网络层） | 网络层 | IP、ICMP、ARP |
| 第1层 | 网络接口层 | 数据链路层+物理层 | Ethernet、Wi-Fi |

**五层模型**（教学常用）：
应用层 → 传输层 → 网络层 → 数据链路层 → 物理层

**数据封装过程**：
- 发送端：应用层数据 → 加TCP头（段Segment）→ 加IP头（包Packet）→ 加帧头帧尾（帧Frame）→ 比特流
- 接收端：逐层解封装，去掉各层头部，最终得到应用数据

**答案解析**:

深入理解网络分层：

1. **为什么要分层**：
   - 分层设计，每层只关心自己的功能
   - 各层独立，修改不影响其他层
   - 便于学习、维护和标准化
   - 类似软件工程中的模块化设计

2. **OSI vs TCP/IP模型**：
   - OSI是理论模型，七层划分细致
   - TCP/IP是实际使用的模型，更简洁
   - OSI的会话层和表示层在TCP/IP中合并到了应用层
   - 数据链路层和物理层合并为网络接口层
   - 面试时五层模型也常被问到（折中版本）

3. **各层的核心职责**：
   - **物理层**：怎么传（比特流、电压、介质）
   - **数据链路层**：传给谁（MAC地址、局域网内传输）
   - **网络层**：走哪条路（IP地址、路由选择、跨网络传输）
   - **传输层**：传到哪个程序（端口号、端到端传输）
   - **应用层**：传什么（具体的应用协议和数据）

4. **数据传输过程示例**：
   - 浏览器访问网站：
   1. 应用层：构造HTTP请求
   2. 传输层：加TCP头（端口号）
   3. 网络层：加IP头（源IP、目的IP）
   4. 链路层：加MAC头（源MAC、下一跳MAC）
   5. 物理层：转成比特流发送
   6. 路由器/交换机逐层转发
   7. 接收方逐层解封装

5. **重要设备工作层级**：
   - 集线器（Hub）：物理层，只是信号放大
   - 交换机（Switch）：数据链路层，根据MAC转发
   - 路由器（Router）：网络层，根据IP路由
   - 网关（Gateway）：传输层及以上，协议转换

**扩展问题**:
- OSI七层模型和TCP/IP四层模型的对应关系是什么？
- 为什么需要网络分层？有什么好处？
- 路由器和交换机有什么区别？分别工作在哪一层？
- 数据在网络中传输时，封装和解封装的过程是怎样的？

## Q2: TCP和UDP的区别

**考察点**: TCP与UDP对比、适用场景

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**TCP（Transmission Control Protocol，传输控制协议）**：
面向连接的、可靠的、基于字节流的传输层协议。

**UDP（User Datagram Protocol，用户数据报协议）**：
无连接的、不可靠的、面向报文的传输层协议。

**详细对比**：

| 维度 | TCP | UDP |
|------|-----|-----|
| 连接性 | 面向连接（三次握手建立连接） | 无连接（直接发送） |
| 可靠性 | 可靠（确认、重传、序号） | 不可靠（不保证送达） |
| 有序性 | 保证顺序 | 不保证顺序 |
| 流量控制 | 有（滑动窗口） | 无 |
| 拥塞控制 | 有（慢开始、拥塞避免等） | 无 |
| 首部开销 | 20字节（不含选项） | 8字节 |
| 传输方式 | 字节流 | 数据报（面向报文） |
| 速度 | 较慢（连接、确认、重传） | 较快 |
| 连接数 | 一对一（点对点） | 一对一、一对多、多对多 |
| 资源占用 | 较多（连接状态、缓冲区等） | 较少 |

**TCP适用场景**：
- 对可靠性要求高的场景
- 文件传输（FTP）
- 网页浏览（HTTP/HTTPS）
- 邮件发送（SMTP）
- 远程登录（SSH）
- 大多数需要可靠传输的场景

**UDP适用场景**：
- 对速度要求高，允许丢包的场景
- 实时视频/音频通话（视频会议、语音通话）
- 直播
- 游戏（快速响应，允许少量丢包）
- DNS查询
- 广播/多播

**答案解析**:

深入理解TCP和UDP：

1. **为什么UDP不可靠还存在**：
   - 不是所有场景都需要可靠传输
   - 可靠性是有代价的（延迟、带宽、资源）
   - 实时性比可靠性更重要的场景，UDP更合适
   - 比如视频通话，丢几帧不影响观看，但延迟高了就不行

2. **面向字节流 vs 面向报文**：
   - TCP：数据被看作一串字节流，没有边界概念
     - 发送方分多少次发，接收方可能一次就收完
     - 也可能发一次，接收方分多次收
     - 需要应用层自己处理分包
   - UDP：每次发送一个完整的报文
     - 发送方发一次，接收方最多收一次（可能丢）
     - 一次recvfrom就能拿到完整报文
     - 有明确的报文边界

3. **UDP如何实现可靠传输**：
   - UDP本身不可靠，但可以在应用层实现可靠性
   - 比如：增加序号、确认、重传机制
   - QUIC协议就是基于UDP实现的可靠传输
   - 这样既保留了UDP的灵活性，又有TCP的可靠性

4. **TCP和UDP的头部结构**：
   - TCP头部：源端口(2) + 目的端口(2) + 序号(4) + 确认号(4) + 数据偏移+标志+窗口(4) + 校验和(2) + 紧急指针(2) = 20字节（最小）
   - UDP头部：源端口(2) + 目的端口(2) + 长度(2) + 校验和(2) = 8字节
   - TCP头部大得多，因为需要维护连接状态

5. **常见应用协议对应的传输层协议**：
   - TCP：HTTP、HTTPS、FTP、SMTP、SSH、Telnet、POP3
   - UDP：DNS、DHCP、SNMP、TFTP、RIP、NTP
   - 两者都可以：DNS（主要UDP，大包用TCP）

**扩展问题**:
- UDP为什么快？具体快在哪里？
- 什么是面向字节流？和面向报文有什么区别？
- 可以用UDP实现可靠传输吗？怎么实现？
- QUIC协议是什么？和TCP有什么区别？

## Q3: TCP的三次握手和四次挥手

**考察点**: TCP连接建立与释放、状态转换

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**三次握手（建立连接）**：

1. **第一次握手（SYN）**：
   - 客户端向服务端发送SYN报文（SYN=1，seq=x）
   - 客户端进入SYN_SENT状态

2. **第二次握手（SYN+ACK）**：
   - 服务端收到SYN，返回SYN+ACK报文（SYN=1，ACK=1，seq=y，ack=x+1）
   - 服务端进入SYN_RCVD状态

3. **第三次握手（ACK）**：
   - 客户端收到SYN+ACK，返回ACK报文（ACK=1，seq=x+1，ack=y+1）
   - 客户端进入ESTABLISHED状态
   - 服务端收到ACK后进入ESTABLISHED状态

```
客户端                            服务端
  | ------- SYN, seq=x -------> |   SYN_SENT
  | <---- SYN+ACK, seq=y, ack=x+1 ---- |   SYN_RCVD
  | ------- ACK, seq=x+1, ack=y+1 ---> |   ESTABLISHED
  |                            |   ESTABLISHED
```

**四次挥手（断开连接）**：

1. **第一次挥手（FIN）**：
   - 主动关闭方发送FIN报文（FIN=1，seq=u）
   - 主动方进入FIN_WAIT_1状态

2. **第二次挥手（ACK）**：
   - 被动方收到FIN，返回ACK（ACK=1，ack=u+1，seq=v）
   - 被动方进入CLOSE_WAIT状态
   - 主动方收到ACK进入FIN_WAIT_2状态

3. **第三次挥手（FIN）**：
   - 被动方数据发完了，发送FIN报文（FIN=1，ACK=1，ack=u+1，seq=w）
   - 被动方进入LAST_ACK状态

4. **第四次挥手（ACK）**：
   - 主动方收到FIN，返回ACK（ACK=1，seq=u+1，ack=w+1）
   - 主动方进入TIME_WAIT状态
   - 被动方收到ACK后进入CLOSED状态
   - 主动方等待2MSL后进入CLOSED状态

```
主动方                            被动方
  | ------- FIN, seq=u -------> |   FIN_WAIT_1
  | <-------- ACK, ack=u+1 ----- |   CLOSE_WAIT
  |   FIN_WAIT_2              |
  | <-------- FIN, seq=w ------ |   LAST_ACK
  | ------- ACK, ack=w+1 -----> |   TIME_WAIT
  |                            |   CLOSED
  |  (等待2MSL后CLOSED)        |
```

**答案解析**:

深入理解三次握手和四次挥手：

1. **为什么需要三次握手（建立连接）**：
   - 确认双方的发送能力和接收能力都正常
   - 第一次握手：客户端发，服务端收 → 服务端知道客户端发正常，自己收正常
   - 第二次握手：服务端发，客户端收 → 客户端知道双方收发都正常
   - 第三次握手：客户端发，服务端收 → 服务端知道客户端收正常，自己发正常
   - 三次握手才能确认双方的收发能力都没问题

2. **三次握手可以携带数据吗**：
   - 前两次不行，第三次可以
   - 因为前两次连接还没建立
   - 第三次握手时，客户端已经确认连接建立了，可以带数据
   - 但如果带数据的话，可以用来防范SYN洪水攻击（TFO等）

3. **为什么需要四次挥手（断开连接）**：
   - TCP是全双工的，两个方向都要单独关闭
   - 主动方发FIN表示自己没有数据要发了
   - 但被动方可能还有数据要发，所以先回ACK
   - 等被动方数据发完了，再发FIN
   - 所以需要四次：FIN → ACK → FIN → ACK

4. **为什么不能三次挥手**：
   - 如果被动方没有数据要发了，ACK和FIN可以合并吗？
   - 理论上可以，但实际中被动方可能还有数据
   - 所以设计成四次，更灵活
   - 有时看起来像三次（被动方数据少，ACK和FIN一起发）

5. **SYN洪水攻击**：
   - 攻击者发送大量SYN报文，但不回ACK
   - 服务端维护半连接队列，占满后无法接受新连接
   - 防御：SYN cookie、缩短超时时间、增加半连接队列大小

**扩展问题**:
- 为什么是三次握手？两次不行吗？
- 为什么是四次挥手？三次不行吗？
- 三次握手的第三次可以携带数据吗？为什么？
- 什么是SYN洪水攻击？如何防御？

## Q4: TCP为什么是三次握手不是两次

**考察点**: 三次握手的必要性、两次握手的问题

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**为什么需要三次握手，而不是两次**：

**原因1：确认双方的收发能力都正常**：
- 两次握手只能确认：客户端发 → 服务端收，服务端发 → 客户端收
- 但服务端不知道客户端的接收能力是否正常
- 三次握手的第三次ACK告诉服务端：客户端收得到，你发的我收到了
- 只有三次才能确认双方的发送和接收能力都没问题

**原因2：防止已失效的连接请求报文突然又传到服务端**：
- 这是 RFC 793 中的主要原因
- 场景：客户端发了第一个SYN，网络延迟了，客户端超时重发了第二个SYN
- 第二个SYN建立了连接，传输完数据，断开连接
- 这时候第一个延迟的SYN才到服务端
- 如果是两次握手，服务端收到就建立连接，发送数据
- 但客户端已经关闭了连接，不会理服务端
- 导致服务端资源浪费
- 三次握手：服务端发回SYN+ACK，客户端收到后发现不是自己想要的，就不回ACK
- 服务端收不到ACK，就不会建立连接

**原因3：同步初始序列号**：
- TCP需要双方交换初始序列号（ISN）
- 客户端的ISN需要告诉服务端（SYN）
- 服务端的ISN需要告诉客户端（SYN）
- 双方都需要确认对方收到了自己的ISN（ACK）
- 最少需要三次交互才能完成

**答案解析**:

深入理解两次握手的问题：

1. **两次握手的问题场景**：
```
客户端A                          服务端B
   | ---- SYN(seq=100) ---> |  （延迟了，没到）
   | 超时重发              |
   | ---- SYN(seq=200) ---> |
   | <--- SYN+ACK --------- |
   | ---- ACK -----------> |
   |    建立连接，传输数据     |
   |    断开连接             |
   |                        |
   | （第一个延迟的SYN到了）   |
   | （旧的SYN(seq=100)）-> |
   |    如果是两次握手        |
   |                     |  B认为连接建立了
   |                     |  B开始发数据
   |  A已经断开了，不理B    |
   |                     |  B资源浪费！
```

2. **三次握手如何解决**：
   - 服务端收到旧SYN后，还是会发SYN+ACK回去
   - 客户端收到后，发现这个序列号不对（不是当前期望的）
   - 客户端发一个RST（复位）报文，告诉服务端连接无效
   - 服务端收到RST后，释放资源
   - 不会建立无效连接

3. **为什么不需要四次握手**：
   - 三次已经够了，能确认双方收发正常
   - 三次握手的第二次（SYN+ACK）把两件事合并了：
     - 确认收到客户端的SYN
     - 发送服务端自己的SYN
   - 所以不需要四次

4. **从可靠性角度理解**：
   - 要达到"可靠"的传输，必须双方都确认对方的初始序列号
   - A要知道B收到了A的ISN（需要A→B→A，两次交互）
   - B要知道A收到了B的ISN（需要B→A→B，两次交互）
   - 但中间的B→A可以合并（SYN+ACK）
   - 所以总共需要3次：A→B（SYN），B→A（SYN+ACK），A→B（ACK）

5. **现实类比**：
   - 两个人打电话：
   - A：喂，听得到吗？（SYN）
   - B：听得到，你呢？（SYN+ACK）
   - A：我也听得到（ACK）
   - 两句不够（B不知道A能不能听到自己说话）
   - 三句才能确认双方都听得到

**扩展问题**:
- 四次挥手为什么不能合并成三次？和三次握手中的SYN+ACK有什么不同？
- 如果三次握手的最后一个ACK丢失了，会发生什么？
- 初始序列号（ISN）是怎么生成的？为什么不能是固定的？
- SYN cookie是什么？它是如何防御SYN洪水的？

## Q5: TCP为什么是四次挥手不是三次

**考察点**: 四次挥手的必要性、全双工、半关闭

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**为什么是四次挥手，而不是三次**：

**核心原因：TCP是全双工的，两个方向需要分别关闭**

TCP连接是全双工的，数据可以在两个方向上独立传输。关闭连接时，每个方向都需要单独关闭，所以需要四次交互。

**详细解释**：

1. **主动方发FIN**：表示我这边没有数据要发了，关闭发送通道
2. **被动方回ACK**：好的，我知道了
3. **被动方发FIN**：我这边也没有数据要发了，关闭发送通道
4. **主动方回ACK**：好的，我知道了

**为什么ACK和FIN不能合并（像三次握手那样）**：
- 三次握手中，SYN和ACK可以合并，因为服务端收到SYN后，可以立即发自己的SYN+ACK
- 但四次挥手中，被动方收到FIN时，可能还有数据没有发完
- 被动方需要先回ACK，告诉对方"我收到了你的关闭请求"
- 然后继续发自己的数据，发完了再发FIN
- 所以ACK和FIN之间可能有一段时间，不能合并

**半关闭状态（Half-Close）**：
- TCP提供了半关闭的能力
- 一方关闭了发送，但仍然可以接收
- 即FIN_WAIT_2状态（主动关闭方）还可以接收数据
- CLOSE_WAIT状态（被动关闭方）还可以发送数据
- 这就是TCP的半关闭特性

**什么情况下可以是三次挥手**：
- 如果被动方没有数据要发了
- 收到FIN后，可以立即发FIN+ACK
- 这样看起来就是三次挥手（FIN → FIN+ACK → ACK）
- 但这只是特殊情况，不是通用情况

**答案解析**:

深入理解四次挥手：

1. **全双工的含义**：
   - TCP连接有两个独立的数据流：发送和接收
   - 两个方向互不影响
   - 关闭一个方向不影响另一个方向
   - 所以需要两个方向分别关闭

2. **CLOSE_WAIT状态的意义**：
   - 被动关闭方处于CLOSE_WAIT状态
   - 这个状态下，被动方还可以继续发送数据
   - 直到数据发完了，才发FIN，进入LAST_ACK
   - CLOSE_WAIT的时间取决于被动方什么时候发完数据

3. **为什么连接建立时可以三次，断开就需要四次**：
   - 建立时，服务端可以把SYN和ACK放在一个报文里发
   - 因为服务端收到SYN时，立即就可以发自己的SYN
   - 断开时，被动方收到FIN时，可能还有数据没发完
   - 必须先回ACK，然后等数据发完了再发FIN
   - 所以ACK和FIN之间有时间差，不能合并

4. **类比理解**：
   - 两个人打电话，说再见：
   - A：我说完了，挂了啊（FIN）
   - B：好的，我知道了（ACK）
   - B：等等，我还有一件事...（继续说）
   - B：好了，我也说完了（FIN）
   - A：好的，拜拜（ACK）
   - 如果B没有要说的了，可以直接说"好的，那挂了吧"（ACK+FIN合并）
   - 但协议设计要考虑通用情况

5. **实际中四次挥手的优化**：
   - 快速关闭：如果被动方没有数据要发，可以将ACK和FIN合并
   - 这时看起来就是三次挥手
   - 但TCP状态机仍然是四个状态转换

**扩展问题**:
- 什么是半关闭？有什么应用场景？
- CLOSE_WAIT状态过多可能是什么原因？
- 四次挥手中，如果最后一个ACK丢失了会怎样？
- 为什么连接建立时SYN和ACK可以合并，断开时就不行？

## Q6: TCP的拥塞控制

**考察点**: 拥塞控制算法、四个阶段、原理

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**拥塞控制**：
防止过多的数据注入网络，导致网络中路由器或链路过载。

**四个核心算法**：

**1. 慢开始（Slow Start）**：
- 连接刚建立时，拥塞窗口（cwnd）从小到大指数增长
- 初始cwnd = 1 MSS（最大报文段长度）
- 每收到一个ACK，cwnd += 1
- 每经过一个RTT，cwnd翻倍
- 增长到慢开始门限（ssthresh）后，进入拥塞避免阶段

**2. 拥塞避免（Congestion Avoidance）**：
- cwnd线性增长，而不是指数增长
- 每经过一个RTT，cwnd += 1
- 增长速度慢，但更稳定
- 目的：避免快速增长导致网络拥塞

**3. 快重传（Fast Retransmit）**：
- 接收方收到失序报文时，立即发送重复ACK
- 发送方收到3个重复ACK，就知道报文丢失了
- 不等超时，立即重传丢失的报文
- 减少等待超时的时间，提高效率

**4. 快恢复（Fast Recovery）**：
- 配合快重传使用
- 收到3个重复ACK时：
  - ssthresh = cwnd / 2
  - cwnd = ssthresh + 3（考虑已经收到的3个重复ACK）
  - 然后进入拥塞避免阶段（线性增长）
- 而不是像超时那样从慢开始重新来
- 因为收到重复ACK说明网络还在工作，只是丢了个别包

**拥塞窗口变化总结**：
- 慢开始：指数增长，直到ssthresh
- 拥塞避免：线性增长，直到检测到丢包
- 检测到丢包（3个重复ACK）：ssthresh减半，cwnd=ssthresh，继续拥塞避免
- 检测到丢包（超时）：ssthresh = cwnd/2，cwnd = 1，重新慢开始

**答案解析**:

深入理解拥塞控制：

1. **拥塞控制 vs 流量控制**：
   - **流量控制**：点对点的，防止发送方发太快，接收方处理不过来（滑动窗口）
   - **拥塞控制**：全局的，防止发送方发太快，网络处理不过来（拥塞窗口）
   - 实际发送窗口 = min(拥塞窗口, 接收窗口)

2. **为什么叫慢开始**：
   - "慢"是相对于突然注入大量数据而言的
   - 实际上增长速度很快（指数增长）
   - 只是从1开始，比直接发满窗口慢
   - 目的是探测网络承载能力

3. **为什么需要快重传和快恢复**：
   - 超时重传的等待时间太长（RTO一般是几百毫秒到几秒）
   - 快重传通过重复ACK提前知道丢包，立即重传
   - 超时说明网络可能很拥塞，所以从1开始慢开始
   - 3个重复ACK说明网络还能传ACK，只是个别丢包，所以不用从头开始

4. **拥塞控制的演进**：
   - **Tahoe**：最早版本，不管超时还是3个重复ACK，都从慢开始重新来
   - **Reno**：增加了快恢复，3个重复ACK时不从头开始
   - **New Reno**：改进了快恢复，处理一个窗口内多个丢包的情况
   - **BBR**：Google提出的新算法，基于带宽和延迟，不是基于丢包

5. **BBR拥塞控制**：
   - 传统算法（Reno等）基于丢包判断拥塞
   - BBR基于带宽和RTT测量
   - 更适合现代网络（有缓冲区的网络，丢包不一定是拥塞）
   - 在有一定丢包率的网络中表现更好
   - Linux 4.9+内核支持

**扩展问题**:
- 拥塞控制和流量控制有什么区别？
- 慢开始真的慢吗？为什么叫慢开始？
- 快重传和快恢复有什么区别和联系？
- BBR和传统的Reno算法有什么不同？

## Q7: TCP的流量控制（滑动窗口）

**考察点**: 滑动窗口原理、流量控制机制

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**流量控制**：
发送方根据接收方的接收能力，调整发送速度，防止接收方缓冲区溢出。

**滑动窗口（Sliding Window）**：
TCP通过滑动窗口机制实现流量控制。

**核心概念**：
- **发送窗口（SWND）**：发送方还没收到确认，可以连续发送的数据量
- **接收窗口（RWND）**：接收方还有多少缓冲区可以接收数据
- 接收方在ACK报文的窗口字段中告知自己的接收窗口大小
- 发送方的发送窗口不能超过接收方的接收窗口

**发送方的缓冲区**：
- 已发送且已确认
- 已发送未确认（发送窗口内）
- 未发送但可以发送（发送窗口内）
- 未发送且不允许发送（发送窗外）

**接收方的缓冲区**：
- 已接收且已提交给应用层
- 已接收未提交（接收窗口内）
- 未接收但可以接收（接收窗口内）
- 未接收且不允许接收（接收窗外）

**滑动窗口的工作过程**：
1. 发送方根据接收窗口大小，发送一批数据
2. 接收方收到数据，放入缓冲区，返回ACK+新的窗口大小
3. 发送方收到ACK，窗口向前滑动，继续发送新数据
4. 如果接收方缓冲区满了，窗口大小为0，发送方停止发送

**零窗口问题**：
- 接收方窗口为0时，发送方停止发送
- 接收方处理完数据后，发送窗口更新通知
- 如果这个通知丢失了，双方就死等
- 解决：发送方有持续计时器（persistence timer）
- 每隔一段时间发送一个窗口探测报文（带1字节数据）
- 询问接收方窗口大小

**答案解析**:

深入理解滑动窗口：

1. **为什么叫滑动窗口**：
   - 窗口的左右边界可以移动
   - 收到新的确认，左边界右移
   - 接收窗口变大，右边界右移
   - 窗口整体向右滑动
   - 所以叫"滑动"窗口

2. **滑动窗口的意义**：
   - 提高传输效率：不用等每个报文的确认，可以连发
   - 流量控制：根据接收能力调整发送速度
   - 可靠传输：配合序号和确认机制

3. **窗口大小的单位**：
   - TCP窗口大小的单位是字节，不是报文数
   - 头部中窗口字段占16位，最大65535字节（64KB）
   - 但这太小了（高速网络下）
   - 所以有窗口扩大选项（Window Scale），最大可到1GB

4. **糊涂窗口综合症（Silly Window Syndrome）**：
   - 接收方缓冲区只剩一点点空间，就通告一个小窗口
   - 发送方就发一点点数据
   - 导致大量小报文，效率极低
   - **解决**：
     - 接收方：不通告小窗口，等有足够空间再通告
     - 发送方：Nagle算法，攒够了再发

5. **Nagle算法**：
   - 发送方避免发送大量小报文
   - 规则：
     - 如果有未确认的数据，就不发送新的小报文
     - 攒到有一个MSS大小或收到ACK再发
   - 减少网络中小报文的数量
   - 但有时会增加延迟（实时性要求高的场景可以关闭）

**扩展问题**:
- 滑动窗口和拥塞窗口有什么区别和联系？
- 什么是零窗口？如何处理零窗口问题？
- 糊涂窗口综合症是什么？如何解决？
- Nagle算法是什么？什么时候需要关闭？

## Q8: TIME_WAIT状态和作用

**考察点**: TIME_WAIT意义、2MSL、过多的危害

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**TIME_WAIT状态**：
TCP四次挥手后，主动关闭方进入TIME_WAIT状态，等待2MSL时间后才进入CLOSED状态。

**什么是MSL**：
- MSL（Maximum Segment Lifetime，最大报文段生存时间）
- TCP报文在网络中存活的最长时间
- RFC推荐是2分钟，实际系统中通常是30秒或1分钟
- 2MSL就是两倍的MSL

**为什么需要TIME_WAIT（两个原因）**：

**原因1：保证最后一个ACK能到达被动关闭方**：
- 如果最后一个ACK丢失了，被动方会超时重发FIN
- 如果主动方直接关闭了，就收不到重发的FIN
- 被动方就无法正常关闭
- TIME_WAIT给了重传FIN一个被接收的机会
- 等待2MSL：ACK发出去 + FIN重传回来，最多2MSL

**原因2：防止"已失效的连接请求报文段"出现在新连接中**：
- 等待2MSL可以让本次连接的所有报文都在网络中消失
- 防止旧连接的延迟报文影响新的连接
- 特别是如果新连接用了和旧连接一样的端口和IP
- 有了2MSL，旧的报文都死掉了，不会混淆

**TIME_WAIT过多的危害**：
1. 占用端口资源（一个连接占一个端口）
2. 占用内存（维护连接状态）
3. 高并发短连接场景下可能耗尽端口

**如何优化TIME_WAIT**：
1. **开启tcp_tw_reuse**：允许将TIME_WAIT的端口用于新的连接
2. **开启tcp_tw_recycle**：快速回收TIME_WAIT（NAT环境有问题，Linux 4.12已移除）
3. **调整tcp_max_tw_buckets**：增大TIME_WAIT的最大数量
4. **减少MSL时间**：不推荐，改内核参数有风险
5. **长连接代替短连接**：从业务层面减少连接建立和断开

**答案解析**:

深入理解TIME_WAIT：

1. **为什么是2MSL**：
   - 最坏情况：最后一个ACK经过MSL时间到达被动方
   - 被动方发现不对（可能超时了），重发FIN
   - 这个FIN又经过MSL时间回到主动方
   - 所以最多2MSL时间，就能知道是否需要重传ACK
   - 2MSL是最长的往返时间 + 处理时间

2. **谁会进入TIME_WAIT**：
   - 主动关闭的一方
   - 也就是先发起FIN的一方
   - HTTP服务中，通常是客户端主动关闭
   - 但如果服务端主动关闭（如Keep-Alive超时），服务端会有TIME_WAIT

3. **TIME_WAIT和CLOSE_WAIT的区别**：
   - **TIME_WAIT**：主动关闭方，等待2MSL，正常现象
   - **CLOSE_WAIT**：被动关闭方，等待应用层调用close
   - CLOSE_WAIT过多通常是程序bug（没有正确关闭连接）

4. **高并发下的TIME_WAIT问题**：
   - 短连接服务（如HTTP）会产生大量TIME_WAIT
   - 客户端端口可能耗尽（65535个端口）
   - 服务端也可能有大量TIME_WAIT（如果是服务端主动关闭）
   - 优化方案：
     - 用长连接（HTTP Keep-Alive）
     - 客户端用连接池
     - 开启tcp_tw_reuse（注意NAT环境）

5. **time_wait状态的连接能复用吗**：
   - 默认不能
   - 开启tcp_tw_reuse后可以（客户端侧）
   - 条件：新连接的时间戳比旧的大（PAWS机制）
   - 这样就不会有旧报文影响新连接的问题
   - 注意：是客户端连接时复用，不是服务端监听时复用

**扩展问题**:
- TIME_WAIT状态有什么作用？为什么需要2MSL？
- TIME_WAIT和CLOSE_WAIT有什么区别？
- 服务器上TIME_WAIT过多怎么办？
- tcp_tw_reuse和tcp_tw_recycle有什么区别？为什么recycle被移除了？

## Q9: HTTP和HTTPS的区别

**考察点**: HTTPS原理、加密方式、HTTP与HTTPS对比

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**HTTP（HyperText Transfer Protocol）**：
超文本传输协议，是Web应用最广泛的协议。

**HTTPS（HTTP Secure）**：
在HTTP的基础上加入了SSL/TLS加密层，提供加密传输和身份验证。

**主要区别**：

| 维度 | HTTP | HTTPS |
|------|------|-------|
| 安全性 | 明文传输，不安全 | 加密传输，安全 |
| 端口 | 80 | 443 |
| 资源消耗 | 低 | 较高（加解密消耗） |
| 证书 | 不需要 | 需要CA证书 |
| 协议层 | 应用层 | HTTP + SSL/TLS（表示层） |
| 速度 | 快 | 较慢（握手和加解密开销） |
| SEO | 一般 | 搜索引擎更偏好 |

**HTTPS的工作原理**：

HTTPS = HTTP + SSL/TLS

**SSL/TLS握手过程（简化版，TLS 1.2）**：
1. **客户端Hello**：客户端发送支持的加密套件、随机数等
2. **服务端Hello**：服务端选择加密套件，返回证书、随机数等
3. **客户端验证证书**：验证证书的合法性（CA签发、有效期、域名匹配等）
4. **密钥交换**：客户端生成预主密钥，用服务端公钥加密后发送
5. **生成会话密钥**：双方根据三个随机数生成对称加密的会话密钥
6. **客户端Finished**：发送加密的Finished消息
7. **服务端Finished**：发送加密的Finished消息
8. **握手完成**：后续HTTP消息用会话密钥加密传输

**HTTPS的安全保障**：
1. **加密传输**：对称加密，第三方无法窃听
2. **身份认证**：证书验证，确认对方身份，防止中间人攻击
3. **数据完整性**：MAC校验，防止数据被篡改

**答案解析**:

深入理解HTTPS：

1. **为什么用对称加密+非对称加密结合**：
   - **非对称加密**：公钥加密，私钥解密；安全但慢
   - **对称加密**：同一个密钥加解密；快但密钥分发难
   - HTTPS用非对称加密来交换对称密钥
   - 然后用对称加密来传输数据
   - 既安全又高效

2. **数字证书的作用**：
   - 证明服务端的公钥确实属于这个域名
   - 防止中间人攻击（中间人生成假公钥）
   - 证书由CA（证书颁发机构）签发
   - 操作系统和浏览器内置了可信CA的根证书
   - 验证证书时，向上追溯到可信根证书就认为有效

3. **TLS握手的详细过程**：
   - 实际过程比简化版复杂
   - 包括：密码套件协商、证书验证、密钥交换、Finished验证
   - TLS 1.2需要2个RTT完成握手
   - TLS 1.3优化到1个RTT，甚至0-RTT

4. **HTTPS的性能优化**：
   - **会话复用**：Session ID / Session Ticket，复用之前的会话密钥
   - **OCSP Stapling**：证书状态查询预取，减少客户端查询时间
   - **HTTP/2**：多路复用等优化
   - **TLS 1.3**：握手更快，加密更安全
   - **CDN加速**：就近接入

5. **HTTPS的成本**：
   - 计算成本：加解密需要CPU
   - 延迟成本：多了TLS握手的RTT
   - 证书成本：虽然有免费的（Let's Encrypt），但高级证书仍要花钱
   - 但现在HTTPS基本是标配，性能影响可以接受

**扩展问题**:
- HTTPS的加密过程是怎样的？对称加密还是非对称加密？
- 数字证书是什么？有什么作用？
- TLS握手的完整过程是怎样的？TLS 1.3有什么改进？
- 什么是中间人攻击？HTTPS如何防止？

## Q10: HTTP状态码（2xx/3xx/4xx/5xx）

**考察点**: 常见状态码含义、分类

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

HTTP状态码是服务端返回的响应状态，分为5大类：

**1xx（信息性状态码）**：请求已接收，继续处理

| 状态码 | 含义 |
|--------|------|
| 100 Continue | 继续，客户端应继续发送请求 |
| 101 Switching Protocols | 切换协议，如升级到WebSocket |

**2xx（成功状态码）**：请求已成功接收、理解、接受

| 状态码 | 含义 |
|--------|------|
| 200 OK | 请求成功 |
| 201 Created | 创建成功（POST/PUT） |
| 204 No Content | 成功，但没有返回内容 |
| 206 Partial Content | 部分内容（范围请求） |

**3xx（重定向状态码）**：需要进一步操作以完成请求

| 状态码 | 含义 |
|--------|------|
| 301 Moved Permanently | 永久重定向 |
| 302 Found | 临时重定向 |
| 303 See Other | 查看其它地址（POST后重定向GET） |
| 304 Not Modified | 未修改，使用缓存 |
| 307 Temporary Redirect | 临时重定向（不改变请求方法） |
| 308 Permanent Redirect | 永久重定向（不改变请求方法） |

**4xx（客户端错误状态码）**：请求有错误，服务端无法处理

| 状态码 | 含义 |
|--------|------|
| 400 Bad Request | 请求参数错误 |
| 401 Unauthorized | 未授权（未登录或token无效） |
| 403 Forbidden | 禁止访问（有权限但被拒绝） |
| 404 Not Found | 资源不存在 |
| 405 Method Not Allowed | 方法不允许 |
| 408 Request Timeout | 请求超时 |
| 409 Conflict | 冲突（如资源已存在） |
| 413 Payload Too Large | 请求体太大 |
| 415 Unsupported Media Type | 不支持的媒体类型 |
| 429 Too Many Requests | 请求过多（限流） |

**5xx（服务端错误状态码）**：服务端处理请求时出错

| 状态码 | 含义 |
|--------|------|
| 500 Internal Server Error | 服务端内部错误 |
| 501 Not Implemented | 未实现 |
| 502 Bad Gateway | 网关错误（代理/网关收到无效响应） |
| 503 Service Unavailable | 服务不可用（超载或维护） |
| 504 Gateway Timeout | 网关超时 |
| 505 HTTP Version Not Supported | 不支持的HTTP版本 |

**答案解析**:

深入理解常见状态码：

1. **301 vs 302 vs 307 vs 308**：
   - 301：永久重定向，POST可能变GET（不同浏览器行为不同）
   - 302：临时重定向，POST可能变GET
   - 307：临时重定向，保持请求方法（POST还是POST）
   - 308：永久重定向，保持请求方法
   - 303：和302类似，但明确要求用GET请求新地址

2. **304缓存机制**：
   - 客户端发送请求，带If-Modified-Since或If-None-Match
   - 服务端判断资源没修改，返回304
   - 客户端使用本地缓存
   - 减少数据传输，提高性能

3. **401 vs 403**：
   - 401 Unauthorized：未认证（不知道你是谁）
   - 403 Forbidden：已认证，但没有权限（知道你是谁，但不让你访问）
   - 401需要登录，403是权限不够

4. **502 vs 504**：
   - 502 Bad Gateway：网关收到了无效响应（上游服务挂了或返回了错误格式）
   - 504 Gateway Timeout：网关等上游响应超时了（上游太慢）
   - 都是网关/代理相关的错误

5. **状态码选择的最佳实践**：
   - 尽量用标准状态码，不要自定义太多
   - 用合适的分类（2xx成功、4xx客户端错、5xx服务端错）
   - RESTful API中合理使用200/201/204/400/401/403/404等

**扩展问题**:
- 301和302有什么区别？307和308呢？
- 401和403有什么区别？
- 502和504有什么区别？
- 304是什么？和缓存有什么关系？

## Q11: HTTP1.0、HTTP1.1、HTTP2.0的区别

**考察点**: HTTP协议演进、各版本特性

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**HTTP/1.0**：
- 1996年发布
- 每次请求都建立一个TCP连接，请求完就断开
- 不支持长连接
- 不支持虚拟主机（Host头）
- 只有GET、POST、HEAD几个方法

**HTTP/1.1**：
- 1997年发布（RFC 2616），最广泛使用的版本
- **长连接**：默认开启Keep-Alive，一个TCP连接可以发多个请求
- **虚拟主机**：Host头部，一个IP可以托管多个网站
- **更多方法**：PUT、DELETE、PATCH、OPTIONS、TRACE、CONNECT
- **缓存控制**：Cache-Control、ETag等更丰富的缓存机制
- **断点续传**：Range请求头，支持分块传输
- **管道化（Pipelining）**：可以先发多个请求，再等响应（但有队头阻塞）

**HTTP/2**：
- 2015年发布，基于SPDY协议
- **二进制分帧**：报文分成二进制帧，不再是文本格式
- **多路复用**：一个TCP连接上可以并行处理多个请求响应
- **头部压缩**：HPACK算法压缩HTTP头部，减少传输量
- **服务器推送**：服务端可以主动向客户端推送资源
- **流量控制**：每个流有独立的流量控制
- **流优先级**：可以设置请求的优先级

**HTTP/3**：
- 2022年标准化（RFC 9114）
- 基于QUIC协议，不再用TCP
- 解决了HTTP/2的队头阻塞问题（TCP层的队头阻塞）
- 0-RTT / 1-RTT握手（更快的连接建立）
- 连接迁移（网络切换不中断）

**答案解析**:

深入理解各版本的改进：

1. **HTTP/1.1的队头阻塞**：
   - HTTP/1.1引入了管道化（Pipelining）
   - 可以一次发多个请求
   - 但响应必须按请求的顺序返回
   - 如果第一个请求很慢，后面的都要等
   - 这就是HTTP队头阻塞（Head-of-Line Blocking）
   - 实际中浏览器都默认关闭了管道化

2. **HTTP/2的多路复用**：
   - 将数据分成二进制帧
   - 每个请求是一个流（Stream），有独立的ID
   - 多个流的帧可以交错传输
   - 一个TCP连接上同时有多个请求响应
   - 解决了HTTP层面的队头阻塞
   - 大大提高了并发性能

3. **HTTP/2仍然有队头阻塞**：
   - 解决了HTTP层的队头阻塞
   - 但TCP层还有队头阻塞
   - 因为TCP是可靠的，一个包丢了，后面的都要等
   - 一个TCP连接上的所有流都会受影响
   - HTTP/3用QUIC（基于UDP）解决了这个问题

4. **头部压缩的重要性**：
   - HTTP/1.1的头部是纯文本，每次请求都要传完整头部
   - 很多请求的头部大部分是重复的（Cookie、User-Agent等）
   - HTTP/2用HPACK压缩，双方维护一张头部表
   - 重复的头部只传索引，大大减少头部大小
   - 小请求场景下，头部压缩效果明显

5. **服务器推送**：
   - 服务端可以主动把客户端需要的资源推过去
   - 比如客户端请求HTML，服务端知道里面引用了CSS和JS
   - 可以一起推过去，不用等客户端解析HTML再请求
   - 但实际使用中效果不一，HTTP/3中已废弃（实际很少用对）

**扩展问题**:
- HTTP/2的多路复用是怎么实现的？
- 什么是队头阻塞？HTTP各版本是如何解决的？
- HTTP/2和HTTP/1.1相比有哪些优势？
- HTTP/3为什么用QUIC？QUIC和TCP有什么区别？

## Q12: GET和POST的区别

**考察点**: GET与POST对比、语义、使用场景

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

GET和POST是HTTP中最常用的两个方法。

**主要区别**：

| 维度 | GET | POST |
|------|-----|------|
| 语义 | 获取资源 | 提交/创建资源 |
| 幂等性 | 是（多次请求结果相同） | 否 |
| 安全性 | 是（不应修改服务器状态） | 否 |
| 参数位置 | URL的Query String | 请求体（Body） |
| 参数长度 | 受URL长度限制（浏览器有限制） | 理论上无限制（受服务端配置） |
| 缓存 | 可以被缓存 | 默认不缓存 |
| 收藏/分享 | 可以（URL中包含所有信息） | 不行 |
| 后退/刷新 | 无害 | 会重新提交表单（浏览器提示） |
| 编码类型 | application/x-www-form-urlencoded | 多种（form/json/multipart等） |
| 书签 | 可以加书签 | 不行 |
| 历史记录 | 会保留在浏览器历史 | 一般不会 |

**HTTP方法的特性**：
- **安全方法**：不修改服务器状态 → GET、HEAD、OPTIONS
- **幂等方法**：多次执行结果相同 → GET、PUT、DELETE、HEAD、OPTIONS
- **可缓存**：响应可以被缓存 → GET、HEAD（POST在特定条件下也可以）

**使用场景**：
- **GET**：查询、获取数据、页面跳转
- **POST**：提交表单、创建资源、上传数据、修改数据（非幂等的操作）

**常见误解澄清**：
1. **GET不能传body吗？**：规范没有禁止，但不推荐，很多服务器/代理不支持
2. **POST比GET安全吗？**：不，都可以被抓包，安全程度一样。HTTPS才安全
3. **GET参数长度有限制？**：HTTP规范没有限制，是浏览器和服务器有各自的限制
4. **POST数据在body里就看不到？**：不是，抓包工具都能看到

**答案解析**:

深入理解GET和POST：

1. **语义层面的区别（最本质）**：
   - GET：从服务器获取资源，应该是只读的，不改变服务器状态
   - POST：向服务器提交数据，可能改变服务器状态
   - 这是RESTful设计的基本原则
   - 但实际中很多人不遵守，用GET做修改也能跑

2. **幂等性**：
   - 幂等：执行一次和执行多次，效果一样
   - GET是幂等的：刷新多少次页面，数据都不变
   - POST不是幂等的：重复提交表单可能创建多个订单
   - 这是设计时需要考虑的重要特性

3. **为什么GET参数放URL，POST放body**：
   - 这是约定俗成的，不是强制规定
   - GET的语义是获取资源，参数是"查询条件"，放URL上直观
   - POST的语义是提交数据，数据是"实体"，放body里合适
   - URL长度有限制，大量参数用POST更方便

4. **浏览器对URL长度的限制**：
   - HTTP规范没有限制URL长度
   - 但实际中浏览器、服务器、代理都有限制
   - IE旧版限制2083字节
   - 现代浏览器一般支持几千到几万字符
   - 建议URL不要太长，必要时用POST

5. **RESTful API中的方法**：
   - GET：查询（SELECT）
   - POST：创建（INSERT）
   - PUT：全量更新（UPDATE）
   - PATCH：部分更新
   - DELETE：删除（DELETE）
   - 每个方法有明确的语义

**扩展问题**:
- GET和POST最本质的区别是什么？
- GET请求的body有用吗？为什么不推荐用？
- 什么是幂等性？GET为什么是幂等的？
- PUT和POST有什么区别？

## Q13: Cookie和Session的区别

**考察点**: Cookie与Session对比、会话管理

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

HTTP是无状态协议，Cookie和Session是用来保持会话状态的两种机制。

**Cookie**：
- 存储在客户端（浏览器）的小型文本文件
- 服务端通过Set-Cookie响应头设置Cookie
- 浏览器后续请求自动携带Cookie
- 有大小和数量限制（每个域名约几十KB，几十个Cookie）
- 不安全（可以被篡改、窃取）

**Session**：
- 存储在服务端的会话数据
- 每个Session有一个唯一的Session ID
- Session ID通常通过Cookie传递给客户端
- 客户端下次请求带Session ID，服务端找到对应的Session
- 相对安全（数据在服务端）

**主要区别**：

| 维度 | Cookie | Session |
|------|--------|---------|
| 存储位置 | 客户端（浏览器） | 服务端 |
| 安全性 | 较低（可被篡改/窃取） | 较高（数据在服务端） |
| 存储大小 | 有限制（约4KB/个） | 无限制（受服务器内存限制） |
| 有效期 | 可以设置较长时间 | 会话级（关闭浏览器失效） |
| 服务器压力 | 无 | 有（占用服务器内存） |
| 跨域 | 受同源策略限制 | 依赖Cookie，也受限制 |
| 禁用Cookie | 不能用 | 可以用URL重写传递Session ID |

**Cookie的属性**：
- **name/value**：键值对
- **domain**：作用域名
- **path**：作用路径
- **expires/max-age**：过期时间
- **secure**：只在HTTPS下发送
- **HttpOnly**：禁止JS访问（防XSS）
- **SameSite**：防止CSRF（Strict/Lax/None）

**Session的工作原理**：
1. 用户第一次访问，服务端创建Session，生成Session ID
2. 服务端通过Set-Cookie把Session ID发给客户端
3. 客户端后续请求自动带Cookie中的Session ID
4. 服务端根据Session ID找到对应的Session
5. 服务端可以在Session中存取用户数据

**答案解析**:

深入理解Cookie和Session：

1. **为什么需要Cookie和Session**：
   - HTTP是无状态的，每次请求都是独立的
   - 但实际应用需要知道"你是谁"（登录状态、购物车等）
   - Cookie和Session就是用来保持状态的

2. **Session和Cookie的关系**：
   - Session依赖Cookie来传递Session ID
   - 但Session不是只能通过Cookie传递
   - 也可以通过URL重写（把Session ID放在URL里）
   - 或者放在请求头里（如Authorization头）

3. **Session的存储方式**：
   - 内存存储（单机，重启丢失）
   - 文件存储
   - 数据库存储
   - Redis存储（推荐，分布式环境）
   - 内存型数据库（如Redis）最常用，性能好，支持分布式

4. **分布式Session的解决方案**：
   - **Session复制**：每个节点复制所有Session（同步开销大）
   - **Session粘滞**：同一用户的请求都路由到同一节点（负载不均衡）
   - **Session集中存储**：存在Redis/数据库中（推荐，扩展性好）
   - **JWT/Token**：无状态，服务端不存Session（见扩展）

5. **Cookie的安全问题**：
   - **XSS攻击**：注入脚本窃取Cookie → 用HttpOnly防护
   - **CSRF攻击**：利用用户登录态发起伪造请求 → 用SameSite/Token防护
   - **Cookie篡改**：用户可以修改Cookie值 → 重要数据不要放Cookie，或加签名

**扩展问题**:
- Session和Cookie有什么关系和区别？
- 禁用Cookie后还能用Session吗？怎么实现？
- 分布式Session有哪些解决方案？
- Cookie有哪些安全属性？分别防什么攻击？

## Q14: 什么是跨域，如何解决

**考察点**: 同源策略、CORS、跨域解决方案

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**同源策略（Same-Origin Policy）**：
浏览器的安全策略，限制不同源的文档或脚本之间的交互。

**什么是同源**：
协议、域名、端口三者都相同，就是同源。

```
http://example.com:80
http://example.com:8080  →  端口不同，不同源
https://example.com      →  协议不同，不同源
http://api.example.com   →  域名不同，不同源
http://example.cn        →  顶级域名不同，不同源
```

**跨域限制的内容**：
- 不能读取Cookie、LocalStorage、IndexedDB
- 不能获取DOM
- AJAX请求被拦截（请求发出去了，但响应被浏览器拦截了）

**注意**：跨域不是请求发不出去，而是浏览器拦截了响应。服务端其实收到了请求。

**跨域解决方案**：

**1. CORS（Cross-Origin Resource Sharing）**：
- 最标准、最推荐的解决方案
- 服务端设置响应头，允许跨域访问
- 主要响应头：
  - `Access-Control-Allow-Origin`：允许的域名
  - `Access-Control-Allow-Methods`：允许的方法
  - `Access-Control-Allow-Headers`：允许的请求头
  - `Access-Control-Allow-Credentials`：是否允许携带Cookie
  - `Access-Control-Max-Age`：预检请求的缓存时间

**2. JSONP**：
- 利用`<script>`标签不受同源策略限制的特点
- 只能发GET请求
- 需要服务端配合返回函数调用
- 有安全风险（XSS），现在基本被CORS取代

**3. 代理服务器（Nginx反向代理）**：
- 前端请求同源的代理服务器
- 代理服务器转发到目标服务器
- 浏览器以为是同源请求
- 配置简单，不需要改业务代码

**4. postMessage**：
- 页面之间（iframe、窗口）通信
- 用`window.postMessage()`发送消息
- `message`事件接收消息

**5. WebSocket**：
- WebSocket不受同源策略限制
- 适合实时通信场景

**6. 域名降级（document.domain）**：
- 适用于一级域名相同，二级域名不同的情况
- 两个页面都设置`document.domain = 'example.com'`
- 比较老的方法，适用范围有限

**答案解析**:

深入理解跨域：

1. **为什么要有同源策略**：
   - 安全：防止恶意网站读取其他网站的数据
   - 如果没有同源策略，你打开恶意网站，它就能读取你银行网站的Cookie和数据
   - 同源策略是浏览器安全的基石

2. **CORS的两种请求**：
   - **简单请求**：GET/POST/HEAD，且Content-Type是常见类型
     - 直接发送请求，服务端返回CORS头
   - **非简单请求（预检请求）**：PUT/DELETE、自定义Header等
     - 先发一个OPTIONS预检请求，询问服务端是否允许
     - 服务端返回允许的响应头
     - 浏览器确认允许后，再发真实请求
     - 预检请求可以缓存（Access-Control-Max-Age）

3. **带Cookie的CORS**：
   - 默认跨域请求不携带Cookie
   - 需要前端设置`withCredentials = true`
   - 服务端设置`Access-Control-Allow-Credentials: true`
   - 此时Access-Control-Allow-Origin不能是`*`，必须是具体域名

4. **为什么img/script/link标签不受跨域限制**：
   - 这些标签是"嵌入"资源，不是读取数据
   - 你可以引用其他网站的图片、脚本、样式
   - 但你不能用JS读取这些资源的内容
   - JSONP就是利用了script标签的这个特性

5. **Nginx反向代理示例**：
```nginx
location /api/ {
    proxy_pass http://api.example.com/;
    # 也可以在这里设置CORS头
    add_header Access-Control-Allow-Origin *;
}
```

**扩展问题**:
- 什么是同源策略？为什么要有同源策略？
- CORS的简单请求和预检请求有什么区别？
- 跨域请求带Cookie需要什么条件？
- JSONP的原理是什么？有什么优缺点？

## Q15: DNS解析过程

**考察点**: DNS工作原理、递归查询、迭代查询

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

**DNS（Domain Name System，域名系统）**：
将域名（如www.example.com）转换为IP地址的分布式数据库系统。

**DNS解析的完整过程**（以访问www.example.com为例）：

1. **浏览器缓存**：浏览器先查自己的DNS缓存
2. **系统缓存**：浏览器缓存没有，查操作系统的缓存（hosts文件 + 系统缓存）
3. **本地DNS服务器（LDNS）**：系统缓存没有，请求本地DNS服务器（一般是ISP提供的）
4. **根DNS服务器**：本地DNS没有，请求根域名服务器
5. **顶级域DNS服务器（TLD）**：根服务器返回.com顶级域服务器地址
6. **权威DNS服务器**：顶级域服务器返回example.com的权威DNS地址
7. **返回结果**：权威DNS返回www.example.com的IP地址
8. **缓存结果**：各级DNS和浏览器缓存结果，供下次使用

**两种查询方式**：

**1. 递归查询**：
- 客户端只发一次请求，对方必须返回最终结果
- 如果对方不知道，它替你去问
- 一般：客户端 → 本地DNS服务器 是递归查询

**2. 迭代查询**：
- 客户端发请求，对方返回自己知道的最好结果（下一步该问谁）
- 客户端自己一步步去问
- 一般：本地DNS → 根 → 顶级域 → 权威 是迭代查询

**DNS缓存**：
- 浏览器缓存：几分钟到几小时
- 系统缓存：几分钟到几小时
- 本地DNS缓存：按TTL时间
- 各级DNS都有缓存，减少查询时间

**答案解析**:

深入理解DNS：

1. **DNS的层级结构**：
   - 根域名：`.`（根服务器全球13组）
   - 顶级域（TLD）：.com、.org、.net、.cn等
   - 二级域：example.com、baidu.com
   - 三级域（子域）：www.example.com、api.example.com
   - 层级结构，分布式管理

2. **为什么有了本地DNS还要根服务器**：
   - 本地DNS不知道所有域名的IP
   - 根服务器知道所有顶级域的地址
   - 顶级域知道所有二级域的权威DNS地址
   - 一级一级往下找
   - 分布式系统，每个节点只需要知道下一级的信息

3. **DNS的记录类型**：
   - **A记录**：域名 → IPv4地址
   - **AAAA记录**：域名 → IPv6地址
   - **CNAME**：域名 → 域名（别名）
   - **MX记录**：邮件服务器
   - **NS记录**：域名服务器
   - **TXT记录**：文本信息（域名验证、SPF等）
   - **PTR记录**：IP → 域名（反向解析）

4. **DNS的优化**：
   - **缓存**：各级缓存，减少查询
   - **DNS预解析**：浏览器提前解析页面中的域名
   - **HTTPDNS**：用HTTP协议请求DNS，绕过运营商Local DNS
   - **智能DNS**：根据地理位置返回最近的IP（CDN的基础）
   - **多DNS服务器**：防止单点故障

5. **DNS安全问题**：
   - **DNS劫持**：篡改DNS解析结果，跳到恶意网站
   - **DNS污染**：向DNS服务器注入错误记录
   - **DNS放大攻击**：DDoS的一种
   - **防御**：DNSSEC（DNS安全扩展）、HTTPS、HTTPDNS

## Q16: 在浏览器输入URL到页面显示的全过程

**考察点**: 网络请求全过程、浏览器渲染

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

从输入URL到页面显示，大致经历以下过程：

**第一步：URL解析与导航**：
1. 用户在地址栏输入URL
2. 浏览器判断是搜索词还是URL
3. 如果是URL，检查协议（没有的话默认加http://）

**第二步：DNS解析**：
1. 浏览器缓存 → 系统缓存 → hosts文件
2. 本地DNS服务器 → 根DNS → 顶级域DNS → 权威DNS
3. 得到服务器的IP地址

**第三步：建立TCP连接**：
1. 浏览器和服务器进行TCP三次握手
2. 如果是HTTPS，还要进行TLS握手
3. 连接建立完成

**第四步：发送HTTP请求**：
1. 浏览器构建HTTP请求报文（请求行、请求头、请求体）
2. 通过TCP连接发送给服务器
3. 请求方法通常是GET（页面访问）

**第五步：服务端处理请求**：
1. 服务器收到HTTP请求
2. 反向代理（如Nginx）转发到应用服务器
3. 应用服务器处理业务逻辑（查询数据库、渲染页面等）
4. 返回HTTP响应（状态码、响应头、响应体）

**第六步：浏览器接收响应**：
1. 浏览器接收响应数据
2. 根据状态码处理（200正常、301重定向、404错误等）
3. 如果是重定向，重新发起请求

**第七步：浏览器渲染页面**：
1. **解析HTML**：构建DOM树
2. **解析CSS**：构建CSSOM树
3. **构建渲染树**：DOM + CSSOM → Render Tree
4. **布局（Layout/Reflow）**：计算元素的位置和大小
5. **绘制（Paint）**：将页面绘制到屏幕上
6. **JS执行**：遇到script标签，暂停渲染，执行JS

**第八步：连接关闭**：
1. 数据传输完成
2. TCP四次挥手断开连接
3. （如果是Keep-Alive，连接保持一段时间）

**答案解析**:

深入理解整个过程：

1. **浏览器渲染的详细过程**：
   - **DOM树**：HTML解析成DOM节点树
   - **CSSOM树**：CSS解析成样式规则树
   - **Render树**：DOM + 样式，只包含可见元素（display:none的不算）
   - **Layout**：计算每个元素的位置和尺寸（回流/重排）
   - **Paint**：将元素绘制到屏幕上（重绘）
   - **Composite**：将多个层合并，显示到屏幕

2. **JS对渲染的影响**：
   - JS可以修改DOM和CSS
   - 所以遇到script标签，HTML解析会暂停
   - 等JS加载执行完再继续
   - 因为JS可能修改DOM结构
   - 可以用defer/async属性优化脚本加载

3. **重排（Reflow）和重绘（Repaint）**：
   - **重排**：元素位置/大小变化，需要重新计算布局（开销大）
   - **重绘**：元素外观变化（颜色等），不需要重新布局（开销较小）
   - 重排一定触发重绘，重绘不一定触发重排
   - 性能优化：减少重排和重绘的次数

4. **性能优化点**：
   - **网络层面**：DNS预解析、CDN加速、减少HTTP请求、压缩资源、缓存
   - **渲染层面**：CSS放头部、JS放底部、减少重排重绘、图片懒加载
   - **服务端层面**：接口优化、数据库优化、缓存

5. **一次请求涉及的技术**：
   - 应用层：HTTP/HTTPS、DNS
   - 传输层：TCP/UDP
   - 网络层：IP、路由
   - 数据链路层：ARP、MAC寻址
   - 物理层：光纤、电磁波
   - 浏览器渲染：HTML/CSS/JS解析

## Q17: ARP协议的工作原理

**考察点**: ARP协议、MAC地址、地址解析

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**ARP（Address Resolution Protocol，地址解析协议）**：
根据IP地址获取物理地址（MAC地址）的协议。

**为什么需要ARP**：
- 网络层用IP地址寻址
- 数据链路层用MAC地址寻址
- 发送数据时，知道了IP地址，还需要知道对应的MAC地址
- ARP就是用来做IP → MAC转换的

**ARP的工作过程**（同一局域网内）：

1. **ARP请求（广播）**：
   - 主机A要给主机B发数据，知道B的IP，但不知道MAC
   - A在局域网内广播ARP请求报文："谁的IP是192.168.1.2？请告诉我你的MAC地址"
   - 广播帧：目的MAC是FF:FF:FF:FF:FF:FF，局域网内所有主机都收到

2. **ARP响应（单播）**：
   - 所有主机收到ARP请求
   - IP不匹配的主机忽略
   - IP匹配的主机B，单播回复ARP响应："我是192.168.1.2，我的MAC是XX:XX:XX:XX:XX:XX"
   - 同时把A的IP和MAC存入自己的ARP缓存

3. **更新缓存**：
   - 主机A收到响应，将B的IP和MAC存入ARP缓存
   - 后续通信直接查缓存，不用再发ARP请求

**ARP缓存**：
- 每个主机都维护一张ARP缓存表
- 存储IP到MAC的映射
- 有过期时间（一般10-20分钟）
- 用`arp -a`命令查看

**跨网段的情况**：
- 如果目标IP不在同一局域网
- ARP请求只能在局域网内广播
- 这时候ARP请求得到的是网关的MAC地址
- 数据先发给网关，由网关转发到其他网络

**答案解析**:

深入理解ARP：

1. **ARP在OSI模型中的位置**：
   - 介于网络层和数据链路层之间
   - 有的教材放在网络层，有的放在链路层
   - 它是IP层和MAC层之间的桥梁

2. **免费ARP（Gratuitous ARP）**：
   - 主机发送ARP请求，查询自己的IP地址
   - 作用：
     - 检查IP是否冲突
     - 更新其他主机的ARP缓存（本机MAC变了）
   - 一般在主机启动时发送

3. **ARP欺骗（ARP Spoofing）**：
   - 攻击者发送伪造的ARP响应
   - 让目标主机把网关IP映射到攻击者的MAC
   - 这样目标主机的流量都经过攻击者
   - 可以窃听、篡改数据
   - 防御：静态ARP、ARP防火墙、VLAN隔离

4. **RARP（反向ARP）**：
   - 和ARP相反：根据MAC地址找IP地址
   - 用于无盘工作站等不知道自己IP的场景
   - 现在基本被DHCP取代了

5. **ARP和路由的关系**：
   - 同一局域网内：直接用ARP找目标MAC
   - 不同局域网：用ARP找网关的MAC，发给网关
   - 网关再根据路由表转发到下一跳
   - 每经过一跳，源MAC和目的MAC都会变，但源IP和目的IP不变

**扩展问题**:
- ARP协议是干嘛的？工作在哪一层？
- ARP欺骗是什么？如何防御？
- 跨网段通信时，ARP的作用是什么？
- 免费ARP是什么？有什么用？

## Q18: 什么是CDN，原理是什么

**考察点**: CDN原理、缓存策略、使用场景

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**CDN（Content Delivery Network，内容分发网络）**：
将网站的静态内容分发到全国各地的边缘节点，用户可以就近获取，提高访问速度。

**CDN的作用**：
1. **加速访问**：用户就近访问，减少延迟
2. **减轻源站压力**：大部分请求由CDN节点处理
3. **提高可用性**：分布式架构，单点故障不影响全局
4. **带宽优化**：减少源站带宽消耗
5. **安全防护**：隐藏源站IP，抗DDoS

**CDN的工作原理**：

1. **用户访问**：用户请求某个静态资源（如图片、JS、CSS）
2. **DNS解析**：
   - DNS解析到CDN的智能DNS服务器
   - 智能DNS根据用户地理位置，返回最近的CDN节点IP
3. **访问CDN节点**：用户访问最近的CDN节点
4. **缓存命中**：
   - 如果CDN节点有缓存，直接返回给用户
5. **回源**：
   - 如果CDN节点没有缓存或缓存过期
   - CDN节点向源站请求资源
   - 缓存到CDN节点
   - 返回给用户

**CDN的关键技术**：
1. **智能DNS解析**：根据用户IP分配最近的节点
2. **缓存策略**：合理设置缓存时间（TTL）
3. **内容分发**：主动推送或被动缓存
4. **负载均衡**：节点之间的负载均衡
5. **缓存更新**：缓存失效、主动刷新

**CDN加速的资源类型**：
- 静态资源：图片、CSS、JS、视频
- 下载文件：安装包、APK
- 流媒体：直播、点播
- 全站加速：动态内容也可以加速（边缘计算）

**答案解析**:

深入理解CDN：

1. **为什么CDN能加速**：
   - **距离近**：用户访问就近的节点，减少物理距离和路由跳数
   - **带宽大**：CDN节点带宽充足
   - **缓存**：大部分请求不用回源，直接从缓存返回
   - **TCP优化**：CDN厂商有各种TCP优化技术

2. **CDN缓存策略**：
   - **缓存时间**：TTL（Time To Live），缓存多久
   - **缓存更新**：
     - 被动失效：TTL到了自动回源
     - 主动刷新：源站更新后，主动刷新CDN缓存（URL刷新/目录刷新/预热）
   - **缓存规则**：按文件类型、URL路径设置不同的缓存时间

3. **CDN回源**：
   - 缓存未命中时，CDN节点从源站拉取资源
   - 回源会增加延迟（需要到源站）
   - 命中率越高，回源越少，效果越好
   - 提高命中率：合理设置缓存时间、预热热门资源

4. **CDN的组成**：
   - **边缘节点**：最靠近用户的缓存节点
   - **区域节点**：汇聚多个边缘节点
   - **中心节点**：和源站对接
   - **智能DNS/GSLB**：全局负载均衡，分配节点
   - **管理平台**：配置、监控、统计

5. **CDN的分类**：
   - **静态CDN**：加速静态资源
   - **动态CDN**：加速动态内容（边缘路由优化）
   - **全站加速**：动静态都加速
   - **直播CDN**：直播流分发
   - **下载CDN**：大文件下载

- CDN的缓存命中率是什么？如何提高？
- 源站更新了内容，CDN怎么更新缓存？
- CDN和普通的缓存有什么区别？

## Q19: WebSocket和HTTP的区别

**考察点**: WebSocket原理、长连接、与HTTP对比

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**WebSocket**：
HTML5提供的一种在单个TCP连接上进行全双工通信的协议。

**为什么需要WebSocket**：
- HTTP是半双工的，只能客户端发请求，服务端返回响应
- 服务端不能主动推送消息给客户端
- 实时性要求高的场景（聊天、游戏、股票），用HTTP轮询效率低

**HTTP轮询的问题**：
- **短轮询**：客户端定时发请求，服务端有数据就返回，没有就返回空
  - 问题：大量无效请求，浪费资源
- **长轮询**：客户端发请求，服务端有数据就返回，没有就挂起等有数据了再返回
  - 问题：连接挂起占用资源，一次只能处理一个响应

**WebSocket的特点**：
1. **全双工**：客户端和服务端可以同时发消息
2. **长连接**：连接建立后一直保持
3. **低开销**：头部小，不需要每次都带完整HTTP头
4. **二进制支持**：可以发送文本和二进制数据
5. **基于HTTP握手**：通过HTTP的Upgrade升级协议

**WebSocket和HTTP的区别**：

| 维度 | HTTP | WebSocket |
|------|------|-----------|
| 连接方式 | 短连接（也有长连接） | 长连接 |
| 通信模式 | 请求-响应（半双工） | 全双工 |
| 服务端推送 | 不支持（只能轮询） | 支持 |
| 头部开销 | 大（每次请求都有完整头部） | 小（连接建立后只有帧头） |
| 协议 | HTTP协议 | WebSocket协议（基于HTTP握手） |
| 端口 | 80/443 | 80/443（和HTTP一样） |
| 适用场景 | 普通网页浏览 | 实时通信、聊天、游戏 |

**WebSocket的建立过程**：
1. 客户端发送HTTP请求，带Upgrade: websocket头
2. 服务端响应101 Switching Protocols
3. 协议升级完成，后续用WebSocket帧通信
4. 连接保持，双方随时可以发消息

**答案解析**:

深入理解WebSocket：

1. **为什么WebSocket握手用HTTP**：
   - 兼容现有HTTP基础设施（代理、防火墙等）
   - 用80/443端口，不会被防火墙拦截
   - 通过Upgrade机制升级协议
   - 是一个很巧妙的设计

2. **WebSocket的帧结构**：
   - 不是文本格式，是二进制帧
   - 帧头包含：FIN位、opcode（文本/二进制/关闭/Ping/Pong）、掩码、长度等
   - 数据载荷
   - 比HTTP报文小得多

3. **WebSocket的心跳机制**：
   - 长连接需要检测连接是否正常
   - Ping/Pong帧：一方发Ping，另一方回Pong
   - 长时间没收到Pong，认为连接断开了
   - 一般几十秒到几分钟一次心跳

4. **WebSocket的应用场景**：
   - 即时通讯（聊天、IM）
   - 实时游戏
   - 股票/期货实时行情
   - 协同编辑（文档协作）
   - 实时监控仪表盘
   - 直播弹幕

5. **WebSocket vs SSE**：
   - **SSE（Server-Sent Events）**：服务端向客户端单向推送
   - WebSocket：双向通信
   - SSE更简单，基于HTTP，自动重连
   - WebSocket功能更强，双向通信
   - 只需要服务端推送的场景，SSE更轻量

**扩展问题**:

- WebSocket是怎么建立连接的？为什么要基于HTTP握手？
- WebSocket和长轮询相比有什么优势？
- WebSocket的心跳机制是什么？为什么需要？

## Q20: 什么是DDoS攻击，如何防御

**考察点**: DDoS攻击原理、常见类型、防御手段

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

**DDoS（Distributed Denial of Service，分布式拒绝服务攻击）**：
攻击者控制大量傀儡机（僵尸网络），同时向目标发送海量请求，耗尽目标的资源（带宽、连接数、CPU等），导致正常用户无法访问。

**常见DDoS攻击类型**：

**1. 网络层攻击（三层/四层）**：
- **SYN洪水（SYN Flood）**：发送大量SYN报文，占满半连接队列
- **UDP洪水（UDP Flood）**：发送大量UDP包，耗尽带宽
- **ICMP洪水（Ping Flood）**：大量ICMP请求，耗尽带宽和CPU
- **放大攻击**：DNS放大、NTP放大，利用反射服务器放大流量

**2. 应用层攻击（七层）**：
- **CC攻击（Challenge Collapsar）**：大量合法请求耗尽服务器资源
- **HTTP洪水**：大量HTTP请求，压垮Web服务器
- **慢速攻击**：Slowloris等，慢速发送请求占满连接

**DDoS防御方法**：

**1. 高防服务器/高防IP**：
- 租用有大带宽和清洗能力的服务器
- 流量先经过高防清洗，正常流量再转发到源站
- 最常用的防御手段

**2. CDN加速**：
- 将静态资源缓存到CDN节点
- 分散流量，源站压力小
- CDN节点多，抗攻击能力强

**3. 负载均衡**：
- 多台服务器分担流量
- 单点压力小
- 配合自动扩容

**4. 流量清洗**：
- 识别异常流量（异常IP、异常速率等）
- 过滤掉攻击流量
- 只放行正常流量

**5. 限速/限流**：
- 对单个IP/用户限速
- 防止单个来源消耗过多资源

**6. 弹性扩容**：
- 攻击来时自动扩容
- 扛住高峰流量
- 云服务商的弹性伸缩

**7. 黑名单/白名单**：
- 封禁攻击IP
- 只允许可信IP访问

**答案解析**:

深入理解DDoS：

1. **SYN洪水攻击原理**：
   - 攻击者发送大量SYN报文，源IP是伪造的
   - 服务端收到SYN，回复SYN+ACK，等待ACK
   - 源IP是假的，永远不会有ACK
   - 半连接队列满了，正常连接进不来
   - **防御**：SYN Cookie、缩短超时时间、增加队列

2. **DNS放大攻击**：
   - 攻击者向开放的DNS服务器发送查询请求
   - 源IP伪造成目标IP
   - DNS服务器将响应发给目标IP
   - 响应比请求大很多（几十倍放大）
   - 用小带宽产生大流量攻击
   - **防御**：关闭开放DNS解析、过滤可疑DNS响应

3. **CC攻击的特点**：
   - 看起来是正常的HTTP请求
   - 不像SYN洪水那样容易识别
   - 主要消耗服务器的CPU、内存、数据库资源
   - **防御**：
     - 验证码（人机识别）
     - 频率限制（单IP请求次数）
     - CDN/WAF（Web应用防火墙）
     - 缓存（减少动态请求）

4. **防御的层次**：
   - **网络层防御**：高防IP、流量清洗、运营商清洗
   - **应用层防御**：WAF、CC防护、验证码
   - **架构层防御**：CDN、负载均衡、弹性扩容
   - **业务层防御**：限流、降级、熔断

5. **DDoS和DoS的区别**：
   - **DoS**：拒绝服务攻击，单台机器发起
   - **DDoS**：分布式拒绝服务，大量机器同时发起
   - DDoS威力大得多，防御难度也大得多
   - 现在的攻击基本都是DDoS

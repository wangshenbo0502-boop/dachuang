# 系统设计面试题（校招版）

## 技术考察重点

- 分布式基础理论（CAP/BASE/一致性）
- 缓存设计（穿透/击穿/雪崩/多级缓存）
- 数据库设计（分库分表/索引/事务）
- 消息队列（可靠性/削峰填谷/顺序性）
- 高并发架构（限流/降级/熔断/负载均衡）
- 常见系统设计题（短链接/秒杀/排行榜/IM）

## 答题模板

系统设计题建议按以下思路展开：

1. **需求分析**：明确功能需求 + 非功能需求（QPS、延迟、可用性）
2. **核心模块**：拆分系统关键组件
3. **数据存储**：表结构设计、存储选型（MySQL/Redis/MongoDB）
4. **高并发优化**：缓存、异步、读写分离、分库分表
5. **高可用设计**：集群、容灾、降级、限流
6. **扩展性**：模块化、微服务、水平扩展

## 高频面试题

### Q1: 设计一个短链接系统？

- **类别**: 系统设计
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

**需求分析**：
- 功能：长 URL → 短 URL 编码、短 URL → 302 重定向、自定义短码、过期时间
- 非功能：QPS 预估（写入 1k/s，读取 10w/s）、99.9% 可用性

**核心模块**：
- 短码生成器 + 存储层 + 重定向服务 + 统计模块

**短码生成策略**：
1. **自增 ID + 62 进制编码**：发号器生成递增 ID，转为 0-9a-zA-Z 的 62 进制字符串，7 位可支持 ~3.5 万亿
2. **哈希算法**：MurmurHash/MD5 取 62 进制，冲突时拼接随机数再哈希

**存储设计**：
- MySQL：短码（主键）→ 长 URL、创建时间、过期时间
- Redis：缓存热点短码 → 长 URL，减轻 DB 压力
- 布隆过滤器：快速判断短码是否存在，防穿透

**高并发优化**：
- 读多写少，Redis 缓存热点数据
- 发号器预生成短码号段，减少 DB 写入
- 302 临时重定向（方便统计点击）vs 301 永久重定向（省带宽）

**高可用设计**：
- 多副本部署 + 负载均衡
- 发号器双机房部署，号段不重叠
- Redis 主从 + 哨兵

</details>

### Q2: 设计一个秒杀系统？如何防超卖？

- **类别**: 系统设计
- **难度**: 较难
- **频率**: 极高

<details>
<summary>答题要点</summary>

**需求分析**：
- 功能：秒杀商品列表、秒杀下单、库存扣减、订单查询
- 特点：瞬时高并发、读多写少、库存有限

**核心挑战**：
- 高并发下库存超卖
- 大量请求拖垮数据库
- 黄牛/刷单

**架构设计**：

1. **前端层**：活动页面静态化 CDN、按钮置灰防重复点击、验证码限流
2. **接入层**：Nginx 限流（limit_req）、负载均衡、黑白名单
3. **业务层**：
   - Redis 预扣库存：秒杀开始前把库存加载到 Redis，用 `DECR` 原子扣减
   - 消息队列异步下单：扣减成功后发消息到 MQ，消费者异步创建订单
   - 库存预热 + 本地缓存：热点商品库存缓存在服务本地内存
4. **数据层**：MySQL 最终一致性，订单表 + 库存表

**防超卖方案**：
1. **Redis 原子操作**：`DECR` 后判断结果 < 0 则库存不足
2. **数据库乐观锁**：`UPDATE stock SET count = count - 1 WHERE id = ? AND count > 0`
3. **数据库行锁**：`SELECT ... FOR UPDATE` 加悲观锁（性能差，不推荐）

**限流降级策略**：
- 限流：令牌桶/漏桶，超过阈值直接返回"已售罄"
- 降级：非核心功能关闭（如推荐、评论）
- 熔断：下游故障时快速失败
- 削峰：MQ 异步处理，平滑流量

</details>

### Q3: 缓存穿透/击穿/雪崩分别是什么？如何解决？

- **类别**: 缓存设计
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

| 问题 | 描述 | 原因 | 解决方案 |
|------|------|------|----------|
| **缓存穿透** | 查询不存在的数据，请求穿透缓存直达 DB | 恶意攻击、非法参数 | 布隆过滤器、缓存空值（短 TTL）、参数校验 |
| **缓存击穿** | 热点 key 过期瞬间，大量并发请求打向 DB | 热点数据过期 | 互斥锁（分布式锁重建缓存）、逻辑过期（永不过期+异步更新） |
| **缓存雪崩** | 大量 key 同时过期，或 Redis 宕机，DB 压力骤增 | 批量过期、缓存集群故障 | 过期时间加随机值、多级缓存（本地+Redis）、Redis 集群高可用、限流降级 |

**布隆过滤器原理**：位图 + 多个哈希函数，将 key 映射到多个位置置 1。查询时只要有一个位置为 0 就一定不存在；全为 1 则可能存在（有误判率）。

**互斥锁方案注意**：用 `SETNX` 加锁，拿到锁的线程查 DB 回写缓存，其他线程自旋等待后重试。注意锁超时和死锁。

**逻辑过期方案**：缓存 value 中存过期时间，读取时判断是否过期，过期则异步启动线程更新缓存，当前线程直接返回旧值（可能短暂不一致）。

</details>

### Q4: 设计一个分布式 ID 生成器？雪花算法原理和问题？

- **类别**: 分布式基础
- **难度**: 中等
- **频率**: 极高

<details>
<summary>答题要点</summary>

**分布式 ID 要求**：全局唯一、趋势递增、高可用、高性能、信息安全（不暴露业务量）

**常见方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| UUID | 简单，无依赖 | 无序，字符串存储，查询慢 |
| 数据库自增 ID | 简单，有序 | 单点瓶颈，扩展性差 |
| 号段模式（美团 Leaf） | 性能好，趋势递增 | 依赖 DB，号段用完阻塞 |
| 雪花算法（Snowflake） | 高性能，有序，不依赖第三方 | 时钟回拨问题 |

**雪花算法（Snowflake）**：
- 64 bit 结构：
  - 1 bit 符号位（0）
  - 41 bit 时间戳（毫秒级，可用 ~69 年）
  - 10 bit 工作机器 ID（5 bit 数据中心 + 5 bit 机器号，支持 1024 节点）
  - 12 bit 序列号（每毫秒 4096 个 ID）

**雪花算法问题**：
1. **时钟回拨**：服务器时钟回拨会导致重复 ID
   - 解决：回拨时间短（如 < 5ms）则等待；回拨时间长则报错或切换到备用 workerId
2. **机器 ID 分配**：需要手动配置或借助 ZooKeeper/Redis 自动分配
3. **单机上限**：每毫秒 4096 个，一般够用

**号段模式原理**：从数据库一次性取一批 ID（号段），用完再取下一批。DB 存 `max_id` 和 `step`，每次更新 `max_id = max_id + step`。

</details>

### Q5: 分布式锁的实现方式？Redis 和 ZooKeeper 实现的优缺点？

- **类别**: 分布式基础
- **难度**: 较难
- **频率**: 高

<details>
<summary>答题要点</summary>

**分布式锁要求**：互斥性、防死锁、可重入、高性能、高可用

**三种主流实现对比**：

| 方案 | 实现方式 | 优点 | 缺点 |
|------|---------|------|------|
| **Redis** | SETNX + 过期时间 + Lua 释放 | 性能高，实现简单，生态好 | 存在锁过期续期问题，极端情况不一致 |
| **ZooKeeper** | 临时有序节点 + watch 机制 | 强一致性，自动释放锁，有序公平 | 性能较低，依赖 ZK 集群 |
| **MySQL** | 唯一索引/for update | 简单，已有基础设施 | 性能差，不可靠，不适合高并发 |

**Redis 分布式锁实现要点**：
- 加锁：`SET key value NX PX expire_time`（原子操作）
- value 设为唯一标识（如 UUID + 线程 ID），防止误删别人的锁
- 解锁：Lua 脚本判断 value 相等后再 DEL（保证原子性）
- 锁续期：Redisson 看门狗（Watchdog），后台线程定期续期
- 红锁（RedLock）：多节点加锁，多数派成功才算加锁成功（争议较大）

**ZooKeeper 实现要点**：
- 加锁：在锁节点下创建临时有序节点
- 判断：自己的节点序号是否最小，是则获得锁
- 等待：监听前一个节点的删除事件，被通知后再次判断
- 释放：会话断开自动删除临时节点，不会死锁

**选型建议**：性能优先选 Redis，一致性要求高选 ZooKeeper。

</details>

### Q6: 如何保证消息队列的消息不丢失？Kafka/RocketMQ 如何做？

- **类别**: 消息队列
- **难度**: 较难
- **频率**: 高

<details>
<summary>答题要点</summary>

**消息丢失的三个环节**：生产者 → Broker → 消费者

**生产者端不丢失**：
- 同步发送：等待 Broker ACK，失败重试
- 异步发送 + 回调：发送后注册回调函数处理失败
- Kafka：`acks=all`（ISR 所有副本都确认）+ `retries` 重试
- RocketMQ：同步发送返回 SEND_OK 才算成功

**Broker 端不丢失**：
- 持久化到磁盘，刷盘策略配置
- Kafka：`replication.factor >= 3` + `min.insync.replicas >= 2`，多副本同步
- RocketMQ：同步刷盘（更可靠）+ 主从同步（DLedger 模式自动切换）

**消费者端不丢失**：
- 关闭自动 ACK，业务处理完成后手动 ACK
- Kafka：`enable.auto.commit=false`，处理完手动 `commitSync`
- RocketMQ：消费成功返回 CONSUME_SUCCESS，失败返回 RECONSUME_LATER

**Kafka 保证不丢失配置**：
```
producer: acks=all, retries=3, retries.backoff.ms=1000
broker:   replication.factor=3, min.insync.replicas=2, unclean.leader.election.enable=false
consumer: enable.auto.commit=false
```

**RocketMQ 保证不丢失**：
- 生产者使用同步发送
- Broker 使用同步刷盘 + 同步主从复制
- 消费者使用集群消费模式，消费成功后再 ACK

**注意**：可靠性和性能是 trade-off，越可靠性能越低，需根据业务权衡。

</details>

### Q7: CAP 理论和 BASE 理论？为什么不能同时满足 CAP？

- **类别**: 分布式基础
- **难度**: 简单
- **频率**: 高

<details>
<summary>答题要点</summary>

**CAP 理论**：分布式系统中，一致性（Consistency）、可用性（Availability）、分区容错性（Partition tolerance）三者不可兼得，最多同时满足两个。

- **C（一致性）**：所有节点在同一时间看到相同的数据
- **A（可用性）**：每个请求都能收到非错误响应（不保证数据最新）
- **P（分区容错性）**：网络分区（节点间通信失败）时系统仍能运行

**为什么不能同时满足？**
- 网络分区（P）是必然存在的（网络故障、机房失联），实际系统必须选 P
- 选了 P 之后：
  - 要 C：分区时为了保证数据一致，必须拒绝写入（牺牲 A）
  - 要 A：分区时每个节点独立响应，数据会不一致（牺牲 C）
- 没有分区时 C 和 A 可以同时满足

**CP 系统**：ZooKeeper、etcd、HBase（强一致，可能不可用）
**AP 系统**：Eureka、Cassandra、Amazon DynamoDB（高可用，最终一致）

**BASE 理论**：CAP 的延伸，基本可用 + 软状态 + 最终一致性
- **Basically Available（基本可用）**：允许损失部分可用性（响应时间变长、功能降级）
- **Soft state（软状态）**：允许系统存在中间状态，不影响整体可用性
- **Eventually consistent（最终一致）**：数据在一段时间后最终达到一致，而非实时一致

**BASE vs ACID**：ACID 是强一致模型，BASE 是弱一致模型，互联网高并发场景通常选择 BASE。

</details>

### Q8: 设计一个实时排行榜系统？

- **类别**: 系统设计
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

**需求分析**：
- 功能：用户得分更新、实时排行榜查询、按维度排行（总榜/日榜/周榜）
- 非功能：高写入（10w QPS）、低延迟查询（< 50ms）、Top N 查询

**方案选型**：

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| MySQL ORDER BY | 简单 | 大数据量排序慢，性能差 | 小数据量 |
| Redis ZSet | 高性能，天然支持排序 | 单 key 内存有限，不支持多维度 | 实时性要求高 |
| 跳表 + 分段 | 灵活，支持高并发 | 实现复杂 | 自研系统 |

**Redis ZSet 方案**：
- ZADD 增加/更新分数，O(log n)
- ZREVRANGE/ZRANGE 查询 Top N，O(log n + m)
- ZRANK 查询用户排名，O(log n)
- 多维度：每个维度一个 ZSet（如 rank:daily:20260728）

**数据量太大的优化**：
- 只保留前 100 万名在 ZSet，后面的不参与排行
- 按分数段分片（分段排行榜），每段一个 ZSet
- 日榜/周榜/月榜独立 ZSet，定时聚合

**高并发写入优化**：
- 写入 MQ 异步更新 ZSet，削峰填谷
- 本地缓存用户分数，批量合并更新
- 分数变更不频繁时用定时任务批量计算

**排行榜展示优化**：
- Top 100 缓存到本地内存，1s 刷新一次
- 翻页查询用 ZREVRANGE + offset（注意深分页问题）

</details>

### Q9: 设计一个支持百万级的点赞系统？

- **类别**: 系统设计
- **难度**: 中等
- **频率**: 中等

<details>
<summary>答题要点</summary>

**需求分析**：
- 功能：点赞/取消点赞、点赞数查询、点赞用户列表、判断是否点赞
- 非功能：高并发写（百万级）、读多写更多、数据最终一致可接受

**核心挑战**：
- 高并发点赞操作
- 防重复点赞
- 点赞计数的准确性

**架构设计**：

1. **接入层**：Nginx 限流、用户登录校验
2. **业务层**：
   - 点赞操作：先写 Redis（原子操作），再异步落库
   - 点赞数：Redis INCR/DECR，定时同步 MySQL
   - 判断是否点赞：Redis Set 存储点赞用户 ID
3. **数据层**：
   - Redis：点赞计数（Hash）+ 用户点赞记录（Set）+ 点赞列表（ZSet）
   - MySQL：点赞表（user_id, item_id, status, create_time）+ 计数表

**防重复点赞**：
- Redis Set 存点赞用户 ID，`SADD` 返回 0 表示已点赞
- 数据库唯一索引（user_id + item_id）兜底

**高并发优化**：
- 写操作全走 Redis，异步同步到 MySQL
- 点赞数用 Redis Hash 存，`HINCRBY` 原子增减
- 取消点赞：Set 中移除 + 计数减 1
- MQ 异步消费：点赞消息入队，消费者批量写入 DB

**数据一致性**：
- Redis 为最终数据，MySQL 为持久化备份
- 定时任务对账：每天凌晨用 MySQL 校正 Redis 数据
- 点赞列表分页查询：先查 Redis ZSet，没有再查 DB

**扩展思考**：
- 点赞数很大时（如 10w+）：前端展示 "10w+"，不展示精确数
- 点赞动画：前端先 +1，后台异步确认，失败回滚

</details>

### Q10: 数据库分库分表怎么设计？垂直拆分 vs 水平拆分？

- **类别**: 数据库设计
- **难度**: 较难
- **频率**: 高

<details>
<summary>答题要点</summary>

**为什么分库分表**：单表数据量过大（千万级以上），查询性能下降，单库连接数/存储有上限。

**拆分方式**：

**垂直拆分**：按业务模块拆分
- **垂直分库**：不同业务的表分到不同数据库（如用户库、订单库、商品库）
- **垂直分表**：大表按字段拆分，冷热数据分离（主表 + 扩展表）
- 优点：业务清晰，便于维护
- 缺点：单表数据量仍可能过大，跨库 join 复杂

**水平拆分**：按数据行拆分
- **水平分库分表**：同一张表的数据按规则分散到多个库多个表
- 优点：解决单表数据量问题，支持水平扩展
- 缺点：路由复杂，跨分片查询、聚合困难

**分片策略**：
1. **范围分片**：按时间范围、ID 范围分片（易热点不均）
2. **哈希分片**：对分片键取模（如 user_id % 16），数据均匀
3. **一致性哈希**：增减节点时数据迁移少
4. **查表法**：映射关系存在路由表中，灵活但多一次查询

**分片键选择原则**：
- 尽量让查询落在单分片上（避免跨片查询）
- 分布均匀，避免热点
- 稳定不变
- 高频查询条件

**分库分表带来的问题**：
1. **跨库 join**：字段冗余、数据同步、应用层聚合
2. **分布式事务**：TCC、Saga、可靠消息最终一致
3. **分页/排序/聚合**：需要各分片查询后合并，深分页困难
4. **ID 唯一性**：分布式 ID（雪花算法、号段模式）
5. **扩容问题**：翻倍扩容（2^n 分片），减少数据迁移量

**什么时候开始分库分表**：单表 500w-1000w 行或单库 QPS 5k+ 考虑。前期尽量用缓存 + 读写分离 + 索引优化，不要过度设计。

</details>

### Q11: 限流算法有哪些？令牌桶 vs 漏桶？如何实现？

- **类别**: 高并发架构
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

**常见限流算法**：

| 算法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **固定窗口** | 单位时间内计数，超过则拒绝 | 简单 | 临界问题（窗口切换瞬间流量翻倍） |
| **滑动窗口** | 将时间分片，滑动计算总数 | 解决临界问题 | 实现稍复杂，存储更多 |
| **漏桶** | 请求入桶，桶满则拒绝，匀速流出 | 平滑输出，削峰填谷 | 无法应对突发流量 |
| **令牌桶** | 匀速生成令牌，请求取令牌，有令牌才通过 | 允许一定突发流量，平均速率稳定 | 实现复杂 |

**令牌桶 vs 漏桶**：
- **漏桶**：出水速率恒定，不管进水多快，出水速度不变 → 强制平滑
- **令牌桶**：令牌以恒定速率生成，桶有容量，突发请求可以一次取走多个令牌 → 允许突发

**令牌桶实现（单机）**：
```
令牌生成速率：r 个/秒
桶容量：b 个
每次请求消耗 1 个令牌
桶空则拒绝
```
- Guava RateLimiter 就是令牌桶实现

**分布式限流实现**：
- Redis + Lua 脚本实现令牌桶/滑动窗口
- Lua 保证原子性，避免并发问题
- 滑动窗口：ZSet 存请求时间戳，移除窗口外的，统计窗口内数量

**限流层级**：
- 接入层：Nginx limit_req（限流）、limit_conn（限制连接数）
- 服务层：Guava RateLimiter 单机限流、Redis 分布式限流
- 网关层：Sentinel、Hystrix

</details>

### Q12: 接口幂等性如何保证？有哪些方案？

- **类别**: 分布式基础
- **难度**: 中等
- **频率**: 高

<details>
<summary>答题要点</summary>

**什么是幂等性**：同一个操作执行一次和执行多次的结果相同，不会产生副作用。

**需要幂等的场景**：
- 用户重复点击提交
- 网络重试（RPC/HTTP 重试、MQ 重试）
- 定时任务重复执行
- 前端页面回退再提交

**幂等性方案**：

1. **唯一索引/唯一主键**：
   - 数据库唯一约束，重复插入报主键冲突
   - 适用：新增操作，如订单号唯一

2. **Token 机制（防重令牌）**：
   - 进入页面前端先申请 token 存 Redis
   - 提交时携带 token，后端删除 token（`DEL` 返回 1 则首次提交）
   - 删除成功才执行业务，失败则重复提交
   - 适用：表单提交、支付等

3. **乐观锁**：
   - 表加 version 字段，`UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`
   - 影响行数为 0 则未更新
   - 适用：更新操作

4. **悲观锁**：
   - `SELECT ... FOR UPDATE` 加行锁
   - 适用：并发不高、更新操作

5. **状态机幂等**：
   - 业务状态流转（如待支付 → 已支付 → 已发货）
   - 只有当前状态是预期状态才允许变更
   - 适用：有状态的业务流程

6. **去重表**：
   - 单独建去重表，用唯一索引防重
   - 业务操作和去重表插入在同一个事务中
   - 适用：复杂业务

7. **MQ 消费幂等**：
   - 消息携带唯一 ID，消费前判断是否已消费
   - Redis 存已消费 ID，或数据库唯一索引

**选型建议**：新增用唯一索引/Token，更新用乐观锁，状态流转用状态机。

</details>

### Q3: 设计一个即时通讯(IM)系统的基础架构？

- **类别**: 系统设计
- **难度**: 较难
- **频率**: 中等

<details>
<summary>答题要点</summary>

**需求分析**：
- 功能：单聊/群聊、消息发送/接收、在线状态、消息已读、消息存储
- 非功能：低延迟、高并发、消息可靠不丢、消息有序

**整体架构**：

```
客户端 → 接入层 → 逻辑层 → 存储层
```

**接入层**：
- WebSocket/TCP 长连接服务（如 Netty 自研、IM 框架）
- 保持用户长连接，消息收发
- 连接路由：用户连接到哪个节点，存在 Redis

**逻辑层**：
- 消息收发处理、离线消息、群聊逻辑
- 消息投递：接收方在线则实时推送，不在线则存离线消息
- 多端同步：手机/PC 多端同步消息

**存储层**：
- 消息存储：HBase/Cassandra（写多读多，宽表）或 MongoDB
- 最近会话：Redis ZSet（每个用户一个会话列表，按时间排序）
- 离线消息：Redis List 或数据库
- 用户关系：MySQL（好友表、群成员表）

**消息可靠性**：
- 消息 ACK 机制：发送方 → 服务端 ACK，服务端 → 接收方 ACK
- 消息重发：超时未 ACK 则重发
- 消息去重：消息 ID 唯一，客户端去重

**消息有序性**：
- 单聊：同一对话的消息按时间戳排序，服务端分配递增序号
- 群聊：群消息有序号，每个群维护一个递增 seq

**高并发优化**：
- 接入层水平扩展，用户按一致性哈希分配节点
- 消息写入 MQ 异步落库
- 热点群聊消息扩散（扇出）优化：读扩散 vs 写扩散

**技术选型参考**：
- 接入层：Netty、Goim、Tigase
- MQ：Kafka/RocketMQ
- 存储：Redis + MySQL + HBase

</details>

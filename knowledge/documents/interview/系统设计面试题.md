# 系统设计面试题（20题）

> 本文档涵盖系统设计面试的核心题型，包括短链接、秒杀、消息队列、缓存、分布式ID、限流、排行榜等经典设计题，以及CAP、BASE、微服务等理论知识。每题均提供标准答题模板（需求分析→架构设计→核心组件→扩展性→总结）。

## Q1: 设计一个短链接系统

**考察点**: 短链接生成、存储与查询、高并发设计、302跳转

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 将长URL转换为短URL
2. 访问短URL时302重定向到原长URL
3. 短链接过期时间设置
4. 自定义短链接后缀
5. 访问统计

#### 非功能需求
- 高可用：服务不能宕机
- 高性能：跳转延迟要低（<100ms）
- 短链接要短（6-8位）
- 防猜测：不能被轻易遍历
- QPS：假设日活100万，生成短链QPS约100，跳转QPS约1万

### 二、架构设计

```
用户 → CDN/负载均衡 → 短链接服务 → 缓存(Redis) → 数据库(MySQL)
```

#### 整体架构
- **接入层**：Nginx负载均衡
- **服务层**：短链接生成服务、短链接跳转服务
- **缓存层**：Redis缓存热点短链接映射
- **存储层**：MySQL持久化存储
- **监控层**：访问统计、异常告警

### 三、核心组件设计

#### 1. 短码生成方案

**方案一：自增ID + Base62编码**
- 数据库自增ID，将ID转换为Base62（0-9, a-z, A-Z）
- 6位Base62可表示 62^6 ≈ 568亿个短码
- 优点：不冲突、短码短、有序
- 缺点：ID可预测，存在被遍历风险

**方案二：哈希算法**
- 对长URL做MD5/SHA256哈希，取前N位
- 优点：不可预测
- 缺点：有哈希冲突，需要处理

**推荐方案**：自增ID + Base62 + 随机混淆
- 用发号器生成唯一ID
- Base62编码后得到短码
- 对短码做简单的置换/加盐，防止被猜到

#### 2. 发号器设计
- 用数据库自增主键或号段模式
- 或用雪花算法生成分布式ID
- 预分配号段到内存，提高生成速度

#### 3. 存储设计
```sql
CREATE TABLE short_url (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    short_code VARCHAR(16) UNIQUE NOT NULL,
    long_url TEXT NOT NULL,
    expire_time DATETIME,
    creator_id BIGINT,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    INDEX idx_short_code (short_code),
    INDEX idx_expire_time (expire_time)
);
```

#### 4. 跳转流程
1. 用户访问短链接
2. 先查Redis缓存，命中则302跳转
3. 未命中则查数据库，写入缓存后跳转
4. 短码不存在返回404
5. 异步记录访问日志

#### 5. 缓存策略
- **缓存预热**：热门短链接提前加载
- **缓存穿透**：短码不存在时缓存空值（设置短过期时间）
- **缓存雪崩**：过期时间加随机值
- **缓存更新**：写数据库后失效缓存（Cache Aside模式）

### 四、扩展性设计

1. **水平扩展**：服务无状态，可水平扩展
2. **分库分表**：数据量大时按短码哈希分表
3. **读写分离**：跳转是读多写少，读库可扩展
4. **CDN加速**：静态资源和热门跳转走CDN
5. **统计功能**：用ClickHouse/Elasticsearch存储访问日志，做数据分析

### 五、总结

短链接系统的核心是**短码生成**和**高性能跳转**。短码生成推荐用自增ID+Base62编码方案，简单可靠不冲突。跳转性能靠缓存扛住大部分读请求，数据库只做持久化。注意防止缓存穿透和短链遍历问题。

**答案解析**:

短链接是系统设计面试的入门题，考察候选人是否有基本的系统设计思维。答题时要先问清楚需求（功能+非功能），再逐步展开。关键要点：短码生成方案对比、缓存策略、302 vs 301的区别（301是永久重定向，浏览器会缓存，不利于统计；302是临时重定向，每次都经过服务）。

**扩展问题**:
- 短码用6位够吗？如何计算容量？
- 301和302重定向有什么区别？各有什么优缺点？
- 如何防止短链接被恶意遍历？
- 如果短链接服务挂了怎么办？

## Q2: 设计一个秒杀系统

**考察点**: 高并发处理、库存扣减、防超卖、限流、削峰

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 商品展示与秒杀活动列表
2. 秒杀下单：用户在活动时间内抢购商品
3. 库存管理：精确扣减库存，不能超卖
4. 订单创建与支付
5. 限购：每个用户限购N件

#### 非功能需求
- 高并发：秒杀瞬间QPS可能达10万+
- 高可用：不能宕机
- 数据一致性：不能超卖，不能少卖
- 用户体验：响应快，结果明确

### 二、架构设计

```
用户 → CDN → 负载均衡 → 网关(限流) → 秒杀服务 → Redis(库存) → MQ → 订单服务 → MySQL
```

#### 整体分层架构
1. **前端层**：活动页面静态化、CDN加速、按钮置灰防重复点击
2. **接入层**：Nginx负载均衡、WAF防护
3. **网关层**：限流、鉴权、灰度
4. **服务层**：秒杀服务、订单服务、库存服务
5. **缓存层**：Redis库存预扣、热点数据缓存
6. **消息队列**：削峰填谷，异步下单
7. **存储层**：MySQL持久化

### 三、核心组件设计

#### 1. 防超卖方案

**方案一：数据库行锁 + 乐观锁**
```sql
UPDATE seckill_goods 
SET stock = stock - 1 
WHERE id = ? AND stock > 0;
```
- 优点：简单，靠数据库保证
- 缺点：数据库压力大，扛不住高并发

**方案二：Redis预扣库存 + 数据库最终一致**
- 活动开始前将库存加载到Redis
- 秒杀时用Redis的DECR或Lua脚本扣减
- 扣减成功后发消息，异步创建订单
- 数据库最终落地
- 优点：性能高，扛得住高并发
- 缺点：需要处理Redis和数据库的一致性

**推荐方案**：Redis预扣库存 + Lua脚本原子操作
```lua
-- Lua脚本：判断库存+扣减，原子执行
local stock = redis.call('GET', KEYS[1])
if tonumber(stock) >= tonumber(ARGV[1]) then
    redis.call('DECRBY', KEYS[1], ARGV[1])
    return 1
else
    return 0
end
```

#### 2. 限流策略
- **前端限流**：按钮置灰、倒计时、验证码
- **网关限流**：令牌桶/漏桶算法，限制总QPS
- **用户限流**：每个用户限购N件，频率限制
- **IP限流**：防止恶意刷单
- **服务降级**：非核心功能降级（如推荐、评论）

#### 3. 削峰填谷
- 用消息队列（Kafka/RocketMQ）缓冲下单请求
- 秒杀成功不直接下单，先入队
- 消费端按数据库处理能力消费，创建订单
- 用户轮询或WebSocket通知结果

#### 4. 防重复提交
- 前端按钮置灰
- 每个用户生成唯一token，下单时校验
- Redis SETNX 实现幂等
- 订单号唯一索引防重复

#### 5. 热点数据处理
- 活动页静态化，CDN缓存
- 商品信息本地缓存+Redis缓存
- 库存单独存Redis，不和其他数据混合
- 热点key用本地缓存兜底

### 四、扩展性设计

1. **分库分表**：订单表按用户ID或时间分库分表
2. **多级缓存**：CDN → Nginx缓存 → 本地缓存 → Redis缓存
3. **弹性伸缩**：秒杀前扩容，结束后缩容
4. **多活动隔离**：不同活动用不同Redis实例，互不影响
5. **监控告警**：实时监控库存、QPS、成功率、异常

### 五、总结

秒杀系统的核心是**抗高并发**和**防超卖**。设计思路是层层设防：前端挡掉一部分、网关限流挡掉一部分、Redis扛住主要压力、MQ削峰、数据库做最终持久化。关键技术点：Redis原子扣库存、消息队列削峰、多级缓存、限流降级。

**答案解析**:

秒杀是系统设计面试的经典难题，考察对高并发场景的理解和解决方案。答题时要体现"分层防御"的思想——不是靠某一个组件扛住所有压力，而是每层都做优化。注意区分"扣库存"和"创建订单"是两个动作，扣库存用Redis保证性能，创建订单走MQ保证最终一致性。

**扩展问题**:
- Redis扣减库存后，消息消费失败怎么办？
- 如何处理用户秒杀成功但不付款的情况？
- 秒杀的流量比预估的大很多怎么办？
- Redis挂了怎么办？

## Q3: 设计一个消息队列

**考察点**: 消息队列架构、消息可靠性、高可用、推拉模型

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 消息的生产与消费
2. 主题（Topic）和分区（Partition）
3. 消息持久化
4. 消息确认机制（ACK）
5. 消费组（Consumer Group）
6. 消息顺序性保证
7. 延迟消息、死信队列

#### 非功能需求
- 高吞吐：百万级消息/秒
- 高可用：多副本，故障自动转移
- 低延迟：毫秒级投递
- 可靠性：消息不丢失
- 可扩展：节点可动态增减

### 二、架构设计

```
Producer → Broker集群 → Consumer
            ↓
         ZooKeeper/KRaft（元数据管理）
```

#### 核心组件
1. **Producer**：消息生产者
2. **Broker**：消息服务器，存储和转发消息
3. **Consumer**：消息消费者
4. **NameNode/Controller**：元数据管理、集群协调
5. **ZooKeeper/KRaft**：集群元数据一致性

### 三、核心组件设计

#### 1. 消息存储模型

**主题-分区模型**：
- 每个Topic分为多个Partition
- 每个Partition是一个有序的消息队列
- 消息按Offset唯一标识
- Partition内有序，Topic间无序

**存储结构**：
- 消息顺序追加写入磁盘文件（顺序写性能高）
- 每个Partition对应多个Segment文件
- 消息索引：偏移量索引 + 时间戳索引
- 定期清理过期消息

#### 2. 高可用设计

**多副本机制**：
- 每个Partition有多个副本（通常3个）
- 一个Leader副本处理读写
- 多个Follower副本同步数据
- Leader故障时，从Follower中选举新Leader

**同步策略**：
- **同步复制**：所有副本都写入成功才返回成功（可靠性高，延迟高）
- **异步复制**：Leader写入成功就返回（性能高，有丢数据风险）
- **ISR机制**：维护一个"同步副本列表"，ISR中的副本都同步了才算成功

#### 3. 消息可靠性保证

**生产端**：
- 发送确认机制（acks=0/1/all）
- 重试机制（网络抖动重试）
- 幂等性：消息去重（Producer ID + Sequence Number）

**存储端**：
- 消息落盘（刷盘策略：同步刷盘/异步刷盘）
- 多副本冗余
- 校验和检测

**消费端**：
- 手动提交Offset（消费成功后再提交）
- 消费失败重试
- 死信队列（重试多次失败的消息）

#### 4. 消费模型

**推（Push）vs 拉（Pull）**：
- **Push模式**：Broker主动推消息给Consumer
  - 优点：实时性好
  - 缺点：Consumer处理不过来时会被压垮
- **Pull模式**：Consumer主动从Broker拉消息
  - 优点：Consumer可以按自己的能力消费
  - 缺点：轮询间隔影响实时性
- **Kafka采用Pull模式**，通过长轮询（Long Polling）兼顾实时性

**消费组**：
- 同组内消费者分摊消息（一个消息只被组内一个消费者消费）
- 不同消费组独立消费（广播效果）
- 重平衡（Rebalance）：消费者增减时重新分配Partition

#### 5. 消息顺序性

- **全局有序**：Topic只有一个Partition（牺牲并发度）
- **分区有序**：同一Key的消息发到同一Partition（常用方案）
- 生产端按Key哈希选Partition

### 四、扩展性设计

1. **水平扩展**：增加Broker节点，Partition可迁移
2. **分区扩容**：增加Partition数量提高并行度
3. **消费端扩展**：增加消费者（不超过Partition数）
4. **存储扩展**：大容量磁盘、冷热数据分离
5. **跨地域部署**：镜像同步、联邦集群

### 五、总结

消息队列的核心是**高性能、高可靠、高可用**。存储上采用顺序写+分区模型提高吞吐；可靠性上通过多副本+ACK机制保证消息不丢；可用性上通过Leader选举和故障转移实现。推拉模型各有优劣，主流MQ（Kafka、RocketMQ）都采用Pull模式。

**答案解析**:

设计消息队列考察对分布式系统核心概念的理解。答题时可以以Kafka或RocketMQ为原型展开。重点讲清楚：存储模型（主题-分区-Offset）、高可用（多副本+Leader选举）、可靠性（生产/存储/消费三端保证）、推拉模型对比。注意区分"至少一次"、"至多一次"、"恰好一次"三种投递语义。

**扩展问题**:
- Kafka和RocketMQ有什么区别？
- 如何保证消息不重复消费？
- 消息积压了怎么处理？
- 什么是Exactly-Once语义？如何实现？

## Q4: 设计一个缓存系统

**考察点**: 缓存架构、缓存问题、淘汰策略、一致性

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 键值存储与读取
2. 过期时间设置
3. 缓存淘汰策略
4. 缓存持久化（可选）
5. 分布式缓存（集群模式）

#### 非功能需求
- 高性能：读写延迟<1ms
- 高可用：故障自动转移
- 高并发：支持10万+ QPS
- 内存效率：高内存利用率

### 二、架构设计

```
应用 → 本地缓存(Caffeine/Guava) → 分布式缓存(Redis Cluster) → 数据库
```

#### 多级缓存架构
1. **一级缓存**：本地缓存（进程内），速度最快，容量小
2. **二级缓存**：分布式缓存（Redis），速度快，容量较大
3. **三级存储**：数据库，持久化存储，速度慢

### 三、核心组件设计

#### 1. 缓存读写策略

**Cache Aside（旁路缓存）——最常用**
- **读**：先读缓存，命中返回；未命中读数据库，写入缓存
- **写**：先写数据库，再删除缓存
- 优点：简单，一致性较好
- 缺点：首次请求cache miss

**Write Through（写穿）**
- 写操作同时更新缓存和数据库
- 缓存层封装了数据库写入
- 优点：数据一致性好
- 缺点：写操作延迟高

**Write Back（写回）**
- 写操作只写缓存，异步批量刷回数据库
- 优点：写性能极高
- 缺点：有丢数据风险，实现复杂

#### 2. 缓存三大问题及解决方案

**（1）缓存穿透**
- 问题：查询不存在的数据，请求直接打到数据库
- 解决方案：
  - 缓存空值（设置较短过期时间）
  - 布隆过滤器（Bloom Filter）：提前过滤不存在的key
  - 参数校验，拦截非法请求

**（2）缓存击穿**
- 问题：热点key过期瞬间，大量请求打到数据库
- 解决方案：
  - 热点数据永不过期
  - 互斥锁（Mutex）：只让一个请求去查库并更新缓存
  - 提前续期（后台线程刷新热点key）

**（3）缓存雪崩**
- 问题：大量key同时过期，或缓存宕机，请求全部打到数据库
- 解决方案：
  - 过期时间加随机值，避免同时过期
  - 多级缓存（本地缓存兜底）
  - 服务熔断降级
  - 缓存集群高可用（哨兵/集群模式）

#### 3. 缓存淘汰策略

常见淘汰算法：
- **FIFO**：先进先出，简单但效果差
- **LRU（Least Recently Used）**：最近最少使用，最常用
- **LFU（Least Frequently Used）**：最不经常使用
- **Random**：随机淘汰

**Redis的淘汰策略**：
- noeviction：不淘汰，写满报错
- allkeys-lru：所有key中LRU淘汰
- volatile-lru：设置了过期时间的key中LRU淘汰
- allkeys-lfu：所有key中LFU淘汰
- volatile-lfu：设置了过期时间的key中LFU淘汰
- allkeys-random / volatile-random：随机淘汰

#### 4. 缓存与数据库一致性

**最终一致性方案**：
- 先更新数据库，再删除缓存（Cache Aside）
- 删除缓存失败：重试机制 + 消息队列保证最终删除
- 延时双删：更新数据库→删缓存→延时几百ms→再删一次

**强一致性方案**：
- 分布式锁（性能差，一般不推荐）
- 读写都加锁（牺牲性能）

**结论**：大多数场景用最终一致性即可，极少数强一致性场景考虑不用缓存。

#### 5. 分布式缓存高可用

**Redis Sentinel（哨兵模式）**：
- 监控主从节点
- 自动故障转移
- 适合一主多从架构

**Redis Cluster（集群模式）**：
- 数据分片（16384个槽位）
- 每个分片一主多从
- 自动故障转移
- 水平扩展能力强

### 四、扩展性设计

1. **集群扩展**：Redis Cluster在线扩缩容
2. **热点key处理**：本地缓存 + 多副本
3. **大key拆分**：大value拆分为小key
4. **冷热分离**：冷数据归档，热数据留在缓存
5. **缓存监控**：命中率、延迟、内存使用率、大key检测

### 五、总结

缓存系统的核心是**提升性能**，但也要处理好三大问题（穿透、击穿、雪崩）和一致性问题。推荐使用Cache Aside模式配合最终一致性方案。生产环境用Redis集群保证高可用和可扩展性，热点数据再加一层本地缓存。

**答案解析**:

缓存是系统设计的基础题，也是实际工作中最常用的优化手段。答题要覆盖缓存策略、三大问题、淘汰算法、一致性、高可用等方面。注意区分"缓存击穿"和"缓存雪崩"的区别——前者是一个热点key过期，后者是大量key同时过期或缓存宕机。

- 如何保证缓存和数据库的一致性？
- 缓存命中率低怎么办？

## Q5: 设计一个分布式ID生成器

**考察点**: 分布式ID方案、雪花算法、号段模式、全局唯一

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 生成全局唯一的ID
2. 支持高并发生成
3. ID有序性（趋势递增）

#### 非功能需求
- 高性能：百万级TPS
- 高可用：不能成为单点故障
- 可扩展：支持水平扩展
- 低延迟：生成ID耗时短

### 二、方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **UUID** | 简单，本地生成，无单点 | 无序，占空间大，不可读 | 不需要有序的场景 |
| **数据库自增ID** | 简单，有序 | 单点风险，性能瓶颈 | 小规模系统 |
| **数据库号段模式** | 性能较好，有序 | 依赖数据库，ID不连续 | 大多数业务场景 |
| **雪花算法（Snowflake）** | 高性能，有序，不依赖第三方 | 时钟回拨问题，依赖机器时间 | 高并发分布式系统 |
| **Redis自增** | 性能好，有序 | 依赖Redis，持久化问题 | 已有Redis基础设施 |

### 三、核心方案设计

#### 方案一：雪花算法（Snowflake）

**结构**（64位，最高位不用）：
```
0 | 时间戳(41位) | 机器ID(10位) | 序列号(12位)
```

- **时间戳**：41位，精确到毫秒，可用约69年（2^41 / (1000*3600*24*365) ≈ 69年）
- **机器ID**：10位，支持1024台机器（2^10 = 1024）
- **序列号**：12位，每毫秒最多4096个ID（2^12 = 4096）

**优点**：
- 纯内存计算，性能极高
- ID趋势递增，有序
- 不依赖任何第三方服务
- 可水平扩展

**缺点和解决**：
- **时钟回拨问题**：
  - 方案1：记录上次生成ID的时间戳，回拨时等待或报错
  - 方案2：使用备用号段
  - 方案3：引入ZooKeeper/文件系统记录时间
- **机器ID分配**：
  - 方案1：配置文件手动分配
  - 方案2：启动时向ZooKeeper/注册中心申请
  - 方案3：IP地址哈希取模

#### 方案二：号段模式

**原理**：
- 数据库维护一张号段表，记录当前号段的最大值和步长
- 服务启动时从数据库申请一个号段（如1-1000）
- 号段用完后再申请下一个号段

```sql
CREATE TABLE id_generator (
    biz_type VARCHAR(64) PRIMARY KEY COMMENT '业务类型',
    max_id BIGINT NOT NULL DEFAULT 0 COMMENT '当前最大ID',
    step INT NOT NULL COMMENT '步长',
    update_time DATETIME NOT NULL
);
```

**获取号段的SQL**：
```sql
BEGIN;
UPDATE id_generator SET max_id = max_id + step WHERE biz_type = ?;
SELECT max_id, step FROM id_generator WHERE biz_type = ?;
COMMIT;
```

**优点**：
- ID连续递增
- 性能较好（号段内纯内存计算）
- 实现简单

**缺点**：
- 依赖数据库
- ID不保证绝对连续（服务重启会浪费一个号段）
- 数据库是单点（需要高可用）

**优化**：
- 双号段缓冲：当前号段快用完时，提前加载下一个号段
- 数据库主从保证高可用

### 四、高可用设计

#### 雪花算法的高可用
- 多节点部署，每个节点不同的机器ID
- 机器ID自动分配（注册中心）
- 时钟回拨检测与处理

#### 号段模式的高可用
- 数据库主从架构
- 多服务节点，每个节点独立申请号段
- 号段预加载，避免申请时阻塞

### 五、扩展性设计

1. **水平扩展**：增加节点即可（雪花算法增加机器ID，号段模式增加服务实例）
2. **业务隔离**：不同业务类型独立号段，互不影响
3. **动态步长**：根据QPS动态调整号段大小
4. **监控告警**：监控号段使用率、生成QPS、异常

### 六、总结

分布式ID生成器的核心要求是**全局唯一、高性能、高可用**。雪花算法性能最好但要处理时钟回拨问题，号段模式简单可靠但依赖数据库。实际项目中，中小团队推荐号段模式（如美团Leaf号段模式），高并发场景推荐雪花算法（如百度UidGenerator）。

**答案解析**:

分布式ID是分布式系统的基础组件，面试常考。答题时要先对比几种方案，再重点讲雪花算法和号段模式。雪花算法是重点——要能画出64位结构图，讲出各部分位数和作用。时钟回拨问题是雪花算法的经典考点。

**扩展问题**:
- 雪花算法的时间戳用完了怎么办？
- 时钟回拨怎么处理？有哪些方案？
- 号段模式如果数据库挂了怎么办？
- 如何生成有业务含义的ID（如带时间、带业务标识）？

## Q6: 设计一个限流器（限流算法）

**考察点**: 限流算法、分布式限流、高可用防护

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 限制接口/服务的请求速率
2. 支持不同维度的限流（用户、IP、接口）
3. 动态调整限流阈值
4. 限流后的处理（拒绝、排队、降级）

#### 非功能需求
- 高性能：限流本身不能成为瓶颈
- 高可用：限流服务挂了不影响业务
- 准确性：限流精度要高

### 二、常见限流算法

#### 1. 固定窗口计数器（Fixed Window）

**原理**：将时间分成固定大小的窗口（如1秒），每个窗口内计数，超过阈值则限流。

**优点**：实现简单，内存占用小
**缺点**：存在"临界问题"——窗口边界处可能通过2倍流量

**临界问题举例**：限流100次/秒，在第0.9秒到第1.9秒之间可能通过200次请求。

#### 2. 滑动窗口计数器（Sliding Window）

**原理**：将时间窗口分成更小的格子，滑动计算当前窗口内的请求数。

**优点**：解决了固定窗口的临界问题，精度较高
**缺点**：实现稍复杂，需要存储多个小窗口的计数

#### 3. 漏桶算法（Leaky Bucket）

**原理**：请求像水一样注入漏桶，漏桶以固定速率流出。桶满了则拒绝新请求。

**优点**：
- 流量整形：输出速率恒定
- 平滑突发流量
**缺点**：
- 无法应对突发流量（桶的容量有限）
- 不能有效利用资源

#### 4. 令牌桶算法（Token Bucket）

**原理**：以固定速率往桶里放令牌，请求需要拿到令牌才能通过。桶有最大容量，满了就不再放。

**优点**：
- 限制平均速率，同时允许一定程度的突发
- 可以处理突发流量
- 最常用的限流算法

**缺点**：
- 实现稍复杂
- 初始状态可能有突发（桶满的状态）

#### 算法对比

| 算法 | 实现难度 | 精度 | 突发流量 | 适用场景 |
|------|---------|------|----------|----------|
| 固定窗口 | 简单 | 低（有临界问题） | 不支持 | 简单限流 |
| 滑动窗口 | 中等 | 较高 | 不支持 | 较精确的计数限流 |
| 漏桶 | 简单 | 高 | 不支持（平滑输出） | 流量整形 |
| 令牌桶 | 中等 | 高 | 支持（桶满时突发） | 大多数场景，接口限流 |

### 三、限流架构设计

#### 1. 单机限流
- 实现：Guava RateLimiter（令牌桶）
- 适用：单实例服务，简单场景
- 缺点：多实例时总限流不好控制

#### 2. 分布式限流

**方案一：Redis + Lua脚本**
- 用Redis实现滑动窗口或令牌桶
- Lua脚本保证原子性
- 优点：准确，可动态调整
- 缺点：依赖Redis，有网络开销

**Redis滑动窗口实现（Lua脚本）**：
```lua
-- KEYS[1]: 限流key
-- ARGV[1]: 窗口大小（毫秒）
-- ARGV[2]: 限流阈值
-- ARGV[3]: 当前时间戳
local key = KEYS[1]
local window = tonumber(ARGV[1])
local limit = tonumber(ARGV[2])
local now = tonumber(ARGV[3])

-- 移除窗口外的记录
redis.call('ZREMRANGEBYSCORE', key, 0, now - window)
-- 统计当前窗口内的请求数
local count = redis.call('ZCARD', key)
if count < limit then
    -- 添加当前请求
    redis.call('ZADD', key, now, now .. math.random())
    -- 设置过期时间
    redis.call('EXPIRE', key, window / 1000 + 1)
    return 1
else
    return 0
end
```

**方案二：网关层限流**
- 在Nginx/网关层实现限流
- 如Nginx的limit_req_zone（漏桶算法）
- 优点：在入口处限流，保护后端
- 缺点：粒度较粗

**方案三：服务端本地限流 + 总控调整**
- 每个服务实例本地限流
- 总QPS = 单实例QPS × 实例数
- 实例数变化时动态调整单实例阈值

### 四、限流策略

#### 限流后的处理方式
1. **直接拒绝**：返回429 Too Many Requests
2. **排队等待**：放入队列，延迟处理（漏桶）
3. **服务降级**：返回降级结果或缓存数据
4. **弹性伸缩**：触发扩容（云原生场景）

#### 限流维度
- 按用户ID限流
- 按IP限流
- 按接口限流
- 按应用/服务限流
- 多级限流：网关层 → 服务层 → 资源层

### 五、扩展性设计

1. **动态调整**：限流阈值可动态配置（配置中心）
2. **多级限流**：入口层 + 服务层 + 资源层多层防护
3. **监控告警**：实时监控限流次数、被限流的请求
4. **降级开关**：可手动关闭限流（紧急情况）
5. **热点自适应**：根据流量自动调整限流阈值

### 六、总结

限流是保护系统的重要手段。令牌桶算法是最常用的限流算法，兼顾了平均速率和突发流量。分布式限流推荐用Redis + Lua实现滑动窗口。实际系统中通常是多层限流：网关层粗粒度限流 + 服务层精细限流。限流的目的不是为了拒绝用户，而是为了保护系统不被打垮。

**答案解析**:

限流是高可用系统设计的基础组件。答题时要讲清楚四种算法的原理、优缺点和对比，重点是令牌桶和漏桶的区别。分布式限流要讲Redis + Lua的实现思路。注意区分"限流"和"熔断降级"——限流是主动控制流量，熔断是故障时的保护机制。

**扩展问题**:
- 令牌桶和漏桶的区别是什么？各适用于什么场景？
- 分布式限流中，Redis挂了怎么办？
- 如何实现精确到毫秒级的限流？
- 什么是自适应限流？如何实现？

## Q7: 设计一个排行榜系统

**考察点**: 排行榜实现、Redis ZSet、更新与查询性能

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 用户得分更新
2. 查询排行榜Top N
3. 查询用户排名
4. 支持多维度排行榜（日榜、周榜、总榜）
5. 同分排名处理

#### 非功能需求
- 高并发：得分更新频繁
- 低延迟：排行榜查询要快
- 实时性：得分更新后排名要及时更新

### 二、方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **数据库ORDER BY** | 简单 | 性能差，数据量大时慢 | 小数据量 |
| **Redis ZSet** | 高性能，O(logN)插入和查询 | 内存占用，大数据量成本高 | 大多数场景 |
| **跳表+分段** | 可扩展，支持超大规模 | 实现复杂 | 超大规模排行榜 |
| **分桶排序** | 分数范围有限时性能极高 | 分数范围大时不适用 | 积分/等级类 |

### 三、核心方案设计

#### 方案一：Redis ZSet（推荐）

**核心数据结构**：
- ZSet（有序集合）：每个元素有一个score（分数），按score排序
- 内部实现：跳表（Skip List）+ 哈希表
- 时间复杂度：插入O(logN)，查询排名O(logN)，Top N O(logN + M)

**常用命令**：
```bash
# 添加/更新分数
ZADD leaderboard 1000 user1
ZADD leaderboard 2000 user2

# 增加分数
ZINCRBY leaderboard 100 user1

# 查询Top 10（从高到低）
ZREVRANGE leaderboard 0 9 WITHSCORES

# 查询用户排名（从0开始）
ZREVRANK leaderboard user1

# 查询某用户的分数
ZSCORE leaderboard user1

# 查询某分数段的用户数
ZCOUNT leaderboard 1000 2000
```

**多维度排行榜**：
- 日榜：`leaderboard:daily:20260728`
- 周榜：`leaderboard:weekly:2026W30`
- 总榜：`leaderboard:total`
- 每个维度一个ZSet，独立维护

**同分排名处理**：
- 方案1：分数 + 时间戳组合（分数相同时先到的排前面）
  - `score = 实际分数 * 1000000 + (MAX_TIMESTAMP - 当前时间戳)`
- 方案2：同分数按用户ID/等级等次级排序

### 四、架构设计

```
用户操作 → 业务服务 → 写MQ → 排行榜服务 → Redis ZSet
              ↓
           读Redis → 返回排行榜
```

#### 读写流程
1. **写路径**：用户得分变化 → 发消息 → 异步更新Redis ZSet
   - 为什么异步？解耦，不影响主流程
   - 为什么用MQ？削峰，保证最终一致
2. **读路径**：直接读Redis，高性能
3. **持久化**：Redis持久化（RDB+AOF），同时数据库存原始记录

### 五、扩展性设计

#### 1. 大数据量处理（百万级以上用户）

**分段排行榜**：
- 按分数段分桶（如0-1000, 1000-2000...）
- 每段一个ZSet
- 查询Top N只查高分段
- 优点：减少单个ZSet大小，提高性能

**分区分片**：
- 按用户ID哈希分到多个ZSet
- 查询Top N时合并结果
- 类似归并排序的思路

#### 2. 历史榜单归档
- 每日/每周生成新榜单
- 历史榜单可以转存到数据库或对象存储
- 只保留近期榜单在Redis中

#### 3. 缓存优化
- 排行榜Top 100可以本地缓存（1秒过期）
- 减少Redis的压力
- 可接受秒级延迟的场景

#### 4. 数据库兜底
- Redis中存热数据，数据库存全量数据
- Redis挂了可以从数据库恢复
- 冷数据查询走数据库

### 六、总结

排行榜系统的核心是**高性能的排序和更新**。Redis ZSet是最常用的解决方案，基于跳表实现，插入和查询都是O(logN)复杂度。中小规模的排行榜直接用单个ZSet即可，超大规模可以考虑分段或分片。写入用MQ异步化，读取直接走Redis保证性能。

**答案解析**:

Redis ZSet是排行榜的标准答案。答题时要讲清楚ZSet的实现原理（跳表）、时间复杂度、常用命令。还要考虑多维度榜单、同分处理、大数据量扩展等问题。注意区分实时排行榜和离线排行榜的不同设计思路。

**扩展问题**:
- Redis ZSet的底层实现是什么？为什么用跳表不用红黑树？
- 如果有一亿用户，一个ZSet存得下吗？怎么办？
- 排行榜的实时性要求很高，怎么保证？
- 如何实现"附近排名"（查我前后各10名）？

## Q8: 设计一个微博/Twitter信息流

**考察点**: Feed流设计、推拉模型、时间线、高并发

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 用户可以发布微博/推文
2. 用户可以关注其他用户
3. 首页信息流（按时间倒序展示关注的人的微博）
4. 点赞、评论、转发
5. 热搜/推荐流

#### 非功能需求
- 高并发：大V发推瞬间百万级阅读
- 低延迟：刷Feed要快
- 高可用：服务不能宕机
- 用户规模：亿级用户，日活千万级

### 二、Feed流核心模型

#### 1. 推模式（Push Model / Write Fan-out）

**原理**：用户发布微博时，同步（或异步）推送到所有粉丝的收件箱（Feed流缓存）。

**优点**：
- 读速度快（直接读自己的Feed缓存）
- 读取时不需要计算

**缺点**：
- 写放大：大V有千万粉丝，写一次要推送千万次
- 存储量大：每个用户都有自己的Feed缓存
- 新关注/取关需要同步历史数据

**适用场景**：粉丝数不多，实时性要求高

#### 2. 拉模式（Pull Model / Read Fan-out）

**原理**：用户刷Feed时，实时从关注的所有人的发件箱中拉取最新微博，聚合排序。

**优点**：
- 写简单：发布微博只写一份
- 存储节省：不需要为每个用户存Feed
- 新关注/取关不用处理历史数据

**缺点**：
- 读复杂：每次刷Feed都要聚合排序
- 读延迟高：关注的人多时更明显
- 不适合关注人数多的用户

**适用场景**：关注人数少，写多读少

#### 3. 推拉结合模式（推荐）

**原理**：
- 普通用户（粉丝少）：推模式
- 大V用户（粉丝多）：拉模式
- 用户刷Feed时：自己的Feed缓存（推的内容） + 大V的最新微博（拉的内容），合并排序

**优点**：
- 兼顾性能和存储
- 大V发博不会压垮系统
- 普通用户的Feed读取仍然很快

### 三、架构设计

```
用户发布 → 微博服务 → 发件箱(发微博表) → MQ → Feed推送服务 → 收件箱(Feed缓存)
                                                          ↓
用户刷Feed ← Feed服务 ← 合并排序 ← 大V拉取 + 收件箱读取
```

#### 核心组件
1. **微博服务**：发布、存储微博内容
2. **用户关系服务**：关注、粉丝关系管理
3. **Feed服务**：Feed流生成、查询
4. **推送服务**：异步推送微博到粉丝Feed
5. **存储层**：MySQL存内容，Redis存Feed缓存

### 四、核心组件设计

#### 1. 存储设计

**微博内容表**（按用户ID分库分表）：
```sql
CREATE TABLE post (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    content TEXT NOT NULL,
    created_at DATETIME NOT NULL,
    like_count INT DEFAULT 0,
    comment_count INT DEFAULT 0,
    repost_count INT DEFAULT 0,
    INDEX idx_user_time (user_id, created_at)
);
```

**用户关系表**（关注表、粉丝表，各存一份）：
```sql
CREATE TABLE follow (
    user_id BIGINT,
    follow_user_id BIGINT,
    created_at DATETIME,
    PRIMARY KEY (user_id, follow_user_id)
);
```

**Feed收件箱**（Redis ZSet或List）：
- Key: `feed:inbox:{user_id}`
- Value: 微博ID，按时间排序
- 每个用户的收件箱只存最近N条（如1000条）

#### 2. Feed推送流程

发布微博后：
1. 写入微博表
2. 获取粉丝列表（过滤掉大V，只推给普通用户）
3. 异步批量推送到各粉丝的收件箱
4. 大V的微博不拉，读的时候再拉

#### 3. Feed拉取流程

用户刷Feed：
1. 读取自己的收件箱（推过来的普通用户微博）
2. 拉取关注的大V的最新微博
3. 两部分合并，按时间排序
4. 返回给用户
4. 记录最后阅读位置，下拉加载更多

#### 4. 大V判定与处理
- 粉丝数超过阈值（如10万）的用户视为大V
- 大V发博不走推送，读时拉取
- 大V的最新微博可以缓存（如缓存最新100条）

### 五、扩展性设计

1. **冷热分离**：热数据（近期微博）存Redis，冷数据存数据库/ES
2. **多级缓存**：Feed列表本地缓存 + Redis缓存
3. **推荐流**：热搜、推荐流用算法排序（非时间序），走推荐系统
4. **分库分表**：按用户ID哈希分库分表
5. **CDN加速**：图片、视频等媒体资源走CDN

### 六、总结

微博/Twitter信息流的核心是**Feed流的推拉模型选择**。纯推和纯拉都有问题，工业界通常采用推拉结合——普通用户推，大V拉。写路径用MQ异步推送，读路径合并推和拉的结果。核心是用空间换时间，用异步换体验。

**答案解析**:

Feed流设计是社交类系统的经典面试题。答题的关键是讲清楚推拉模型的对比和推拉结合的方案。要体现出对"大V"这个特殊角色的处理——大V是推模式的瓶颈，需要特殊处理。另外，还要提到存储设计、分库分表、缓存等工程细节。

**扩展问题**:
- 大V的定义标准是什么？如何动态调整？
- 用户新关注了一个人，Feed流怎么处理历史微博？
- Feed流的排序除了时间序还有什么方式？
- 如何处理已删除/隐藏的微博？

## Q9: 设计一个聊天系统（IM）

**考察点**: 即时通讯、消息可靠性、在线状态、长连接

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 单聊和群聊
2. 消息发送与接收
3. 消息已读/未读状态
4. 在线状态显示
5. 消息历史记录
6. 消息推送（离线消息）

#### 非功能需求
- 低延迟：消息送达要快（<100ms）
- 高可靠：消息不丢、不重、不乱序
- 高并发：百万级同时在线
- 高可用：服务不宕机

### 二、架构设计

```
客户端 → 接入层(WebSocket/TCP) → 消息路由 → 消息服务 → 存储
              ↓
            连接管理器（维护用户-连接映射）
```

#### 整体架构
1. **接入层**：长连接网关，维护客户端连接
2. **路由层**：消息路由，找到目标用户所在的接入节点
3. **服务层**：消息处理、会话管理、群组管理
4. **存储层**：消息存储、用户资料、关系链
5. **推送层**：离线消息推送（APNs/FCM/厂商推送）

### 三、核心组件设计

#### 1. 长连接接入

**协议选择**：
- **WebSocket**：Web端，基于HTTP升级
- **TCP自定义协议**：移动端，更轻量、更可控
- **QUIC/HTTP3**：新一代，减少握手延迟

**连接管理**：
- 用户连接到哪个接入节点是随机的
- 需要维护"用户ID → 接入节点ID"的映射（存在Redis/一致性哈希）
- 心跳检测：客户端定时发心跳，服务端检测超时断开

**接入层设计**：
- 多节点部署，水平扩展
- DNS轮询/智能DNS分配接入节点
- 每台机器支持10万+连接（调优内核参数）

#### 2. 消息可靠性保证

**消息投递流程**：
1. 发送方发消息到服务端
2. 服务端返回ACK（确认收到）
3. 服务端推送给接收方
4. 接收方返回ACK（确认收到）
5. 服务端标记消息已送达

**消息不丢**：
- 发送方超时未收到ACK则重试
- 服务端消息持久化后再ACK
- 消息ID去重（防止重试导致重复）

**消息不重**：
- 每条消息有唯一ID（客户端生成）
- 接收方去重（按消息ID）

**消息有序**：
- 单聊：按发送时间排序（服务端时间）
- 群聊：群内有递增序号（seq）
- 客户端按seq排序展示

#### 3. 消息存储

**存储选型**：
- **近期消息（热数据）**：Redis（最近几天）
- **历史消息（冷数据）**：HBase/Cassandra/MySQL
- **消息同步**：用消息队列同步到历史库

**漫游消息**：
- 用户换设备也能看到历史消息
- 每个会话保存最后读取位置（last_read_seq）

#### 4. 群聊设计

**群消息扩散**：
- 方案1：写扩散（群消息存每个成员的收件箱）
  - 读快，写慢（群大了写放大严重）
- 方案2：读扩散（群消息只存一份，成员各自拉取）
  - 写快，读慢
- **实际方案**：小群写扩散，大群读扩散

**群类型**：
- 普通群（<100人）：写扩散
- 大群/万人群：读扩散 + 推送通知

#### 5. 在线状态

**状态类型**：在线、离线、忙碌、隐身

**实现方式**：
- 用户连接建立时标记为在线
- 连接断开时（心跳超时）标记为离线
- 状态存在Redis，订阅/发布通知变更

### 四、扩展性设计

1. **接入层扩展**：水平扩展，增加节点即可
2. **消息路由**：一致性哈希，用户路由到固定节点
3. **分库分表**：消息表按用户ID或会话ID分库分表
4. **消息队列**：Kafka解耦消息处理和存储
5. **多机房部署**：就近接入，异地容灾

### 五、总结

IM系统的核心是**长连接管理**和**消息可靠性**。接入层维护海量长连接，消息路由负责找到目标用户的连接节点。可靠性靠"三次握手"（发送ACK、送达ACK、已读回执）和消息持久化保证。群聊的关键是选择写扩散还是读扩散，取决于群规模。

**答案解析**:

IM系统是比较有难度的系统设计题。答题时要讲清楚长连接、消息可靠性、在线状态这几个核心点。消息可靠性是重点——要从消息不丢、不重、不乱序三个维度展开。注意区分"消息发送成功"和"消息送达对方"是两个不同的确认。

**扩展问题**:
- 如何保证消息的时序性？
- 群聊消息的已读状态怎么实现？
- 一台接入服务器能承载多少连接？如何优化？
- 消息已读功能如何实现？会有什么性能问题？

## Q10: 设计一个搜索系统

**考察点**: 搜索引擎架构、倒排索引、相关性排序、分布式搜索

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 全文检索：关键词搜索文档
2. 相关性排序：最相关的结果排前面
3. 多条件过滤：分类、时间、标签等过滤
4. 搜索建议/自动补全
5. 高亮显示
6. 分页查询

#### 非功能需求
- 高性能：搜索响应<200ms
- 可扩展：数据量增长可水平扩展
- 相关性：搜索结果要准确
- 实时性：数据更新后多久能搜到

### 二、架构设计

```
数据来源 → 数据采集 → 索引构建 → 索引集群 → 搜索服务 → 用户
              ↓
            词典/分词器/排序模型
```

#### 核心模块
1. **数据采集层**：爬取/同步待搜索的数据
2. **索引构建层**：分词、建立倒排索引
3. **索引存储层**：分布式索引集群
4. **搜索服务层**：查询解析、检索、排序
5. **业务层**：搜索建议、统计、AB测试

### 三、核心组件设计

#### 1. 倒排索引（Inverted Index）

**原理**：
- 正排索引：文档ID → 关键词列表
- 倒排索引：关键词 → 包含该词的文档ID列表

**倒排表结构**：
```
关键词 → [文档ID1, 文档ID2, ...] + 词频 + 位置信息
```

**倒排索引的构建过程**：
1. 文档分词（中文分词如IK、Jieba）
2. 建立词项词典（Term Dictionary）
3. 建立倒排列表（Posting List）
4. 索引压缩（差值编码、位图压缩）

#### 2. 分词器

**中文分词方法**：
- 基于词典匹配：正向/反向最大匹配（简单但歧义多）
- 基于统计：HMM、CRF（准确率高）
- 基于深度学习：BiLSTM+CRF、BERT（最先进）

**常用分词器**：
- IK Analyzer、Jieba、HanLP（中文）
- Standard Analyzer、English Analyzer（英文）

#### 3. 相关性排序（Ranking）

**TF-IDF**：
- TF（词频）：词在文档中出现的频率
- IDF（逆文档频率）：词在所有文档中的稀有程度
- TF-IDF = TF × IDF
- 衡量一个词对文档的重要程度

**BM25**：
- TF-IDF的改进版，考虑了文档长度等因素
- Elasticsearch/Lucene的默认排序算法
- 更符合实际搜索场景

**深度学习排序**：
- Learning to Rank（LTR）：用机器学习训练排序模型
- 语义向量检索：用Embedding做语义匹配（Dense Retrieval）
- 多阶段排序：粗排（召回）→ 精排 → 重排

#### 4. 分布式搜索架构

**Elasticsearch架构**：
- **Index**：索引，类似数据库的表
- **Shard**：分片，索引分成多个分片分布在不同节点
- **Replica**：副本，每个分片有多个副本
- **Node**：节点，每个节点存部分分片
- 查询时协调节点汇总各分片结果

**查询流程**：
1. 查询解析（Query Parsing）
2. 改写和优化（Query Rewrite）
3. 倒排索引查询（Scatter）
4. 结果合并排序（Gather）
5. 返回Top N结果

#### 5. 搜索建议（Suggestion）

**实现方式**：
- Trie树/前缀树：前缀匹配
- 热门搜索词表：按热度排序推荐
- 纠错建议：编辑距离（拼写纠错）
- Elasticsearch的Completion Suggester

### 四、扩展性设计

1. **水平扩展**：增加节点，分片再平衡
2. **读写分离**：主分片写，副本分片读
3. **冷热分离**：热数据SSD，冷数据普通存储
4. **多级缓存**：热门搜索结果缓存
5. **近实时搜索**：索引刷新间隔可调（如1秒）

### 五、总结

搜索系统的核心是**倒排索引**和**相关性排序**。倒排索引实现了从关键词到文档的快速查找，排序算法决定了搜索结果的质量。工业界常用Elasticsearch作为搜索基础设施，它基于Lucene，支持分布式和高可用。现代搜索系统通常是"召回 + 精排 + 重排"的多阶段架构。

**答案解析**:

搜索系统是比较有深度的系统设计题。答题时要从倒排索引原理讲起，然后扩展到分词、排序、分布式架构。重点是倒排索引的原理和查询流程。如果能提到多阶段排序（召回→精排→重排）和语义搜索，会很加分。

**扩展问题**:
- 倒排索引如何做复合查询（AND/OR/NOT）？
- Elasticsearch的深度分页问题怎么解决？
- 什么是倒排索引的压缩？为什么需要压缩？
- 如何处理同义词和多义词？

## Q11: 设计一个支付系统

**考察点**: 支付流程、资金安全、幂等性、分布式事务

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 一、需求分析

#### 功能需求
1. 用户发起支付
2. 对接第三方支付渠道（微信、支付宝、银联等）
3. 支付状态回调与通知
4. 退款
5. 对账
6. 资金流水记录

#### 非功能需求
- 高可用：支付不能宕机
- 数据一致性：资金不能出错
- 安全性：防篡改、防重放、防钓鱼
- 可追溯：每笔资金流向可查

### 二、架构设计

```
用户 → 业务服务 → 支付网关 → 支付核心 → 支付渠道(微信/支付宝)
                          ↓
                     账务系统/对账系统
```

#### 核心模块
1. **支付网关**：对外提供支付接口，参数校验、签名验证
2. **支付核心**：支付状态机、订单管理、渠道路由
3. **渠道对接层**：对接各第三方支付渠道
4. **账务系统**：记账、资金流水
5. **对账系统**：与渠道对账，差错处理
6. **风控系统**：风险识别和拦截

### 三、核心组件设计

#### 1. 支付核心流程

**标准支付流程**：
1. 用户提交订单 → 业务系统创建订单
2. 业务系统调用支付服务创建支付单
3. 支付服务生成支付链接/二维码返回
4. 用户完成支付
5. 第三方支付渠道异步回调支付结果
6. 支付服务更新支付状态
7. 支付服务通知业务系统支付结果
8. 业务系统更新订单状态

**关键设计点**：
- **支付单号**：全局唯一，幂等键
- **支付状态机**：待支付 → 支付中 → 支付成功/支付失败/已关闭
- **同步返回 + 异步通知**：用户跳转是同步，支付结果是异步回调

#### 2. 幂等性设计

**为什么需要幂等**：
- 用户重复点击支付
- 第三方回调重复通知
- 网络超时重试

**实现方案**：
- 唯一支付单号作为幂等键
- 数据库唯一索引防重复
- 状态机约束：只有待支付状态才能发起支付
- 接口加防重Token

#### 3. 数据一致性

**分布式事务问题**：
- 业务订单和支付单不在同一个数据库
- 支付成功和业务状态更新不在同一个事务

**解决方案：最终一致性 + 补偿**

**方案一：本地消息表**
```
本地事务：
1. 更新支付状态
2. 写入消息表（待通知）

异步任务：
3. 扫描消息表，通知业务系统
4. 通知成功标记为已通知
5. 失败重试（有最大重试次数）
```

**方案二：消息队列事务消息**
- RocketMQ事务消息
- 半消息 → 执行本地事务 → 提交/回滚消息

**方案三：TCC**
- Try-Confirm-Cancel
- 实现复杂，一般不用

#### 4. 安全性设计

- **签名验证**：请求和回调都做签名校验（RSA/MD5）
- **防重放攻击**：时间戳 + nonce
- **HTTPS加密**：传输层加密
- **敏感信息脱敏**：卡号、身份证等不存明文
- **风控拦截**：异常交易识别和拦截
- **操作日志**：所有关键操作留痕

#### 5. 对账系统

**为什么要对账**：
- 防止丢单、错单
- 保证资金正确
- 发现异常交易

**对账流程**：
1. T+1下载渠道对账单
2. 与本地支付单比对
3. 发现差异（长款、短款、状态不一致）
4. 差错处理（补单、退款、人工介入）

### 四、扩展性设计

1. **多渠道接入**：抽象统一的渠道接口，新渠道只需实现接口
2. **渠道路由**：根据金额、渠道可用性、费率智能路由
3. **分库分表**：支付单按用户ID或时间分库分表
4. **灰度发布**：新渠道/新功能灰度放量
5. **监控告警**：支付成功率、回调延迟、对账差异

### 五、总结

支付系统的核心是**资金安全和数据一致性**。设计原则是：**宁可错杀，不可放过；宁可慢，不可错**。关键技术点：幂等设计、状态机、异步通知、最终一致性、对账。支付系统是金融级系统，对可靠性要求极高，每一步都要考虑异常情况和补偿机制。

**答案解析**:

支付系统是业务系统设计中的高频面试题，重点考察对分布式事务、幂等性、数据一致性的理解。答题时要突出"资金安全第一"的思想。核心要点：支付流程、幂等设计、最终一致性、对账机制。不要只讲正常流程，异常处理才是重点——超时、重试、重复回调、对账差错等。

#### 5. 推荐系统

**推荐架构**：
- **召回层**：多路召回（热门、分类、协同过滤、向量召回）
- **排序层**：精排模型（CTR预估）
- **重排层**：多样性、新颖性调整

**数据来源**：
- 用户行为：观看、点赞、收藏、评论
- 用户画像：年龄、性别、兴趣标签
- 视频特征：分类、标签、质量分

### 四、扩展性设计

1. **存储扩展**：对象存储天然可扩展，冷热分离降成本

### 五、总结

视频网站的核心是**视频处理**和**分发加速**。上传后需要经过转码生成多种清晰度的格式，播放靠CDN加速。存储是大头，需要对象存储+冷热分离。推荐系统是视频平台的核心竞争力，通常是多路召回+精排+重排的多阶段架构。

### 二、架构设计

```
用户 → 上传/下载服务 → 对象存储
            ↓
         元数据服务 → MySQL/Redis
```

### 三、核心组件设计

#### 1. 文件上传

**分片上传**：
- 大文件切成小块（如4MB一片）
- 分片并发上传，提高速度
- 上传完成后合并分片

**断点续传**：
- 记录已上传的分片
- 中断后从上次位置继续
- 用文件MD5 + 分片索引标记进度

**秒传**：
- 上传前计算文件MD5
- 如果服务器已有相同MD5的文件，直接复用
- 只存一份物理文件，逻辑上是多个用户的文件
- 节省存储空间 + 提升上传体验

#### 2. 文件存储

**对象存储**：
- 物理文件存在对象存储（OSS/S3）
- 按内容哈希命名（去重）

**元数据存储**：
- 文件ID、文件名、大小、类型、MD5、路径、所属用户等
- 存MySQL，按用户ID分库分表

**存储优化**：
- **去重**：相同内容只存一份（MD5/SHA1判断）
- **压缩**：可压缩文件压缩存储
- **冷热分离**：常用文件存热存储，长期不用转冷存储
- **多副本**：对象存储自带多副本

#### 3. 文件分享

**分享机制**：
- 生成分享链接 + 提取码
- 设置有效期、访问次数限制
- 分享的文件不复制，只是增加一个引用

#### 4. 多端同步

**同步机制**：
- 增量同步：只同步变化的文件
- 版本号/时间戳判断是否需要同步
- 冲突处理：文件同时修改时的冲突策略

### 四、扩展性设计

1. **存储扩展**：对象存储水平扩展
2. **元数据扩展**：分库分表
3. **CDN加速下载**：热门文件走CDN
4. **上传加速**：就近接入点上传
5. **弹性伸缩**：上传下载服务无状态，可水平扩展

### 五、总结

网盘系统的核心是**文件存储和传输优化**。关键技术：分片上传、断点续传、秒传（去重）。存储上用对象存储存物理文件，数据库存元数据。秒传技术既能提升用户体验又能节省存储成本，是网盘的标志性技术。

网盘系统相对简单，重点是文件上传的几个关键技术：分片上传、断点续传、秒传。答题时把这几个点讲清楚就差不多了。可以顺带提一下存储优化和元数据设计。

## Q16: 什么是分布式事务，解决方案

**考察点**: 分布式事务理论、常见方案对比、适用场景

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是分布式事务

分布式事务是指事务的参与者、支持事务的服务器、资源服务器等分别位于不同的节点上，且属于不同的应用。分布式事务需要保证多个节点上的操作要么全部成功，要么全部失败。

简单说：**一个事务操作涉及多个数据库/服务，要保证ACID特性**。

### 分布式事务的产生原因

- 微服务架构：一个业务操作跨多个服务
- 分库分表：一个操作跨多个数据库
- 异构数据源：操作不同类型的数据库

### 分布式事务解决方案

#### 方案一：2PC（两阶段提交）

**两阶段**：
1. **准备阶段（Prepare）**：协调者询问所有参与者是否可以提交事务，参与者执行事务但不提交，返回Yes/No
2. **提交阶段（Commit/Rollback）**：
   - 所有参与者都返回Yes → 协调者通知所有参与者提交
   - 有任何一个返回No → 协调者通知所有参与者回滚

**优点**：
- 强一致性
- 实现相对简单

**缺点**：
- 同步阻塞：所有参与者阻塞等待协调者指令
- 单点故障：协调者挂了就卡住了
- 数据不一致：提交阶段网络异常可能导致部分提交部分没提交
- 性能差：锁资源时间长

**代表**：XA协议、Seata AT模式

#### 方案二：3PC（三阶段提交）

在2PC基础上增加了一个阶段：
1. **CanCommit**：询问是否可以提交
2. **PreCommit**：预提交
3. **DoCommit**：真正提交

引入了超时机制，减少阻塞。但仍然存在数据不一致问题，实际用得少。

#### 方案三：TCC（Try-Confirm-Cancel）

**三个阶段**：
1. **Try**：尝试执行业务，预留资源
2. **Confirm**：确认执行业务（真正提交）
3. **Cancel**：取消执行业务（回滚释放资源）

**与2PC的区别**：
- 2PC是数据库层的，TCC是业务层的
- TCC需要每个服务实现Try/Confirm/Cancel三个接口

**优点**：
- 性能较好（锁粒度小，时间短）
- 最终一致性

**缺点**：
- 对业务侵入大，每个服务要写三个接口
- 实现复杂，要考虑幂等、空回滚、悬挂等问题

**适用场景**：对性能要求高的核心业务（如支付、交易）

#### 方案四：本地消息表 + 可靠消息最终一致性

**原理**：
1. 在同一个本地事务中，执行业务操作 + 写入消息表
2. 后台定时任务扫描消息表，发送消息到MQ
3. 消费者消费消息，执行本地事务
4. 消费成功标记消息为已完成，失败重试

**优点**：
- 实现简单
- 对业务侵入较小
- 性能好

**缺点**：
- 消息表和业务表耦合
- 只适用于最终一致性场景

#### 方案五：事务消息（RocketMQ）

**原理**：
1. 发送半消息（Half Message）到MQ
2. MQ返回确认后，执行本地事务
3. 根据本地事务结果，提交或回滚消息
4. 事务状态未知时，MQ回查事务状态

**优点**：
- 不用写本地消息表
- 性能好
- 与业务解耦

**缺点**：
- 依赖RocketMQ
- 需要实现事务回查接口

#### 方案六：Saga模式

**原理**：
- 长事务拆分为多个本地事务
- 每个本地事务有对应的补偿操作
- 顺序执行，某个失败则反向执行补偿

**两种实现方式**：
1. **编排式（Choreography）**：各服务通过事件驱动，自己监听和触发
2. **协调式（Orchestration）**：有一个协调者统一指挥

**优点**：
- 适合长事务
- 性能较好

**缺点**：
- 隔离性差（中间状态可见）
- 补偿逻辑复杂

**适用场景**：长流程业务（如订单创建→库存扣减→支付→物流）

### 方案对比与选型

| 方案 | 一致性 | 性能 | 实现复杂度 | 业务侵入 | 适用场景 |
|------|--------|------|-----------|----------|----------|
| 2PC/XA | 强一致 | 差 | 中 | 低 | 传统单体、并发不高 |
| TCC | 最终一致 | 好 | 高 | 高 | 核心交易、性能要求高 |
| 本地消息表 | 最终一致 | 好 | 低 | 中 | 大多数业务场景 |
| 事务消息 | 最终一致 | 好 | 中 | 低 | 有RocketMQ基础设施 |
| Saga | 最终一致 | 好 | 高 | 中 | 长事务、多服务编排 |

### 选型建议

1. **能不用分布式事务就不用**：尽量在设计层面避免
2. **大多数场景**：最终一致性 + 消息队列（本地消息表或事务消息）
3. **核心交易场景**：TCC（性能要求高）或 Seata AT（快速接入）
4. **长流程业务**：Saga模式

**答案解析**:

分布式事务是后端面试的高频难题。答题时要先讲清楚什么是分布式事务、为什么会有这个问题，然后逐一介绍各种方案的原理、优缺点，最后给出选型建议。重点是2PC、TCC、本地消息表、事务消息这几种。注意区分强一致性和最终一致性的不同适用场景。

**扩展问题**:
- 2PC和3PC的区别？3PC解决了什么问题？
- TCC的空回滚、悬挂问题是什么？怎么解决？
- Seata的AT模式原理是什么？
- 最终一致性和强一致性怎么选？

## Q17: 什么是CAP定理

**考察点**: CAP理论、三者关系、选型

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### CAP定理定义

CAP定理（CAP Theorem），又称布鲁尔定理（Brewer's theorem），是分布式系统中最重要的理论之一。它指出：**一个分布式系统不可能同时满足一致性（Consistency）、可用性（Availability）和分区容错性（Partition Tolerance）这三个基本需求，最多只能同时满足其中的两个**。

### 三个核心概念

#### C：一致性（Consistency）
- 所有节点在同一时间看到的数据是一致的
- 写操作成功后，从任何节点读取都应该读到最新值
- 即：所有访问都能获得最新的数据副本

#### A：可用性（Availability）
- 每个请求都能收到一个（非错误的）响应
- 服务一直可用，而且是正常响应时间
- 不保证返回的是最新版本的数据

#### P：分区容错性（Partition Tolerance）
- 分布式系统在遇到网络分区（节点间网络断开）时，仍然能够对外提供服务
- 网络分区是分布式系统的常态，不是异常
- 在现代分布式系统中，P是必须满足的

### CAP的权衡

因为在分布式系统中，网络分区（P）是不可避免的，所以实际上CAP是在**C和A之间做选择**：

#### CP：一致性 + 分区容错（牺牲可用性）
- 网络分区时，为了保证数据一致性，系统拒绝部分请求
- 代表：ZooKeeper、HBase、MongoDB（强一致模式）
- 适用场景：金融、支付等对数据一致性要求极高的场景

#### AP：可用性 + 分区容错（牺牲一致性）
- 网络分区时，为了保证可用性，每个节点独立响应请求
- 数据可能不一致，分区恢复后通过同步达成一致
- 代表：DynamoDB、Cassandra、CouchDB
- 适用场景：电商商品详情、社交内容等对可用性要求高的场景

#### CA：一致性 + 可用性（无法分区容错）
- 没有分区时可以同时满足C和A
- 但一旦有网络分区，就必须在C和A之间选择
- 代表：传统关系型数据库单节点（不算分布式系统）

### 对CAP的常见误解

1. **"CAP是三选二"**——更准确地说，在分区存在时，C和A二选一。没有分区时可以同时满足C和A。
2. **"一致性就是ACID的一致性"**——CAP的C是指线性一致性（所有节点同一时间看到相同数据），ACID的C是指事务的一致性约束，两者不同。
3. **"AP系统数据就一定不一致"**——AP是最终一致性，分区恢复后数据会同步，最终达成一致。

### CAP与BASE的关系

- CAP是理论基础
- BASE是CAP中AP方案的延伸
- BASE的核心是最终一致性

**答案解析**:

CAP定理是分布式系统的基础理论，面试几乎必考。回答时要讲清楚C、A、P三个概念，以及为什么只能三选二。重点是：在分布式系统中P是必须的，所以实际是C和A的权衡。能讲清楚常见的CP和AP系统的例子会更好。

**扩展问题**:
- 为什么说分布式系统中P是必须的？
- ZooKeeper是CP还是AP？为什么？
- Eureka是CP还是AP？为什么？
- 最终一致性有哪些模型？

## Q18: 什么是BASE理论

**考察点**: BASE理论、最终一致性、与ACID的对比

**难度**: 简单

**频率**: ⭐⭐⭐⭐

**标准答案**:

### BASE理论定义

BASE是Basically Available（基本可用）、Soft state（软状态）和Eventually consistent（最终一致性）三个短语的缩写。

BASE理论是对CAP定理的延伸，核心思想是：**即使无法做到强一致性（Strong Consistency），但可以通过适当的方式达到最终一致性（Eventual Consistency）**。

BASE理论是对传统ACID的反向思维——牺牲强一致性来换取高可用性和性能。

### BASE的三个要素

#### 1. Basically Available（基本可用）
- 分布式系统在出现不可预知的故障时，允许损失部分可用性
- 但不等同于系统不可用
- 例如：
  - 响应时间适当增加（正常0.5s，故障时2s）
  - 功能降级（非核心功能不可用，核心功能可用）
  - 限流熔断（保护系统不被打垮）

#### 2. Soft State（软状态）
- 允许系统存在中间状态，而这个中间状态不会影响系统整体可用性
- 即：允许数据在不同节点之间同步有延迟
- 例如：
  - 主从复制的延迟
  - 订单"处理中"状态

#### 3. Eventually Consistent（最终一致性）
- 所有的数据副本，在经过一段时间的同步后，最终能够达到一个一致的状态
- 不需要实时一致，但最终要一致
- 是BASE的核心

### 最终一致性的分类

1. **因果一致性（Causal Consistency）**：有因果关系的操作顺序要保证
2. **读己之所写（Read Your Writes）**：自己写入的数据自己能立刻读到
3. **会话一致性（Session Consistency）**：同一会话内保证读己之所写
4. **单调读一致性（Monotonic Read Consistency）**：读到某个版本后，不会读到更旧的版本
5. **单调写一致性（Monotonic Write Consistency）**：写操作按顺序执行

### BASE vs ACID

| 维度 | ACID | BASE |
|------|------|------|
| **思想** | 强一致性 | 最终一致性 |
| **可用性** | 牺牲可用性保证一致性 | 牺牲一致性保证可用性 |
| **事务** | 严格事务 | 不要求严格事务 |
| **适用** | 金融、支付等核心场景 | 互联网高并发场景 |
| **代表** | 关系型数据库 | NoSQL、微服务 |

### 为什么需要BASE

互联网场景的特点：
- 用户量大，高并发
- 对可用性要求极高（不能宕机）
- 对短暂的数据不一致有容忍度
- 强一致性的性能成本太高

因此，很多互联网系统选择BASE模型，用最终一致性换取高可用和高性能。

**答案解析**:

BASE理论是分布式系统的基础理论之一，通常和CAP一起考。回答时要讲清楚三个核心概念（基本可用、软状态、最终一致性），以及和ACID的对比。重点是最终一致性——它不是"不一致"，而是"暂时不一致，最终一致"。

**扩展问题**:
- 最终一致性和强一致性怎么选？
- 实现最终一致性有哪些方案？
- 什么是读己之所写？如何实现？
- 哪些业务场景适合BASE，哪些不适合？

## Q19: 什么是微服务，微服务的优缺点

**考察点**: 微服务概念、优缺点、拆分原则

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是微服务

微服务（Microservices）是一种架构风格，将一个大型单体应用拆分为一组小型、独立的服务，每个服务运行在自己的进程中，服务之间通过轻量级机制（通常是HTTP REST API或消息队列）进行通信。

这些服务围绕业务能力构建，并且可以通过全自动部署机制独立部署。

### 微服务的核心特征

1. **单一职责**：每个服务只做一件事，围绕业务能力组织
2. **独立部署**：每个服务可以独立部署，不影响其他服务
3. **技术异构**：不同服务可以用不同的技术栈
4. **独立扩展**：按服务维度进行水平扩展
5. **数据隔离**：每个服务有自己的数据库
6. **去中心化治理**：各个团队自治

### 微服务的优点

#### 1. 独立部署与发布
- 单个服务的修改不需要重新部署整个应用
- 发布频率可以大大提高
- 故障影响范围小（一个服务挂了不影响其他）

#### 2. 技术栈灵活
- 不同服务可以选择最合适的技术栈
- 新团队可以用新技术，不需要迁就老系统
- 可以渐进式技术升级

#### 3. 团队自治
- 小团队（2 Pizza Team）负责一个或多个服务
- 团队端到端负责，效率高
- 减少跨团队沟通成本

#### 4. 按需扩展
- 可以只给压力大的服务扩容
- 资源利用率更高
- 比单体整体扩容成本低

#### 5. 故障隔离
- 一个服务的内存泄漏不会拖垮整个系统
- 可以做熔断降级，保证核心功能可用

#### 6. 便于理解和维护
- 单个服务代码量小，新人上手快
- 业务边界清晰

### 微服务的缺点

#### 1. 分布式系统的复杂性
- 网络延迟、网络分区
- 分布式事务问题
- 服务调用链路过长，排查问题困难
- 数据一致性问题

#### 2. 运维复杂度高
- 需要部署和监控成百上千个服务
- 需要完善的DevOps基础设施
- 对运维团队要求高

#### 3. 服务间调用开销
- 跨服务调用有网络开销
- 分布式事务有性能损耗
- 接口变更需要协调多方

#### 4. 数据一致性挑战
- 每个服务有自己的数据库
- 跨服务事务需要分布式事务方案
- 最终一致性增加了业务复杂度

#### 5. 测试复杂度
- 集成测试需要启动多个服务
- 端到端测试复杂且脆弱
- 需要Mock大量依赖

#### 6. 服务治理挑战
- 服务发现、负载均衡、熔断降级
- 限流、权限控制
- 接口版本管理

### 微服务拆分原则

1. **单一职责原则**：一个服务只做一件事
2. **高内聚低耦合**：相关的功能放一起，减少跨服务调用
3. **按业务能力拆分**：围绕业务领域，而不是技术层
4. **团队边界**：考虑团队组织结构（康威定律）
5. **独立部署**：确保拆分后能独立部署和发布
6. **数据独立**：每个服务有自己的数据存储

### 什么时候适合微服务

- 系统复杂度高，单体难以维护
- 团队规模大，需要并行开发
- 业务发展快，需要快速迭代
- 不同模块的性能需求差异大
- 有完善的DevOps基础设施和能力

### 什么时候不适合微服务

- 团队小（<10人），业务简单
- 早期创业公司，业务方向不确定
- 没有完善的运维和基础设施
- 团队缺乏分布式系统经验

**答案解析**:

微服务是后端面试的基础题，几乎必问。回答时要先定义清楚什么是微服务，然后从优点和缺点两方面展开，最后讲一下拆分原则和适用场景。注意不要只讲优点不讲缺点——面试官能讲出微服务的痛点才是有实战经验的表现。分布式系统复杂性、运维复杂度、数据一致性是三个最重要的缺点。

**扩展问题**:
- 微服务和SOA有什么区别？
- 服务拆分的粒度怎么把握？拆太细了怎么办？
- 微服务之间怎么通信？同步还是异步？
- 什么是康威定律？和微服务有什么关系？

## Q20: 如何设计高可用系统

**考察点**: 高可用设计、冗余、故障转移、降级熔断

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是高可用

高可用（High Availability，HA）是指系统在面对各种异常时仍然能够持续提供服务的能力。通常用可用性（Availability）来衡量：

可用性 = 系统正常运行时间 / 总时间

常见的可用性等级：
- 99%（两个9）：年停机约3.65天
- 99.9%（三个9）：年停机约8.76小时
- 99.99%（四个9）：年停机约52.6分钟
- 99.999%（五个9）：年停机约5.26分钟

### 高可用设计的核心思想

**冗余 + 故障检测 + 自动转移 + 降级兜底**

没有单点故障，任何一个组件挂了都有备份顶上。

### 高可用设计的各个层面

#### 1. 接入层高可用

**DNS层**：
- DNS轮询：一个域名解析到多个IP
- 智能DNS：按地理位置/运营商解析到最近节点
- DNS故障自动切换（健康检查 + 自动切换）

**负载均衡层（Nginx/LVS/F5）**：
- 主备模式：主节点挂了备节点顶上（Keepalived + VIP）
- 集群模式：多个负载均衡节点同时工作
- 健康检查：自动剔除故障节点

#### 2. 应用层高可用

**无状态设计**：
- 应用服务不保存状态（状态存Redis/数据库）
- 请求可以打到任意一个节点
- 方便水平扩展和故障转移

**集群部署**：
- 每个服务至少部署2个实例
- 负载均衡分发请求
- 自动剔除不健康的实例

**弹性伸缩**：
- 根据负载自动扩缩容
- 应对流量突增

#### 3. 服务治理与容错

**服务发现**：
- 注册中心（Nacos、Eureka、Consul）
- 服务启动时注册，下线时注销
- 健康检查，自动剔除故障实例

**负载均衡**：
- 客户端负载均衡（Ribbon、LoadBalancer）
- 服务端负载均衡（Nginx）

**熔断降级**：
- 熔断器（Hystrix、Sentinel、Resilience4j）
- 下游服务故障时快速失败，不消耗资源
- 降级返回兜底数据或默认值
- 故障恢复后自动半开探测

**限流**：
- 防止流量突增打垮系统
- 网关限流 + 服务限流多层防护

**超时与重试**：
- 合理设置超时时间
- 失败重试（幂等场景）
- 重试有次数限制和退避策略

#### 4. 数据层高可用

**数据库高可用**：
- **主从复制**：主库写，从库读，主库挂了从库顶上
- **主主复制**：双主互备（需处理冲突）
- **MHA / Orchestrator**：MySQL自动故障转移
- **分库分表**：降低单库故障影响范围

**缓存高可用**：
- Redis Sentinel（哨兵模式）：一主多从，自动故障转移
- Redis Cluster（集群模式）：分片+副本，高可用+水平扩展

**存储高可用**：
- 对象存储（OSS/S3）：多副本，高可用
- RAID：磁盘冗余

#### 5. 多机房/多地域部署

**同城双活**：
- 两个机房同时提供服务
- 距离近，延迟低
- 机房级故障自动切换

**异地多活**：
- 多个城市的机房同时提供服务
- 用户就近接入
- 一个城市出问题可以切到其他城市
- 数据同步是难点

**两地三中心**：
- 生产中心 + 同城灾备 + 异地灾备
- 传统金融级方案

#### 6. 监控与运维

**全方位监控**：
- 基础设施监控（CPU、内存、磁盘、网络）
- 应用监控（QPS、延迟、错误率）
- 业务监控（订单量、支付成功率等）
- 链路追踪（SkyWalking、Jaeger）

**告警体系**：
- 多级告警（警告→严重→紧急）
- 多渠道通知（邮件、短信、电话）
- 告警收敛，避免告警风暴

**预案与演练**：
- 制定各种故障的应急预案
- 定期故障演练（混沌工程）
- 确保故障时能快速响应

### 高可用设计原则

1. **避免单点**：任何组件都不能是单点
2. **故障隔离**：一个组件故障不扩散
3. **降级兜底**：非核心功能可降级，核心功能优先保障
4. **快速恢复**：故障后能快速恢复（自动化）
5. **灰度发布**：新版本灰度上线，发现问题快速回滚
6. **容量规划**：提前预估流量，预留冗余

### 总结

高可用系统的设计是一个系统性工程，需要从接入层、应用层、数据层、多机房、监控运维等多个层面综合考虑。核心思想是**冗余**和**自动化**——没有单点故障，故障自动发现和转移。同时，高可用不是100%可用，而是根据业务需求选择合适的可用性等级（几个9），平衡成本和收益。

**答案解析**:

高可用是系统设计面试的基础题，考察候选人对整个技术栈高可用方案的了解程度。答题时要分层展开，从接入层到数据层，再到多机房和监控，展现系统性思维。重点是应用层的服务治理（熔断、限流、降级、重试）和数据层的主从复制/故障转移。能提到混沌工程、灰度发布等实践会加分。

**扩展问题**:
- 99.99%可用性意味着什么？一年可以停机多久？
- 如何实现数据库的高可用？有哪些方案？
- 什么是混沌工程？为什么需要混沌工程？
- 系统突然流量翻了10倍，怎么保证高可用？

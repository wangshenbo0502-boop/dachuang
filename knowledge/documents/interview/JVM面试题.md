## Q1: JVM内存区域划分

**考察点**: JVM运行时数据区、各区域作用、线程私有与共享

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

JVM 运行时数据区分为以下几个部分：

### 1. 线程私有区域

#### （1）程序计数器（Program Counter Register）

- 当前线程所执行的字节码的行号指示器
- 每个线程有独立的程序计数器
- 如果执行的是 Java 方法，记录的是字节码指令地址
- 如果执行的是 Native 方法，计数器值为空（Undefined）
- 唯一一个在 JVM 规范中没有规定任何 OutOfMemoryError 的区域

#### （2）Java 虚拟机栈（VM Stack）

- 每个方法执行时都会创建一个**栈帧**（Stack Frame）
- 栈帧包含：局部变量表、操作数栈、动态链接、方法出口
- 方法调用到执行完成的过程，对应栈帧在虚拟机栈中入栈到出栈
- 两种异常：
  - StackOverflowError：栈深度超过 JVM 允许的深度
  - OutOfMemoryError：栈扩展时无法申请到足够内存

#### （3）本地方法栈（Native Method Stack）

- 为 Native 方法服务
- 作用和虚拟机栈类似，只是服务的对象不同
- HotSpot 虚拟机中，本地方法栈和虚拟机栈合二为一
- 也会抛出 StackOverflowError 和 OutOfMemoryError

### 2. 线程共享区域

#### （4）Java 堆（Heap）

- JVM 管理的内存中最大的一块
- 所有线程共享，在 JVM 启动时创建
- 唯一目的：存放对象实例和数组
- 垃圾收集器管理的主要区域（GC堆）
- 从内存回收角度：新生代（Eden、Survivor0、Survivor1）和老年代
- 从内存分配角度：多个线程私有的分配缓冲区（TLAB）
- 物理上可以不连续，逻辑上连续
- 通过 -Xmx 和 -Xms 控制大小
- 抛出 OutOfMemoryError

#### （5）方法区（Method Area）

- 所有线程共享
- 存储已被 JVM 加载的类信息、常量、静态变量、即时编译器编译后的代码等
- JVM 规范中是堆的逻辑部分，但有个别名叫"Non-Heap"（非堆）
- 很多人用"永久代"来实现方法区（JDK7及之前）
- JDK8 用"元空间"（Metaspace）代替，使用本地内存
- 抛出 OutOfMemoryError

#### （6）运行时常量池（Runtime Constant Pool）

- 是方法区的一部分
- 存放编译期生成的各种字面量和符号引用
- 具备动态性：运行期间也可以将新的常量放入池中（如 String.intern()）

### 3. 直接内存（Direct Memory）

- 不是 JVM 运行时数据区的一部分
- NIO 中使用，通过 Native 函数库直接分配堆外内存
- 通过 DirectByteBuffer 对象操作
- 也可能导致 OutOfMemoryError
- 不受 -Xmx 限制，但受本机总内存限制

### 4. 总结图

```
JVM运行时数据区
├── 线程私有
│   ├── 程序计数器
│   ├── Java虚拟机栈
│   └── 本地方法栈
├── 线程共享
│   ├── Java堆
│   └── 方法区
│       └── 运行时常量池
└── 直接内存（非JVM运行时数据区）
```

**答案解析**:

JVM 内存区域划分是 JVM 面试的基础题，必须准确掌握。

需要区分哪些区域是线程私有的，哪些是线程共享的：
- 线程私有：程序计数器、虚拟机栈、本地方法栈
- 线程共享：堆、方法区

程序计数器是唯一不会 OOM 的区域，因为它只是一个行号指示器，大小固定。

方法区在不同版本的 JDK 中实现不同：
- JDK7 及之前：永久代（PermGen），在堆中
- JDK8 及之后：元空间（Metaspace），使用本地内存

直接内存不是 JVM 运行时数据区，但经常和 NIO 一起考察。

**扩展问题**:
- 哪些区域是线程私有的？哪些是共享的？
- 哪些区域会 OOM？哪些不会？
- JDK7 和 JDK8 的方法区有什么区别？
- 什么是栈帧？包含哪些部分？
- 堆内存一定是线程共享的吗？

## Q2: 垃圾回收算法有哪些

**考察点**: 标记清除、复制算法、标记整理、分代收集

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 标记-清除算法（Mark-Sweep）

**原理**：分为"标记"和"清除"两个阶段。先标记出所有需要回收的对象，标记完成后统一回收所有被标记的对象。

**优点**：
- 最基础的算法，实现简单

**缺点**：
- 效率不高（标记和清除两个过程效率都不高）
- 会产生大量内存碎片，可能导致大对象无法分配

**适用场景**：老年代（因为对象存活率高，复制算法代价大）

### 2. 复制算法（Copying）

**原理**：将可用内存按容量划分为大小相等的两块，每次只使用其中一块。当这一块用完了，就将还存活着的对象复制到另一块上面，然后再把已使用过的内存空间一次清理掉。

**优点**：
- 实现简单，运行高效
- 不会产生内存碎片
- 只要移动堆顶指针，按顺序分配内存即可

**缺点**：
- 内存利用率低，只有一半
- 对象存活率高时，复制操作增多，效率降低

**适用场景**：新生代（对象存活率低，大部分对象都是朝生夕死）

**HotSpot 中的应用**：
- 新生代分为 Eden 和两个 Survivor 区（8:1:1）
- 每次使用 Eden 和其中一个 Survivor
- 回收时，将存活对象复制到另一个 Survivor
- 如果 Survivor 空间不够，通过分配担保进入老年代

### 3. 标记-整理算法（Mark-Compact）

**原理**：标记过程和标记-清除一样，但后续不是直接对可回收对象进行清理，而是让所有存活的对象都向一端移动，然后直接清理掉端边界以外的内存。

**优点**：
- 不会产生内存碎片
- 内存利用率高

**缺点**：
- 需要移动对象，成本较高
- 比标记-清除多了整理的过程

**适用场景**：老年代（对象存活率高，不适合复制算法）

### 4. 分代收集算法（Generational Collection）

**原理**：根据对象存活周期的不同将内存划分为几块，一般是新生代和老年代，根据各个年代的特点采用最适当的收集算法。

- **新生代**：对象存活率低，用**复制算法**
- **老年代**：对象存活率高，用**标记-清除**或**标记-整理**算法

这是当前商业虚拟机都采用的算法。

### 5. 对比总结

| 算法 | 标记-清除 | 复制算法 | 标记-整理 |
|------|----------|---------|----------|
| 速度 | 中等 | 快 | 慢 |
| 内存碎片 | 有 | 无 | 无 |
| 内存利用率 | 高 | 低（50%） | 高 |
| 移动对象 | 不需要 | 需要 | 需要 |
| 适用年代 | 老年代 | 新生代 | 老年代 |

**答案解析**:

垃圾回收算法是 JVM 面试的核心考点。四种算法中，分代收集不是一种具体的算法，而是一种思想，根据不同年代的特点选择不同的算法。

新生代用复制算法，因为新生代对象大多朝生夕死，存活对象少，复制代价小。老年代用标记-清除或标记-整理，因为老年代对象存活率高，复制代价大。

标记-清除和标记-整理的区别在于是否移动对象。标记-清除不移动对象，但会产生碎片；标记-整理移动对象，没有碎片，但开销大。

CMS 收集器用的是标记-清除，G1 收集器整体上是标记-整理，局部（两个Region之间）是复制算法。

**扩展问题**:
- 复制算法的优缺点？
- 标记清除和标记整理的区别？
- 为什么新生代用复制算法，老年代用标记整理？
- 什么是分代收集？为什么要分代？
- CMS 用的什么算法？G1 用的什么算法？

## Q3: 垃圾收集器有哪些，各有什么特点

**考察点**: 7种经典垃圾收集器、适用年代、特点对比

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

HotSpot JVM 有 7 种经典垃圾收集器：

### 1. 新生代收集器

#### （1）Serial 收集器

- **算法**：复制算法
- **特点**：单线程，收集时必须暂停所有用户线程（STW）
- **优点**：简单高效，没有线程交互开销
- **缺点**：STW 时间长
- **适用场景**：客户端模式、内存小的应用
- 最古老、最基础的收集器

#### （2）ParNew 收集器

- **算法**：复制算法
- **特点**：Serial 的多线程版本
- **优点**：多线程并行收集，效率高
- **缺点**：仍有 STW
- **适用场景**：服务端模式，和 CMS 配合使用
- 除了 Serial，只有它能和 CMS 配合

#### （3）Parallel Scavenge 收集器

- **算法**：复制算法
- **特点**：多线程并行收集，关注**吞吐量**
- **优点**：高吞吐量（高效利用 CPU 时间）
- **缺点**：STW 时间可能较长
- **适用场景**：后台计算任务，不需要太多交互
- 也叫"吞吐量优先收集器"
- 有自适应调节策略（-XX:+UseAdaptiveSizePolicy）

### 2. 老年代收集器

#### （4）Serial Old 收集器

- **算法**：标记-整理
- **特点**：Serial 的老年代版本，单线程
- **适用场景**：客户端模式，或作为 CMS 的后备预案

#### （5）Parallel Old 收集器

- **算法**：标记-整理
- **特点**：Parallel Scavenge 的老年代版本，多线程
- **适用场景**：和 Parallel Scavenge 配合，注重吞吐量

#### （6）CMS 收集器（Concurrent Mark Sweep）

- **算法**：标记-清除
- **特点**：以获取最短回收停顿时间为目标
- **优点**：并发收集，低停顿
- **缺点**：
  - 对 CPU 资源敏感
  - 无法处理浮动垃圾
  - 有内存碎片（标记-清除）
  - 最后可能退化为 Serial Old
- **四个阶段**：
  1. 初始标记（STW，短）
  2. 并发标记（和用户线程并发）
  3. 重新标记（STW，比初始标记长）
  4. 并发清除（和用户线程并发）

### 3. 全代收集器

#### （7）G1 收集器（Garbage-First）

- **算法**：整体标记-整理，局部（Region间）复制
- **特点**：
  - 面向服务端应用
  - 可预测的停顿时间模型
  - Region 划分内存
  - 兼顾吞吐量和低延迟
- **优点**：
  - 低停顿，且停顿时间可控
  - 不会产生内存碎片
  - 可指定最大停顿时间
- **适用场景**：大内存、多 CPU 的服务端应用
- JDK9 及以后的默认收集器

### 4. 对比总结

| 收集器 | 年代 | 算法 | 线程 | 特点 | 目标 |
|--------|------|------|------|------|------|
| Serial | 新生代 | 复制 | 单线程 | 简单高效 | - |
| ParNew | 新生代 | 复制 | 多线程 | Serial多线程版 | - |
| Parallel Scavenge | 新生代 | 复制 | 多线程 | 吞吐量优先 | 吞吐量 |
| Serial Old | 老年代 | 标记-整理 | 单线程 | Serial老年代版 | - |
| Parallel Old | 老年代 | 标记-整理 | 多线程 | Parallel老年代版 | 吞吐量 |
| CMS | 老年代 | 标记-清除 | 并发+并行 | 低停顿 | 最短停顿 |
| G1 | 全代 | 标记-整理+复制 | 并发+并行 | Region、可预测停顿 | 可控停顿 |

**答案解析**:

7 种垃圾收集器是 JVM 面试的重点和难点。可以按年代来记忆：
- 新生代：Serial、ParNew、Parallel Scavenge
- 老年代：Serial Old、Parallel Old、CMS
- 全代：G1

可以按组合来记忆：
- Serial + Serial Old：客户端模式
- ParNew + CMS：低延迟组合
- Parallel Scavenge + Parallel Old：吞吐量组合
- G1：兼顾吞吐量和延迟

CMS 是面试重点，需要记住它的四个阶段，其中初始标记和重新标记需要 STW，并发标记和并发清除是和用户线程并发的。

G1 是现在的主流收集器，它把内存划分成多个 Region，每次只回收一部分 Region，可以控制停顿时间。

**扩展问题**:
- CMS 的工作过程？有哪几个阶段？
- CMS 的缺点有哪些？
- G1 和 CMS 的区别？
- G1 的 Region 是什么？
- 吞吐量和停顿时间的区别？

## Q4: 什么是类加载机制，类加载过程

**考察点**: 类加载的五个阶段、每个阶段做什么

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 什么是类加载机制

JVM 把描述类的数据从 Class 文件加载到内存，并对数据进行校验、转换解析和初始化，最终形成可以被 JVM 直接使用的 Java 类型，这就是 JVM 的类加载机制。

### 2. 类加载的五个阶段

类加载过程分为 5 个阶段：**加载、验证、准备、解析、初始化**。

其中验证、准备、解析三个部分统称为**连接**。

```
加载 → 验证 → 准备 → 解析 → 初始化
     |---------连接---------|
```

#### （1）加载（Loading）

**做什么**：
- 通过类的全限定名获取定义此类的二进制字节流
- 将这个字节流所代表的静态存储结构转化为方法区的运行时数据结构
- 在内存中生成一个代表这个类的 java.lang.Class 对象，作为方法区这个类的各种数据的访问入口

**类加载器**：
- 启动类加载器（Bootstrap ClassLoader）
- 扩展类加载器（Extension ClassLoader）
- 应用程序类加载器（Application ClassLoader）
- 自定义类加载器

#### （2）验证（Verification）

**目的**：确保 Class 文件的字节流中包含的信息符合当前虚拟机的要求，不会危害虚拟机自身的安全。

**四个阶段**：
1. 文件格式验证：验证字节流是否符合 Class 文件格式规范
2. 元数据验证：对字节码描述的信息进行语义分析
3. 字节码验证：通过数据流和控制流分析，确定程序语义是合法的
4. 符号引用验证：对类自身以外的信息进行匹配性校验

#### （3）准备（Preparation）

**做什么**：
- 为**类变量**（static 变量）分配内存并设置**零值**
- 内存分配在方法区中
- 注意：是类变量，不是实例变量

```java
public static int value = 123;
// 准备阶段后 value = 0，不是 123
// 初始化阶段后 value = 123
```

特殊情况：如果是 final static 常量，在准备阶段就会赋值。
```java
public static final int value = 123;
// 准备阶段后 value = 123
```

#### （4）解析（Resolution）

**做什么**：
- 将常量池内的**符号引用**替换为**直接引用**
- 符号引用：用一组符号来描述所引用的目标
- 直接引用：直接指向目标的指针、相对偏移量或能间接定位到目标的句柄

**解析内容**：
- 类或接口的解析
- 字段解析
- 类方法解析
- 接口方法解析

#### （5）初始化（Initialization）

**做什么**：
- 执行类构造器 `<clinit>()` 方法
- `<clinit>()` 由编译器自动收集类中所有类变量的赋值动作和静态代码块中的语句合并产生
- 父类的 `<clinit>()` 先执行，子类的后执行
- JVM 会保证 `<clinit>()` 方法在多线程环境中被正确地加锁、同步

### 3. 类初始化的时机（主动引用）

1. 创建类的实例（new）
2. 访问类的静态变量或静态方法
3. 反射调用（Class.forName）
4. 初始化子类时，父类先初始化
5. JVM 启动时的主类（包含 main 方法的类）

**被动引用**（不会初始化）：
1. 通过子类引用父类的静态字段，不会导致子类初始化
2. 通过数组定义来引用类，不会触发此类的初始化
3. 常量在编译阶段会存入调用类的常量池中，不会触发定义常量的类的初始化

**答案解析**:

类加载机制是 JVM 面试的重点。五个阶段：加载、验证、准备、解析、初始化。

准备阶段容易出错：准备阶段是为 static 变量赋零值，不是赋用户指定的值。但 final static 常量例外，因为 ConstantValue 属性的存在，准备阶段就会赋值。

初始化阶段执行 `<clinit>()` 方法，这个方法是编译器自动生成的，由静态变量赋值和静态代码块合并而成。

类初始化的时机也是常考点，需要区分主动引用和被动引用。被动引用的三种情况需要记住：子类引用父类静态字段、数组引用、常量引用。

**扩展问题**:
- 类加载的五个阶段？
- 准备阶段和初始化阶段的区别？
- 什么是符号引用和直接引用？
- <clinit>() 和 <init>() 的区别？
- 什么情况下会触发类初始化？

## Q5: 什么是双亲委派模型，有什么好处

**考察点**: 双亲委派模型、类加载器、双亲委派的好处和破坏

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 类加载器分类

从 JVM 角度看，只有两种类加载器：
- 启动类加载器（Bootstrap ClassLoader）：C++ 实现，是 JVM 的一部分
- 其他类加载器：Java 实现，继承自 ClassLoader

从开发者角度看，有三种类加载器：

**（1）启动类加载器（Bootstrap ClassLoader）**
- 加载 `<JAVA_HOME>\lib` 目录下的类
- 如 rt.jar、tools.jar 等
- 开发者无法直接引用

**（2）扩展类加载器（Extension ClassLoader）**
- 加载 `<JAVA_HOME>\lib\ext` 目录下的类
- 由 sun.misc.Launcher$ExtClassLoader 实现

**（3）应用程序类加载器（Application ClassLoader）**
- 也叫系统类加载器
- 加载用户类路径（ClassPath）上的类
- 由 sun.misc.Launcher$AppClassLoader 实现
- 程序中默认的类加载器

**（4）自定义类加载器**
- 继承 ClassLoader，重写 findClass 方法
- 可以实现热部署、代码加密等功能

### 2. 双亲委派模型

**工作过程**：
1. 一个类加载器收到类加载请求
2. 它首先不会自己去尝试加载，而是把这个请求**委派给父类加载器**去完成
3. 每一层的类加载器都是如此，因此所有的加载请求最终都应该传送到顶层的启动类加载器中
4. 只有当父加载器反馈自己无法完成这个加载请求（它的搜索范围中没有找到所需的类），子加载器才会尝试自己去加载

```
应用程序类加载器 → 扩展类加载器 → 启动类加载器
```

**为什么叫"双亲"？**
- 翻译问题，parent 翻译为"双亲"
- 其实是"父委派"，是单亲（只有一个父加载器）

### 3. 双亲委派的好处

**（1）避免类的重复加载**
- 一个类只会被最顶层的能加载它的加载器加载一次
- 保证了同一个类不会被不同的加载器加载多次

**（2）安全性**
- 防止核心 API 被篡改
- 比如用户自己写一个 java.lang.String 类，会被启动类加载器优先加载 rt.jar 中的 String，用户写的不会被加载
- 保证了 Java 核心库的安全性

### 4. 破坏双亲委派模型

双亲委派模型不是一个强制性的约束模型，而是 Java 设计者推荐的类加载器实现方式。

**历史上三次大规模"破坏"：**

**第一次**：JDK1.2 之前，用户重写 loadClass 方法就可以破坏。

**第二次**：SPI（Service Provider Interface）机制，如 JDBC、JNDI 等，需要启动类加载器加载用户类路径下的代码。用线程上下文类加载器（Thread Context ClassLoader）解决。

**第三次**：热部署、热加载，如 OSGi，实现模块化部署。每个模块有自己的类加载器，需要时替换。

**答案解析**:

双亲委派模型是类加载机制的核心，也是面试高频题。

双亲委派的核心思想是：向上委派，向下尝试。子加载器收到请求先委派给父加载器，父加载器加载不了子加载器才自己加载。

最大的好处是安全性，保证了 Java 核心类不会被篡改。比如你自己写一个 java.lang.String，由于双亲委派，会先让启动类加载器去加载，启动类加载器在 rt.jar 中找到了 String，就直接返回了，不会加载你写的那个。

破坏双亲委派的情况也需要了解，特别是 SPI 机制和 OSGi。

## Q6: 如何判断对象是否可以被回收

**考察点**: 引用计数法、可达性分析算法、GC Roots

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

判断对象是否可以被回收，有两种算法：**引用计数法**和**可达性分析算法**。

### 1. 引用计数法（Reference Counting）

**原理**：
- 给对象中添加一个引用计数器
- 每当有一个地方引用它时，计数器值 +1
- 当引用失效时，计数器值 -1
- 任何时刻计数器为 0 的对象就是不可能再被使用的

**优点**：
- 实现简单
- 判定效率高

**缺点**：
- 无法解决**循环引用**的问题

```java
class A {
    public B b;
}
class B {
    public A a;
}

A a = new A();
B b = new B();
a.b = b;
b.a = a;
a = null;
b = null;
// 此时a和b互相引用，计数器都不为0
// 但实际上它们已经不可能被访问了
```

由于循环引用的问题，**主流 JVM（如 HotSpot）都没有采用引用计数法**。

### 2. 可达性分析算法（Reachability Analysis）

**原理**：
- 通过一系列称为 **GC Roots** 的对象作为起始点
- 从这些节点开始向下搜索，搜索走过的路径称为**引用链**
- 当一个对象到 GC Roots 没有任何引用链相连时（即从 GC Roots 到这个对象不可达），则证明此对象是不可用的

**GC Roots 包括**：
1. **虚拟机栈（栈帧中的局部变量表）中引用的对象**
2. **方法区中类静态属性引用的对象**
3. **方法区中常量引用的对象**
4. **本地方法栈中 JNI（Native 方法）引用的对象**
5. JVM 内部的引用（如基本数据类型对应的 Class 对象、常驻异常对象等）
6. 所有被同步锁（synchronized）持有的对象

### 3. 对象自救（finalize）

即使在可达性分析中不可达的对象，也不是"非死不可"。

**过程**：
1. 对象在可达性分析后发现没有与 GC Roots 相连的引用链
2. 进行第一次标记，并判断是否有必要执行 finalize() 方法
   - 对象没有覆盖 finalize() 方法，或 finalize() 已经被调用过 → 没必要执行 → 回收
   - 对象覆盖了 finalize() 方法且还没执行过 → 有必要执行
3. 如果有必要执行，对象会被放入 F-Queue 队列
4. 稍后由一个低优先级的 Finalizer 线程去执行它
5. GC 对 F-Queue 中的对象进行第二次小规模标记
6. 如果对象在 finalize() 中成功拯救自己（重新与引用链上的任何一个对象建立关联）→ 第二次标记时被移除"即将回收"集合
7. 如果还没逃脱 → 真的被回收

**注意**：
- finalize() 方法只会被系统自动调用一次
- 不推荐使用 finalize()，运行代价大，不确定性大
- JDK9 已废弃 finalize()

**答案解析**:

判断对象是否可以被回收是垃圾回收的基础。主流 JVM 用的是可达性分析算法，不是引用计数法。

引用计数法虽然简单，但有循环引用的问题，所以 HotSpot 没有用。

可达性分析算法的核心是 GC Roots，需要记住哪些可以作为 GC Roots。最常考的是：虚拟机栈中引用的对象、方法区静态变量引用的对象、方法区常量引用的对象、本地方法栈中引用的对象。

对象的 finalize() 方法是一个"逃生门"，但不推荐使用，因为它执行时间不确定，甚至可能不执行，而且代价大。

## Q7: 什么是内存泄漏和内存溢出

**考察点**: 内存泄漏、内存溢出的概念、区别、常见场景

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 基本概念

**内存溢出（OutOfMemoryError，OOM）**：
- 程序在申请内存时，没有足够的内存空间供其使用
- 简单说：内存不够用了

**内存泄漏（Memory Leak）**：
- 程序中已动态分配的堆内存由于某种原因**程序未释放或无法释放**
- 造成系统内存的浪费，导致程序运行速度减慢甚至系统崩溃等严重后果
- 简单说：用了的内存不还，导致可用内存越来越少

### 2. 两者的关系

- 内存泄漏是原因之一
- 内存泄漏积累到一定程度，就会导致内存溢出
- 内存溢出不一定是内存泄漏导致的，也可能是内存确实不够

```
内存泄漏 → 累积 → 内存溢出
```

### 3. 常见的内存泄漏场景

**（1）静态集合类**
```java
public class Test {
    private static List<Object> list = new ArrayList<>();
    
    public void add() {
        Object obj = new Object();
        list.add(obj); // 静态集合持有对象引用，不会被回收
    }
}
```
静态变量的生命周期和 JVM 一样长，持有对象导致对象无法回收。

**（2）各种连接（数据库连接、网络连接、IO连接）**
- 连接用完后没有关闭（close）
- 连接池使用不当，连接没有释放

**（3）未关闭的资源**
- 文件流、输入输出流没有 close
- 监听器没有注销
- 单例模式持有外部引用

**（4）ThreadLocal 内存泄漏**
- ThreadLocal 使用完没有 remove
- ThreadLocalMap 的 key 是弱引用，但 value 是强引用
- ThreadLocal 对象被回收后，key 变成 null，value 无法被访问到
- 但 value 仍然被 ThreadLocalMap 引用，无法回收

**（5）内部类和外部类的引用**
- 非静态内部类默认持有外部类的引用
- 如果内部类对象被长期持有，外部类对象也无法回收

**（6）缓存**
- 缓存使用不当，没有设置过期策略
- 缓存越来越大，导致内存溢出

### 4. 常见的 OOM 场景

**（1）Java 堆溢出**
- 对象数量过多，超过堆内存容量
- 常见原因：内存泄漏、大对象过多、堆内存设置太小

**（2）虚拟机栈和本地方法栈溢出**
- StackOverflowError：栈深度过大（递归太深）
- OutOfMemoryError：栈扩展时内存不足

**（3）方法区/元空间溢出**
- 加载的类太多，如动态生成大量类
- 常量池溢出

**（4）直接内存溢出**
- NIO 使用直接内存过多

### 5. 排查方法

1. 通过内存快照分析工具（MAT、JProfiler）分析 dump 文件
2. 查看内存中对象的数量和占用大小
3. 定位是内存泄漏还是内存不足
4. 如果是泄漏，找到泄漏点；如果是不足，调整堆大小

**答案解析**:

内存泄漏和内存溢出是两个不同但相关的概念。内存溢出是结果，内存泄漏是原因之一。

内存泄漏的根本原因是：长生命周期的对象持有短生命周期对象的引用，导致短生命周期对象无法被回收。

常见的内存泄漏场景需要记住，特别是 ThreadLocal 的内存泄漏问题，是面试高频考点。

排查 OOM 的一般思路是：先获取 dump 文件，然后用 MAT 等工具分析，看是哪些对象占用了大量内存，然后定位到代码。

- 常见的内存泄漏场景有哪些？
- ThreadLocal 为什么会内存泄漏？
- 如何排查 OOM 问题？

## Q9: Java的四种引用类型在GC中的表现

**考察点**: 强软弱虚四种引用、GC回收策略、实际应用

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

Java 有四种引用类型：**强引用**、**软引用**、**弱引用**、**虚引用**。

### 1. 强引用（Strong Reference）

**定义**：最常见的引用，如 `Object obj = new Object()`。

**GC 表现**：
- 只要强引用存在，垃圾回收器**永远不会回收**被引用的对象
- 内存不足时，JVM 宁愿抛出 OutOfMemoryError，也不会回收强引用对象

```java
Object obj = new Object(); // 强引用
obj = null; // 取消强引用，对象可以被回收
```

### 2. 软引用（Soft Reference）

**定义**：使用 SoftReference 类实现。

**GC 表现**：
- 内存**充足时**：不会回收
- 内存**不足时**：才会回收
- 只有在即将抛出 OOM 之前，才会回收这些软引用对象

```java
SoftReference<Object> softRef = new SoftReference<>(new Object());
Object obj = softRef.get(); // 获取对象，可能为null
```

**应用场景**：
- 内存敏感的缓存
- 图片缓存、网页缓存

### 3. 弱引用（Weak Reference）

**定义**：使用 WeakReference 类实现。

**GC 表现**：
- 只要发生 GC，就会被回收**（不管内存是否足够）
- 生命周期更短

```java
WeakReference<Object> weakRef = new WeakReference<>(new Object());
Object obj = weakRef.get(); // GC后可能为null
```

**应用场景**：
- WeakHashMap
- ThreadLocal
- 生命周期更短的缓存

### 4. 虚引用（Phantom Reference）

**定义**：使用 PhantomReference 类实现。

**GC 表现**：
- get() 方法**永远返回 null**
- 必须和引用队列（ReferenceQueue）联合使用
- 对象被回收前会被放入引用队列，收到系统通知
- 不影响对象的生命周期

```java
ReferenceQueue<Object> queue = new ReferenceQueue<>();
PhantomReference<Object> phantomRef = new PhantomReference<>(new Object(), queue);
```

**应用场景**：
- 管理堆外内存（如 NIO 的 DirectByteBuffer）
- 对象回收前的清理工作

### 5. 对比总结

| 引用类型 | 回收时机 | get()返回 | 是否需要引用队列 | 用途 |
|---------|---------|-----------|---------------|------|
| 强引用 | 从不回收 | 总是返回对象 | - | 普通对象引用 |
| 软引用 | 内存不足时 | 内存充足时返回对象 | 可选 | 内存敏感缓存 |
| 弱引用 | GC时 | GC前返回对象 | 可选 | WeakHashMap、ThreadLocal |
| 虚引用 | 对象回收时 | 永远返回null | 必须 | 堆外内存管理 |

**答案解析**:

四种引用类型在 GC 中的表现不同，强度从强到弱依次是：强引用 > 软引用 > 弱引用 > 虚引用。

强引用是默认的，我们平时写的代码几乎都是强引用。

软引用和弱引用的区别在于回收时机：软引用内存不足才回收，弱引用每次 GC 都回收。所以软引用适合做缓存，弱引用适合做更"弱"的场景。

虚引用最特殊，它的 get() 永远返回 null，它的唯一作用就是在对象被回收时收到通知。常用于管理堆外内存。

ThreadLocalMap 的 key 是弱引用，这也是一个常考点。

## Q10: 什么是GC Roots，有哪些

**考察点**: GC Roots的概念、种类、可达性分析

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 什么是 GC Roots

GC Roots（垃圾回收根节点）是可达性分析算法的起点。

从这些根对象出发，向下搜索，能到达的对象就是存活的，不能到达的就是可以回收的。

### 2. 常见的 GC Roots

**（1）虚拟机栈（栈帧中的局部变量表）中引用的对象**
- 各个线程被调用的方法堆栈中使用到的参数、局部变量、临时变量等
- 这是最常见的 GC Roots

```java
public void method() {
    Object obj = new Object(); // obj是局部变量，是GC Root
    // ...
}
```

**（2）方法区中类静态属性引用的对象**
- 静态变量引用的对象

```java
public class Test {
    private static Object obj = new Object(); // 静态变量引用的对象
}
```

**（3）方法区中常量引用的对象**
- 字符串常量池（String Table）里的引用

```java
// 字符串常量池中的常量引用的对象
String s = "hello";
```

**（4）本地方法栈中 JNI（Native 方法）引用的对象**
- Native 方法中引用的对象

**（5）JVM 内部的引用**
- 基本数据类型对应的 Class 对象
- 一些常驻的异常对象（比如 NullPointException、OutOfMemoryError）
- 系统类加载器
- 等等

**（6）所有被同步锁（synchronized）持有的对象**
- 被锁住的对象不会被回收

**（7）反映 JVM 内部情况的 JMXBean、JVMTI 中注册的回调、本地代码缓存等**

### 3. 为什么这些可以作为 GC Roots

这些对象都是**肯定不会被回收的**对象，它们是"根"。从这些根出发，能到达的对象都是正在被使用的，不能回收；不能到达的就是没人用的，可以回收。

简单说：GC Roots 是当前正在被使用的、不能回收的对象。

### 4. 可达性分析的过程

```
GC Roots → 引用链 → 存活对象
```

1. 从 GC Roots 开始
2. 沿着引用链向下遍历
3. 所有被遍历到（标记）的对象都是存活的
4. 没有被标记的对象就是可以回收的

**答案解析**:

GC Roots 是可达性分析的基础，也是面试常考点。

需要记住主要的四类 GC Roots：
1. 虚拟机栈中引用的对象
2. 方法区静态变量引用的对象
3. 方法区常量引用的对象
4. 本地方法栈中引用的对象

简单记忆：栈中引用的、方法区静态和常量引用的、本地方法引用的。

这些对象之所以能作为根，是因为它们是当前正在被使用的，肯定不能被回收。从这些根出发能到达的对象，说明也在被使用，不能回收。

## Q11: 新生代和老年代的比例和为什么

**考察点**: 堆内存分代、Eden/Survivor比例、为什么这么分

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 1. 堆内存分代

Java 堆分为**新生代**和**老年代**。

- **新生代**：存放新创建的对象，大部分对象朝生夕死
- **老年代**：存放存活时间长的对象，经过多次 GC 仍然存活的对象

### 2. 默认比例

**新生代 : 老年代 = 1 : 2**（默认）

即新生代占堆的 1/3，老年代占 2/3。

可以通过 `-XX:NewRatio` 参数调整，默认值为 2，表示老年代是新生代的 2 倍。

### 3. 新生代内部比例

新生代又分为：
- **Eden 区**：伊甸园，对象出生的地方
- **Survivor0 区（From）**：幸存者0区
- **Survivor1 区（To）**：幸存者1区

**Eden : Survivor0 : Survivor1 = 8 : 1 : 1**（默认）

可以通过 `-XX:SurvivorRatio` 参数调整，默认值为 8，表示 Eden 是 Survivor 的 8 倍。

```
新生代（1份）
├── Eden (8/10)
├── Survivor0 (1/10)
└── Survivor1 (1/10)
```

### 4. 为什么这么分？

**（1）为什么要分代？**

不同生命周期的对象采用不同的回收算法：
- 新生代：对象存活率低，用**复制算法**
- 老年代：对象存活率高，用**标记-清除**或**标记-整理**

分代可以提高垃圾回收的效率。

**（2）为什么新生代比例小？**

因为新生代的对象大多数都是朝生夕死的，很快就会被回收，不需要太大的空间。

研究表明，98% 的对象都是"朝生夕死"的，所以新生代不需要太大。

**（3）为什么 Survivor 区是两个，比例是 8:1:1？**

新生代使用复制算法，需要两块区域来复制对象。

8:1:1 的比例是基于统计数据：
- 每次 GC 后，只有约 10% 甚至更少的对象存活
- 所以一个 Survivor 区（10%）足够存放存活对象
- Eden 区设大一点（80%），可以容纳更多新对象，减少 GC 次数

两个 Survivor 区是为了解决内存碎片问题，并且始终有一个 Survivor 区是空的。

**（4）对象什么时候进入老年代？**

1. **年龄达到阈值**：默认 15 岁（`-XX:MaxTenuringThreshold`），每次 GC 存活年龄+1
2. **大对象直接进入老年代**：超过 `-XX:PretenureSizeThreshold` 设置大小的对象
3. **动态年龄判断**：Survivor 区中相同年龄的所有对象大小总和大于 Survivor 空间的一半，年龄大于等于该年龄的对象直接进入老年代
4. **分配担保**：Minor GC 后，存活对象太多，Survivor 区放不下，通过分配担保进入老年代

**答案解析**:

堆内存分代是 JVM 的重要概念。默认比例：新生代:老年代 = 1:2，新生代内部 Eden:Survivor = 8:1:1。

分代的原因是不同生命周期的对象适合不同的回收算法。新生代对象存活率低，适合复制算法；老年代对象存活率高，适合标记-清除或标记-整理。

Survivor 区有两个，是复制算法的需要。8:1:1 的比例是基于统计数据，大部分对象在第一次 GC 就死了，所以一个 Survivor 区足够。

对象进入老年代的四种情况也需要记住，特别是动态年龄判断和分配担保。

**扩展问题**:
- 新生代和老年代的比例是多少？
- 为什么要分代？
- Survivor 区为什么有两个？
- Eden 和 Survivor 的比例是多少？为什么？
- 对象什么时候进入老年代？

## Q12: 什么是 STW（Stop The World）

**考察点**: STW的概念、发生时机、各种收集器的STW

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 什么是 STW

**Stop-The-World（STW）**：在垃圾回收过程中，JVM 会暂停所有用户线程，整个应用程序会停顿，什么也干不了。

STW 是不可避免的，即使是 CMS、G1 这些号称低延迟的收集器，也有 STW 阶段，只是时间短而已。

### 2. 为什么需要 STW

垃圾回收的过程中，需要确保对象的引用关系不再变化，否则会导致回收错误。

比如可达性分析过程中，如果用户线程还在运行，对象引用关系一直在变，就无法准确标记哪些对象是存活的。

所以需要 STW，暂停所有用户线程，确保在一致性的快照中进行垃圾回收。

### 3. 各收集器的 STW 情况

**Serial/Serial Old**：
- 整个 GC 过程都是 STW
- 停顿时间长

**Parallel Scavenge/Parallel Old**：
- 整个 GC 过程都是 STW
- 多线程并行回收，STW 时间比 Serial 短

**CMS**：
- 初始标记：STW，时间很短
- 并发标记：和用户线程并发，不停顿
- 重新标记：STW，时间比初始标记长，但比并发标记短很多
- 并发清除：和用户线程并发，不停顿

CMS 的目标是降低 STW 时间，把最耗时的并发标记和并发清除放到和用户线程并发执行。

**G1**：
- 初始标记：STW，很短
- 并发标记：和用户线程并发
- 最终标记：STW，很短
- 筛选回收：STW，但可以控制停顿时间

G1 可以指定最大停顿时间（`-XX:MaxGCPauseMillis`），它会尽量在这个时间内完成回收。

### 4. 如何减少 STW 时间

1. **选择合适的垃圾收集器**：CMS、G1 等低延迟收集器
2. **调整堆大小**：堆太小会频繁 GC，太大单次 GC 时间长
3. **调整新生代比例**：减少 Minor GC 时间
4. **减少大对象**：大对象直接进入老年代，增加 Full GC 概率
5. **优化代码**：减少对象创建，减少内存泄漏

### 5. 注意事项

- STW 是不可避免的，只能尽量缩短
- 不同的垃圾收集器 STW 时间不同
- 对于交互性强的应用，选择低延迟收集器
- 对于后台计算任务，吞吐量优先的收集器也可以接受

**答案解析**:

STW 是垃圾回收中的重要概念，所有收集器都有 STW，只是时间长短不同。

STW 的根本原因是：垃圾回收需要一个一致性的快照，用户线程运行会改变对象引用关系，导致无法准确回收。

CMS 和 G1 等并发收集器把最耗时的部分放到并发阶段，只在必要的阶段 STW，大大缩短了停顿时间。

但并发收集器也有代价：需要更多的 CPU 资源，吞吐量会下降。这是一个权衡。

**扩展问题**:
- 什么是 STW？为什么需要 STW？
- 哪些 GC 阶段会 STW？
- CMS 有哪些阶段需要 STW？
- G1 有哪些阶段需要 STW？
- 如何减少 STW 时间？

## Q13: CMS 和 G1 垃圾收集器的区别

**考察点**: CMS和G1的对比、各自的优缺点、适用场景

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 基本介绍

**CMS（Concurrent Mark Sweep）**：
- 老年代收集器
- 基于标记-清除算法
- 以获取最短回收停顿时间为目标
- 适合对响应速度要求高的应用

**G1（Garbage-First）**：
- 面向服务端的全代收集器
- 基于标记-整理（整体）+ 复制（局部）算法
- 可预测的停顿时间模型
- JDK9 及以后的默认收集器

### 2. 核心区别

| 特性 | CMS | G1 |
|------|-----|----|
| 收集范围 | 老年代 | 全代（新生代+老年代） |
| 内存布局 | 传统分代（连续空间） | Region 划分（不连续） |
| 算法 | 标记-清除 | 标记-整理 + 复制 |
| 内存碎片 | 有 | 无 |
| 停顿时间 | 低，但不可预测 | 可控，可指定最大停顿时间 |
| 吞吐量 | 较高 | 略低（开销大） |
| 适用内存 | 小到中等 | 大内存 |
| 最小内存建议 | - | 建议 6G 以上 |
| 浮动垃圾 | 有 | 有 |
| 全量GC | Serial Old（单线程，很慢） | 有专门的Full GC |

### 3. 内存布局不同

**CMS**：
- 传统的分代布局
- 新生代一块连续空间，老年代一块连续空间

**G1**：
- 把堆划分成多个大小相等的独立区域（Region）
- 每个 Region 可以是 Eden、Survivor、Old、Humongous（大对象）
- Region 之间不需要连续
- 每次只回收一部分 Region，根据回收价值选择

### 4. 算法不同

**CMS**：标记-清除算法
- 优点：并发、低停顿
- 缺点：产生内存碎片，可能导致 Full GC

**G1**：
- 整体看：标记-整理算法
- 局部看（两个 Region 之间）：复制算法
- 不会产生内存碎片

### 5. 停顿时间模型

**CMS**：
- 停顿时间短，但不可预测
- 不能指定最大停顿时间

**G1**：
- 可预测的停顿时间模型
- 可以通过 `-XX:MaxGCPauseMillis` 指定最大停顿时间（默认 200ms）
- G1 会根据每个 Region 的回收价值（回收能释放多少空间、需要多少时间），选择回收价值最高的 Region，在指定时间内完成回收

### 6. 适用场景

**CMS**：
- 重视服务的响应速度
- 希望系统停顿时间最短
- 堆内存不是特别大
- JDK8 及之前常用

**G1**：
- 大内存（建议 6G 以上）
- 需要可预测的停顿时间
- 面向服务端应用
- JDK9 及以后默认

**答案解析**:

CMS 和 G1 是两个重要的垃圾收集器，也是面试高频考点。

最大的区别在于内存布局：CMS 是传统的分代（连续空间），G1 是 Region 划分（不连续）。

G1 的 Region 设计有很多好处：
1. 可以控制停顿时间，每次只回收一部分 Region
2. 不会有内存碎片
3. 不需要连续的内存空间

G1 可以预测停顿时间，这是它的一大卖点。它根据每个 Region 的回收价值来选择回收哪些 Region，在有限的时间内获得最大的回收效益。

G1 虽然也有 STW，但可以控制时间。CMS 的停顿时间也短，但不可控。

**扩展问题**:
- CMS 和 G1 的区别？
- G1 的 Region 是什么？
- G1 为什么可以控制停顿时间？
- G1 用的什么算法？
- 什么场景下选择 G1？

## Q14: 什么是方法区/元空间

**考察点**: 方法区的概念、永久代到元空间的变化、方法区的内容

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. 什么是方法区

方法区是 JVM 运行时数据区的一部分，所有线程共享。

**存储内容**：
- 已被 JVM 加载的**类信息**（类名、访问修饰符、字段描述、方法描述等）
- **常量**
- **静态变量**
- 即时编译器编译后的**代码缓存**
- 运行时常量池

方法区是 JVM 规范中的一个概念，不同的虚拟机有不同的实现。

### 2. 永久代（PermGen）- JDK7 及之前

**HotSpot 在 JDK7 及之前用"永久代"来实现方法区**。

- 永久代在堆内存中（逻辑上独立，但物理上在堆里）
- 大小受 `-XX:PermSize` 和 `-XX:MaxPermSize` 控制
- 默认大小比较小，容易出现 OOM

**JDK7 的变化**：
- 字符串常量池从永久代移到了堆中
- 符号引用移到了 Native Memory

### 3. 元空间（Metaspace）- JDK8 及以后

**JDK8 彻底废弃了永久代，改用元空间**。

- 元空间不在堆中，使用**本地内存**（直接内存）
- 默认情况下，元空间的大小仅受本地内存限制
- 通过 `-XX:MetaspaceSize` 和 `-XX:MaxMetaspaceSize` 控制大小
- 类的元数据存储在 native memory
- 字符串常量池在堆中

### 4. 为什么要废弃永久代

**（1）容易内存溢出**
- 永久代大小不好设置，太小容易 OOM，太大浪费
- 类和方法的大小难以预估

**（2）调优困难**
- 永久代 GC 复杂，Full GC 才会回收永久代
- 永久代的 GC 成本高

**（3）与其他 JVM 统一**
- 其他 JVM（如 JRockit、J9）没有永久代
- 移除永久代便于融合

**（4）HotSpot 自身发展需要**
- 为后续的模块化、Native 方法管理等打基础

### 5. 方法区的垃圾回收

方法区也会有垃圾回收，主要回收两部分内容：
1. **废弃常量**：没有任何地方引用的常量
2. **无用的类**：需要同时满足三个条件：
   - 该类的所有实例都已经被回收
   - 加载该类的 ClassLoader 已经被回收
   - 该类的 java.lang.Class 对象没有在任何地方被引用

方法区的 GC 性价比比较低，所以一般不是 GC 的重点。

**答案解析**:

方法区是 JVM 内存模型中的重要区域，需要理解它的概念和不同 JDK 版本的变化。

JDK7 之前用永久代实现方法区，JDK8 之后用元空间。最大的区别是：永久代在堆中，元空间使用本地内存。

为什么改？因为永久代有很多问题：大小不好设置、容易 OOM、调优困难等。元空间使用本地内存，理论上不会有永久代的 OOM 问题（只要本地内存够）。

方法区也会 GC，但主要回收废弃常量和无用的类。类的卸载条件比较苛刻，需要满足三个条件。

**扩展问题**:

- 永久代和元空间的区别？
- 为什么 JDK8 要移除永久代？
- 方法区会 GC 吗？回收什么？
- 类卸载的条件是什么？

## Q15: 对象的创建过程

**考察点**: 对象创建的五个步骤、内存分配、初始化

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 1. 对象创建的过程

对象的创建分为以下几个步骤：

#### （1）类加载检查

- JVM 遇到 new 指令时
- 首先检查这个指令的参数是否能在常量池中定位到一个类的符号引用
- 检查这个符号引用代表的类是否已被加载、解析和初始化
- 如果没有，先执行相应的类加载过程

#### （2）分配内存

类加载检查通过后，为新生对象分配内存。

**分配方式**：

1. **指针碰撞（Bump The Pointer）**
   - 堆内存是规整的，用过的放一边，没用过的放一边
   - 中间放着一个指针作为分界点指示器
   - 分配内存就是把指针向空闲那边移动一段距离
   - 适用：Serial、ParNew 等带 Compact 过程的收集器

2. **空闲列表（Free List）**
   - 堆内存不是规整的，已使用和空闲的交错在一起
   - JVM 维护一个列表，记录哪些内存块是可用的
   - 分配时从列表中找一块足够大的空间划分给对象
   - 适用：CMS 这种基于 Mark-Sweep 的收集器

**线程安全问题**：

对象创建非常频繁，需要保证线程安全。两种解决方案：

1. **CAS + 失败重试**：对分配内存空间的动作进行同步处理
2. **TLAB（本地线程分配缓冲）**：每个线程在堆中预先分配一小块内存，哪个线程要分配内存，就在哪个线程的 TLAB 上分配。只有 TLAB 用完了，才需要同步分配。通过 `-XX:+/-UseTLAB` 设定

#### （3）初始化零值

内存分配完成后，JVM 将分配到的内存空间都初始化为零值（不包括对象头）。

- 保证了对象的实例字段在 Java 代码中可以不赋初始值就直接使用
- 程序能访问到这些字段的数据类型所对应的零值

如果用了 TLAB，这步可以提前到 TLAB 分配时进行。

#### （4）设置对象头

初始化零值后，JVM 对对象进行必要的设置：
- 这个对象是哪个类的实例
- 如何才能找到类的元数据信息
- 对象的哈希码
- 对象的 GC 分代年龄
- 等等

这些信息放在**对象头**（Object Header）中。

#### （5）执行 init 方法

上面的工作完成后，从 JVM 视角看，对象已经产生了。

但从 Java 程序视角看，对象创建才刚刚开始——`<init>` 方法还没有执行，所有的字段都还是零值。

执行 new 指令之后会接着执行 `<init>` 方法，把对象按照程序员的意愿进行初始化。

### 2. 对象的内存布局

对象在内存中存储的布局可以分为 3 块：
1. **对象头（Header）**：Mark Word + 类型指针
2. **实例数据（Instance Data）**：对象真正存储的有效信息
3. **对齐填充（Padding）**：不是必然存在，起占位符作用

**答案解析**:

对象创建过程是 JVM 面试的基础题，分为五步：类加载检查、分配内存、初始化零值、设置对象头、执行 init 方法。

内存分配的两种方式：指针碰撞和空闲列表。用哪种取决于堆内存是否规整，堆内存是否规整取决于 GC 算法是否有压缩整理功能。

线程安全的两种解决方案：CAS 和 TLAB。TLAB 是每个线程私有的分配缓冲区，避免了多线程竞争。

对象的内存布局也需要了解：对象头、实例数据、对齐填充。

## Q16: 什么是 TLAB

**考察点**: TLAB的概念、作用、优缺点

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 1. 什么是 TLAB

**TLAB（Thread Local Allocation Buffer，本地线程分配缓冲）**：

- 每个线程在 Java 堆中预先分配的一小块内存
- 专门用于该线程创建对象时分配内存
- 每个线程有自己的 TLAB，其他线程不能使用

### 2. 为什么需要 TLAB

对象创建是非常频繁的操作，如果每次创建对象都要在堆上分配内存，需要同步（因为堆是线程共享的），会影响性能。

TLAB 让每个线程有自己的分配缓冲区，线程创建对象时，优先在自己的 TLAB 上分配，不需要同步，提高了效率。

### 3. TLAB 的工作原理

1. 每个线程在堆的 Eden 区分配一块内存作为自己的 TLAB
2. 线程创建对象时，先在自己的 TLAB 中分配
3. 如果 TLAB 空间不够了，再用 CAS 的方式在 Eden 区分配（或者申请新的 TLAB）

```
Eden区
├── TLAB1（线程1专用）
├── TLAB2（线程2专用）
├── TLAB3（线程3专用）
└── 公共Eden区（所有线程共享，CAS分配）
```

### 4. 特点

**优点**：
- 提高对象分配的效率，减少同步开销
- 每个线程在自己的 TLAB 上分配，不需要加锁
- 没有多线程竞争问题

**缺点**：
- 空间有一定浪费（每个线程的 TLAB 可能用不完）
- 是空间换时间的策略

### 5. 相关参数

| 参数 | 说明 |
|------|------|
| -XX:+UseTLAB | 开启TLAB（默认开启） |
| -XX:TLABSize | 设置TLAB大小 |
| -XX:+ResizeTLAB | 自动调整TLAB大小（默认开启） |
| -XX:TLABWasteTargetPercent | TLAB浪费占Eden的比例，默认1% |

### 6. 注意事项

- TLAB 只是分配时线程私有，对象本身还是所有线程共享的
- TLAB 只影响对象的分配，不影响对象的访问
- 大对象会直接在 Eden 区分配，不走 TLAB

**答案解析**:

TLAB 是为了解决对象分配时的线程安全问题和性能问题而设计的。

对象分配是很频繁的操作，如果每次都用 CAS 来分配，性能会受影响。TLAB 让每个线程有自己的分配缓冲区，大部分情况下不需要同步，只有 TLAB 用完了才需要同步。

TLAB 是在 Eden 区中的，属于堆的一部分，只是分配时线程私有。对象本身还是所有线程都可以访问的。

TLAB 会有一定的空间浪费，因为每个线程的 TLAB 可能用不完，但这是空间换时间的策略，总体上是划算的。

- TLAB 是线程私有的吗？对象也是线程私有的吗？
- TLAB 用完了怎么办？

## Q17: JIT 即时编译器

**考察点**: JIT的概念、编译过程、优化技术

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 1. 什么是 JIT

**JIT（Just-In-Time，即时编译器）**：

Java 代码一开始是通过解释器解释执行的，当 JVM 发现某个方法或代码块运行特别频繁（"热点代码"），就会把这些代码编译成**本地机器码**，并且进行各种优化，以提高执行效率。这个编译器就是 JIT 编译器。

### 2. 解释执行和编译执行

**解释执行**：
- 解释器逐条把字节码翻译成机器码执行
- 启动快，执行慢
- 第一次执行就可以开始

**编译执行（JIT）**：
- 把热点代码编译成本地机器码
- 启动慢，执行快
- 需要先编译，但编译后执行效率高

Java 是**解释 + 编译**混合模式，结合了两者的优点：
- 启动时解释执行，快速启动
- 运行过程中，热点代码编译执行，提高性能

### 3. 热点代码

**热点代码**：被多次执行的代码。有两类：

1. **被多次调用的方法**：整个方法作为编译对象
2. **被多次执行的循环体**：以整个方法为编译对象（栈上替换 OSR）

**热点探测**：判断代码是不是热点代码。

两种方式：
1. **基于采样的热点探测**：周期性检查各个线程的栈顶，如果某个方法经常出现在栈顶，就是热点方法
   - 优点：简单、高效
   - 缺点：不精确

2. **基于计数器的热点探测**：为每个方法（甚至代码块）建立计数器，统计执行次数，超过阈值就是热点
   - 优点：精确
   - 缺点：开销大

**HotSpot 使用的是基于计数器的热点探测**。

两个计数器：
- **方法调用计数器**：统计方法被调用的次数
- **回边计数器**：统计循环体执行的次数

### 4. 两种 JIT 编译器

HotSpot 有两个 JIT 编译器：

**Client Compiler（C1 编译器）**：
- 客户端模式
- 编译速度快
- 优化较少
- 启动快

**Server Compiler（C2 编译器）**：
- 服务端模式
- 编译速度慢
- 优化很多
- 启动慢，但运行效率高
- 适用于服务端应用

**分层编译（JDK8 默认开启）**：
- 结合 C1 和 C2 的优点
- 先 C1 编译，快速启动
- 热点代码再用 C2 深度优化

### 5. 常见的 JIT 优化技术

1. **方法内联**：把被调用的方法代码原封不动地"复制"到调用方法中，减少方法调用开销
2. **逃逸分析**：分析对象的作用域，如果对象不会逃逸出方法，可以在栈上分配
3. **标量替换**：把对象拆成标量，直接在寄存器或栈上分配
4. **栈上分配**：对象在栈上分配，方法结束自动销毁，不需要 GC
5. **公共子表达式消除**：如果两个表达式计算结果一样，就只算一次
6. **数组边界检查消除**：如果能确定数组下标不会越界，就去掉边界检查
7. **循环展开**：把循环体展开，减少循环控制的开销
8. **常量传播**：把常量直接代入使用的地方

**答案解析**:

JIT 是 Java 性能优化的重要手段，也是面试常考点。

Java 不是纯解释执行的，也不是纯编译执行的，而是解释 + 编译混合模式。一开始解释执行，热点代码编译执行。

热点代码的判断是基于计数器的，方法调用计数器和回边计数器。

JIT 的优化技术很多，特别是方法内联、逃逸分析、栈上分配这些，经常被问到。

逃逸分析是很重要的优化：如果分析出一个对象不会逃逸出方法，就可以在栈上分配，不需要 GC，大大提高性能。

## Q18: 什么是逃逸分析

**考察点**: 逃逸分析的概念、逃逸类型、优化技术

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 1. 什么是逃逸分析

**逃逸分析（Escape Analysis）**：

分析对象的动态作用域，判断一个对象是否会逃逸出方法或线程。

如果对象不会逃逸，就可以进行一些优化：栈上分配、标量替换、消除同步等。

### 2. 逃逸的类型

**（1）方法逃逸**

对象在方法内定义后，被方法外部引用，导致逃逸出方法。

```java
// 逃逸：返回对象引用
public User createUser() {
    User user = new User(); // user逃逸了
    return user;
}

// 逃逸：赋值给外部变量
public User user;
public void createUser() {
    user = new User(); // user逃逸了
}
```

**（2）线程逃逸**

对象被其他线程访问到，逃逸出当前线程。

```java
// 线程逃逸：被其他线程访问
public static User user;
public void createUser() {
    user = new User(); // 可能被其他线程访问
}
```

逃逸程度从低到高：
- 不逃逸 < 方法逃逸 < 线程逃逸

### 3. 基于逃逸分析的优化

**（1）栈上分配（Stack Allocation）**

如果对象不会逃逸出方法，就可以在栈上分配内存，而不是在堆上分配。

- 方法执行结束，栈帧出栈，对象自动销毁
- 不需要 GC，减轻 GC 压力
- 分配效率高

**（2）标量替换（Scalar Replacement）**

如果对象不会逃逸，并且对象可以被拆散，就把对象的成员变量拆成标量（基本类型），直接在栈上分配这些标量。

```java
// 原始代码
public void test() {
    Point p = new Point(1, 2);
    System.out.println(p.x + p.y);
}

// 标量替换后
public void test() {
    int x = 1;
    int y = 2;
    System.out.println(x + y);
}
```

对象都不用创建了，直接用基本类型，效率更高。

**（3）同步消除（Synchronization Elimination）**

如果对象不会逃逸出线程，就不可能被多个线程同时访问，那么这个对象上的同步操作就可以消除掉。

```java
// 原始代码
public void test() {
    StringBuffer sb = new StringBuffer();
    sb.append("a");
    sb.append("b");
}

// 同步消除后
public void test() {
    // StringBuffer的synchronized被去掉了
}
```

StringBuffer 的方法都是 synchronized 的，但如果 sb 对象不会逃逸出方法，就不可能有线程安全问题，同步可以消除。

### 4. 相关参数

| 参数 | 说明 |
|------|------|
| -XX:+DoEscapeAnalysis | 开启逃逸分析（JDK8默认开启） |
| -XX:+PrintEscapeAnalysis | 打印逃逸分析结果 |
| -XX:+EliminateAllocations | 开启标量替换 |
| -XX:+EliminateLocks | 开启同步消除 |

**答案解析**:

逃逸分析是 JIT 的重要优化技术，也是面试常考点。

逃逸分析本身不是优化，它是其他优化的基础。通过逃逸分析判断对象是否逃逸，然后进行栈上分配、标量替换、同步消除等优化。

栈上分配是最常被问到的。对象在栈上分配，方法结束自动销毁，不需要 GC，大大减少了 GC 的压力。

但不是所有对象都能栈上分配，只有不逃逸的对象才行。而且 HotSpot 实际上不是直接栈上分配，而是通过标量替换来实现的。

**扩展问题**:

- 逃逸有哪几种类型？
- 基于逃逸分析有哪些优化？
- 什么是栈上分配？有什么好处？
- 所有对象都能栈上分配吗？

## Q19: OOM 的常见原因和排查方法

**考察点**: OOM的类型、原因、排查工具和方法

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 1. OOM 的类型

**（1）Java 堆溢出（Java heap space）**

```
java.lang.OutOfMemoryError: Java heap space
```

**原因**：
- 内存泄漏：对象被持有无法释放
- 内存不足：堆太小，对象太多
- 大对象过多：一次性创建过多大对象

**（2）虚拟机栈溢出**

两种情况：
```
java.lang.StackOverflowError // 栈深度溢出
java.lang.OutOfMemoryError: unable to create new native thread // 线程太多
```

**原因**：
- StackOverflowError：递归太深，方法调用链太长
- 无法创建线程：创建的线程太多，栈空间不足

**（3）方法区/元空间溢出**

```
java.lang.OutOfMemoryError: PermGen space // JDK7
java.lang.OutOfMemoryError: Metaspace // JDK8
```

**原因**：
- 加载的类太多，如动态生成大量类
- 反射、动态代理生成的类过多
- 永久代/元空间设置太小

**（4）直接内存溢出**

```
java.lang.OutOfMemoryError: Direct buffer memory
```

**原因**：
- NIO 使用直接内存过多
- 没有设置最大直接内存

### 2. 常见原因总结

1. **内存泄漏**：最常见，长生命周期对象持有短生命周期对象引用
2. **堆内存设置过小**：-Xmx 设置太小
3. **大对象**：一次性加载过多数据到内存
4. **内存碎片**：CMS 等标记清除算法导致
5. **线程过多**：创建大量线程
6. **动态类过多**：反射、动态代理、JSP 等
7. **直接内存泄漏**：NIO DirectByteBuffer

### 3. 排查工具

**（1）jmap**：生成堆转储快照（dump 文件）
```bash
jmap -dump:format=b,file=heap.hprof <pid>
```

**（2）jhat**：分析 dump 文件（不常用，用 MAT 更好）
```bash
jhat heap.hprof
```

**（3）MAT（Memory Analyzer Tool）**：专业的内存分析工具
- 分析内存泄漏
- 查看大对象
- 查看对象引用关系

**（4）VisualVM / JProfiler**：综合分析工具
- 实时监控内存
- 分析堆转储
- 性能分析

**（5）jstat**：查看 GC 情况
```bash
jstat -gc <pid> 1000 10 # 每秒一次，共10次
```

### 4. 排查步骤

1. **获取 dump 文件**
   - 配置 `-XX:+HeapDumpOnOutOfMemoryError`，OOM 时自动生成
   - 或用 jmap 手动生成

2. **分析 dump 文件**
   - 用 MAT 打开 dump 文件
   - 查看 Histogram：哪些对象最多，占用内存最大
   - 查看 Leak Suspects：内存泄漏嫌疑报告
   - 查看 Dominator Tree：支配树，找大对象

3. **定位代码**
   - 找到占用内存最多的对象
   - 查看引用链，找到为什么没被回收
   - 定位到具体代码

4. **解决问题**
   - 如果是内存泄漏：修复泄漏点
   - 如果是内存不足：调大堆内存
   - 如果是大对象：优化代码，分批处理

**答案解析**:

OOM 是实际工作中经常遇到的问题，也是面试常考点。

首先要区分不同类型的 OOM：堆溢出、栈溢出、方法区/元空间溢出、直接内存溢出。不同类型的原因不同。

最常见的是堆溢出，原因可能是内存泄漏，也可能是内存不足。

排查的核心是获取 dump 文件，然后用 MAT 等工具分析。找到占用内存最多的对象，然后看引用链，找到为什么没被回收，定位到代码。

实际工作中，内存泄漏是最常见的原因，需要重点关注。

- jmap：生成 dump 文件
- jstack：查看线程堆栈
- jhat：分析 dump（已被 MAT 取代）

实际排查问题时，一般先用 jps 找到进程 ID，然后用 jstat 看 GC 情况，用 jstack 看线程情况，必要时用 jmap 生成 dump 用 MAT 分析。

这些工具都是面试常考题，需要知道每个工具的作用和基本用法。

## Q1: 什么是RAG，RAG的原理和流程

**考察点**: RAG概念、工作原理、完整流程

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

RAG（Retrieval-Augmented Generation，检索增强生成）是一种结合信息检索与大语言模型生成能力的技术框架。它通过从外部知识库中检索相关文档片段，作为上下文补充到Prompt中，让大模型基于检索到的知识生成更准确、更有时效性的回答。

### RAG的核心原理

RAG的核心思想是：**让大模型"开卷考试"**，即在生成回答前先从知识库中找到相关参考资料，再基于这些资料生成答案，从而减少幻觉、提升事实准确性。

### RAG的完整流程（标准RAG Pipeline）

#### 1. 数据准备阶段（离线/索引阶段）

- **文档加载（Document Loading）**：从各种来源（PDF、Word、网页、数据库等）加载原始文档
- **文档切分（Document Splitting/Chunking）**：将长文档切分成合适大小的文本块（Chunk），常见策略包括按字符切分、按语义切分、递归字符切分等
- **向量嵌入（Embedding）**：将每个文本块通过Embedding模型转换为向量表示
- **向量存储（Vector Store）**：将向量和原始文本存入向量数据库，建立索引

#### 2. 检索生成阶段（在线/查询阶段）

- **查询向量化（Query Embedding）**：将用户的问题转换为向量
- **相似度检索（Retrieval）**：在向量数据库中检索与查询向量最相似的Top K个文本块
- **Prompt构建（Prompt Construction）**：将检索到的相关文本块和用户问题组合成完整的Prompt
- **LLM生成（Generation）**：将Prompt送入大模型，生成基于检索知识的回答

### RAG的关键优势

1. **减少幻觉**：基于真实文档生成，回答有据可依
2. **知识时效性**：知识库可随时更新，无需重新训练模型
3. **成本低廉**：相比微调，RAG的实施和维护成本低很多
4. **可解释性**：可以溯源回答所依据的文档片段
5. **数据安全**：私有知识无需上传训练，适合企业内部知识库

**答案解析**:

RAG是当前大模型应用最主流的技术范式之一，面试中几乎必考。回答时要注意区分**离线索引阶段**和**在线查询阶段**，讲清楚从文档到向量、从查询到生成的完整链路。2026年的RAG技术已经发展到RAG 2.0阶段，出现了GraphRAG、 Adaptive RAG、Modular RAG等进阶形态，但基础RAG流程仍是核心。

**扩展问题**:
- RAG有哪些常见的优化策略？
- 什么是Naive RAG、Advanced RAG、Modular RAG的区别？
- RAG的评估指标有哪些？
- 如何选择合适的Chunk大小和切分策略？

## Q2: RAG和微调（Fine-tuning）的区别和选型

**考察点**: RAG vs 微调、技术选型、适用场景

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

RAG和微调是两种互补的大模型优化技术，它们解决的问题不同，适用场景也各有侧重。

### 核心区别对比

| 维度 | RAG（检索增强生成） | 微调（Fine-tuning） |
|------|---------------------|---------------------|
| **原理** | 检索外部知识+上下文注入 | 调整模型参数，学习新知识 |
| **知识更新** | 实时更新，只需更新知识库 | 重新训练，周期较长 |
| **实现成本** | 低，适合快速迭代 | 高，需要算力和数据 |
| **数据需求** | 原始文档即可 | 需要高质量标注数据 |
| **幻觉控制** | 较好，可溯源 | 较差，知识内化不透明 |
| **回答风格** | 依赖Prompt设计 | 可以学习特定风格和语气 |
| **推理成本** | 较高（需要检索+长上下文） | 较低（直接推理） |
| **可解释性** | 高，可追溯来源 | 低，黑盒 |
| **适用场景** | 知识问答、企业知识库 | 风格迁移、任务定制、能力增强 |

### 选型建议

#### 优先选择RAG的场景：
1. **知识频繁更新**：如产品文档、政策法规、实时资讯
2. **需要事实准确性**：如法律问答、医疗咨询，必须可溯源
3. **数据是原始文档**：没有大量标注数据
4. **快速上线验证**：MVP阶段，需要快速迭代
5. **企业内部知识库**：大量非结构化文档需要检索利用
6. **数据安全敏感**：不愿将数据用于模型训练

#### 优先选择微调的场景：
1. **特定输出格式**：需要严格遵循某种格式或风格
2. **减少推理成本**：RAG需要长上下文，成本更高
3. **学习复杂模式**：如代码生成、特定领域推理能力
4. **数据量充足**：有高质量的指令微调数据
5. **需要情感/人格定制**：如特定品牌语气、角色设定
6. **降低延迟要求**：RAG的检索过程增加了延迟

#### 最佳实践：RAG + 微调结合
在实际项目中，往往是两者结合使用：
- 用微调让模型掌握特定领域的推理能力和输出风格
- 用RAG提供具体的事实性知识和最新信息
- 即"微调学能力，RAG供知识"

**答案解析**:

这道题考察对两种核心技术的深度理解和工程选型能力。回答的关键是要展现出**工程思维**——没有绝对的好坏，只有场景适配。2026年的趋势是：随着模型上下文窗口越来越大（如GPT-4o支持128K甚至200K），RAG的地位依然重要，因为长上下文并不等于精准检索，而且长上下文推理成本高昂。同时，LoRA/QLoRA等参数高效微调技术的普及也让微调门槛大幅降低。

**扩展问题**:
- 什么是参数高效微调（PEFT）？有哪些方法？
- 如何评估RAG和微调的效果？
- RAG的推理延迟通常是多少？如何优化？
- 什么是检索增强微调（Retrieval-Augmented Fine-tuning）？

## Q3: 什么是向量数据库，常用的向量数据库有哪些

**考察点**: 向量数据库概念、作用、主流产品对比

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是向量数据库

向量数据库（Vector Database）是专门用于存储、索引和查询高维向量数据的数据库系统。与传统关系型数据库不同，向量数据库的核心能力是**相似度搜索**——给定一个查询向量，快速找到数据库中与之最相似的向量。

向量数据库的核心能力：

1. **向量存储**：存储Embedding向量及其关联的元数据
2. **近似最近邻搜索（ANN）**：在海量向量中高效检索相似向量
3. **索引构建**：通过各种索引算法（如HNSW、IVF、PQ等）加速检索
4. **元数据过滤**：支持按标签、分类等元数据进行过滤检索
5. **增删改查**：支持向量的动态更新和CRUD操作

### 为什么需要向量数据库

传统数据库无法高效处理高维向量的相似度查询：
- 暴力搜索计算量太大（O(n)复杂度）
- 需要专门的索引结构来加速近似最近邻搜索
- 需要结合元数据过滤和向量检索的混合查询

### 常用的向量数据库

#### 1. 专用向量数据库

| 数据库 | 特点 | 适用场景 |
|--------|------|----------|
| **Pinecone** | 全托管SaaS服务，无需运维，支持大规模 | 企业级应用、快速上线 |
| **Weaviate** | 开源，支持GraphQL，内置模块化 | 开源项目、需要自建 |
| **Qdrant** | Rust编写，高性能，支持过滤，开源 | 性能要求高的场景 |
| **Milvus** | 开源，LF AI基金会项目，分布式架构 | 超大规模向量检索 |
| **Chroma** | 轻量级，Python友好，本地快速原型 | 原型开发、小型项目 |
| **Vespa** | 雅虎开源，功能全面，支持复杂查询 | 搜索推荐系统 |

#### 2. 传统数据库的向量扩展

| 数据库 | 向量支持方式 | 特点 |
|--------|-------------|------|
| **PostgreSQL + pgvector** | 插件扩展 | 已有PG基础设施的首选 |
| **Redis + Redis-VSS** | Redis Stack模块 | 低延迟、缓存场景 |
| **Elasticsearch** | 原生dense_vector | 已有ES搜索基础设施 |
| **MongoDB** | Atlas Vector Search | 文档数据库+向量检索 |

#### 3. 云厂商向量服务

- **AWS OpenSearch Serverless with Vector Search**
- **Azure AI Search (Vector Search)**
- **Google Vertex AI Vector Search (原Matching Engine)**
- **阿里云 向量检索服务（DashVector）**

### 选型建议

1. **快速原型/小项目**：Chroma、FAISS（非数据库，是向量索引库）
2. **企业级生产环境**：Pinecone、Weaviate、Milvus
3. **已有基础设施**：pgvector（PG）、Redis-VSS（Redis）、Elasticsearch
4. **极致性能**：Qdrant、Milvus
5. **云原生**：各云厂商的向量搜索服务

**答案解析**:

向量数据库是RAG技术栈的核心组件之一。面试中要讲清楚向量数据库和传统数据库的本质区别——**从精确匹配到相似度匹配**。2026年的趋势是：向量数据库正在从专用组件向通用数据库的标配能力演进，越来越多的传统数据库加入了向量支持，同时专用向量数据库也在向多模态、混合检索方向发展。

**扩展问题**:
- 向量数据库的索引算法有哪些？（HNSW、IVF、PQ、LSH等）
- 什么是ANN（近似最近邻）搜索？为什么不做精确最近邻？
- 如何选择合适的向量相似度度量方式？（余弦相似度、欧氏距离、内积）
- 向量数据库如何处理亿级以上的向量规模？

## Q4: 什么是Embedding，常用的Embedding模型

**考察点**: Embedding概念、原理、主流模型对比

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是Embedding

Embedding（嵌入）是将离散的、非结构化的数据（如文本、图像、音频）转换为连续的、低维的稠密向量表示的过程。这些向量能够捕获数据的语义信息，使得语义相似的数据在向量空间中距离更近。

#### 核心特性

1. **语义相似性**：语义相近的词/句子，其向量在空间中的距离也近
2. **维度固定**：无论输入文本多长，输出向量的维度是固定的（如1536维、1024维、768维）
3. **可计算**：向量之间可以进行数学运算（加减乘除、相似度计算）
4. **稠密表示**：与One-Hot编码的稀疏向量不同，Embedding是稠密的

#### 经典例子

Word Embedding中的经典类比：
- `vec("国王") - vec("男人") + vec("女人") ≈ vec("女王")`
- `vec("北京") - vec("中国") + vec("法国") ≈ vec("巴黎")`

### Text Embedding的层次

1. **Word Embedding**：词级别的嵌入（Word2Vec、GloVe）
2. **Sentence Embedding**：句子/段落级别的嵌入（Sentence-BERT）
3. **Document Embedding**：整篇文档的嵌入表示

### 常用的Embedding模型

#### 1. 闭源/API模型

| 模型 | 提供商 | 维度 | 特点 |
|------|--------|------|------|
| **text-embedding-3-large** | OpenAI | 3072 | 效果最好，通用领域最强 |
| **text-embedding-3-small** | OpenAI | 1536 | 性价比高，速度快 |
| **text-embedding-ada-002** | OpenAI | 1536 | 经典模型，性价比高 |
| **Cohere embed v3** | Cohere | 1024 | 多语言支持好 |
| **Voyage v3** | Voyage AI | 1024 | 长文本检索效果好 |

#### 2. 开源模型

| 模型 | 开发者/机构 | 维度 | 特点 |
|------|------------|------|------|
| **BGE系列（BGE-M3）** | 智源BAAI | 1024 | 中文效果最好，支持多粒度 |
| **GTE系列（GTE-Qwen2）** | 阿里巴巴 | 1536 | 中英文兼顾，性能优秀 |
| **E5系列（E5-mistral）** | 微软 | 4096 | 通用能力强，支持长文本 |
| **Sentence-BERT** | UKP Lab | 768 | 经典基线模型 |
| **Qwen2.5-Embed** | 通义千问 | 1536 | 2025年新出，中文效果出色 |
| **bge-large-zh-v1.5** | 智源BAAI | 1024 | 中文检索的经典基线 |

#### 3. 多模态Embedding模型

- **CLIP**：OpenAI，文本-图像对齐
- **BLIP-2**：Salesforce，多模态理解
- **Qwen-VL**：通义千问，多模态嵌入
- **CogVLM**：智谱AI，中文多模态

### Embedding选型建议

1. **中文场景优先**：BGE-M3、GTE-Qwen2、Qwen2.5-Embed
2. **英文/通用场景**：OpenAI text-embedding-3、E5系列
3. **私有化部署**：BGE-M3、GTE系列开源模型
4. **快速原型**：OpenAI API
5. **长文档**：支持长上下文的模型（如BGE-M3支持8192 tokens）

**答案解析**:

Embedding是连接非结构化数据和向量数据库的桥梁，也是RAG系统效果的关键因素之一。面试中不仅要知道Embedding是什么，还要能比较不同模型的优劣，理解Embedding质量对RAG效果的影响。2026年的趋势是：Embedding模型的能力不断增强，从单一的文本检索向多模态、长文本、多语言方向发展，同时轻量化的小模型效果也越来越好。

**扩展问题**:
- 如何评估Embedding模型的质量？
- 什么是Embedding的维度？维度越高越好吗？
- 如何处理长文档的Embedding？
- 什么是对称Embedding和非对称Embedding？

## Q5: 什么是LangChain，核心组件有哪些

**考察点**: LangChain框架、核心模块、架构理解

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是LangChain

LangChain是一个用于开发大语言模型（LLM）应用的开源框架，由Harrison Chase于2022年10月创建。它提供了一套标准化的工具和抽象，让开发者可以快速构建基于LLM的应用，如聊天机器人、问答系统、智能Agent等。

LangChain的核心理念：
1. **组件化**：将LLM应用的各个环节抽象为可复用的组件
2. **链式组合**：通过Chain将多个组件串联起来
3. **生态丰富**：集成了上百种LLM、向量数据库、工具等

### LangChain核心组件

#### 1. 模型（Models）

LangChain支持的模型接口：
- **LLM**：大语言模型（如GPT-3.5、Claude、文心一言等）
- **Chat Models**：对话模型，支持消息格式输入输出
- **Embedding Models**：嵌入模型，用于文本向量化

统一的接口设计使得切换不同模型非常方便。

#### 2. 提示模板（Prompts）

- **PromptTemplate**：基础提示模板，支持变量注入
- **ChatPromptTemplate**：对话提示模板，支持多角色消息
- **FewShotPromptTemplate**：少样本提示模板
- 支持动态选择Prompt、模板加载等功能

#### 3. 链（Chains）

Chain是LangChain的核心抽象，将多个组件按顺序串联：
- **LLMChain**：最基础的链，Prompt + LLM + OutputParser
- **RetrievalQA**：检索问答链（RAG）
- **ConversationalRetrievalChain**：带对话历史的RAG链
- **SequentialChain**：顺序链，多步执行
- **RouterChain**：路由链，根据输入选择不同的链

#### 4. 检索增强（Retrieval）

- **Document Loaders**：文档加载器，支持PDF、Word、HTML、Markdown等100+格式
- **Text Splitters**：文本切分器，多种切分策略
- **Vector Stores**：向量数据库集成（Pinecone、Chroma、FAISS等）
- **Retrievers**：检索器，支持多种检索策略

#### 5. 内存（Memory）

用于保存对话历史和上下文信息：
- **ConversationBufferMemory**：完整对话历史
- **ConversationBufferWindowMemory**：滑动窗口记忆
- **ConversationSummaryMemory**：摘要记忆
- **ConversationTokenBufferMemory**：基于Token数的记忆
- **Entity Memory**：实体记忆

#### 6. 代理（Agents）

Agent是LangChain的高级功能，让LLM能够自主决策并使用工具：
- **Tools**：工具集（搜索、计算器、数据库查询等）
- **Toolkits**：工具包，一组相关工具
- **Agent Executor**：代理执行器
- 支持ReAct、Plan-and-Execute等多种Agent范式

#### 7. 回调（Callbacks）

- 支持日志记录、流式输出、追踪等
- 集成LangSmith用于调试和监控

#### 8. 输出解析器（Output Parsers）

将LLM的原始输出解析为结构化数据：
- **PydanticOutputParser**：解析为Pydantic对象
- **JsonOutputParser**：解析为JSON
- **ListOutputParser**：解析为列表
- **RetryOutputParser**：带重试机制的解析器

### LangChain生态系统

- **LangChain**：核心框架
- **LangSmith**：调试、测试、监控、评估平台
- **LangServe**：将LangChain应用部署为API服务
- **LangGraph**：基于图的Agent编排框架（2024年后重点发展方向）

**答案解析**:

LangChain是大模型应用开发的事实标准框架之一。回答这道题要展现出对整个框架体系的理解，而不仅仅是罗列组件名。2026年的LangChain已经发展为一个完整的生态系统，特别是LangGraph的崛起标志着从线性Chain向图结构Agent编排的范式转变。面试中提到LangGraph会加分。

**扩展问题**:
- LangChain和LlamaIndex的区别和选型？
- 什么是LangGraph？它解决了什么问题？
- LangChain的Memory是如何工作的？
- 如何用LangChain实现一个RAG系统？

## Q6: 什么是Agent，Agent的核心能力

**考察点**: Agent概念、核心能力、架构设计

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是Agent

LLM Agent（大语言模型智能体）是一种以大语言模型为"大脑"，能够自主感知环境、进行决策、调用工具并执行任务的智能系统。与传统的RAG或单轮问答不同，Agent具有**自主性**和**目标导向性**——给定一个目标，Agent能够自主规划步骤、选择工具、执行操作，直到完成目标。

### Agent的核心能力

#### 1. 规划（Planning）

将复杂目标分解为可执行的子任务：
- **任务分解**：将大目标拆分为多个小步骤
- **反思与优化**：根据执行结果调整计划
- **多步推理**：通过Chain of Thought进行逐步推理

#### 2. 记忆（Memory）

- **短期记忆/上下文记忆**：对话历史、当前任务状态
- **长期记忆**：知识库、历史经验、用户偏好
- **工作记忆**：当前任务的中间结果和思考过程

#### 3. 工具使用（Tool Use）

调用外部工具获取信息或执行操作：
- **信息获取类**：搜索引擎、知识库、数据库
- **操作执行类**：代码执行、文件操作、API调用
- **计算类**：计算器、数学推理
- **多模态类**：图像生成、语音处理

#### 4. 推理与决策（Reasoning & Decision）

- 理解用户意图和目标
- 评估当前状态与目标的差距
- 选择下一步行动（调用工具、回答问题、继续追问）
- 判断任务是否完成

#### 5. 自主执行（Autonomous Execution）

- 无需人类逐步骤指令
- 能够自主在"思考→行动→观察"循环中迭代
- 处理意外情况和错误重试

### Agent的典型架构

经典的Agent循环（ReAct范式）：
```
用户输入 → 思考(Thought) → 行动(Action) → 观察(Observation) → 思考(Thought) → ... → 最终答案(Final Answer)
```

一个完整的Agent系统通常包含：
1. **LLM核心**：负责推理和决策
2. **工具集**：Agent可调用的外部工具
3. **记忆模块**：保存历史和上下文
4. **规划器**：任务分解和计划制定
5. **执行器**：工具调用和结果获取
6. **反思模块**：评估和优化执行过程

### Agent的应用场景

1. **个人助理**：日程管理、邮件处理、信息查询
2. **代码助手**：代码生成、调试、代码库分析
3. **数据分析Agent**：自动分析数据、生成报告
4. **研究Agent**：文献调研、信息整理
5. **客服Agent**：多轮对话、问题解决
6. **多Agent协作**：多个Agent分工合作完成复杂任务

**答案解析**:

Agent是2024-2026年AI领域最热门的方向之一，被认为是大模型应用的下一个范式。回答这道题要讲清楚Agent和传统LLM应用的本质区别——**从"被动响应"到"主动规划执行"**。2026年的Agent技术已经从单Agent向多Agent协作发展，出现了AutoGPT、CrewAI、AutoGen、LangGraph等多种框架和实现。

- 什么是Plan-and-Execute Agent？和ReAct有什么区别？
- 如何设计Agent的评估指标？

## Q7: ReAct范式是什么

**考察点**: ReAct原理、Agent推理范式、思维+行动结合

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是ReAct范式

ReAct（Reasoning + Acting，推理+行动）是由普林斯顿大学和Google Research在2022年提出的一种Agent推理范式。它的核心思想是：让大语言模型**交替生成推理过程（Thought）和行动（Action）**，通过行动获取外部信息（Observation），再基于新的信息继续推理，形成一个"思考→行动→观察→思考"的迭代循环。

### ReAct的核心循环

```
Question: 用户的问题/目标

Thought: 我需要先做什么？（推理过程）
Action: 调用某个工具/行动（具体行动）
Observation: 工具返回的结果（观察结果）

Thought: 基于观察结果，我接下来应该做什么？
Action: 下一步行动
Observation: 下一步观察结果

...（多轮迭代）

Thought: 我已经有足够的信息来回答了
Final Answer: 最终答案
```

### ReAct的三个关键要素

#### 1. Thought（思考/推理）
- 模型对当前状态的分析和推理
- 解释为什么要采取某个行动
- 体现了模型的"思维过程"
- 类似于Chain of Thought

#### 2. Action（行动）
- 模型决定调用的具体工具或操作
- 格式通常为：动作名称 + 输入参数
- 例如：`Search: "人工智能发展历史"`

#### 3. Observation（观察）
- 工具执行后的返回结果
- 为模型提供新的外部信息
- 是下一轮推理的输入

### ReAct vs 其他范式

#### ReAct vs Chain of Thought (CoT)
- **CoT**：只有推理，没有行动，纯靠模型内部知识
- **ReAct**：推理+行动结合，可以获取外部信息
- ReAct在需要外部知识的任务上表现更优

#### ReAct vs Plan-and-Execute
- **ReAct**：边思考边行动，每步都重新规划，更灵活
- **Plan-and-Execute**：先制定完整计划，再逐步执行，更适合复杂任务
- 现代Agent框架通常结合两者

### ReAct的优势

1. **可解释性强**：每一步都有Thought解释，推理过程透明
2. **事实准确性高**：通过行动获取真实信息，减少幻觉
3. **灵活适应**：可以根据观察结果动态调整策略
4. **错误恢复**：如果行动失败，可以换一种方式重试
5. **人类可干预**：可以在Thought层面理解Agent的决策过程

### ReAct的局限性

1. **步骤较多**：简单问题也可能走多步，效率低
2. **容易跑偏**：多轮迭代后可能偏离原始目标
3. **Token消耗大**：每轮都要把历史放进去
4. **质量依赖模型能力**：模型推理能力差的话效果不好

**答案解析**:

ReAct是Agent最经典、最基础的推理范式，几乎所有Agent框架都支持或基于ReAct。回答时要讲清楚ReAct的三个核心要素（Thought/Action/Observation）以及迭代循环的过程。2026年虽然出现了很多更复杂的Agent范式（如Plan-and-Execute、Reflection、Tree of Thoughts等），但ReAct仍然是基础中的基础，面试必问。

**扩展问题**:
- 什么是Self-Ask与ReAct的区别？
- ReAct的Prompt怎么设计？
- 如何优化ReAct的效率和准确率？
- 什么是ReWOO（Reasoning Without Observation）？

## Q8: 什么是Function Calling/工具调用

**考察点**: Function Calling概念、原理、应用场景

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是Function Calling

Function Calling（函数调用/工具调用）是大语言模型的一项重要能力：模型可以根据用户的意图，自主判断是否需要调用外部函数（工具），并生成符合特定格式的函数调用请求（JSON格式），开发者据此执行实际的函数调用，再将结果返回给模型继续处理。

简单说：**模型不直接执行函数，而是告诉开发者"请帮我调用这个函数，参数是这些"，开发者执行后把结果告诉模型**。

### Function Calling的工作原理

#### 1. 函数定义
开发者提前向模型描述可用的函数信息，包括：
- 函数名称（name）
- 函数功能描述（description）
- 参数列表（parameters）：包括名称、类型、是否必填、描述等
- 使用JSON Schema格式定义

#### 2. 用户提问
用户输入自然语言问题。

#### 3. 模型决策
模型判断：
- 是否需要调用工具？
- 调用哪个工具？
- 传入什么参数？
- 输出结构化的函数调用请求

#### 4. 执行函数
开发者解析模型输出的函数调用格式，实际执行函数/API调用，获取返回结果。

#### 5. 返回结果
将函数执行结果返回给模型，模型基于结果生成最终回答。

### Function Calling的格式示例

以OpenAI API为例：

```python
# 1. 定义函数
functions = [
    {
        "name": "get_weather",
        "description": "获取指定城市的天气信息",
        "parameters": {
            "type": "object",
            "properties": {
                "city": {
                    "type": "string",
                    "description": "城市名称"
                },
                "date": {
                    "type": "string",
                    "description": "日期，格式为YYYY-MM-DD"
                }
            },
            "required": ["city"]
        }
    }
]

# 2. 用户提问后，模型返回函数调用
# model_response: {"name": "get_weather", "arguments": '{"city": "北京", "date": "2026-07-28"}'}

# 3. 执行函数并将结果返回给模型继续生成
```

### Function Calling的应用场景

1. **信息检索增强**：调用搜索引擎、数据库、知识库
2. **API编排**：调用第三方服务（天气、地图、金融等）
3. **代码执行**：执行Python代码、数学计算
4. **智能家居控制**：控制智能设备
5. **数据处理**：数据分析、格式转换
6. **多模态交互**：调用图像生成、语音合成等
7. **企业内部系统集成**：调用内部业务系统

### 主流模型的Function Calling支持

| 模型/厂商 | 工具调用能力 |
|-----------|-------------|
| **GPT-4o / GPT-4** | 强，支持并行调用、结构化输出 |
| **Claude 3.5 Sonnet** | 强，工具调用准确率高 |
| **Gemini 2.0** | 支持函数调用 |
| **通义千问Qwen2.5** | 中文场景工具调用表现优秀 |
| **DeepSeek V3** | 开源模型中工具调用能力强 |
| **Llama 3.1** | 开源，原生支持工具调用 |

### Function Calling的关键技术点

1. **参数提取准确性**：模型能否正确从自然语言中提取参数
2. **意图识别**：模型能否准确判断是否需要调用工具
3. **多工具选择**：多个工具时选择正确的工具
4. **并行调用**：一次调用多个函数（减少轮次）
5. **错误处理**：函数调用失败时的重试和降级策略

**答案解析**:

Function Calling是Agent的核心技术基础，也是大模型从"聊天机器人"走向"智能助手"的关键能力。回答时要讲清楚**模型不执行函数，只生成调用指令**这个核心机制。2026年的Function Calling已经从单函数调用发展到支持并行调用、流式调用、结构化输出等高级能力，同时开源模型的工具调用能力也在快速提升。

## Q9: 什么是Prompt Engineering，常用的Prompt技巧

**考察点**: Prompt工程、核心技巧、应用方法

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是Prompt Engineering

Prompt Engineering（提示工程/提示词工程）是一门研究如何设计和优化输入提示（Prompt），以引导大语言模型生成高质量、符合预期输出的技术和方法论。

好的Prompt可以：
- 提升回答的准确性和相关性
- 控制输出的格式和风格
- 减少模型幻觉
- 提升复杂任务的完成度
- 降低Token消耗

### 常用的Prompt技巧

#### 1. 清晰明确的指令（Clear Instructions）

- 直接告诉模型要做什么，而不是不要做什么
- 使用分隔符区分指令和输入内容
- 明确输出格式和要求

```
请将以下文本总结为3个要点，用中文输出，每点不超过20字：
---
[待总结文本]
---
```

#### 2. Few-Shot Learning（少样本学习）

在Prompt中提供几个示例，让模型学习模式：

```
请将用户输入转换为JSON格式：

输入：张三，25岁，北京人
输出：{"name": "张三", "age": 25, "city": "北京"}

输入：李四，30岁，上海人
输出：{"name": "李四", "age": 30, "city": "上海"}

输入：王五，28岁，广州人
输出：
```

#### 3. Chain of Thought（思维链，CoT）

引导模型逐步推理，而不是直接给出答案：

```
请一步步思考并解答以下问题：
一个商店卖苹果，3个苹果卖10元，买10个以上打8折。
问：买15个苹果需要多少钱？

请先写出推理步骤，再给出最终答案。
```

进阶形式：
- **Zero-Shot CoT**：加上"让我们一步步思考"即可触发
- **Self-Consistency**：多次采样，选最多票的答案
- **Tree of Thoughts**：树形搜索多路径推理

#### 4. 角色设定（Role Prompting）

给模型设定一个专业角色：

```
你是一位资深的Java技术面试官，有10年面试经验。
请根据候选人的简历，提出5个有深度的技术问题，
涵盖基础知识、项目经验和系统设计三个维度。
```

#### 5. 结构化输出（Structured Output）

指定输出的格式结构（JSON、Markdown、XML等）：

```
请分析以下产品评论，输出JSON格式，包含以下字段：
- sentiment: "正面" | "负面" | "中性"
- keywords: 关键词列表
- summary: 一句话摘要

评论内容：[评论文本]
```

#### 6. 自我一致性与反思（Self-Consistency / Reflection）

让模型自我检查和优化答案：

```
请回答以下问题，然后对你的答案进行自我审查，
找出可能的错误或不足，并进行修正。

问题：[用户问题]
```

#### 7. 提示模板分层

将Prompt结构化：
- **System Prompt**：系统级设定（角色、规则、约束）
- **Context**：上下文信息（检索到的文档、历史对话）
- **User Query**：用户具体问题
- **Output Format**：输出格式要求

#### 8. 检索增强提示（RAG Prompting）

将检索到的相关信息插入Prompt中：

```
请根据以下参考资料回答用户问题，如果资料中没有答案，
请回答"根据现有资料无法回答"。

参考资料：
1. [检索片段1]
2. [检索片段2]

用户问题：[用户问题]
```

#### 9. ReAct提示（Reasoning + Acting）

用于Agent场景，引导模型思考-行动-观察迭代：

```
你可以使用以下工具：
- Search: 搜索互联网
- Calculator: 数学计算

使用格式：
Thought: 你的思考
Action: 工具名称
Action Input: 工具输入
Observation: 工具返回结果
...（重复）
Thought: 我现在有了答案
Final Answer: 最终答案
```

### Prompt工程的最佳实践

1. **迭代优化**：Prompt不是一蹴而就的，需要反复测试调整
2. **具体明确**：越具体的指令，输出越可控
3. **分步执行**：复杂任务拆分为多个步骤
4. **提供示例**：Few-shot通常比Zero-shot效果好
5. **约束输出**：明确格式、长度、风格等约束
6. **测试评估**：建立评估集，量化Prompt效果

**答案解析**:

Prompt工程是大模型应用开发的基础能力，也是面试中常考的内容。回答时要从原理到技巧，从简单到复杂地展开，展现出系统性的理解。2026年的趋势是：随着模型能力的增强，简单的Prompt技巧可能不再那么重要，但复杂任务的Prompt设计（如Agent、多步骤推理）仍然是核心能力。同时，Prompt工程正在向更体系化的方向发展，出现了DSPy等自动Prompt优化框架。

- 如何评估Prompt的效果？

## Q10: 什么是Chain of Thought（思维链）

**考察点**: CoT原理、变种、适用场景

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 什么是Chain of Thought

Chain of Thought（思维链，简称CoT）是Google Brain在2022年提出的一种Prompt技术，核心思想是：**让大语言模型在给出最终答案之前，先输出中间的推理步骤**，就像人类解题时的"草稿纸"一样。

传统的Prompt直接让模型输出答案，而CoT引导模型"先思考，再回答"，通过显式的推理过程来提升复杂推理任务的效果。

### CoT的基本形式

#### 标准Prompt（无CoT）：
```
问题：停车场有3辆车，又开来了2辆，然后开走了1辆，现在有几辆车？
答案：4辆
```

#### CoT Prompt：
```
问题：停车场有3辆车，又开来了2辆，然后开走了1辆，现在有几辆车？
思考过程：
一开始有3辆车。
开来2辆后，3 + 2 = 5辆。
开走1辆后，5 - 1 = 4辆。
答案：4辆
```

### CoT的主要形式

#### 1. Few-Shot CoT（少样本思维链）
在Prompt中提供几个带推理过程的示例，让模型模仿这种逐步推理的方式。这是原始CoT论文提出的方法。

#### 2. Zero-Shot CoT（零样本思维链）
不需要示例，只需要在问题后面加上一句话：
> "让我们一步步思考（Let's think step by step）"

就能触发模型的推理能力，效果在很多任务上接近Few-Shot CoT。

#### 3. Self-Consistency（自我一致性）
- 多次运行CoT，得到多个推理路径和答案
- 采用"投票"机制，选择出现次数最多的答案
- 类似于"集思广益"，显著提升准确率

#### 4. Tree of Thoughts（思维树，ToT）
- 将推理过程组织成树状结构
- 每个节点是一个思维状态
- 可以探索多条推理路径，评估和剪枝
- 适合需要深度搜索的复杂问题

#### 5. Graph of Thoughts（思维图，GoT）
- 将推理过程建模为有向图
- 支持更复杂的推理结构（合并、分支、循环）
- 比树状结构更灵活

### CoT为什么有效

1. **分解问题**：将复杂问题分解为多个简单子问题
2. **占用工作记忆**：中间步骤保存在上下文中，减少信息丢失
3. **误差修正**：每一步都可以检查和修正
4. **更好地利用模型知识**：逐步推理帮助模型检索相关知识
5. **可解释性**：推理过程透明，便于调试

### CoT的适用场景

CoT在以下任务中效果显著：
- **算术推理**：数学题、计算题
- **常识推理**：需要常识的推理题
- **符号推理**：逻辑推理、符号操作
- **多步决策**：需要多步骤规划的任务
- **代码生成**：复杂的编程问题

**不适用的场景**：
- 简单的事实问答
- 创意写作
- 简单分类任务

### CoT的局限性

1. **Token消耗大**：推理过程增加了大量Token
2. **推理速度慢**：输出更长的内容需要更多时间
3. **不一定正确**：有推理过程不代表推理正确
4. **模型依赖**：小模型效果不明显，需要足够大的模型
5. **不可控**：推理路径可能偏离预期

**答案解析**:

CoT是大模型推理能力的关键技术之一，也是理解大模型工作原理的重要窗口。回答时要讲清楚CoT的核心思想、主要变种和适用场景。2026年CoT已经从单一技术发展为一个完整的技术谱系，从Zero-Shot CoT到ToT、GoT，再到与Agent结合的各种变体，是大模型推理研究的基础。

## Q11: 大模型的幻觉问题及缓解方法

**考察点**: 幻觉定义、产生原因、缓解策略

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是大模型幻觉

幻觉（Hallucination）是指大语言模型生成的内容在语法和流畅度上看起来合理，但**事实上是错误的、虚构的或没有依据的**。

幻觉的主要表现形式：

1. **事实性幻觉**：编造不存在的事实、数据、人物、事件
   - 例如：编造不存在的论文引用、错误的历史事件日期
2. **推理幻觉**：推理过程逻辑错误，导致结论错误
3. **指令幻觉**：编造不存在的指令或约束
4. **来源幻觉**：编造不存在的引用来源、文献

### 幻觉产生的原因

#### 1. 模型层面
- **训练数据问题**：数据中本身存在错误、矛盾、偏见
- **知识截止日期**：训练数据有时间限制，最新信息不知道
- **参数化知识局限**：模型的知识存储在参数中，检索不精确
- **概率生成本质**：模型基于概率生成下一个token，不保证事实正确
- **知识模糊区**：对于不确定的信息，模型倾向于"编造"而不是说不知道

#### 2. 训练目标层面
- **最大似然训练目标**：只追求生成流畅文本，不追求事实准确
- **RLHF的副作用**：强化学习可能让模型更"自信地胡说"

#### 3. Prompt层面
- 指令不明确，模型不确定正确答案
- 上下文信息不足或有冲突
- 引导性提问导致模型迎合用户预期

### 幻觉的缓解方法

#### 1. 检索增强生成（RAG）
- **原理**：让模型基于检索到的真实文档生成回答
- **效果**：最有效的幻觉缓解手段之一
- **关键点**：检索质量、引用标注、"不知道"的能力

#### 2. 提示工程优化
- **明确指令**：告诉模型"不知道就说不知道"
- **思维链**：让模型逐步推理，暴露错误环节
- **少样本示例**：提供正确的示例引导
- **要求引用**：要求模型标注答案来源
- **自我检查**：让模型验证自己的答案

#### 3. 微调与对齐
- **事实性微调**：用高质量事实数据微调
- **RLHF/RLAIF**：通过人类/AI反馈强化事实准确性
- **"不知道"训练**：训练模型学会表达不确定性
- **Constitutional AI**：基于原则的自我修正

#### 4. 解码策略优化
- **降低温度（Temperature）**：较低的temperature减少随机性
- **Top-p / Top-k采样**：控制输出的多样性
- **Beam Search**：多路径搜索，选择最优路径
- **确定性采样**：使用Greedy Decoding

#### 5. 后处理与验证
- **事实核查**：用搜索引擎或知识库验证关键事实
- **一致性检查**：多次生成，检查答案一致性
- **引用验证**：验证引用来源是否真实存在
- **分类器检测**：训练专门的幻觉检测模型

#### 6. 工具调用
- **搜索引擎**：不确定时主动搜索验证
- **知识库查询**：从可信数据源获取信息
- **计算器/代码执行**：数学问题用工具验证

#### 7. 模型架构改进
- **检索增强模型**：模型原生支持检索（如RETRO）
- **不确定性建模**：让模型能表达置信度
- **模块化知识**：将事实知识与推理能力分离

### 幻觉评估方法

1. **人工评估**：专家标注，金标准但成本高
2. **自动评估**：
   - 事实一致性模型（如FactScore、TruthfulQA）
   - 基于检索的事实核查
   - 自一致性检查
3. **引用准确率**：检查引用是否真实支持答案

**答案解析**:

幻觉是大模型应用中最核心的挑战之一，也是面试高频问题。回答时要从"是什么→为什么→怎么办→怎么评估"的逻辑链条展开。2026年的技术发展趋势是：幻觉问题虽然没有被彻底解决，但通过RAG+工具调用+自我验证的组合方案，在很多场景下已经可以将幻觉控制在可接受的范围内。同时，学术界也在从模型架构层面探索更根本的解决方案。

**扩展问题**:

- RAG就能完全解决幻觉问题吗？为什么？
- 什么是Self-Correction（自我修正）？
- 如何在产品中处理不可避免的幻觉？

## Q12: 什么是上下文窗口（Context Window）

**考察点**: 上下文窗口概念、影响、优化策略

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是上下文窗口

上下文窗口（Context Window）是指大语言模型在一次推理中能够处理的最大Token数量，包括输入的Prompt和输出的回答两部分。

简单说：**上下文窗口就是模型的"短期记忆容量"——它能同时看到多少内容**。

### 关键概念

#### 1. 输入Token + 输出Token = 总Token
上下文窗口是输入和输出共享的。例如，一个128K上下文的模型：
- 如果输入用了100K Token，那么输出最多只能有28K Token
- 输入越长，留给输出的空间越少

#### 2. 上下文长度的演进
- **GPT-3**：2K → 175B参数时代的标准
- **GPT-3.5**：4K → 8K → 16K → 128K
- **GPT-4**：8K → 32K → 128K → 200K（GPT-4o）
- **Claude 3**：200K → 1M（Claude 3 Opus）
- **Gemini 2.0**：1M+
- **开源模型**：从4K到128K甚至1M不等（如Llama 3.1 405B支持128K）

### 大上下文窗口的优势

1. **长文档处理**：可以直接输入整本书、长报告
2. **少样本学习**：可以放入更多示例
3. **RAG优化**：可以放入更多检索片段，减少遗漏
4. **长对话**：支持更长的多轮对话历史
5. **代码理解**：可以理解整个代码库
6. **减少信息丢失**：不需要频繁摘要或截断

### 大上下文窗口的挑战

#### 1. 成本问题
- Token费用通常是线性增长的，128K输入比4K贵32倍
- 长上下文推理的计算成本更高

#### 2. 速度问题
- 上下文越长，推理速度越慢
- 预填充阶段（处理输入）的时间与上下文长度正相关

#### 3. "中间迷失"问题（Lost in the Middle）
- 研究发现，模型对上下文开头和结尾的信息记忆更好
- 中间部分的信息容易被忽略
- 并非上下文越长，效果就线性提升

#### 4. 注意力机制的限制
- Transformer的自注意力复杂度是O(n²)
- 超长上下文需要特殊的优化技术

### 长上下文技术

模型实现长上下文的技术方案：

1. **位置编码优化**
   - RoPE（旋转位置编码）：支持通过外推扩展上下文
   - ALiBi：不使用位置编码，用注意力偏置
   - YaRN：改进的RoPE外推方法

2. **注意力优化**
   - FlashAttention：GPU显存优化的注意力实现
   - 滑动窗口注意力（Sliding Window Attention）
   - 稀疏注意力（Sparse Attention）
   - 线性注意力（Linear Attention）

3. **上下文压缩技术**
   - 关键信息提取和摘要
   - 向量检索选择相关片段
   - 层次化注意力

### 实际应用中的策略

1. **合理利用RAG**：不要盲目追求大上下文，用检索筛选相关内容
2. **上下文窗口管理**：
   - 对话历史摘要（Summary）
   - 滑动窗口（只保留最近N轮）
   - 实体提取和记忆
3. **成本控制**：在满足需求的前提下，选择合适的上下文长度
4. **信息排序**：重要信息放在开头或结尾（利用首因/近因效应）
5. **分块处理**：超长文档分块处理，再汇总结果

**答案解析**:

上下文窗口是理解大模型能力边界的核心概念。回答时要讲清楚上下文窗口的含义、发展趋势、技术挑战和应用策略。2026年的大模型上下文窗口已经普遍达到128K以上，部分模型支持1M甚至更长，但实际应用中"大上下文≠好效果"，如何合理利用和管理上下文才是关键。同时，上下文窗口和RAG是互补关系，不是替代关系。

- RoPE位置编码为什么支持外推？
- 大上下文窗口会完全取代RAG吗？
- 如何评估模型在长上下文中的表现？

## Q13: 什么是Token，如何计算Token数量

**考察点**: Token概念、分词原理、计费与优化

**难度**: 简单

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是Token

Token（令牌/词元）是大语言模型处理文本的基本单位。模型不是逐字或逐词处理文本的，而是先将文本切分成一个个Token，再对每个Token进行处理。

简单说：**Token是模型"读"和"写"的最小单位**。

### Token的构成

Token不一定是完整的单词，它可以是：
- **完整的词**：如 "hello"、"人工智能"
- **词的一部分**：如 "unhappily" 可能被切为 "un", "happi", "ly"
- **标点符号**：如 ","、"。"、"！"
- **数字**：如 "2026" 可能是一个或多个Token
- **特殊符号**：如空格、换行符

### Token与字符/单词的大致换算

**英文**：
- 1个Token ≈ 4个英文字符
- 1个Token ≈ 0.75个英文单词
- 100个英文单词 ≈ 133个Token

**中文**：
- 1个Token ≈ 1-2个汉字
- 100个汉字 ≈ 50-100个Token（取决于分词方式）
- 中文的Token效率通常比英文低（同样内容消耗更多Token）

### 分词算法（Tokenization）

主流大模型使用的分词方法：

#### 1. BPE（Byte-Pair Encoding，字节对编码）
- GPT系列、Llama系列使用
- 原理：从字符开始，不断合并出现频率最高的字符对
- 优点：词表大小可控，能处理任意文本
- 结果：常见词是完整的，罕见词被拆成子词

#### 2. WordPiece
- BERT、早期Google模型使用
- 与BPE类似，但合并策略不同（基于似然最大化）

#### 3. Unigram
- T5、XLNet使用
- 从一个大词表开始，逐步删除低概率词

#### 4. SentencePiece
- 支持多种分词算法的工具库
- 支持直接处理原始字节，不需要预处理

### 为什么需要Token

1. **控制词表大小**：如果每个词都是一个Token，词表会无限大
2. **处理未登录词**：子词分词可以处理任何新词
3. **共享词素**：不同形式的词共享词根，模型更容易学习
4. **计算效率**：固定词表大小便于模型架构设计

### 如何计算Token数量

#### 方法1：使用官方工具
- **OpenAI Tokenizer**：OpenAI官网提供的在线工具
- **tiktoken**：OpenAI开源的Python分词库
- **Hugging Face Tokenizers**：通用分词库

```python
# 使用tiktoken计算
import tiktoken
encoding = tiktoken.encoding_for_model("gpt-4o")
text = "你好，世界！Hello, World!"
tokens = encoding.encode(text)
print(f"Token数量: {len(tokens)}")
```

#### 方法2：估算
- 英文：字符数 ÷ 4 ≈ Token数
- 中文：汉字数 ÷ 1.5 ≈ Token数
- 中英文混合：按比例估算

#### 方法3：API返回
大多数LLM API会在返回结果中包含Token使用量：
- `prompt_tokens`：输入Token数
- `completion_tokens`：输出Token数
- `total_tokens`：总Token数

### Token与成本

大模型API通常按Token计费：
- 输入Token（Input/Prompt Tokens）：价格较低
- 输出Token（Output/Completion Tokens）：价格较高，通常是输入的2-3倍

成本优化策略：
1. 精简Prompt，去除冗余内容
2. 使用更短的系统提示
3. 对话历史摘要，而不是保留全部
4. RAG中控制检索片段数量
5. 选择合适的模型（小模型更便宜）
6. 缓存常用的Embedding和Prompt

**答案解析**:

Token是大模型最基础的概念之一，但面试中经常被问到，因为它直接关系到成本、性能和应用设计。回答时要讲清楚Token是什么、为什么用Token而不是字/词、如何计算、以及和成本的关系。2026年虽然模型越来越便宜，但Token仍然是大模型应用的核心成本因素，Token优化是工程实践中的重要技能。

- BPE分词的具体过程是怎样的？
- Token数量和模型显存占用的关系？
- 什么是Token的位置编码？

## Q14: RAG的优化方法有哪些（提升准确率的手段）

**考察点**: RAG优化策略、全链路优化思维

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

RAG的优化是一个系统性工程，需要从数据、索引、检索、生成、评估等全链路进行优化。以下是各环节的主要优化方法：

### 一、数据预处理优化

#### 1. 文档清洗
- 去除格式标签、页眉页脚、目录等噪声
- 统一格式（编码、标点、空格）
- 提取结构化信息（标题、表格、列表）

#### 2. 文档分块（Chunking）优化
- **选择合适的Chunk大小**：通常200-1000字，需要权衡
- **重叠（Overlap）**：相邻Chunk之间保留重叠，避免上下文断裂
- **语义切分**：按语义边界切分（如句子、段落、章节），而不是按字符硬切
- **递归字符切分**：优先按段落、句子切分，不行再按字符
- **结构化切分**：根据文档结构（标题层级）进行切分
- **小分块+父文档**：检索用小分块，返回用父文档（Parent Document Retrieval）

#### 3. 数据增强
- 为每个Chunk生成问题、摘要、关键词
- 多语言翻译增强
- 同义词改写

### 二、Embedding优化

#### 1. 模型选择
- 选择领域适配的Embedding模型
- 中文场景优先选择中文优化的模型（BGE-M3、GTE等）
- 考虑Embedding维度和效果的平衡

#### 2. 微调Embedding模型
- 用领域数据微调Embedding模型
- 使用对比学习提升领域内效果
- 训练查询-文档对的对齐模型

#### 3. 查询优化
- **查询改写（Query Rewriting）**：用LLM改写用户问题，使其更适合检索
- **查询扩展（Query Expansion）**：扩展同义词、相关概念
- **HyDE（Hypothetical Document Embeddings）**：先用LLM生成一个假设的答案，再用这个答案去检索
- **多查询检索（Multi-Query）**：生成多个不同角度的查询，分别检索后合并

### 三、检索策略优化

#### 1. 混合检索（Hybrid Search）
- 向量检索 + 关键词检索（BM25）结合
- 兼顾语义相似度和关键词匹配
- 使用RRF（Reciprocal Rank Fusion）等方法融合结果

#### 2. 重排序（Rerank）
- 先用向量检索召回Top K（如Top 50）
- 再用更强的Rerank模型精排到Top N（如Top 5）
- 常用模型：Cohere Rerank、BGE-Reranker、Cross-Encoder

#### 3. 检索策略
- **MMR（最大边际相关性）**：在相关性和多样性之间平衡
- **元数据过滤**：先按时间、类别等过滤，再做向量检索
- **分层检索**：先粗筛再精筛
- **Self-RAG**：模型自己判断是否需要检索、检索什么

### 四、索引优化

#### 1. 索引算法选择
- **HNSW**：图索引，速度快、精度高，最常用
- **IVF**：倒排文件，适合大规模数据
- **PQ/OPQ**：乘积量化，压缩向量，节省空间

#### 2. 多索引策略
- 按主题、时间、业务线分库
- 不同类型文档使用不同的索引策略

### 五、生成阶段优化

#### 1. Prompt优化
- 明确指示模型只基于检索内容回答
- 设计"不知道"的兜底机制
- 要求引用来源（增加可信度，减少幻觉）
- 结构化输出格式

#### 2. 上下文管理
- 选择最相关的片段，控制上下文长度
- 对检索结果进行排序和去重
- 长上下文时注意"Lost in the Middle"问题

#### 3. 推理优化
- 使用Chain of Thought提升推理准确性
- 让模型自我验证答案
- 多轮生成，逐步精炼

### 六、高级RAG技术

#### 1. GraphRAG
- 从文档中提取实体和关系，构建知识图谱
- 结合图检索和向量检索
- 适合需要多跳推理和全局理解的场景

#### 2. Adaptive RAG
- 根据问题类型自适应选择检索策略
- 简单问题直接回答，复杂问题走RAG
- 动态调整检索的数量和方式

#### 3. Modular RAG
- 模块化的RAG架构，各组件可替换
- 支持多种检索策略和生成策略

#### 4. Corrective RAG
- 检索后评估结果质量

## Q15: 什么是重排序（Rerank），作用是什么

**考察点**: Rerank概念、原理、与向量检索的关系

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 什么是重排序

重排序（Rerank）是RAG检索流程中的一个关键环节：先用向量检索（或混合检索）快速召回一批候选文档（通常是Top 50-100），然后用一个更强大但更慢的模型对这些候选文档进行精细排序，选出最相关的Top N个文档传给LLM生成答案。

简单说：**粗筛找候选，精排选最优**。

### 为什么需要Rerank

向量检索的问题：
1. **Embedding是双向编码器（Bi-Encoder）**：查询和文档分别编码，交互信息少
2. **精度有限**：为了速度牺牲了一定的精度
3. **语义匹配不够精细**：对细微语义差异的捕捉能力有限

Rerank模型使用**交叉编码器（Cross-Encoder）**：
- 查询和文档一起输入模型
- 可以做更深度的语义交互
- 精度更高，但速度慢（不能用于大规模检索）

### Rerank的工作流程

```
用户查询
    ↓
[向量检索/混合检索] → 快速召回 Top K（如K=50或100）
    ↓
[Rerank模型] → 精细打分排序 Top N（如N=5或10）
    ↓
Top N文档 → 送入LLM生成回答
```

### 两阶段检索的优势

1. **精度更高**：Rerank模型做深度语义匹配，准确率显著提升
2. **效率可控**：第一阶段保证速度，第二阶段只处理少量候选
3. **成本平衡**：在效果和性能之间取得最佳平衡
4. **灵活组合**：第一阶段可以用混合检索，第二阶段用Rerank精排

### 常用的Rerank模型

#### 1. 闭源/API模型
- **Cohere Rerank 3**：业界领先的Rerank模型，支持多语言
- **Jina Reranker**：Jina AI提供，效果优秀
- **Voyage Reranker**：Voyage AI提供

#### 2. 开源模型
- **BGE-Reranker**：智源BAAI开源，中文效果好
  - `bge-reranker-large`、`bge-reranker-v2-m3`
- **GTE Reranker**：阿里巴巴开源
- **Cross-Encoder系列**：Sentence-Transformers提供
  - `cross-encoder/ms-marco-MiniLM-L-12-v2`
- **Qwen Reranker**：通义千问开源Rerank模型
- **bce-reranker**：网易有道开源

### Bi-Encoder vs Cross-Encoder

| 维度 | Bi-Encoder（向量检索） | Cross-Encoder（Rerank） |
|------|----------------------|----------------------|
| **输入方式** | 查询和文档分别编码 | 查询和文档一起输入 |
| **交互方式** | 只有最后一步计算相似度 | 全程深度交互 |
| **速度** | 快（预计算+向量检索） | 慢（每个文档都要过模型） |
| **精度** | 较低 | 较高 |
| **适用规模** | 百万/亿级 | 百/千级（两阶段中的第二阶段） |
| **索引方式** | 需要建立向量索引 | 不需要（在线计算） |

### Rerank的最佳实践

#### 1. 召回数量选择
- 召回太少：漏掉相关文档（召回率低）
- 召回太多：Rerank计算量大，延迟高
- 经验值：Top 50-100个候选，Rerank后取Top 5-10

#### 2. 阈值设置
- 设置最低相似度阈值，过滤掉不相关的结果
- 没有达到阈值的文档不送入LLM

#### 3. 与混合检索结合
- 第一阶段用BM25 + 向量检索的混合检索
- 第二阶段用Rerank精排
- 三重保障，效果最佳

#### 4. 领域适配
- 通用Rerank模型在特定领域可能效果不好
- 可以用领域数据微调Rerank模型

### Rerank的局限性

1. **增加延迟**：多了一步推理，整体响应时间变长
2. **增加成本**：多调用一次模型
3. **模型依赖**：Rerank质量取决于模型能力
4. **长文档处理**：文档太长时Cross-Encoder效果下降

**答案解析**:

Rerank是RAG优化中投入产出比很高的一项技术，通常能带来显著的准确率提升。回答时要讲清楚两阶段检索的设计思想——**用速度换精度，分层处理**。2026年Rerank已经成为生产级RAG系统的标配，新的模型也在不断提升Rerank的效果和效率。同时，也出现了一些新的方向，如轻量级Rerank模型、多模态Rerank等。

## Q16: 什么是LangGraph，和LangChain的区别

**考察点**: LangGraph概念、Agent编排、与LangChain关系

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是LangGraph

LangGraph是LangChain团队在2024年推出的一个基于**图结构**的Agent编排框架。它扩展了LangChain的能力，让开发者可以构建更复杂、更可控的有状态Agent应用。

LangGraph的核心理念：**用有向图（Directed Graph）来表示Agent的工作流，节点是函数/工具，边是状态转移**。

### LangGraph的核心概念

#### 1. State（状态）
- 图中流转的共享数据结构
- 每个节点读取和更新State
- 支持状态的累加、合并和持久化

#### 2. Nodes（节点）
- 图中的计算单元
- 每个节点是一个函数，接收State，返回更新后的State
- 可以是LLM调用、工具执行、数据处理等

#### 3. Edges（边）
- 连接节点的有向边
- 定义状态流转的方向

#### 4. Conditional Edges（条件边）
- 根据当前State动态决定下一个节点
- 实现分支、循环等控制流

#### 5. Entry Point & Finish
- 入口节点：图的起点
- 结束节点：图的终点

### LangGraph的典型Agent模式

#### 1. ReAct Agent（思考-行动循环）
```
开始 → Agent(思考+决策) → 条件判断 → 工具调用 → Agent → ... → 结束
                                          ↓
                                       直接回答 → 结束
```

#### 2. Plan-and-Execute Agent
```
开始 → 规划 → 执行计划 → 评估 → 完成？ → 是 → 结束
                               ↓ 否
                            重新规划
```

#### 3. Multi-Agent协作
```
监督Agent → 分配任务 → [Agent1] [Agent2] [Agent3] → 汇总 → 结束
```

### LangGraph vs LangChain 的区别

| 维度 | LangChain | LangGraph |
|------|-----------|-----------|
| **编排方式** | 线性的Chain（链式） | 图结构（节点+边） |
| **控制流** | 固定顺序，分支能力弱 | 支持分支、循环、条件跳转 |
| **状态管理** | Memory模块，较复杂 | 内置State，天然有状态 |
| **循环能力** | 弱（需要特殊处理） | 原生支持循环（Agent循环） |
| **适用场景** | 简单RAG、单轮对话、顺序处理 | 复杂Agent、多步骤推理、多Agent协作 |
| **灵活性** | 较低，流程固定 | 高，可动态调整路径 |
| **可观测性** | 回调机制 | 每步状态清晰，便于调试 |
| **学习曲线** | 较平缓 | 有一定学习成本 |
| **定位** | 通用LLM应用框架 | 专业Agent编排框架 |

### 为什么需要LangGraph

传统LangChain的Chain是线性的，不适合Agent场景：
1. **Agent需要循环**：思考→行动→观察→思考...是一个循环
2. **Agent需要分支**：有时调用工具，有时直接回答
3. **Agent需要状态管理**：每一步的结果都要累积
4. **Agent需要持久化**：支持断点续跑、人类介入

LangGraph用图结构优雅地解决了这些问题。

### LangGraph的优势

1. **原生支持循环**：Agent的思考-行动循环天然适用
2. **灵活的控制流**：条件边支持复杂的分支逻辑
3. **内置状态管理**：统一的State机制，减少心智负担
4. **支持人工介入**：Human-in-the-loop，人类可以在节点间介入
5. **时间旅行**：可以回溯到任意状态重新执行
6. **持久化**：支持检查点，随时保存恢复
7. **流式输出**：支持Token级和步骤级的流式输出
8. **并行执行**：支持节点并行执行

### LangGraph的应用场景

1. **复杂Agent**：需要多轮工具调用的智能体
2. **多Agent系统**：多个Agent协作完成任务
3. **工作流自动化**：需要分支、循环的复杂工作流
4. **研究工作流**：文献调研、数据分析流水线
5. **代码Agent**：代码生成、调试、测试的循环

**答案解析**:

LangGraph是2024-2026年大模型应用开发的重要技术趋势，代表了从线性Chain向图结构Agent编排的范式转变。回答时要讲清楚LangGraph解决了什么问题、和LangChain的关系（不是替代，而是增强）、以及核心概念。2026年LangGraph已经成为构建生产级Agent的事实标准框架，面试中提到LangGraph会展现出对前沿技术的关注。

## Q17: 大模型的推理加速方法有哪些

**考察点**: 推理优化、性能优化、推理引擎

**难度**: 困难

**频率**: ⭐⭐⭐⭐

**标准答案**:

大模型推理是计算密集型任务，推理加速是大模型应用落地的关键。以下从不同层面介绍主要的推理加速方法：

### 一、算法层面优化

#### 1. 模型压缩
- **量化（Quantization）**：
  - 8-bit量化：精度损失小，显存减半
  - 4-bit量化（GPTQ、AWQ、QLoRA）：显存大幅减少
  - 2-bit/3-bit量化：极致压缩，精度损失较大
- **剪枝（Pruning）**：移除不重要的权重
- **知识蒸馏（Distillation）**：大模型教小模型
- **模型结构优化**：MoE、稀疏注意力等

#### 2. 推理策略优化
- **KV Cache优化**：
  - 缓存之前Token的Key和Value，避免重复计算
  - 分页注意力（PagedAttention）：像操作系统管理内存一样管理KV Cache
  - 是vLLM等推理引擎的核心技术
- **投机采样（Speculative Decoding）**：
  - 用小模型（草稿模型）快速生成候选Token
  - 用大模型验证，一次性接受多个Token
  - 可以2-3倍加速，几乎无精度损失
- **Medusa / Lookahead Decoding**：
  - 多个预测头并行预测未来Token
  - 不需要额外的草稿模型
- **并行解码**：批量处理，提高吞吐

### 二、系统层面优化

#### 1. 推理引擎优化
| 引擎 | 特点 |
|------|------|
| **vLLM** | PagedAttention，高吞吐，服务化部署首选 |
| **TensorRT-LLM** | NVIDIA官方，极致性能优化 |
| **vLLM + TensorRT-LLM** | 两者结合，效果最佳 |
| **Text Generation Inference (TGI)** | Hugging Face官方，易用稳定 |
| **SGLang** | 结构化生成，RadixAttention，性能优秀 |
| **llama.cpp** | CPU/Mac推理，GGUF格式，边缘部署 |
| **MLC LLM** | 跨平台部署优化 |
| **DeepSpeed-MII** | 微软DeepSpeed团队 |

#### 2. 内存优化
- **KV Cache复用**：相同前缀的请求共享KV Cache
- **分页注意力（PagedAttention）**：动态分配，减少内存碎片
- **显存共享**：多模型共享显存
- **CPU Offload**：部分计算放到CPU/内存

#### 3. 调度优化
- **连续批处理（Continuous Batching）**：
  - 不等一个Batch完成，随时插入新请求
  - 大幅提升GPU利用率和吞吐
- **优先级调度**：按优先级处理请求
- **动态批大小**：根据负载自动调整

### 三、硬件层面优化

#### 1. GPU选型
- **训练**：A100、H100、H200（高显存、高带宽）
- **推理**：A10、A30、L4、L40s（性价比高）
- **消费级**：RTX 4090、RTX A6000（小模型/原型）
- **NVIDIA Blackwell架构**：GB200，推理性能大幅提升

#### 2. 硬件加速技术
- **Tensor Core**：FP8、FP16矩阵运算加速
- **Transformer Engine**：Hopper架构的FP8支持
- **NVLink / NVSwitch**：多GPU高速互联
- **MIG**：GPU实例分割，提升利用率

### 四、服务层面优化

#### 1. 模型服务化
- **统一接口**：OpenAI兼容API
- **负载均衡**：多实例负载分担
- **弹性伸缩**：根据流量自动扩缩容

#### 2. 缓存策略
- **前缀缓存（Prefix Caching）**：缓存相同的系统提示和对话历史
- **Embedding缓存**：缓存常用查询的Embedding
- **结果缓存**：相同问题直接返回缓存答案

#### 3. 请求优化
- **流式输出（Streaming）**：边生成边返回，降低首Token延迟

1. **选择合适的模型**：在满足需求的前提下选最小的模型
2. **上下文管理**：控制输入长度，减少Token数

## Q18: 什么是LoRA/QLoRA

**考察点**: 参数高效微调、LoRA原理、QLoRA优势

**难度**: 中等

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

### 什么是LoRA

LoRA（Low-Rank Adaptation，低秩适配）是一种**参数高效微调**（Parameter-Efficient Fine-Tuning, PEFT）技术，由微软在2021年提出。它的核心思想是：**不直接修改原始模型的权重，而是通过训练两个低秩矩阵来模拟权重的更新**。

### LoRA的原理

#### 传统微调
- 更新模型所有权重
- 需要的参数量 = 模型总参数量
- 例如：7B模型微调需要7B个参数的显存

#### LoRA微调
- 原始模型权重冻结（不更新）
- 在某些层（通常是注意力层的Q、V矩阵）上添加两个低秩矩阵A和B
- 前向传播时：`output = Wx + BAx`，其中B是r×d，A是d×r，r是秩（通常很小，如4-64）
- 只训练A和B这两个矩阵的参数
- 参数量 = 2 × d × r（d是维度，r是秩）

#### 低秩的含义
- 秩r远小于原始维度d
- 例如：d=4096，r=8，则参数减少4096/8=512倍
- 理论基础：大模型的权重更新本质上是低秩的

### LoRA的优势

1. **显存占用低**：只训练少量参数，大幅减少显存需求
   - 7B模型全量微调需要约100GB显存
   - LoRA微调只需要约10-20GB显存
2. **训练速度快**：参数少，计算量小
3. **成本低**：不需要昂贵的A100/H100，消费级GPU也能微调7B模型
4. **多任务灵活**：每个任务一个LoRA权重，切换方便
   - 原始模型权重不变
   - 不同任务加载不同的LoRA权重
   - 可以合并多个LoRA权重
5. **无推理开销**：训练后可以将LoRA权重合并到原始模型中，推理时没有额外开销
6. **效果好**：在很多任务上接近全量微调的效果

### LoRA的关键参数

- **r（秩）**：LoRA矩阵的秩，越大参数量越多，通常4-64
- **alpha（缩放系数）**：控制LoRA输出的权重，通常设为r的2倍
- **目标层（target_modules）**：哪些层应用LoRA，通常是q、v，也可以是q、k、v、o
- **dropout**：LoRA的dropout率

### 什么是QLoRA

QLoRA（Quantized LoRA，量化LoRA）是华盛顿大学在2023年提出的技术，在LoRA的基础上进一步降低显存需求。

#### QLoRA的核心创新
1. **4位量化基础模型**：将预训练模型量化为4位（NF4格式）
2. **反向传播时反量化**：只在计算梯度时反量化
3. **分页优化器**：用CPU内存做分页，处理显存峰值
4. **双重量化**：量化常量本身也被量化

#### QLoRA的效果
- **7B模型**：仅需约5GB显存即可微调
- **13B模型**：约10GB显存
- **70B模型**：约48GB显存（单张24GB显卡不够，但两张可以）
- 效果接近全量微调（在很多任务上差距小于1%）

### QLoRA的关键技术

1. **NF4（NormalFloat 4-bit）**：
   - 专门为神经网络权重设计的4位量化格式
   - 比普通的4位量化精度更高
   - 基于权重服从正态分布的假设

2. **双重量化（Double Quantization）**：
   - 将量化的缩放因子也量化
   - 进一步节省显存

3. **分页优化器（Paged Optimizers）**：
   - 利用NVIDIA的统一内存特性
   - 显存不够时自动将优化器状态转到CPU内存
   - 类似操作系统的虚拟内存

### LoRA/QLoRA的应用场景

1. **领域适配**：将通用模型适配到特定领域（法律、医疗、金融）
2. **指令微调**：用指令数据让模型学会遵循指令
3. **风格迁移**：学习特定的写作风格、回复语气
4. **工具调用增强**：提升模型的工具调用能力
5. **个性化**：针对个人用户的偏好微调
6. **多任务学习**：每个任务一个LoRA适配器

### LoRA的局限性

1. **不是所有任务都适合**：需要大幅改变模型行为的任务可能效果有限
2. **秩的选择需要调参**：r太小可能容量不足，太大失去效率优势
3. **多LoRA叠加可能有干扰**：多个LoRA同时加载时效果可能不如预期
4. **仍然需要一定的训练数据**：数据太少时效果不好

**答案解析**:

LoRA/QLoRA是大模型微调领域最核心的技术，极大地降低了微调的门槛和成本。回答时要讲清楚LoRA的原理（低秩分解）、优势（参数高效）、以及QLoRA在此基础上的创新（4位量化+分页优化器）。2026年LoRA已经成为微调的标准做法，全量微调只有在数据量非常大、模型需要彻底改造时才会使用。同时，也出现了很多LoRA的变体，如LoRA-FA、DoRA、AdaLoRA等。

- 全量微调、LoRA、QLoRA三者的效果对比？
- LoRA的r值怎么选？对效果有什么影响？
- 什么是DoRA（Weight-Decomposed Low-Rank Adaptation）？

## Q19: 什么是RLHF

**考察点**: RLHF概念、流程、对齐技术

**难度**: 中等

**频率**: ⭐⭐⭐⭐

**标准答案**:

### 什么是RLHF

RLHF（Reinforcement Learning from Human Feedback，基于人类反馈的强化学习）是一种让大语言模型的输出更符合人类偏好的对齐技术。它通过人类标注者对模型输出进行评分，训练一个奖励模型（Reward Model），再用强化学习的方法让大模型最大化奖励分数，从而对齐人类偏好。

RLHF是ChatGPT成功的关键技术之一，也是现代大语言模型训练流程中的标准步骤。

### RLHF的完整流程

RLHF通常分为三个阶段：

#### 第一阶段：监督微调（SFT, Supervised Fine-Tuning）
- **目标**：让模型学会遵循指令，产出基本合格的回答
- **数据**：高质量的指令-回答对（由人类标注者编写）
- **方法**：标准的监督学习，用交叉熵损失微调
- **结果**：得到SFT模型，能够遵循指令但输出质量不稳定

#### 第二阶段：训练奖励模型（RM, Reward Model）
- **目标**：训练一个能给模型回答打分的模型，分数代表人类偏好程度
- **数据收集**：
  - 输入同一个Prompt，让SFT模型生成多个回答（通常4-10个）
  - 人类标注者对这些回答进行排序（排名，而不是打分）
  - 收集大量的"Prompt + 回答排序"数据对
- **训练方法**：
  - 用SFT模型初始化奖励模型
  - 使用排序损失（Ranking Loss）训练
  - 输入：Prompt + 回答 → 输出：标量分数
  - 训练目标：让人类更喜欢的回答获得更高的分数
- **结果**：得到奖励模型，可以自动给任何回答打分

#### 第三阶段：强化学习微调（RL Fine-Tuning）
- **目标**：用奖励模型作为奖励信号，通过强化学习优化SFT模型
- **算法**：PPO（Proximal Policy Optimization，近端策略优化）
- **核心机制**：
  - **策略模型（Policy）**：即正在被优化的LLM
  - **奖励信号**：奖励模型给出的分数
  - **KL散度惩罚**：防止模型偏离SFT模型太远（避免"奖励黑客"）
  - **价值模型（Value Model）**：估计状态价值，辅助PPO训练
- **奖励函数**：
  ```
  最终奖励 = RM奖励 - β × KL(当前模型 || SFT模型)
  ```
  - KL惩罚的作用：保证模型输出的多样性和自然度，防止为了高分而输出模式化的内容
- **结果**：得到RLHF模型，输出更符合人类偏好

### RLHF为什么有效

1. **对齐人类偏好**：让模型的输出更符合人类的价值观和审美
2. **提升有用性**：回答更有帮助、更切题
3. **增强安全性**：减少有害、不当的输出
4. **提升对话体验**：输出更自然、更像人类

### RLHF的挑战和局限性

#### 1. 成本高昂
- 需要大量高质量的人类标注
- 标注者需要培训，质量参差不齐
- 强化学习训练过程计算成本高

#### 2. 奖励黑客（Reward Hacking）
- 模型可能找到"投机取巧"的方式获得高分
- 例如：过度使用某些词汇、重复表达肯定语气
- KL惩罚可以一定程度缓解，但不能完全解决

#### 3. 标注者偏差
- 标注者的个人偏好会影响模型
- 不同文化、背景的标注者标准不同
- 可能引入偏见

#### 4. 对齐税（Alignment Tax）
- RLHF可能会轻微降低模型的某些能力（如推理、编码）
- 模型可能变得"过于礼貌"而不够直接

### RLHF的演进与替代方案

#### 1. RLAIF（AI Feedback）
- 用更强的AI模型代替人类标注
- 成本更低，速度更快
- 如Claude、GPT-4作为"AI标注员"

#### 2. Constitutional AI（宪法AI）
- 让模型根据一套"宪法"（原则）进行自我批评和修正
- 减少对人类标注的依赖
- Anthropic提出的方法

#### 3. DPO（Direct Preference Optimization）
- 直接用偏好数据优化模型，不需要训练奖励模型和RL
- 更简单、更稳定、更高效
- 2023年提出，正在成为RLHF的热门替代方案

#### 4. ORPO（Odds Ratio Preference Optimization）
- 将SFT和偏好优化合二为一
- 更简洁的训练流程

**答案解析**:

RLHF是理解现代大语言模型训练流程的关键概念。回答时要讲清楚RLHF的三个阶段（SFT→RM→PPO）、每个阶段的目标和方法，以及RLHF的挑战和演进。2026年的趋势是：RLHF虽然仍是主流，但DPO、ORPO等更简洁的方法正在快速发展，同时RLAIF也在降低对齐的成本。面试中如果能提到DPO等新方法，会展现出对前沿技术的了解。

**扩展问题**:
- 为什么RLHF用排序而不是直接打分？
- PPO算法的核心思想是什么？
- 什么是奖励黑客？有哪些例子？
- DPO和RLHF的区别是什么？DPO为什么更简单？

## Q20: 如何评估大模型应用的效果

**考察点**: 评估体系、评估指标、评估方法

**难度**: 困难

**频率**: ⭐⭐⭐⭐⭐

**标准答案**:

大模型应用的效果评估是一个系统性工程，需要从多个维度、使用多种方法进行综合评估。以下是完整的评估框架：

### 一、评估维度

#### 1. 效果维度（Effectiveness）
- **准确性**：回答是否正确
- **相关性**：回答是否切题
- **完整性**：是否完整回答了问题
- **一致性**：多次回答是否一致
- **安全性**：是否有有害、偏见内容

#### 2. 体验维度（Experience）
- **流畅度**：语言是否自然流畅
- **响应速度**：首Token延迟、整体耗时
- **交互体验**：多轮对话的连贯性
- **有用性**：对用户是否真正有帮助

#### 3. 工程维度（Engineering）
- **吞吐量**：每秒处理请求数
- **成功率**：正常响应的比例
- **成本**：单次请求的成本
- **稳定性**：系统可用性

### 二、RAG系统的评估

#### 1. 检索质量评估
- **Recall@K**：Top K结果中包含正确答案的比例
- **Precision@K**：Top K结果中相关文档的比例
- **MRR（平均倒数排名）**：第一个相关文档排名的倒数的平均值
- **NDCG**：考虑排名位置的归一化折损累计增益
- **评估方法**：
  - 人工标注相关文档
  - 构建评估数据集（问题+相关文档ID）

#### 2. 生成质量评估
- **忠实度（Faithfulness）**：回答是否基于检索到的文档，有无编造
- **答案相关性（Answer Relevance）**：回答是否针对问题
- **信息完整性**：是否覆盖了所有关键点
- **评估方法**：
  - 人工评估：金标准但成本高
  - LLM-as-Judge：用更强的LLM（如GPT-4）作为评委打分
  - 专门的评估框架：RAGAS、TruLens、DeepEval

#### 3. 端到端评估
- **正确率**：回答是否正确解决了用户问题
- **满意度**：用户对回答的满意程度
- **解决率**：问题是否被彻底解决（不需要追问）

### 三、Agent系统的评估

#### 1. 任务完成率
- Agent是否成功完成了给定的任务
- 完成任务的步骤数是否合理

#### 2. 工具使用评估
- 工具调用的准确率
- 工具选择的合理性
- 参数提取的正确率

#### 3. 规划能力评估
- 任务分解的合理性
- 路径选择的效率
- 错误恢复能力

#### 4. 评估框架
- **AgentBench**：多维度Agent评估基准
- **WebArena**：基于真实网站的Agent评估
- **AgentEval**：LLM-based评估

### 四、评估方法

#### 1. 人工评估
- **优势**：最准确，能捕捉细微差别
- **劣势**：成本高、速度慢、不可重复、有主观偏差
- **适用**：最终质量把关、Bad Case分析
- **最佳实践**：
  - 制定清晰的评估标准和打分规则
  - 多人标注，计算一致性（Cohen's Kappa）
  - 抽样评估，定期进行

#### 2. 自动评估
- **基于规则**：关键词匹配、格式检查
- **基于Embedding**：计算答案与参考答案的相似度
- **LLM-as-Judge**：
  - 用GPT-4、Claude等强模型作为评委
  - 设计评估Prompt，让LLM打分或判断
  - 速度快、可扩展、成本适中
  - 注意：LLM评委也可能有偏差，需要校准

#### 3. 在线评估
- **A/B测试**：不同版本的效果对比
- **用户反馈**：点赞/点踩、满意度评分
- **行为指标**：追问率、解决率、留存率
- **业务指标**：转化率、客服人工转接率等

### 五、评估工具与框架

| 框架 | 特点 |
|------|------|
| **RAGAS** | 专门的RAG评估框架，支持忠实度、相关性等指标 |
| **TruLens** | TruEra出品，RAG评估+可观测性 |
| **DeepEval** | 开源评估框架，支持多种测试类型 |
| **LangSmith** | LangChain生态，评估+追踪+调试 |
| **Promptfoo** | Prompt测试和评估工具 |
| **Helicone** | LLM可观测性平台，含评估功能 |
| **OpenAI Evals** | OpenAI官方评估框架 |

### 六、评估最佳实践

#### 1. 建立评估数据集
- 覆盖典型场景和边界Case
- 包含容易出错的难例
- 定期更新和扩充
- 数据量：至少100-200条才有统计意义

#### 2. 建立评估基线
- 上线前测一次基线分数
- 每次迭代都对比基线
- 量化优化效果

#### 3. 多层级评估
- **单元测试**：每个组件的单元测试（Prompt、Chain、Tool）
- **集成测试**：端到端流程测试
- **回归测试**：防止优化引入新问题
- **人工抽检**：定期人工抽查质量

#### 4. 持续监控
- 线上数据的质量监控
- 用户反馈收集和分析
- Bad Case定期复盘
- 数据驱动的迭代优化

### 七、常见的评估陷阱

1. **只看平均分**：忽略了长尾Bad Case的影响
2. **评估集过拟合**：在评估集上调参，导致泛化性差
3. **LLM评委的偏差**：LLM评委可能有偏好（如偏好更长的答案）
4. **只看自动指标**：自动指标和真实用户体验可能有差距
5. **忽视成本和速度**：效果再好，成本太高也无法落地

**答案解析**:

评估是大模型应用工程化的核心环节，没有评估就无法迭代优化。这道题考察的是工程化思维和系统性思考能力。回答时要从多个维度、多种方法展开，展现出完整的评估体系认知。2026年，LLM-as-Judge已经成为主流的评估方法，同时也出现了RAGAS等专门的评估框架。面试中如果能提到具体的评估框架和实践经验，会很加分。

**扩展问题**:
- 什么是LLM-as-Judge？它有什么优缺点？
- RAGAS的核心评估指标有哪些？如何计算？
- 如何构建一个好的评估数据集？
- 评估大模型应用时，如何平衡效果和成本？

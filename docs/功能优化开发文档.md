# AI 就业成长平台功能优化与开发设计文档

> 文档类型：现有功能优化方案  
> 编写日期：2026-09-30  
> 适用代码基线：当前 `main` 分支  
> 文档目标：将现有功能从“个人就业工具集合”升级为“社会信息驱动、岗位要求清晰、材料可信、成长可反馈”的就业成长工作台。

---

## 1. 产品判断

当前系统已经具备：

- 首页工作台；
- 个人就业档案；
- AI 就业画像；
- 岗位知识库和岗位匹配；
- 我的简历；
- 投递记录与浏览器自动化基础；
- 成长规划；
- 就业资源检索；
- AI 求职助手。

但现有体验存在一个共同问题：

> 系统知道用户是谁，却还不够知道“外部就业市场正在发生什么”，也没有把外部变化转化为用户今天可以完成的具体行动。

因此下一阶段不应继续单独堆叠 AI 文案，而应围绕下面这条主线重组功能：

```text
社会热点与市场变化
        ↓
目标职业需要什么
        ↓
用户当前有哪些证据
        ↓
岗位匹配与简历调整
        ↓
投递和面试反馈
        ↓
成长任务与能力变化
```

### 1.1 优化后的产品定位

建议将产品定位为：

> **面向大学生的社会就业信息与个人能力成长工作台。**

核心价值不是“替用户生成一段文字”，而是让用户看懂：

1. 现在社会和行业需要什么；
2. 哪些岗位适合自己；
3. 自己缺什么能力和证据；
4. 应该如何修改简历和投递材料；
5. 完成行动后是否真的变强。

### 1.2 设计原则

1. **先给外部事实，再给个性化建议。**  
   首页、就业画像和资源中心必须先展示可追溯的社会信息，再解释它与用户的关系。

2. **先展示结论，再允许深入查看。**  
   用户在卡片上就能看到匹配度、关键技能、缺口和下一步，不应被迫点进多层页面。

3. **所有 AI 结果必须有来源或证据。**  
   岗位技能来自岗位文本、职业技能词典或知识库；简历亮点来自用户确认过的经历；成长任务来自岗位缺口和实际反馈。

4. **自动化只减少重复操作，不替用户承担不可逆风险。**  
   可以自动解析、生成、预填、排队、记录，但最终提交、验证码和异常页面必须允许用户确认或接管。

5. **每个页面都要有下一步行动。**  
   页面不只展示信息，还要告诉用户“现在可以做什么”。

## 2. 现有功能问题总览

| 模块 | 当前状态 | 主要不足 | 优化目标 |
|---|---|---|---|
| 首页 | 有个人指标、画像、岗位方向和知识入口 | 信息过度围绕个人，缺少社会热点、行业变化和市场解释 | 建立“市场变化 + 我的影响 + 今日行动”首页 |
| 个人档案 | 表单、技能、项目、竞赛、实习维护 | 信息密度低，视觉表现弱，缺少一眼可懂的能力概览 | 升级为“档案编辑 + 能力仪表盘 + 证据完整度” |
| AI 就业画像 | 综合评分、雷达图、优势短板、推荐方向 | 只分析用户，不展示企业和岗位对人才的真实要求 | 增加职业画像、企业需求、技能需求和差距解释 |
| 岗位匹配 | 岗位搜索、智能匹配、详情页分析 | 岗位卡片不够直观，技能要求需要进入详情页才能看 | 卡片直接显示必备技能、加分技能、缺口和投递建议 |
| 投递助手 | 独立投递中心，岗位详情页粘贴链接后自动化 | 操作链过长，用户感觉是在使用一个额外系统 | 将投递能力嵌入“我的简历”，形成材料生成到投递的连续流程 |
| 我的简历 | 有版本、选择内容、AI 优化和预览 | AI 生成表达泛化、缺少证据约束，质量不稳定 | 以主档案和岗位 JD 为输入，生成可解释、可编辑、可校验内容 |
| 成长规划 | 有路线、任务、项目、面试建议和资源 | 交互少，没有完成记录、反馈、积分或结果变化 | 变成任务驱动的成长系统，记录完成事实并更新能力 |
| 就业资源 | 只有搜索框和 RAG 搜索结果 | 没有默认内容、热点推荐、时间和来源信息 | 增加“今日热点、热门技能、岗位趋势、专题知识”首页 |

## 3. 首页优化：从个人仪表盘升级为就业市场工作台

### 3.1 目标体验

用户进入首页后，应该在 10 秒内回答四个问题：

- 今天就业市场有什么变化？
- 这些变化和我的目标岗位有什么关系？
- 我当前最值得补的能力是什么？
- 我今天可以完成哪一个行动？

### 3.2 推荐布局

```text
顶部：欢迎语 + 当前目标岗位 + 档案完整度

第一屏左侧：今日就业热点
第一屏右侧：热点对我的影响

第二屏：目标岗位市场概览
        岗位数量、热门技能、常见学历、城市分布、企业类型

第三屏：我的当前状态
        能力雷达、证据完整度、匹配岗位数、投递漏斗

第四屏：今日行动
        补充一条项目成果 / 学习一个技能 / 优化一份简历 / 查看一个岗位
```

### 3.3 今日热点卡片

每条热点至少包含：

| 字段 | 说明 |
|---|---|
| 标题 | 事实性标题，避免纯营销文案 |
| 类型 | 政策、行业、技术、校招、企业、薪资、招聘季 |
| 发布时间 | 明确显示日期和时间 |
| 来源 | 来源机构或原始网页 |
| 摘要 | 80 至 120 字 |
| 影响岗位 | 关联到前端、后端、AI、数据、产品等方向 |
| 用户关系 | “与你的 Java 后端目标岗位相关” |
| 行动按钮 | 查看详情、查看相关技能、生成学习任务 |

### 3.4 信息来源策略

推荐采用“来源分级 + 内容审核 + 缓存”的方式：

1. **一级来源：**政府部门、教育部门、官方招聘公告、企业官方招聘页、权威研究机构。
2. **二级来源：**正规媒体、招聘平台公开报告、行业协会。
3. **三级来源：**技术社区和个人文章，仅作为补充，不直接用于政策结论。

不建议第一版直接大规模抓取社交平台。优先使用可授权的 RSS、公开 API、官方页面和人工维护的来源白名单。热点数据需要保存原文链接、发布时间、抓取时间和内容摘要，避免知识库中出现无法追溯的“AI 编造热点”。

### 3.5 后端接口建议

```text
GET /api/insights/feed
参数：category、target_job、limit、cursor

GET /api/insights/{id}

GET /api/market/overview
参数：target_job、city、period

POST /api/insights/{id}/feedback
参数：relevant、not_relevant、hide
```

第一期可以先复用现有知识库，把带有 `published_at`、`source_url`、`source_name`、`topic_tags` 的文档作为热点数据；后续再增加独立的资讯表和定时采集任务。

## 4. 个人档案优化：从表单页升级为能力档案

### 4.1 当前问题

当前档案页主要是基本信息表单和经历列表。它适合“填写数据”，但不适合让用户理解自己的就业状态。用户填写完后看不到：

- 哪些能力已经比较完整；
- 哪些经历最有价值；
- 哪些字段缺失会影响岗位匹配；
- 自己的能力变化；
- 哪些内容可以直接用于简历。

### 4.2 推荐页面结构

```text
左侧：个人摘要、目标岗位、档案完整度、证据完整度

右侧第一行：能力雷达图 + 经历结构图 + 完整度进度

下方：基本信息 / 技能 / 项目 / 实习 / 竞赛 / 证书

每条经历：内容、关联技能、成果证据、可用于简历、待补字段
```

### 4.3 ECharts 图表

建议至少增加以下图表：

1. **能力雷达图**  
   编程基础、框架应用、数据能力、工程实践、项目经验、沟通表达。

2. **经历构成环图**  
   技能、项目、实习、竞赛、证书的数量和有效证据数量。

3. **目标岗位覆盖条形图**  
   当前档案对目标岗位的必备技能覆盖率、加分技能覆盖率。

4. **档案完整度进度图**  
   基本信息、经历内容、成果数据、证据链接分别计算。

5. **能力变化折线图**  
   记录每次画像分析、任务完成或用户确认后的能力分变化。

不要让图表只是装饰。每张图表都要能点击进入相应的编辑或补充操作。

### 4.4 能力证据字段

现有技能、项目、竞赛和实习建议逐步增加：

```text
evidence_status: draft | confirmed | verified
evidence_source: user | project | certificate | mentor | imported
result_summary: 成果摘要
metric_value: 数值或结果
evidence_url: 证据链接
related_skills: 关联技能
resume_ready: 是否允许用于简历
last_verified_at: 最近确认时间
```

第一期不需要一次完成所有字段。优先增加 `result_summary`、`related_skills`、`resume_ready` 和 `evidence_status`，就能明显改善简历和岗位匹配质量。

## 5. AI 就业画像优化：增加社会化职业画像

### 5.1 当前问题

现有画像主要回答“你有什么优点和缺点”，但用户还需要知道：

- 目标岗位在企业中具体做什么；
- 企业通常需要哪些技能；
- 哪些技能是硬门槛；
- 哪些技能是加分项；
- 同类岗位的常见项目经历是什么；
- 用户和目标岗位之间差距有多大；
- 差距需要多少时间和行动补齐。

### 5.2 新版画像分为四层

#### 第一层：我的能力状态

- 当前综合竞争力；
- 维度能力；
- 可信证据数量；
- 最近变化；
- 主要优势和风险。

#### 第二层：目标职业画像

- 目标岗位职责；
- 常见工作任务；
- 常见技术栈；
- 常见项目场景；
- 常见学历和专业要求；
- 常见企业类型。

#### 第三层：企业需求画像

- 必备技能；
- 高频技能；
- 近期开启岗位中的新增技能；
- 高频业务场景；
- 典型招聘阶段；
- 不同企业的要求差异。

#### 第四层：差距和行动

- 已满足；
- 部分满足；
- 缺失；
- 无法判断；
- 对应证据；
- 推荐补足任务；
- 预计改善的岗位覆盖率。

### 5.3 推荐视觉表达

```text
左：我的能力雷达
中：岗位要求雷达
右：差距列表

下方：
岗位要求技能矩阵
企业类型对比
常见项目案例
我的下一步行动
```

### 5.4 数据设计

职业画像不要完全依赖大模型。建议使用：

- 现有岗位知识库中的岗位文档；
- 结构化岗位技能抽取；
- 用户目标岗位；
- 可配置的技能同义词表；
- 职业技能分类数据；
- 用户的匹配、投递和面试反馈。

O*NET 提供职业、技能、知识、任务和技术技能等职业信息的 Web Services；ESCO 提供标准化的职业、技能和能力分类。它们适合作为技能归一化和职业关系的参考层，但面向中国大学生时不能直接替代国内招聘数据，国内岗位文本和政策信息仍应作为主要依据。详见文末的 [O*NET Web Services](https://www.onetonline.org/help/onet/webservices) 和 [ESCO Web Service API](https://esco.ec.europa.eu/en/use-esco/use-esco-services-api/esco-web-service-api)。

### 5.5 接口建议

```text
GET /api/career-profile/{user_id}

GET /api/career-profile/{user_id}/market-context
参数：target_job、city、period

GET /api/career-profile/{user_id}/skill-gap
参数：target_job
```

返回结果必须区分：

```json
{
  "skill": "SQL",
  "requirement_type": "required",
  "market_frequency": 0.82,
  "user_level": "basic",
  "evidence": ["项目经历：校园就业系统"],
  "gap": "需要补充复杂查询、索引和性能优化案例",
  "recommended_action": "完成一个带索引优化的查询项目"
}
```

## 6. 岗位匹配优化：列表直接展示技能和投递判断

### 6.1 当前问题

当前岗位列表需要用户进入详情后才能看到匹配技能和缺口。这会导致用户不断点进点出，无法快速比较岗位。

### 6.2 新岗位卡片

岗位卡片应直接包含：

```text
岗位标题 / 企业类型 / 城市 / 更新时间

匹配度：82%
投递建议：建议投递 / 补强后投递 / 暂不建议

硬条件：
学历满足、专业待确认、实习时间满足

必备技能：
Python ✓   SQL △   Docker ×

加分技能：
FastAPI、Linux、数据分析

下一步：
查看岗位 / 生成岗位简历 / 加入成长计划
```

### 6.3 匹配规则

分为三步：

1. **硬条件判断**  
   毕业时间、学历、专业、城市、实习时间、语言或证书要求。

2. **技能覆盖判断**  
   必备技能、常见技能、加分技能分别计算，不再只给一个总分。

3. **证据解释**  
   每个“已掌握”必须能回指到用户档案中的经历；无法找到证据时显示“待确认”。

### 6.4 评分建议

```text
硬条件：不满足则降级为“暂不建议”
必备技能覆盖：40%
项目场景匹配：25%
加分技能覆盖：15%
证据可信度：10%
个人偏好匹配：10%
```

权重仅作为 MVP 初始配置，后续应通过人工标注岗位样本校准。

### 6.5 前端改造

- 岗位列表增加技能标签和覆盖状态；
- `matched_skills` 与 `missing_skills` 直接显示前 3 至 5 项；
- 增加“只看我适合的岗位”；
- 增加“缺口最小”“成长价值最高”“最新发布”排序；
- 支持岗位卡片直接生成岗位简历；
- 详情页保留完整解释和岗位正文。

当前项目已有 `matched_skills`、`missing_skills` 和匹配分返回结构，可以优先完成前端展示改造，后续再补硬条件模型。

## 7. 投递能力优化：从独立功能变成简历工作台技能

### 7.1 产品调整

“投递助手”不应该成为用户必须单独学习的一个页面。它应该是“我的简历”里的一个技能：

```text
我的简历
  → 选择岗位
  → 生成岗位版本
  → 检查材料
  → 准备投递
  → 预填岗位页面
  → 用户确认发送
  → 自动记录结果
```

独立的投递中心可以保留，但主要职责改为：

- 查看历史投递；
- 查看当前阶段；
- 补充反馈；
- 管理失败和待跟进事项。

### 7.2 我的简历新增“投递工作台”

在简历版本页增加：

1. **选择目标岗位**；
2. **岗位需求摘要**；
3. **简历覆盖率**；
4. **需补充材料**；
5. **求职信和开场白**；
6. **投递字段预览**；
7. **开始预填**；
8. **投递后记录状态**。

### 7.3 自动化边界

“自动投递”在技术和合规上不能简单理解为后台无条件点击提交。需要处理：

- 登录态；
- 验证码；
- 滑块或风控；
- 平台页面变化；
- 用户隐私字段；
- 招聘平台服务条款；
- 错误岗位或重复投递。

推荐采用三级模式：

| 模式 | 行为 |
|---|---|
| 准备模式 | 生成简历、求职信、开场白和字段映射 |
| 预填模式 | 打开浏览器页面并自动填写，用户检查后提交 |
| 用户授权模式 | 用户明确授权后执行可逆步骤，遇到验证码、异常和最终提交暂停 |

第一期应实现“从我的简历一键准备并预填”，不建议实现无确认的批量海投。成熟开源项目也普遍将岗位发现、材料生成、申请跟踪和浏览器预填拆开处理；可参考文末的 [Job Sentinel](https://github.com/harshitwandhare/job-sentinel) 和 [JobSync](https://github.com/Gsync/jobsync)。

### 7.4 路由与接口调整

前端：

```text
/resume?job_id=...
/resume/:version_id/apply
/applications
```

后端：

```text
POST /api/resume/versions/{id}/application-pack
POST /api/resume/versions/{id}/prefill
POST /api/applications/{id}/confirm
POST /api/applications/{id}/feedback
```

现有 `/applications/{id}/automation/start` 可以保留为底层能力，由简历工作台调用，不再作为用户必须理解的主入口。

## 8. 我的简历优化：解决 AI 内容“拉跨”

### 8.1 当前问题

当前简历已经有版本、选择经历、预览和 AI 优化，但 AI 生成内容质量不稳定，主要风险是：

- 描述空泛；
- 句式重复；
- 没有突出用户实际职责；
- 没有针对 JD；
- 量化数字可能是模型补写；
- 技能关键词和项目经历没有形成证据关系。

### 8.2 简历生成流程

改为四步，不让 AI 一次直接写完整简历：

```text
事实抽取
  → 岗位要求解析
  → 证据选择
  → 内容改写
  → 用户确认
```

### 8.3 每条项目经历的生成模板

建议统一为：

```text
动作 + 技术/方法 + 具体场景 + 可验证结果
```

例如：

```text
负责就业岗位数据清洗与接口开发，使用 Python 和 FastAPI 完成数据处理及查询接口，
将岗位信息按技能、城市和岗位方向进行结构化，为前端检索和匹配功能提供数据支持。
```

如果用户没有提供数字，不允许 AI 自行编造“提升 30%”“降低 50%”等结果。可以生成：

```text
结果数据待补充：请填写处理数据量、接口响应时间或实际使用人数。
```

### 8.4 AI 输出必须拆成可审核字段

```json
{
  "source_experience_id": 12,
  "original": "用户原始项目描述",
  "optimized": "岗位针对性表达",
  "used_skills": ["Python", "FastAPI"],
  "added_facts": [],
  "missing_evidence": ["项目规模"],
  "confidence": 0.86,
  "status": "pending_review"
}
```

### 8.5 简历质量评分

增加四类评分：

- 事实完整度；
- 岗位关键词覆盖；
- 项目成果清晰度；
- 可读性和 ATS 兼容性。

不要只显示总分，应显示“为什么得分”和“下一处该改什么”。

Reactive Resume 的成熟做法包括实时预览、多格式导出、区块排序和结构化编辑；Resume Matcher 则把主简历、JD 定制、关键词提示和面试准备串起来。本项目应借鉴这些流程，但将“用户事实证据”和“岗位成长反馈”作为自己的差异。可参考文末的 [Reactive Resume](https://github.com/reactive-resume/reactive-resume) 和 [Resume Matcher](https://github.com/srbhr/Resume-Matcher)。

## 9. 成长规划优化：从结果展示变为成长过程

### 9.1 当前问题

当前成长规划有阶段、任务、项目、面试建议和资源，但主要是静态展示。用户看完之后没有明确的完成动作，也没有反馈“完成之后变好了多少”。

### 9.2 任务卡片必须可操作

每个任务增加：

| 字段 | 示例 |
|---|---|
| 任务名称 | 完成 SQL 索引优化练习 |
| 来源 | 目标岗位缺少 SQL 性能优化证据 |
| 预计用时 | 90 分钟 |
| 截止日期 | 2026-10-05 |
| 产物 | Git 提交、练习截图、复盘文字 |
| 状态 | 未开始、进行中、已完成、已验证 |
| 反馈 | 难度、耗时、是否遇到问题 |
| 影响 | SQL 技能证据 +1、岗位覆盖率 +5% |

### 9.3 交互流程

```text
查看任务
  → 开始任务
  → 打开知识资源 / 面试题 / 项目模板
  → 提交完成证据
  → AI 检查或用户确认
  → 更新技能状态
  → 更新岗位匹配度
  → 推荐下一个任务
```

### 9.4 面试题和知识库必须可跳转

当前推荐资源和面试建议不能只是文本列表，应改为可操作卡片：

- 查看知识详情；
- 加入学习计划；
- 标记已读；
- 开始练习；
- 收藏；
- 标记“我还不会”；
- 生成面试问答；
- 记录回答；
- 获取 AI 反馈。

### 9.5 成长反馈页面

增加：

- 本周完成任务数；
- 连续学习天数；
- 已补齐技能数；
- 岗位匹配度变化；
- 简历覆盖率变化；
- 面试题掌握度；
- 待复盘事项。

不要过度游戏化。积分和徽章只能作为辅助，核心反馈应该是：

```text
上周：SQL 只有基础记录
本周：完成索引优化练习并补充项目证据
变化：目标岗位 SQL 覆盖从 40% 提升到 70%
```

### 9.6 数据模型建议

新增：

```text
growth_tasks
growth_task_checkins
growth_task_evidence
skill_progress_snapshots
interview_practice_records
```

接口：

```text
GET /api/growth/tasks
POST /api/growth/tasks/{id}/start
POST /api/growth/tasks/{id}/complete
POST /api/growth/tasks/{id}/feedback
GET /api/growth/progress
POST /api/interview-practice
```

## 10. 就业资源优化：默认推荐“今日热点”

### 10.1 页面定位

就业资源不应只是一个搜索框。建议改成：

```text
就业资源中心
  ├─ 今日热点
  ├─ 热门技能
  ├─ 岗位趋势
  ├─ 校招政策
  ├─ 面试准备
  ├─ 简历指导
  └─ 全文搜索
```

### 10.2 默认首页内容

默认展示四组：

1. **今日热点**  
   社会、政策、行业和招聘变化。

2. **热门技能**  
   近期岗位中高频或增长较快的技能，但必须显示统计周期和数据来源。

3. **岗位方向专题**  
   例如前端开发、Java 后端、AI 应用、数据分析、测试开发。

4. **与你相关**  
   基于用户目标岗位、技能缺口和历史浏览推荐内容。

### 10.3 搜索结果卡片

每条结果显示：

- 标题；
- 内容类型；
- 适用岗位；
- 发布时间；
- 更新时间；
- 来源；
- 相关技能；
- 摘要；
- 推荐理由；
- 加入成长计划；
- 收藏和反馈。

搜索结果需要区分：

```text
事实资讯
岗位知识
技能教程
简历指导
面试题
政策文件
```

不要把不同类型内容混在同一个列表里，否则用户难以判断信息用途。

### 10.4 RAG 和热点数据的边界

RAG 检索适合回答“这项技能是什么”“岗位要求如何理解”“如何准备面试”。  
热点推荐需要额外保存时间、来源、抓取状态和过期时间，不能仅依赖静态 Markdown 知识库。

建议新增：

```text
content_items
content_sources
content_tags
content_user_events
```

状态字段：

```text
draft | published | expired | archived
```

推荐接口：

```text
GET /api/resources/home
GET /api/resources/trending
GET /api/resources/recommended
POST /api/resources/{id}/read
POST /api/resources/{id}/favorite
POST /api/resources/{id}/feedback
```

## 13. 验收标准

### 首页

- 首屏能看到至少 3 条有来源和日期的热点；
- 每条热点能说明与用户目标岗位的关系；
- 首页存在明确的“今日行动”；
- 无热点数据时显示可解释的降级状态，不展示假数据。

### 个人档案

- 至少有雷达图、经历构成图和档案完整度；
- 图表点击后能进入对应补充位置；
- 用户能看出哪些经历可以用于简历；
- 保存后图表和完整度立即更新。

### AI 就业画像

- 除用户优缺点外，能看到目标岗位和企业需求；
- 每个技能差距都有来源和下一步建议；
- 画像结果区分事实、模型判断和用户待确认内容。

### 岗位匹配

- 岗位列表卡片直接展示技能要求；
- 用户无需进入详情即可看到已具备和待提升技能；
- 详情页能解释匹配度来源；
- 不满足硬条件时必须明确说明原因。

### 我的简历与投递

- 从简历页可以直接选择岗位并生成岗位版本；
- AI 生成内容可以逐条查看原文、改写内容和证据来源；
- 未确认的 AI 内容不能静默覆盖正式简历；
- 自动化遇到验证码、异常页面或最终提交时可以暂停并交给用户。

### 成长规划

- 每项任务都有状态、完成动作和反馈入口；
- 面试题和知识资源可以直接加入任务或打开；
- 完成任务后能看到技能覆盖率或证据数量变化；
- 页面可以展示历史成长记录，而不是每次重新生成一份静态计划。

### 就业资源

- 默认进入页面时不是空搜索页；
- 热点、技能、政策和面试内容有明确分类；
- 每条内容显示来源、时间和推荐理由；
- 用户可以收藏、已读、加入成长任务并反馈“不相关”。

## 14. 技术与产品风险

1. **热点信息时效性风险**  
   所有热点必须带发布时间和过期策略，不能把旧内容当今日信息。

2. **岗位数据来源风险**  
   优先接入公开、授权或官方来源，不直接依赖不稳定的页面抓取。

3. **自动投递风险**  
   不保存招聘平台密码，不绕过验证码和风控，不实现无确认批量海投。

4. **AI 编造风险**  
   简历、画像和成长建议必须区分“用户事实”“外部事实”和“模型建议”。

5. **推荐偏差风险**  
   热门技能不等于适合所有人，应同时展示适用岗位、统计周期和数据范围。

6. **信息过载风险**  
   首页只展示少量高价值信息，其余内容通过专题、搜索和个性化推荐进入。

> 简历编辑、岗位匹配、申请跟踪和热点推荐本身都不是足够强的差异化能力。当前项目应把这些能力连接到“大学生真实经历、岗位技能证据、成长反馈和可信投递”上，形成完整闭环。

## 16. 最终建议

下一轮开发不要八个模块平均用力。建议优先做一条能被用户明显感知的闭环：

```text
首页今日热点
  → 查看目标岗位需求
  → 岗位卡片看到技能缺口
  → 在我的简历生成岗位版本
  → 一键准备投递材料
  → 把缺口加入成长任务
  → 完成任务后更新匹配结果
```

这条链路完成后，首页、画像、岗位、简历、投递、成长和资源就不再是分散页面，而会变成同一个就业成长过程的不同视角。

# AI 就业竞争力评估与提升系统优化报告

> 更新日期：2026-09-27
>
> 代码基线：`main` 分支提交 `5eb1de2`
>
> 报告目标：围绕大学生创新创业大赛，重新梳理现有功能、产品特色与下一阶段开发路线。

**项目定位与核心结论**

当前项目已经具备学生档案、AI 就业画像、岗位匹配、简历生成、成长规划、AI 对话助手和 RAG 知识库等基础能力，但这些功能目前更像若干独立的 AI 工具，尚未形成一个让评委能够快速理解、让学生愿意持续使用、又能通过数据证明效果的完整产品闭环。

项目不应继续定位成普通的“AI 简历生成器”或“就业信息平台”，建议升级为：

> **面向大学生的职业能力数字孪生与可信投递平台。**

比赛中的核心特色建议确定为：

> **职业能力数字孪生 + 可信投递实验闭环。**

系统把学生的课程、技能、项目、竞赛、证书和实习经历整理成可追溯的“能力证据”；再根据具体岗位完成资格判断、可解释匹配、事实受控的简历生成和投递材料准备；由 AI 辅助网页预填，但由学生审核并完成最终提交；最后把投递、笔试、面试和录用结果反向用于修正能力画像与成长任务。

完整链路如下：

```text
真实经历采集
→ 职业能力数字孪生
→ 岗位解析与硬条件过滤
→ 可解释匹配与技能缺口
→ 可信岗位简历和投递问答
→ AI 预填 + 用户确认提交
→ 投递状态、回执和面试反馈
→ 结果反哺能力画像与成长计划
```

这条链路比“调用大模型生成一份简历”更有比赛辨识度，原因是它同时解决了大学生求职中的三个真实问题：**不知道自己适合什么、不会证明自己为什么适合、投递后不知道下一步应该改什么。**

> **现状说明：**当前代码已经实现前述链路中的账号与档案、AI 分析、岗位匹配、简历和成长规划等基础部分；投递记录、网页预填、人工确认投递、回执保存和结果反馈闭环尚未实现。下文凡涉及这些新增能力，均为下一阶段设计，不应在答辩中表述为已经完成。

## 第一板块：目前项目功能如何优化

### 1.1 当前项目已经具备的真实基础

| AI 求职助手 | 支持求职问答和对话式档案整理 | 更像通用聊天窗口，无法直接驱动业务动作 | 变成贯穿档案、岗位、简历、投递和复盘的操作入口 |

| 简历功能 | 多版本简历、AI 优化、预览、打印/PDF | 生成内容与真实经历之间缺少强约束，岗位定制流程不够完整 | 建立主档案、岗位版本、事实校验和变更对照 |

对标后可以得到一个明确结论：简历编辑、JD 匹配、投递看板和网页预填已经存在成熟开源思路，单独实现其中任何一项都很难形成比赛特色。本项目真正应建立的差异，是将它们连接到**大学生真实能力证据、事实可信控制和成长反馈实验**上。

### 1.3 将学生档案优化为“能力证据库”

#### 当前问题

现在的档案能够记录“会 Python”“参加过某竞赛”“做过某项目”，但系统还不能稳定回答：

- 这项能力从哪里得来？
- 学生在项目中具体负责什么？
- 有什么结果能够证明？
- 这条信息是否经过本人确认或导师审核？
- AI 生成简历时使用了哪一条原始经历？

如果没有这些信息，岗位匹配和简历生成即使语言流畅，也可能只是“看起来合理”，无法体现项目的可信性。

#### 优化方案：能力证据卡

每项关键能力不再只是一个技能标签，而是建立一张“能力证据卡”。建议至少包含：

| 字段 | 示例 |
|---|---|
| 能力名称 | Python 数据分析 |
| 能力类型 | 编程技能 / 项目能力 / 通用能力 |
| 来源经历 | 校园招聘数据分析项目 |
| 本人职责 | 数据清洗、特征设计、接口开发 |
| 使用场景 | 处理 3 类招聘数据并构建分析接口 |
| 结果或产物 | 项目仓库、演示截图、报告、奖项证明 |
| 时间范围 | 2026-03 至 2026-06 |
| 证据链接 | Git 仓库、文件、证书或导师评价 |
| 可信状态 | 待补证 / 本人确认 / 导师确认 / 系统校验 |
| 可使用范围 | 仅分析 / 可写入简历 / 可用于投递 |

#### 建议实现

1. 将技能、项目、竞赛、证书和实习统一映射为“经历—能力—证据”关系。
2. AI 可以从自然语言中抽取候选证据，但不得直接标记为已验证。
3. 简历中的每一条项目亮点都保存 `evidence_id`，支持点击回看原始经历。
4. 未获得证据支持的数字、奖项、证书、公司、日期和职位名称，不允许自动写入正式简历。
5. 提供“证据完整度”，提示学生补充职责、成果、材料和量化信息，而不是让模型凭空补全。

#### 优化价值

能力证据库会成为岗位匹配、简历生成、面试训练和成长规划共同使用的数据底座，避免每个模块各自维护一套互相矛盾的学生信息。

### 1.4 将 AI 就业画像优化为“职业能力数字孪生”

“AI 就业画像”容易被理解成一次性的分析报告。建议把它升级为会随学生经历和求职结果持续变化的职业能力数字孪生。

数字孪生不是给学生打一个笼统的“就业竞争力 85 分”，而是维护以下五类状态：

1. **能力状态：**具备哪些技能，每项技能对应什么证据，证据强度如何。
2. **目标状态：**期望岗位、行业、城市、薪资、实习或校招时间窗口。
3. **资格状态：**专业、学历、毕业时间、实习时长、语言证书等硬条件。
4. **行为状态：**查看、收藏、投递了哪些岗位，在哪个环节停止。
5. **反馈状态：**哪些简历获得回应，面试在哪类问题上失分，哪些成长任务有效。

建议在首页用“目标岗位雷达 + 证据完整度 + 当前求职漏斗 + 本周行动”替代大段 AI 文字。这样评委能一眼看到学生现在是谁、目标是什么、差距在哪里、系统建议做什么。

### 1.5 将岗位匹配优化为“硬条件过滤 + 可解释匹配”

#### 第一步：先判断能不能投

以下条件应在 AI 语义匹配之前处理：

- 招聘对象和毕业年份；
- 学历、专业或资格证要求；
- 工作或实习年限；
- 工作城市、到岗时间和出勤天数；
- 岗位是否过期；
- 是否已经投递过同公司同岗位；
- 是否存在明确不接受条件。

如果硬条件不满足，应直接显示“不满足的原因”，而不是给出一个看似不错的综合分。

#### 第二步：再判断适不适合

建议把匹配结果拆成多个可解释维度，而不是只显示一个百分比：

| 维度 | 解释内容 |
|---|---|
| 必备技能覆盖 | 岗位的必备技能中，有多少具备可信证据 |
| 加分技能覆盖 | 哪些能力可以形成竞争优势 |
| 项目场景相似度 | 学生项目与岗位工作场景是否接近 |
| 证据可信度 | 匹配依据是自述、项目材料还是导师确认 |
| 成长成本 | 缺失能力预计需要多少时间补足 |
| 个人偏好 | 城市、行业、薪资和工作方式是否符合预期 |

综合分可以作为排序工具，但必须同时展示：

```text
岗位要求：具备 REST API 开发经验
匹配证据：校园就业系统项目中负责 FastAPI 接口开发
证据位置：项目经历第 2 条 / Git 提交记录
可信状态：本人确认，待导师复核
```

评分权重在 MVP 阶段可以由项目组配置，但必须使用人工标注样本做校准，不能把主观权重包装成科学结论。

### 1.6 将简历优化为“可信岗位简历工作台”

#### 建议的简历分层

1. **主档案：**保存所有经过用户确认的真实经历，不直接用于投递。
2. **岗位版本：**针对某个 JD，从主档案中选择、排序和改写相关内容。
3. **投递快照：**记录实际投递时的简历 PDF、问答内容、岗位版本和时间，后续不可静默覆盖。

#### 建议增加的关键功能

- JD 关键词、职责和硬条件结构化解析；
- “原文—AI 建议—最终文本”三栏对照；
- 每条 AI 内容显示证据来源；
- 对雇主、职位、日期、学历、证书、奖项和数字执行结构化事实校验；
- 对缺少证据的内容标红并禁止直接进入正式版本；
- ATS 基础检查，如栏目缺失、复杂表格、不可复制文本和关键词覆盖；
- 简历版本差异对比，展示为某个岗位做了哪些调整；
- 一键生成岗位简历、求职信、邮件正文和常见投递问题草稿。

这里应重点学习 Tailored 的思路：**真实性约束必须落到数据层和保存流程，而不只是提示词。**模型即使生成了错误内容，也应该在保存前被规则拦截。

### 1.7 将成长规划优化为“可执行任务与效果复盘”

当前成长规划不能只输出“建议学习 Java、提升沟通能力”一类泛化建议。建议每条建议转换为任务：

| 字段 | 示例 |
|---|---|
| 缺口来源 | 目标岗位中 12/20 个要求出现 SQL |
| 成长任务 | 完成 SQL 查询练习并用于一个项目 |
| 预计周期 | 2 周 |
| 验收产物 | 练习记录、项目提交、复盘文档 |
| 截止时间 | 2026-10-15 |
| 当前状态 | 未开始 / 进行中 / 已完成 / 已验证 |
| 效果判断 | 完成后是否提高岗位覆盖或面试表现 |

投递或面试失败后，系统不应直接断言“因为技能不足”，而应让用户选择或记录可观察反馈，如“简历未通过”“笔试算法题失分”“项目表达不清楚”。之后再据此调整任务优先级。

### 1.8 将 AI 助手优化为统一操作入口

AI 助手应从“回答问题”升级为“带确认的业务协作入口”，例如：

- “把这段项目经历整理为证据卡，但先让我确认。”
- “分析这个岗位，告诉我硬条件是否满足。”
- “使用已确认的证据生成岗位简历，不要补充未知数字。”
- “把这个岗位加入待投递队列。”
- “根据昨天的面试反馈，调整本周成长任务。”

所有会改变正式档案、简历或投递状态的操作，都应展示变更内容并由用户确认。这样既能提高 AI 的可用性，也能避免聊天模型直接修改关键数据。

### 1.9 优化 RAG、评测、隐私和系统可靠性

#### RAG 知识库

- 每条知识记录来源、发布日期、更新时间、地区和适用人群；
- 回答校招政策、应届生身份和就业手续时必须给出来源；
- 将外部 JD、网页内容和上传文件视为不可信输入，防止其指令影响系统提示或读取无关数据；
- 建立 50—100 个大学生就业问题的小型评测集，评估检索命中、引用正确和回答完整性；
- 记录模型、提示词、检索结果和版本，保证比赛演示能够复现。

#### 隐私与安全

- 联系方式、身份证、家庭住址等敏感字段分级存储与最小化展示；
- 不保存招聘网站密码、短信验证码或双因素验证码；
- 用户可导出和删除自己的数据；
- 简历对外分享采用限时链接和访问控制；
- 记录 AI 使用了哪些个人字段，支持用户撤销授权。

#### 生产可靠性

- 统一业务数据库的生产配置和迁移流程；
- 验证 PostgreSQL、SMTP、并发注册、唯一约束和备份恢复；
- 增加登录失败限流、操作审计和异常告警；
- 增加注册、登录、简历生成、岗位匹配和投递队列的端到端测试；
- 为外部模型调用设置超时、重试、降级和成本上限。

### 1.10 现有功能优化的实施顺序

#### P0：先把数据底座做可信

1. 建立能力证据卡和证据状态。
2. 简历内容关联证据，并增加结构化事实校验。
3. 岗位解析增加硬条件和要求分类。
4. 统一岗位、简历和成长任务之间的数据关系。

#### P1：把现有功能连成可演示链路

1. 从一个真实 JD 生成可解释匹配结果。
2. 从匹配证据生成岗位简历并展示变更对照。
3. 从技能缺口生成可执行成长任务。
4. 首页展示能力、目标、投递漏斗和本周任务。

#### P2：建立评测与生产保障

1. 构建人工标注的岗位匹配和简历事实评测集。
2. 完善 RAG 来源治理与引用。
3. 完成隐私、审计、备份和生产部署验证。

## 第二板块：项目还能拓展什么功能

### 2.1 核心拓展：AI 可信投递助手

用户提出的“AI 简历投递助手”应当成为项目的核心新增功能，但产品名称和设计不建议强调“全自动海投”。建议正式命名为：

> **AI 可信投递助手**

它的目标不是替学生尽可能多地点击投递，而是帮助学生**选择值得投的岗位、准备可信材料、减少重复填表、保留申请记录，并从结果中学习**。

#### 完整产品流程

```text
粘贴岗位链接或 JD
→ 提取公司、职位、职责、要求、地点和截止时间
→ 检查毕业年份、学历、专业、地点等硬条件
→ 用能力证据解释匹配项与缺口
→ 生成岗位简历、求职信和投递问答
→ 执行结构化事实校验
→ 用户逐条审核并形成材料包
→ 浏览器扩展识别招聘表单并预填
→ 未识别或敏感字段交给用户
→ 用户完成验证码和最终提交
→ 保存投递快照与成功回执
→ 跟踪笔试、面试、录用或拒绝状态
→ 结果反哺数字孪生和成长任务
```

### 2.2 AI 可信投递助手的七个模块

#### 模块一：岗位采集与结构化解析

输入方式按优先级设计：

1. 用户粘贴岗位链接；
2. 用户粘贴 JD 文本；
3. 浏览器扩展从当前招聘页采集；
4. 对允许访问的企业招聘页或公开 API 建立来源适配器。

解析结果包括公司、岗位、地点、招聘类型、毕业年份、学历专业、技能要求、职责、加分项、截止时间和原始链接。系统必须保存原始文本与抓取时间，便于岗位发生变化时复核。

#### 模块二：资格和风险检查

在生成材料前先回答：

- 是否满足应届生或实习生身份要求；
- 是否满足学历、专业、毕业时间和到岗要求；
- 岗位是否过期或重复；
- 是否与用户的城市、行业和岗位偏好冲突；
- 岗位信息是否缺失、来源不明或疑似异常；
- 当前是否已有适合该岗位的可信证据。

不满足硬条件时，系统默认不进入待投递队列，但允许用户查看理由并手动决定。

#### 模块三：可信材料包

每个岗位生成一个独立材料包：

- 岗位定制简历；
- 求职信；
- 邮件正文；
- 自我介绍；
- “为什么选择本公司/岗位”等常见问题草稿；
- 岗位匹配报告；
- 内容证据清单；
- 投递前检查结果。

材料包中的每条关键内容都应能回到能力证据卡。未经支持的事实不得通过正式校验。

#### 模块四：投递问题答案库

许多招聘网站会重复询问到岗时间、期望地点、是否接受调剂、项目经历和职业规划。系统可以维护答案库，但需要分为：

- **稳定字段：**姓名、邮箱、学校、专业等，可自动预填；
- **偏好字段：**城市、薪资、到岗时间等，预填后需要确认；
- **岗位相关开放题：**必须结合 JD 生成，并显示证据来源；
- **敏感字段：**身份证、健康、家庭、政治面貌等，默认不自动填写；
- **验证码和承诺声明：**必须由用户本人处理。

#### 模块五：投递预演和人工确认

真正执行前展示一张投递确认单：

- 公司、岗位和原始链接；
- 将要使用的简历版本；
- 将要填写的联系方式与答案；
- AI 修改内容与原始事实的差异；
- 尚未确认或证据不足的字段；
- 可能涉及的隐私信息；
- 是否发现同岗位重复投递。

用户确认后才能进入预填阶段。首次支持某个招聘网站时，默认只做预填，不做自动提交。

#### 模块六：浏览器扩展和表单预填

可借鉴 jobApplier 与 Guild 的浏览器扩展思路，优先实现以下能力：

1. 识别姓名、邮箱、电话、教育、项目和工作经历等常见字段；
2. 使用站点适配器处理已支持页面；
3. 对未知页面使用字段标签和上下文进行辅助映射；
4. 对低置信度字段进行高亮，不自动填写；
5. 自动上传当前岗位对应的简历文件；
6. 页面发生变化、登录失效或出现验证码时暂停；
7. 默认不点击最终提交按钮。

第一版不要承诺“支持所有招聘网站”。比赛 MVP 只需要在一个模拟招聘页面和一个结构稳定、允许测试的页面上完成可验证预填，即可证明技术链路。

#### 模块七：投递看板与结果反馈

建议状态流转为：

```text
待分析 → 不符合硬条件 / 待准备
→ 材料生成中 → 待审核 → 待投递
→ 已预填 → 已投递 → 已读
→ 笔试 → 面试 → 录用 / 拒绝 / 用户放弃
```

只有检测到成功页面、回执编号、确认邮件或用户手动确认后，才能标记为“已投递”。系统还要保存投递时间、岗位快照、简历版本和表单答案，避免后续无法解释投了什么。

### 2.3 AI 可信投递助手的技术设计建议

#### 系统组成

| 层级 | 建议职责 |
|---|---|
| Web 前端 | 岗位收件箱、匹配解释、材料包审核、投递看板和复盘 |
| 后端服务 | 岗位解析、规则判断、证据检索、材料生成、状态流转和审计 |
| AI 服务层 | JD 结构化、能力映射、文本改写、开放题草稿和面试复盘 |
| 规则与校验层 | 硬条件、重复投递、事实一致性、敏感字段和风险拦截 |
| 浏览器扩展 | 当前页面采集、字段识别、受控预填、文件上传和人工接管 |
| 数据层 | 用户档案、证据、岗位、材料版本、投递、回执、反馈和评测日志 |

#### 建议新增核心数据表

| 数据表 | 主要内容 |
|---|---|
| `evidence_items` | 能力证据、来源经历、材料链接、可信状态和使用范围 |
| `job_postings` | 原始 JD、解析结果、来源、版本和截止时间 |
| `job_requirements` | 硬条件、必备技能、加分项和职责 |
| `job_matches` | 资格判断、多维评分、证据映射和缺口 |
| `application_packets` | 岗位简历、求职信、答案和审核状态 |
| `application_answers` | 问题、草稿、最终答案、证据和敏感级别 |
| `applications` | 申请状态、时间、渠道、回执和投递快照 |
| `application_events` | 状态变化、面试、拒绝原因和用户备注 |
| `growth_tasks` | 缺口来源、任务、产物、状态和效果 |
| `audit_logs` | AI 生成、用户确认、预填和状态修改记录 |

#### AI 输出约束

- JD 解析使用固定 JSON Schema；
- 所有生成内容携带来源证据 ID；
- 对公司、职位、日期、学历、证书、奖项和数字执行确定性校验；
- 模型无法确认的信息必须返回 `unknown`，不得猜测；
- 外部网页文本不能修改系统规则，也不能请求读取无关个人数据；
- 正式保存前执行规则校验，正式投递前再次执行用户确认。

### 2.4 必须坚持的产品和安全边界

AI 可信投递助手不应设计成无差别海投工具，必须明确以下限制：

1. 不保存招聘网站密码、短信验证码或双因素验证码。
2. 不绕过登录、验证码、反自动化措施和平台访问限制。
3. 默认只进行表单预填，最终提交由用户完成。
4. 不在用户不知情时批量投递。
5. 不自动填写敏感字段和法律承诺类字段。
6. 不把“点击了按钮”视为投递成功，必须保存可验证回执。
7. 不使用未经证据支持的数字、奖项、证书、公司、职位和日期。
8. 不因模型评分较低而替用户做最终职业决定。

这些边界不是功能削弱，而是项目“可信”和“以学生为中心”的组成部分，也能够降低比赛答辩中关于隐私、虚假简历和平台合规的质疑。

### 2.5 项目的比赛特色：职业能力数字孪生 + 可信投递实验闭环

#### 特色一：职业能力数字孪生

普通简历系统保存的是文本，数字孪生保存的是“学生能力在当前时间点的结构化状态”，包括能力、证据、目标、资格、行为和反馈。它会随着新项目、新竞赛、新投递和新面试不断更新。

#### 特色二：证据驱动的可解释匹配

系统不只说“匹配度 86%”，而是解释岗位要求由哪条经历支撑、证据可信度如何、哪些硬条件不满足、哪些缺口能够在短期补足。

#### 特色三：事实受控的 AI 材料生成

AI 只能在用户确认的真实经历范围内选择、重组和表达，关键事实由程序规则再次校验。这样可以把“减少 AI 幻觉”变成能够演示和测量的技术机制。

#### 特色四：人机协同的可信投递

AI 负责理解岗位、准备材料和预填表单；用户负责审核敏感信息、处理验证码、确认承诺并最终提交。系统保留全过程记录和投递快照。

#### 特色五：投递结果成为成长实验

每次投递可以看作一次小型实验：

```text
目标岗位 + 能力证据 + 简历版本 + 投递答案
→ 是否获得回应
→ 是否进入笔试或面试
→ 哪个环节出现问题
→ 下一项成长任务是什么
```

经过多次投递后，系统不再只给通用建议，而是能回答“什么类型的岗位更适合该学生”“哪类项目表达更容易获得回应”“完成哪些任务后匹配和面试表现有所改善”。

### 2.6 与普通 AI 求职产品的差异

| 普通产品常见做法 | 本项目建议做法 |
|---|---|
| 上传简历后生成一个匹配分 | 先检查硬条件，再给出证据级匹配解释 |
| 依靠提示词要求模型不要编造 | 在数据层和保存流程执行结构化事实校验 |
| 自动生成更好听的项目描述 | 每条描述回链到真实经历和证据 |
| 追求更多、更快的自动投递 | 追求适合、可信、可审核、可复盘的投递 |
| 投递完成即结束 | 将回应、面试和拒绝反馈给能力模型与成长任务 |
| 服务泛化的社会求职者 | 聚焦大学生校招、实习、竞赛和项目能力转化 |

一句话概括差异：

> **别人帮助用户“多投简历”，本项目帮助大学生“用真实证据投对岗位，并从每次结果中持续成长”。**

### 2.7 其他可拓展功能

AI 可信投递助手完成后，可以沿同一数据底座继续拓展，而不是再做互不相关的小工具。

#### 1. AI 模拟面试与证据追问

根据实际 JD 和已投递简历生成面试问题，重点追问简历中的项目职责和结果；识别回答与证据卡之间的矛盾；输出 STAR 表达建议和待补知识点。面试结束后把失分项转为成长任务。

#### 2. 校招日历与行动提醒

聚合宣讲会、网申截止、笔试、面试和材料提交时间；根据目标行业生成秋招、春招时间线；提醒学生避免错过截止日期。来源和更新时间必须显示。

#### 3. Git 与项目材料智能取证

在用户授权后读取 Git 提交、README、接口文档和项目报告，自动提取“做了什么、使用什么技术、产生什么成果”的候选证据；由用户确认后写入能力证据库。该功能特别适合计算机类学生，也能增强比赛技术特色。

#### 4. 导师或辅导员协同评审

学生可以邀请导师对项目职责、竞赛成果和能力证据进行确认；导师只看到学生授权的内容。经确认的证据在简历和岗位匹配中显示更高可信等级。

#### 5. 高校就业服务驾驶舱

在学生明确授权和数据匿名化后，为高校展示专业层面的岗位需求趋势、共性技能缺口、投递转化和需要重点支持的群体。不得向教师直接暴露个人敏感求职记录。

#### 6. 匿名求职经验知识库

将面试题型、招聘流程和常见失败原因匿名化，形成按公司、岗位和年份组织的经验库；结合 RAG 为学生提供有来源、有时效的准备建议。

### 2.8 比赛 MVP 范围

为了避免功能过大，建议比赛版本只做一条完整、稳定、可量化的链路：

1. 用户维护一份真实学生档案和 5—10 张能力证据卡。
2. 粘贴一个真实或经过授权使用的岗位 JD。
3. 系统完成硬条件检查和证据级匹配解释。
4. 生成一份事实受控的岗位简历和 2—3 个投递问题答案。
5. 用户逐条审核，系统展示事实校验结果。
6. 浏览器扩展在模拟招聘页或一个稳定页面完成预填。
7. 用户手动提交，系统保存成功回执和投递快照。
8. 录入一次模拟或真实面试反馈，系统更新成长任务。

这八步全部跑通，比展示二十个未连通的 AI 功能更有说服力。

### 2.9 建议开发路线图

#### 第一阶段：可信数据底座（第 1—2 周）

- 能力证据卡；
- JD 结构化模型；
- 硬条件规则；
- 证据与岗位要求映射；
- 简历内容事实校验。

#### 第二阶段：材料包与投递看板（第 3—4 周）

- 岗位收件箱；
- 岗位简历、求职信和答案生成；
- 用户审核和版本对比；
- 投递状态与事件记录；
- 投递快照和重复投递检查。

#### 第三阶段：受控预填（第 5—6 周）

- Chrome Manifest V3 扩展；
- 模拟招聘页；
- 常见字段识别；
- 未知字段高亮；
- 文件上传和人工接管；
- 回执保存。

#### 第四阶段：反馈闭环与评测（第 7—8 周）

- 面试反馈录入；
- 成长任务自动调整；
- 埋点和实验指标；
- 20—50 名学生小规模试用；
- 修复演示链路和整理答辩材料。

### 2.10 小规模验证与量化指标

建议邀请 20—50 名不同专业和年级的学生，在获得知情同意后完成小规模试用。所有展示数据应匿名化，不能用虚构的“准确率提升”代替真实验证。

#### 评测设计

- **对照 A：**学生手工阅读 JD、修改简历和填写表单；
- **对照 B：**只使用关键词或普通 AI 简历生成；
- **实验组：**使用证据驱动匹配、事实校验和可信投递助手。

#### 核心指标

| 指标 | 测量方法 |
|---|---|
| 硬条件识别准确率 | 与人工标注的学历、毕业时间、专业等条件对比 |
| 岗位要求抽取 F1 | 与人工标注的必备技能、加分项和职责对比 |
| 匹配解释可理解性 | 学生与就业指导教师 5 分量表评价 |
| 简历事实错误率 | 生成内容中无证据或与档案冲突的事实占比 |
| 单次材料准备时间 | 从输入 JD 到确认材料包的时间 |
| 表单预填准确率 | 正确预填字段数 / 可预填字段总数 |
| 人工修改率 | 用户修改的 AI 内容或预填字段占比 |
| 重复投递率 | 被系统识别并阻止或提醒的重复申请比例 |
| 回应率与面试转化 | 在相近岗位和时间窗口内进行观察，不夸大因果 |
| 成长任务完成率 | 用户完成并提交验收产物的任务比例 |

比赛材料中应报告样本量、岗位类型、测试时间和局限性。如果样本较小，可以重点证明效率、事实可靠性和解释可用性，不要轻率宣称系统显著提高录用率。

### 2.11 5—7 分钟比赛演示脚本

1. **问题引入（30 秒）：**大学生有项目和竞赛经历，却不知道如何对应岗位要求；普通 AI 容易生成无法证明的内容，投递后也缺少反馈。
2. **数字孪生（45 秒）：**展示某位匿名学生的目标岗位、能力证据和证据完整度。
3. **岗位解析（45 秒）：**粘贴一个 JD，系统抽取硬条件、必备技能和加分项。
4. **可解释匹配（60 秒）：**展示“要求—证据—可信状态—缺口”，并明确一个不满足项。
5. **可信简历（60 秒）：**生成岗位版本，点击一条简历描述回看证据；故意展示一条无证据数字被系统拦截。
6. **AI 可信投递（60 秒）：**审核材料包，打开模拟招聘页，由扩展预填；未知和敏感字段保持为空，由用户确认并提交。
7. **结果闭环（45 秒）：**保存回执，录入面试反馈，系统将“项目表达不足”转为新的成长任务。
8. **实验结果（30 秒）：**展示小规模测试中的准备时间、事实错误率和预填准确率变化。
9. **总结（20 秒）：**强调系统不是自动海投，而是帮助大学生用真实证据投对岗位，并从每次结果中成长。

### 2.12 建议的答辩表述

> 我们不是又做了一个 AI 简历生成器，而是构建了面向大学生的职业能力数字孪生与可信投递平台。系统把课程、项目、竞赛和实习转化为可追溯的能力证据，先检查岗位硬条件，再解释每项要求由什么真实经历支撑；AI 只能基于已确认事实生成岗位简历和投递答案，并在用户审核后辅助预填，最终提交仍由学生完成。投递、笔试和面试结果会反向更新学生的能力模型与成长任务。我们希望优化的不是海投数量，而是岗位选择质量、材料真实性、投递效率和持续成长效果。

### 2.13 最终开发取舍

参赛前应坚持以下取舍：

- **优先做闭环，不优先堆功能；**
- **优先做事实可信，不优先追求文案华丽；**
- **优先做一个站点或模拟页稳定预填，不宣称全网自动投递；**
- **优先展示真实学生、真实岗位和真实操作记录，不用纯演示数据证明效果；**
- **优先量化节省时间、事实错误率和解释质量，再观察回应率和面试转化；**
- **优先突出大学生能力成长，不与通用招聘平台比岗位数量。**

如果资源有限，最值得集中完成的创新主线只有一条：

> **真实经历形成能力证据 → 证据解释岗位匹配 → 证据约束简历生成 → 用户确认后完成可信投递 → 投递结果反哺能力成长。**

这条主线既能复用当前项目已经实现的档案、AI 分析、岗位匹配、简历、成长规划和 RAG 基础，也能形成清晰的比赛故事、可实现的技术方案和可量化的实验结果。

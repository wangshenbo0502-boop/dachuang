# 大创项目优化报告：可信就业成长闭环

更新日期：2026-09-26

项目：AI 就业竞争力评估与提升系统

本轮开发基线：GitHub `main` 提交 `4fedd21`

## 1. 建议的项目特色

**面向大学生的“证据驱动、可解释、可反馈”的就业成长闭环。**

学生授权建立账号后，用真实档案中的课程、技能、项目、竞赛和实习形成“能力证据卡”；系统给每个目标岗位展示匹配点、证据出处、缺口和可信度；学生审核定制简历并决定是否投递；投递进度、面试反馈再反哺成长计划。核心演示链路：

> 真实经历录入 → 能力证据卡 → 岗位匹配与缺口解释 → 定制简历 → 人工确认投递 → 进度与结果记录 → 成长建议更新

答辩时不要只展示“用了 AI”。建议展示同一位学生在投递前后的一条完整决策链：某个岗位为什么推荐、简历的哪句话来自哪条经历、为什么建议补足某项技能、投递结果如何改变下一步行动。**竞赛获奖无法保证**；特色点能否成立，取决于真实用户试验与量化结果。

## 2. 开源项目对标（2026-09-26 查阅 GitHub）

1. [JobSync](https://github.com/Gsync/jobsync)：集成投递记录、简历管理、AI 简历评审、岗位匹配、求职信和自动发现岗位。可借鉴其“岗位发现后由用户确认入库”及投递状态看板。我们的差异化应落在大学生能力证据、技能缺口和成长反馈。
2. [Reactive Resume](https://github.com/reactive-resume/reactive-resume)：成熟的开源简历编辑、模板、预览与多格式导出。可借鉴简历版本和导出体验；本项目应突出“简历内容须可追溯到真实学生经历”，避免泛化的美化生成。
3. [Job Sentinel](https://github.com/harshitwandhare/job-sentinel)：面向大学门户及公开招聘源的职位聚合、匹配和针对岗位的简历生成。可借鉴可插拔数据源；本项目要针对中国高校校招、实习、应届生身份和成长规划建立本土化知识与评价集。
4. [Job Agent](https://github.com/anton-karlovskiy/job-agent)：使用浏览器自动填表，支持先进行不提交的预演，再执行投递。可借鉴适配器、预演和障碍处理；本项目的自动投递应默认由学生最后确认，不绕过登录、验证码或平台限制。

以上为功能对标，不代表代码复用或已在本项目实现。

## 3. 本轮已完成：正式账号与数据隔离

### 后端与数据库

- 新增 `accounts` 表：`id`、唯一 `username`、唯一 `email`、`password_hash`、唯一 `profile_id`、`email_verified`、`is_active`、`token_version`、创建/更新时间及最近登录时间。原 `users` 表继续承担学生就业档案职责；新账号通过 `profile_id` 与它建立一对一关系。
- 新增 `email_codes` 表：按邮箱和用途唯一存储 HMAC 摘要、过期时间、发送时间、当日次数和错误次数。验证码按注册或重置密码用途隔离，为随机 6 位数字、5 分钟有效；同邮箱 60 秒间隔、每天最多 10 次、连续输错 5 次需重新获取。验证码不进入 HTTP 响应。
- 密码使用 Argon2id 哈希。登录颁发有期限的 HS256 JWT；服务端验证签名、过期时间、账号状态和 `token_version`；登出递增版本，令该账号旧 token 失效。
- 新增 `POST /api/auth/email/send-code`、`POST /api/auth/register`、`POST /api/auth/login`、`GET /api/auth/me`、`POST /api/auth/logout`、`POST /api/auth/reset-password`。
- 新增 `GET /api/users/me`、`PUT /api/users/me`。旧 `/api/users/{user_id}` 接口暂留给现有前端兼容，但必须是当前 token 对应的档案；禁止直接通过旧 `POST /api/users` 创建无账号档案。
- 档案、AI 画像、成长规划、简历及版本、岗位匹配历史、聊天和 SSE 接口均要求登录。客户端传入的 `user_id` 与 token 不一致时拒绝；记录详情检查记录所有者。知识管理和 AI 用量接口也要求登录。
- 当前代码保留旧演示档案，不执行破坏性清理；没有账号绑定的旧档案不会通过新认证入口被访问。既有业务表未删除。

### 前端

- 将“输入档案编号”改为 QQ 邮箱加密码登录；新增验证码注册页与忘记密码页，注册后自动进入系统；重置密码会撤销旧 token。
- Pinia `useAuthStore` 统一维护账号、档案、token 和加载状态。token 保存在本机 `localStorage`；刷新后调用 `/api/auth/me` 再加载档案。路由守卫将未登录用户带到登录页，并保留原目标路径。
- Axios 请求与 SSE 请求自动携带 Bearer token。收到 401 时清除本地凭证。退出登录调用服务端撤销接口，同时立即清除本地状态。
- 设置页改为展示当前绑定邮箱。

### 主要文件

新增：`backend/app/models/account.py`、`backend/app/schemas/auth.py`、`backend/app/auth/security.py`、`backend/app/auth/dependencies.py`、`backend/app/api/auth.py`、`backend/tests/test_auth_api.py`、`backend/tests/auth_helpers.py`、`frontend/src/stores/auth.ts`、`frontend/src/utils/authSession.ts`、`frontend/src/views/login/RegisterView.vue`、`frontend/src/views/login/ForgotPasswordView.vue`。

## 4. 配置、启动与验收

1. 在 `backend/.env` 配置 `DATABASE_URL`、`JWT_SECRET`（至少 32 字符随机值）、`JWT_ACCESS_MINUTES`。生成示例：`python -c "import secrets; print(secrets.token_urlsafe(48))"`。复制并编辑 `backend/.env.example`，勿提交真实密钥。
2. 开发机无 SMTP 时设 `APP_ENV=development`、`DEV_EMAIL_CODE_MODE=true`，验证码只写入后端开发日志，不返回前端。正式部署设 `DEV_EMAIL_CODE_MODE=false`，配置 `SMTP_HOST`、`SMTP_PORT`、`SMTP_USERNAME`、`SMTP_PASSWORD`、`SMTP_FROM`，并使用 QQ 邮箱的 SMTP 授权码。生产 SMTP 真实投递尚需在部署环境验证。
3. 在 `backend` 运行 `python -m pip install -r requirements.txt`、`python init_db.py`、`python -m uvicorn main:app --reload`；在 `frontend` 运行 `npm install`、`npm run dev`。初始化使用配置的业务 `DATABASE_URL` 创建缺失表，不删除旧表。
4. 打开 `/register`，填写 QQ 邮箱并获取验证码；完成注册后自动进入首页。刷新页面确认仍登录；退出后确认旧 token 的 `/api/auth/me` 返回 401。
5. 注册两个账号 A/B；携带 A 的 token 请求 `GET /api/users/{B的档案ID}`、B 的 AI 历史或 B 的简历版本，预期 403。无 token 请求个人接口，预期 401。
6. 本轮执行结果：前端 `npm run type-check` 与 `npm run build` 通过；后端 `python -m compileall app` 通过；`python -m pytest tests -q` 为 **38 通过、1 跳过**。跳过的是需独立 PostgreSQL 测试库的测试。当前未验证真实 QQ SMTP、真实 PostgreSQL 部署或浏览器端完整人工流程，不能宣称这些环境已经通过验收。

代码现状需在部署前澄清：业务 `DATABASE_URL` 默认仍可退回 SQLite，`backend/.env.example` 的旧示例为 MySQL；知识库则独立使用 PostgreSQL + pgvector。若比赛部署目标是“业务与知识库均 PostgreSQL”，应明确配置业务库的 PostgreSQL URL，并做一次带真实数据的迁移与回归验证，不能仅凭提示词中的技术栈描述推定已完成。

- [ ] 对旧演示档案制定备份、清理或本人认领流程；正式上线前避免数据库中长期留存无人认领的个人数据。

### P1：能向评委展示的特色闭环

- [ ] **能力证据卡**：每条技能、项目成果关联原始经历、时间、本人职责和可验证材料；AI 建议必须给出证据链接或标明“待补证”。
- [ ] **可解释岗位匹配**：把岗位要求拆成必备技能、加分技能和约束条件；显示匹配理由、缺口和权重。建立人工标注的小型校招岗位集，比较匹配准确率与解释可用性。
- [ ] **真实经历约束的简历版本**：不同岗位生成不同简历版本；每条亮点需回链到能力证据卡，用户审核后才能导出。
- [ ] **成长计划反馈**：面试未通过原因或投递状态更新后，重新排序技能缺口与学习任务；展示“建议是否带来结果改善”而非只给静态建议。
- [ ] **大学生场景知识**：补充校招时间线、实习转正、应届生身份、竞赛与项目表达等资料，并标记来源、更新时间和适用地区。

### P2：简历自动投递（你提出的新方向）

建议先做**“智能投递助手”**，再逐步加入自动执行。一个可落地的方案：

1. **岗位接入**：优先使用企业公开招聘页、允许访问的 API 或用户主动提供的岗位链接；为每个来源做适配器，保存原始链接、岗位版本、抓取时间与来源。
2. **投递前校验**：检查岗位是否过期或重复、校招资格是否满足、地域/薪资是否符合偏好，并计算岗位与学生档案的匹配分及证据。低匹配或缺材料时不进入待投递队列。
3. **材料生成**：从已审核的档案和简历版本生成岗位定制版简历、求职信与问答草稿。未获证据支持的成绩、年限和项目数字必须提示用户确认。
4. **预演与人工确认**：先展示即将提交的岗位、企业、简历版本、联系方式和所有表单答案；用户确认后才执行提交。首次接入某招聘网站时默认只填表不提交。
5. **执行适配器**：允许的官方接口优先；无接口时采用受控浏览器填表。遇登录、验证码、双因素验证或页面变化，暂停交由用户处理；遵守招聘网站规则和发送频率，保留操作日志与截图。
6. **结果闭环**：记录“待审核、已投递、已读、笔试、面试、录用、拒绝”等状态；对重复投递进行幂等检查；统计岗位类别的回应率和面试转化率，反馈到简历与成长计划。

优先交付一个**单网站、人工确认、可复盘**的 MVP，再评估扩展。大规模无差别海投既难证明效果，也容易损害学生求职体验。不要把“自动填表”直接写成“已自动投递成功”；必须收到可验证的回执才标记成功。

## 6. 可量化的竞赛验证方案

- 数据：征得同意的学生档案样本、真实校招/实习岗位、人工标注的岗位要求与适配程度；隐去姓名和联系方式。
- 对照：学生手工投递流程、仅关键词匹配、现有 AI 匹配、加入证据与反馈闭环后的系统。
- 指标：岗位匹配准确率/召回率、解释可理解性评分、简历事实错误率、每次投递准备时间、重复投递率、投递回应率、面试转化率、用户满意度。
- 设计：记录同一时间窗与相近岗位条件下的对照结果，报告样本量与不确定性；“回应率提升”须来自真实样本，不能由演示数据推算。
- 展示：使用一条经过用户授权的完整匿名案例，并附系统决策依据、修改前后差异与真实投递状态。

## 7. 建议的答辩表述

> 我们针对大学生求职信息分散、岗位要求不透明、简历内容难以证明和投递后缺少反馈的问题，构建了以学生真实经历为证据的就业成长闭环。系统给出可解释的岗位匹配与技能缺口，辅助生成可追溯的岗位简历，经学生确认后完成投递，并用结果持续修正成长建议。我们用真实校招岗位和学生样本评估匹配、效率和事实可靠性，而不是只展示模型生成效果。

# 管理员独立系统：架构与接口契约 v1

本文是待实施需求，现有源码基线见 [README](README.md)。代码参考见 [核心关键代码](02-核心关键代码.md)，任务顺序见 [分阶段提示词](03-分阶段提示词与验收.md)。

## 1. 系统边界

```text
求职者/招聘者浏览器 → frontend:5173 → backend:8000 /api/* → 业务数据库
                                                ↑
                                  /internal/admin/v1/*
                                  仅服务调用，默认关闭
                                                ↑
管理员浏览器 → admin-frontend:5174 → admin-backend:8001 → 管理数据库
                                      /admin-api/v1/*

原知识库 PostgreSQL/pgvector ← 原业务后端；管理端首期不直接访问
```

箭头表示允许的调用方向。业务后端不向管理后端回调；管理侧通过查询命令结果完成恢复。生产端口仅作内部服务示意，不能据此宣称已有域名或线上地址。

| 维度 | 管理系统 | 现有业务系统 |
|---|---|---|
| 浏览器应用 | 新 `admin-frontend/`，独立登录页、布局、路由、Store | 原 `frontend/`，保留两类身份入口 |
| 后端进程 | 新 `admin_app.main:app`，8001 | 原 `main:app`，8000 |
| 浏览器认证 | 独立数据库会话和 HttpOnly Cookie | 现有 Bearer JWT |
| 数据库 | 管理身份、会话、审计、命令意图 | 账号、岗位、投递、业务执行凭据 |
| 配置 | 独立 `.env`、独立数据库凭证与服务密钥 | 原配置继续有效，内部 API 新配置默认关闭 |
| 代码共享 | 只接受已生成的 OpenAPI 类型或无业务契约产物 | 不接受跨应用 ORM、Session、服务函数导入 |
| 发布 | 独立锁文件、镜像、健康检查、迁移步骤 | 无需为管理前端每次变更同步发布 |

管理库允许本地独立 SQLite 文件；生产新管理库采用 PostgreSQL。原业务库的 SQLite/MySQL/PostgreSQL 选择保持不变，实际使用的数据库方言必须验证。多个数据库可以在同一数据库服务实例上，但须使用独立 database 和账号，禁止跨库 SQL/FK。

## 2. 首期功能与页面

| 页面路由 | 必需功能 | 数据来源与限制 |
|---|---|---|
| `/login` | 用户名/密码、错误提示、防重复提交、会话过期提示 | 管理认证；没有公开注册和业务身份切换 |
| `/overview` | 求职者/招聘者数量、启用账号数、发布/限制岗位数、按状态投递数 | 业务汇总 API；不下载所有记录前端计算 |
| `/accounts` | 按角色/状态/关键词分页、账号详情、启用/禁用、填写理由 | 账号 DTO；邮箱脱敏，不展示密码和完整档案 |
| `/recruiters` | 企业资料摘要、账号状态、岗位数量、跳转岗位列表 | 招聘者 DTO；企业资料标注“招聘者填写，未认证” |
| `/jobs` | 岗位筛选、详情、平台限制/解除限制、治理理由与历史 | 招聘领域 API；不冒用招聘者修改职位正文 |
| `/applications` | 投递编号、岗位、脱敏主体、状态、时间、分页筛选 | 只读元数据；禁止完整简历、反馈原文和状态代改 |
| `/commands` | 最近操作、执行状态、结果待确认查询、使用原键重试 | 管理命令意图与业务凭据联合确认 |
| `/audit-logs` | 按操作者/操作/对象/结果/时间筛选，查看脱敏前后变化 | 管理审计；业务动作关联业务凭据 |
| `/administrators` | 超级管理员创建账号、修改角色、禁用账号、吊销会话 | 管理库；阻止禁用最后一个超级管理员 |
| `/403`、`/unavailable`、404 | 权限不足、服务不可用、页面不存在 | 真实状态页面，不能伪装为空列表 |

每个业务页面具备 loading、empty、error、ready 四种状态。上游离线显示“业务服务暂不可用”；概览不得补随机数或将失败解释为 0。危险操作必须弹出对象名称、影响和必填理由，提交期间禁用重复点击，结果待确认期间不能假装成功。

桌面使用侧边导航、顶栏、面包屑与内容区；手机使用抽屉导航和卡片列表，390px 宽下不能整体横向溢出。UI 用“求职者”展示 `student`，避免把后台账号与业务账号都简称为“用户”。

首期明确不实现：企业资质认证工作流、投诉受理、批量删除、数据导出、查看私人简历/AI 对话、代投递/代录用、SMTP/AI 密钥编辑、知识库内容编辑与索引重建。扩展这些能力时另写契约、权限和验收，不在首期留可点击但无效的入口。

## 3. 权限与身份

### 3.1 管理员角色

首期使用固定角色到权限集合的映射，不建立通用权限编辑器；权限改变后，下次服务端请求立即按数据库当前角色校验。

| 权限 | `super_admin` | `operator` | `auditor` |
|---|---|---|---|
| `overview:read`、`accounts:read`、`recruiters:read`、`jobs:read` | 是 | 是 | 是 |
| `applications:read`、`commands:read`、`audit:read` | 是 | 是 | 是 |
| `accounts:status_write`、`jobs:moderate` | 是 | 是 | 否 |
| `administrators:manage` | 是 | 否 | 否 |

`commands:read` 中，operator 只看自己发起的命令；super_admin/auditor 可看全部脱敏结果。审计中身份取服务端会话，不接受前端传入的 actor。首期没有 `*` 通配权限，新增权限必须显式加入映射。

超级管理员通过交互式 CLI 首次创建，密码用隐藏输入，不使用默认密码，不从进程命令参数接收密码。公开 API 不提供管理员注册。创建后续管理员、变更角色、禁用/改密均记录审计并吊销相关会话。防止最后一个超级管理员被禁用/降级时，使用专用单行锁记录序列化这些操作；仅“先 count 再 update”不足以防止并发绕过。

管理 username 去首尾空白并转小写后匹配 `[a-z0-9_.-]{3,64}`，唯一性按该规范值建立。管理密码长度 12～128 字符，禁止全空白但不做 trim 或大小写转换；与原业务密码策略分别管理。角色输入必须是上述三个固定值。所有涉及创建、角色变更和禁用的管理操作都有理由；登录、退出、改密属于认证接口，不要求业务命令的版本/幂等字段。

### 3.2 管理浏览器会话

- 管理账号使用 Argon2 密码散列，数据库不存明文密码。
- 登录生成 32 字节随机会话值；数据库只保存会话值 SHA-256，Cookie 保存原值。绝对有效期 8 小时，首期不自动续期。
- 生产 Cookie 名 `__Secure-dachuang_admin_session`，`HttpOnly; Secure; SameSite=Strict; Path=/admin-api/v1`，不设置 Domain。
- 本地 HTTP 使用独立名称 `dachuang_admin_dev`，只在 development/testing 允许 `Secure=false`。Cookie 不按端口隔离，不能只靠 5173/5174 区分登录状态。
- 会话关联 `admin_accounts.session_version`。每次请求检查账号启用、版本、会话到期和吊销状态；登出吊销当前会话，改密/禁用/改角色吊销该账号全部会话。
- 同步 CSRF token 存在管理会话中，登录和 `/auth/me` 返回该 token。前端仅内存保存，写请求带 `X-CSRF-Token`；服务端常量时间比较。
- 所有修改请求验证 Origin，必须等于配置的管理站点 origin；登录尚无会话，仅执行 Origin、JSON Content-Type、请求大小和登录限流检查。
- 登录错误统一提示凭证无效，不泄露账号存在性；生产按 IP 和账号组合限流，跨 worker 共享计数，可使用管理数据库计数表。不能用仅进程内计数声称生产限流完成。
- 管理 API 不接受现有业务 Bearer JWT。管理 Cookie 不作为原业务 API 的有效凭证。

### 3.3 服务间调用

内部 API 前缀 `/internal/admin/v1`，由业务后端拥有，受 `INTERNAL_ADMIN_ENABLED=false` 默认开关保护。禁用时不注册路由；原业务启动不要求管理库或内部密钥存在。

启用后配置单独的 `INTERNAL_ADMIN_SERVICE_SECRET`，至少 32 字节随机熵，与原 `JWT_SECRET` 不同，仅管理后端和业务后端持有。生产使用 HTTPS 或具有等价保密保证的受控服务网络；公网反向代理拒绝整个 `/internal/` 路径。

管理后端按单次请求签发 30 秒 HS256 服务 JWT：

| 声明 | 固定约束 |
|---|---|
| `iss` | `dachuang-admin-service` |
| `aud` | `dachuang-business-internal` |
| `sub` | `admin-service` |
| `actor` | 从已验证管理会话获取的管理员 ID 字符串 |
| `scope` | 当前内部接口需要的唯一权限字符串 |
| `req` | 请求方法、原样 path/query、幂等键及原始 body 字节的 SHA-256 |
| `iat/exp` | 签发时间/到期时间，寿命不超过 30 秒 |
| `jti` | 单次调用 UUID，区别于业务 `command_id` |

业务后端固定算法、issuer、audience、subject 和允许 scope，检查请求摘要及时间。写操作还依靠持久化 command_id 幂等；短时重复读取允许，写操作重放返回同一结果，不重复执行。`X-Admin-Id`、`X-Role` 等普通头不能作为身份来源。内部 API 不开放浏览器 CORS。

该模型信任管理后端已经完成管理员权限校验；共享服务密钥持有者属于可信服务。不能宣称业务端能独立证明每个管理员的实时角色。未来跨组织场景可换为独立服务身份与非对称签名，首期不扩展。

## 4. 数据所有权与迁移

### 4.1 管理数据库

| 表 | 必需字段/约束 |
|---|---|
| `admin_accounts` | UUID id、唯一规范化 username、password_hash、role、is_active、session_version、created_at、updated_at |
| `admin_sessions` | token_hash 主键、admin_id FK、version、csrf_token、expires_at、revoked_at |
| `admin_commands` | UUID id 全局唯一、actor_id、operation、resource_id、request_hash、冻结请求正文、expected_version、reason、state、result、created_at、updated_at |
| `admin_audit_logs` | UUID id、actor_id、action、resource_type/id、command_id、event_kind、脱敏 before/after、outcome、request_id、created_at；追加写；命令事件的 command_id/event_kind 唯一 |
| `admin_security_lock` | 固定单行，用于最后一个超级管理员约束 |
| `admin_login_limits` | 规范化账号/IP 摘要、窗口起点、次数、锁定截止时间 |

命令状态固定为 `pending/unknown/succeeded/rejected`。`unknown` 表示无法确认业务端是否提交。`rejected` 仅用于得到业务明确拒绝的终态；网络断开和响应解析失败均不能直接设为 rejected。

管理表中业务 account_id/job_id 是外部标识，不建立跨库外键。冻结命令只保存此次操作必需字段，不保存访问凭证或完整对象副本。

### 4.2 原业务数据库的最小改动

| 对象 | 改动 | 兼容要求 |
|---|---|---|
| `accounts` | 新增 `management_version INTEGER NOT NULL DEFAULT 0` | 只用于管理账号状态的乐观锁；原登录/登出不写此字段 |
| `recruitment_jobs` | 新增 `moderation_status VARCHAR(20) NOT NULL DEFAULT 'allowed'` 和 `management_version INTEGER NOT NULL DEFAULT 0` | 旧岗位默认允许；原 `status` 值不变 |
| `business_admin_receipts` | command_id 主键、actor、operation、resource_id、request_hash、reason、before/after、http_status、response_json、created_at | 执行结果和业务审计的权威凭据，与变更同事务提交 |

岗位 `management_version` 在正文编辑、发布/下架、平台限制变化时统一递增，避免管理员使用已过期的页面作决定。字段不接受原岗位编辑 DTO 的直接输入。治理理由存凭据，不加到公开岗位对象里。

原业务库通过现有兼容迁移入口补列、注册新模型建表；新管理库使用独立 Alembic。`create_all()` 不负责给旧表补列，必须提供旧库迁移测试。迁移可重复执行；禁止删除旧表、重建真实库、修改既有用户 ID 或将招聘者改成管理员。

### 4.3 业务规则

1. 禁用业务账号：同事务更新 `is_active=false`、`token_version=token_version+1`、`management_version+1` 和凭据。重新启用也增加凭证版本，旧 token 不恢复有效；启用后需重新登录。
2. 已禁用招聘者的岗位继续遵循原过滤逻辑。投递历史及简历快照保留，启用账号不批量改写岗位状态。
3. 平台限制岗位：只将 `moderation_status` 改为 `blocked`，保留原 `draft/published/closed`。公共列表、详情和新投递必须统一要求 `allowed`。
4. 招聘者可以查看被限制岗位及“平台限制中”的提示，但发布操作必须拒绝；编辑正文不解除限制。原前端仅增加此必要状态和提示，不增加管理员入口。
5. 解除限制只恢复 `allowed`。若岗位原来是 published 且招聘者启用，它会重新展示；弹窗明确说明这一影响。closed/draft 岗位不会被自动发布。
6. 管理员不能修改招聘投递终态、删除投递、编辑简历快照或改变数据所有权。
7. 已提交的禁用/限制对后续请求生效。提交前已通过授权的在途业务请求可能完成；若要“撤回全部在途请求”，须另行设计，首期不作此承诺。
8. 所有同时修改岗位的代码使用相同版本/状态条件更新；不能仅依赖 SQLite 不提供的行级 `FOR UPDATE` 语义。PostgreSQL/MySQL 的锁与 SQLite 的条件更新分别做并发验证。

## 5. DTO 与响应

成功响应统一为 `{code: 0, message, data, request_id}`；管理错误使用非 0 数字 code，并使用真实 HTTP 状态。内部 API 和管理 API 采用相同结构，原 `/api/*` 的已有响应保持兼容。

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [
      {"id": 12, "role": "recruiter", "display_name": "示例招聘者", "email_masked": "12***@qq.com", "is_active": true, "management_version": 0}
    ],
    "total": 1,
    "page": 1,
    "page_size": 20
  },
  "request_id": "示意请求编号"
}
```

- `AccountSummary`：id、role、display_name、email_masked、is_active、management_version、created_at、last_login_at。
- `RecruiterSummary`：account_id、display_name、is_active、company_name、city、industry、description、contact_name_masked、contact_email_masked、job_count。无认证状态伪装。
- `JobSummary/Detail`：id、recruiter_id、title、company_name、category、city、salary、employment_type、education、experience、description、requirements、tags、status、moderation_status、management_version、published_at、created_at、updated_at。
- `ApplicationSummary`：id、job_id、job_title、company_name、student_id、student_display_name_masked、recruiter_id、status、created_at、updated_at。没有 resume_snapshot、note、feedback。
- `Overview`：student_total、recruiter_total、active_account_total、published_job_total、blocked_job_total、applications_by_status、as_of。published_job_total 按公开可见条件计算，统计不承诺跨表同一瞬间强一致。
- `CommandResult`：command_id、state、operation、resource_id、created_at、updated_at、result；非终态 result=null，终态 result=`{http_status, response}`，response 为保存的业务 envelope，不含服务 token。
- `BusinessReceiptDTO`：command_id、actor_id、operation、resource_id、request_hash、reason、before、after、http_status、response、created_at。内部命令查询的 data 使用此结构；管理浏览器只能获得权限范围内的 CommandResult 和审计 DTO，不直接暴露内部凭据的完整结构。

分页参数：page≥1，1≤page_size≤100，默认 20；keyword 长度≤100。使用绑定参数及白名单排序，默认 created_at DESC、id DESC；时间返回 UTC ISO 8601，前端按 Asia/Shanghai 展示。详情同样采用白名单，不允许 `row.__dict__` 或全列序列化。

| HTTP | 代码 | 含义/前端行为 |
|---|---|---|
| 401 | 6101 | 未登录、失效会话；清理管理端状态并进入管理登录页 |
| 403 | 6103 | 权限/CSRF/来源不通过；不触发反复登录 |
| 404 | 6404 | 资源不存在或无权看到的命令 |
| 409 | 6409 | 版本冲突、状态无变化或幂等键绑定了不同请求；刷新后由用户重新决定 |
| 422 | 6422 | 参数错误；精确到字段，裁剪 Pydantic 错误中的敏感输入 |
| 429 | 6429 | 登录/调用限流；提示稍后重试 |
| 502 | 6502 | 上游返回非法结构；读操作显示服务错误，写操作进入待确认流程 |
| 503 | 6503 | 服务依赖不可用；已有写入意图时不可据此判断业务失败 |
| 202 | 0 | 命令已受理但结果未确定；展示 pending/unknown 与 command_id |

HTTP 状态区分两层：内部业务命令直接返回 200 或已持久化的业务 4xx；管理浏览器收到已经建立的命令对象时，终态统一 HTTP 200/code=0，具体成功或拒绝由 state 和 result.http_status 表达，非终态为 HTTP 202/code=0。管理侧受理前的认证、参数、键冲突仍返回对应 4xx。前端不能将所有 HTTP 200 视为业务操作成功；版本冲突拒绝需要读取 result.response.message。

## 6. API 契约清单

表中 API 均为待新增。接口路径使用不同前缀隔离，内部路径不能从浏览器直连。成功读接口为 200，创建管理员为 201，写命令按下文返回 200/202。

### 6.1 管理浏览器 API：`/admin-api/v1`

| 方法与相对路径 | 权限 | 输入/输出 |
|---|---|---|
| POST `/auth/login` | 匿名，Origin + 限流 | username/password → 设置 Cookie，返回 admin/permissions/csrf_token |
| GET `/auth/me` | 有效会话 | admin/permissions/csrf_token；Cache-Control: no-store |
| POST `/auth/logout` | 会话 + CSRF | 吊销会话、清 Cookie，返回 data=null |
| GET `/overview` | overview:read | Overview |
| GET `/accounts` | accounts:read | role、is_active、keyword、分页 → AccountSummary 列表 |
| GET `/accounts/{id}` | accounts:read | AccountSummary |
| POST `/accounts/{id}/status` | accounts:status_write | AccountStatusCommand + Idempotency-Key → CommandResult |
| GET `/recruiters`、`/recruiters/{id}` | recruiters:read | keyword/city/is_active/分页；RecruiterSummary |
| GET `/jobs`、`/jobs/{id}` | jobs:read | recruiter_id/status/moderation_status/keyword/city/分页；Job DTO |
| POST `/jobs/{id}/moderation` | jobs:moderate | JobModerationCommand + Idempotency-Key → CommandResult |
| GET `/applications` | applications:read | job_id/recruiter_id/student_id/status/分页 → ApplicationSummary |
| GET `/commands`、`/commands/{command_id}` | commands:read | 查询本地意图；pending/unknown 时有界查询业务凭据 |
| POST `/commands/{command_id}/retry` | 原命令写权限且本人，或 super_admin | 无新正文；按冻结内容、原 ID 重新发送；终态仅返回原结果 |
| GET `/audit-logs` | audit:read | actor_id/action/resource_type/resource_id/outcome/from/to/分页 |
| GET/POST `/administrators` | administrators:manage | 分页；创建时 username/password/role/reason，不回传密码 |
| PATCH `/administrators/{id}` | administrators:manage | role/is_active、expected_version、reason；保护最后一个超级管理员 |
| POST `/administrators/{id}/revoke-sessions` | administrators:manage | reason；增加 session_version |
| POST `/auth/change-password` | 有效会话 + CSRF | current_password/new_password；吊销全部会话，要求重新登录 |

管理账号更新使用 `session_version` 作为 expected_version：角色、状态、改密和全量吊销都增加该版本，不另外引入名字相近的管理员版本字段。

### 6.2 业务内部 API：`/internal/admin/v1`

| 方法与相对路径 | 服务 scope | 对应能力 |
|---|---|---|
| GET `/overview` | overview:read | 业务汇总 |
| GET `/accounts`、`/accounts/{id}` | accounts:read | 账号脱敏查询 |
| POST `/accounts/{id}/status` | accounts:status_write | 账号状态命令；200 成功或结构化 4xx 拒绝 |
| GET `/recruiters`、`/recruiters/{id}` | recruiters:read | 招聘者资料查询 |
| GET `/jobs`、`/jobs/{id}` | jobs:read | 岗位治理查询 |
| POST `/jobs/{id}/moderation` | jobs:moderate | 岗位限制命令 |
| GET `/applications` | applications:read | 投递元数据查询 |
| GET `/commands/{command_id}` | commands:read | 已提交凭据；不存在时 404，不代表先前请求一定失败 |

内部查命令必须验证签名 actor 与凭据 actor 一致。operator 只能发起自己的查询；super_admin/auditor 查看其他人的结果时，由管理后端完成读权限校验，再用命令已存 actor 生成只具备 commands:read 的服务请求。不得允许浏览器指定内部 actor。

```json
{"is_active": false, "expected_version": 3, "reason": "重复发布与岗位描述不符的内容，经核查暂停账号"}
```

```json
{"moderation_status": "blocked", "expected_version": 7, "reason": "岗位包含无关推广内容，暂停展示"}
```

上述两种输入均禁止额外字段。reason 去除首尾空白后长度为 5～500，expected_version 是非负整数。请求头 `Idempotency-Key` 必须是 UUID，与 command_id 相同；actor、role、token_version 不得从请求正文赋值。

### 6.3 命令一致性与恢复

1. 管理后端检查会话、权限、CSRF 和 DTO，在管理库持久化命令意图与“已受理”审计后，才能发 HTTP 请求。管理库失败时不发送业务命令。
2. 同 command_id、同 actor、同操作和同正文返回已有命令；不同绑定返回 409。后端重试使用冻结原始 JSON 字节，不重新排序/重建为不同请求。
3. 业务后端先验服务凭证，再在独立数据库事务中占用 command_id、执行条件更新并保存响应/脱敏变化。凭据唯一约束抵御并发重复执行。
4. 业务成功与凭据一起提交。版本冲突、资源不存在等明确拒绝也保存终态凭据；SQL/审计写失败时事务回滚，不保存假成功。
5. 管理端收到可验证且与本次命令对应的业务凭据响应后更新本地命令与终态审计；若该本地写失败，仍保留先前 pending 意图，可通过业务凭据恢复。服务鉴权层 401/403、代理错误或路由不存在等没有执行凭据的响应不冒充业务拒绝，记录集成错误并保留待确认，供排查后按原 ID 恢复。
6. 超时、连接中断、5xx、非法响应设 unknown；对浏览器返回 202 和 command_id。如果无法保存 unknown，保留 pending，效果同样是待确认。
7. 查询不到业务凭据只说明当前未查到。等待正在运行的请求后，可以使用同一 command_id 和冻结正文重试；不得用新 ID 重试来“修复超时”。
8. 前端每 2 秒查询一次，30 秒后停止自动轮询，保留待确认提示和命令详情入口；重新打开页面可继续查询。服务端恢复扫描 pending/unknown，限速、单命令互斥，关闭页面不丢命令。
9. 首期命令与凭据不自动清理，避免清理后旧键重新执行。后续引入保留策略时必须保留去重墓碑或限定并验证键有效期。

不存在跨两个数据库的 ACID 事务承诺；可靠性来自意图先落盘、业务本地事务、幂等凭据和可查询恢复。

## 8. 技术参考与判定优先级

FastAPI 的依赖机制用于服务端鉴权和权限检查；JWT 验签必须固定算法并检查声明。参见 [FastAPI 安全指南](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)。

命令使用独立 Session 与事务边界，避免认证查询触发 autobegin 后再次错误调用 begin；异常应回滚整笔业务写入。参见 [SQLAlchemy Session Basics](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)。

前端 route meta 可用于访问控制展示，但它不替代 API 授权；路由守卫需要检查匹配记录上的约束。参见 [Vue Router 路由元信息](https://router.vuejs.org/guide/advanced/meta.html)。

服务间客户端显式设置连接、读取、写入与连接池超时。参见 [HTTPX 超时配置](https://www.python-httpx.org/advanced/timeouts/)。

以上用于核对机制，不要求升级现有项目到最新版本。实施时先核对安装版本，锁定兼容依赖。发生冲突时优先级为：当次用户要求与仓库规则 → 本文边界与契约 → 关键代码参考 → 具体工具默认行为。

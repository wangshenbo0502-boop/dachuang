# 管理员独立系统：AI 开发提示词套件

编写日期：2026-10-08。适用项目：大学生就业竞争力评估与提升系统（当前仓库 `dachuang`）。

**交付状态：仅完成设计与提示词文档，未实现管理员系统。** 文档中的新目录、接口、配置、表和代码均为待实施方案，不能描述为当前已有能力。

## 1. 目标与使用顺序

新增独立的管理员前端、管理员后端和管理员数据库，使管理系统与现有招聘、求职系统分别构建、运行、认证和发布。业务数据仍由原业务后端负责，通过版本化内部 API 提供管理查询与命令，避免跨系统导入 ORM、共享登录状态和直接改库。

本次“分离”指**管理员系统与现有业务系统分离**。招聘者和求职者继续使用现有 `frontend/`、`backend/`，不顺带将二者拆成两个系统。

| 文档 | 用途 | AI 何时阅读 |
|---|---|---|
| [本文件](README.md) | 总提示词、真实项目基线、执行约束 | 每次新会话首先阅读 |
| [01-架构与接口契约](01-架构与接口契约.md) | 服务边界、功能、权限、数据、接口和失败语义 | 开发每个阶段前阅读相关章节 |
| [02-核心关键代码](02-核心关键代码.md) | 鉴权、内部 API、幂等事务、前端权限的关键实现 | 对应阶段开发时引用 |
| [03-分阶段提示词与验收](03-分阶段提示词与验收.md) | 可复制的阶段提示词、依赖、测试、启动和交付标准 | 一次执行一个阶段 |

建议先把第 3 节的总提示词交给 AI，再依次发送 P0～P6 阶段提示词。一次性执行时可补充：“在授权范围内按顺序完成 P0～P6；遇到外部依赖阻塞时记录阻塞，不伪造完成结果。”

**使用边界：**本套提示词供后续明确授权实施时使用。本次用户只要求编写 Markdown，因此不会据此创建应用、安装依赖、迁移数据库、提交、推送或部署。未来执行者也必须先判断当次任务是审阅文档还是实施功能。

## 2. 当前项目基线：已从代码核对

| 当前事实 | 证据路径 | 对设计的影响 |
|---|---|---|
| 前端为 Vue 3、TypeScript、Vite、Pinia、Element Plus | `frontend/package.json` | 管理前端沿用技术栈，独立依赖与构建，不引入 React |
| 后端为 FastAPI、SQLAlchemy 2、Pydantic 2；已有 HTTPX、PyJWT、Argon2 | `backend/requirements.txt` | 管理后端使用同类技术，但不依赖原后端 Python 包 |
| 当前前端没有管理员路由，后端没有管理员认证模块 | `frontend/src/router/index.ts`、`backend/main.py`、`backend/app/auth/dependencies.py` | 新增独立系统，无需虚构“旧管理员迁移” |
| 账号角色只有 `student`、`recruiter` | `backend/app/schemas/auth.py` | 不在业务账号中新增 `admin`，不扩展原登录选择器 |
| `Account` 保存 `is_active`、`token_version`，并依赖 `users.id` | `backend/app/models/account.py` | 管理账号独立建表，不创建学生档案，不复用业务账号 |
| 每次认证查询账号状态和凭证版本 | `backend/app/auth/dependencies.py` | 禁用业务账号时原子增加 `token_version`，使旧凭证持续失效 |
| 原 JWT 只包含 `sub/ver/iat/exp`，使用业务 `JWT_SECRET` | `backend/app/auth/security.py` | 管理会话和内部调用凭证必须独立，不能仅检查同一个 JWT 中的角色 |
| 招聘岗位状态为 `draft/published/closed` | `backend/app/models/recruitment.py` | 平台限制单独建字段，不篡改招聘者的岗位生命周期 |
| 投递状态为 `submitted/reviewing/interview/offered/rejected/withdrawn`，保留简历快照 | `backend/app/services/recruitment_service.py` | 管理端首期只看投递元数据，不修改快照、反馈和录用结果 |
| 岗位列表、详情、投递路径检查发布状态及招聘账号是否启用 | `backend/app/services/recruitment_service.py` | 平台岗位限制必须接入这些路径，不能仅从列表隐藏 |
| `serialize()` 按 ORM 全列返回；若直接用于账号会暴露不应公开的字段 | `backend/app/services/recruitment_service.py` | 管理接口一律使用明确的 DTO 字段白名单 |
| 业务库默认 SQLite，知识库是单独的 PostgreSQL/pgvector | `backend/app/config.py` | 不把知识库当作业务库；不为新管理系统强制迁移现有业务库 |
| 原迁移方式是 `create_all` 加兼容列补齐 | `backend/app/database/bootstrap.py` | 原库只做兼容性增量迁移，新管理库单独使用 Alembic |
| 前端默认端口 5173，代理 `/api` 到 8000 | `frontend/vite.config.ts` | 管理前端与后端使用新端口，不修改原开发代理 |

上述为编写时的本地源码事实，不代表在线环境、运行测试或远端分支已验证。未来执行先重新核对，不按旧行号或历史测试数量实施。

## 3. 可直接复制的总提示词

```text
你是本项目的资深全栈开发工程师。请先阅读仓库规则，以及：
docs/管理员独立系统/README.md
docs/管理员独立系统/01-架构与接口契约.md
docs/管理员独立系统/02-核心关键代码.md
docs/管理员独立系统/03-分阶段提示词与验收.md

目标：为现有大学生就业系统新增真正独立的管理员前端、后端和数据库。
现有求职者、招聘者业务继续使用 frontend/ 和 backend/。
新增 admin-frontend/、admin-backend/，通过受保护的内部 API 管理原业务。

先判断本次授权范围。如果用户只要求文档、评审或方案，只输出相应文档，禁止实施。
如果用户明确要求开发，按本套文档 P0～P6 顺序执行；仅执行用户授权的阶段。

不可违反的要求：
1. 遵守用户关于子智能体的限制；没有明确授权时由当前主智能体顺序完成。
2. 先检查 git status 和当前源码，保留既有未提交改动，不擅自切换分支、清理或覆盖文件。
3. 管理端保持 Vue 3 + TypeScript + Vite + Pinia + Element Plus；后端保持 FastAPI + SQLAlchemy + Pydantic。
4. 管理账号、会话、权限、审计、命令日志由管理数据库拥有；原业务数据由业务数据库拥有。
5. 管理后端不得连接业务数据库，不得 import 原 backend/app，不得读取知识库、SMTP 或 AI 的真实密钥。
6. 业务后端不得依赖管理后端运行；管理后端不可用时，原求职与招聘仍可运行。
7. 不给业务 Account 增加 admin 角色，不在原登录页增加管理员身份，不让两套系统接受对方凭证。
8. 管理浏览器只访问 /admin-api/v1；只有管理后端能调用 /internal/admin/v1。
9. 内部 API 必须同时验证服务签名、作用域、请求绑定和调用来源的网络边界；不能相信浏览器传入的管理员头。
10. 业务账号/岗位管理写命令要求理由、对象版本和幂等键；业务变更与业务侧审计凭据同事务提交。
11. 超时不等于操作失败。管理端显示“结果待确认”，查询同一 command_id，禁止换新幂等键盲目重试。
12. 管理端展示脱敏账号和投递元数据，不返回密码散列、会话、验证码、AI 对话、完整简历快照或配置密钥。
13. 不复制招聘业务实现到管理端，不新增 Kafka、Kubernetes、通用工作流引擎或其他首期不需要的基础设施。
14. 保留原有学生/招聘者登录、所有权校验、岗位发布、投递和反馈行为；只新增契约明确要求的治理约束。
15. 文档中的示例是关键实现参考，不是已经运行的应用。生成代码前补齐其注明的模型、配置、装配和测试。
16. 接口实现后以各自 OpenAPI 为准，生成客户端类型并做契约差异检查；不得让文档、DTO 和真实返回长期分叉。
17. 只有获得当次授权才提交、推送或部署；测试一律使用隔离数据，不访问真实账号或发送真实邮件。

工作方式：
- 每阶段先说明本阶段目标、读取的文件、允许修改范围和验收条件。
- 对鉴权、幂等、并发、治理状态等行为先建立能揭示错误的测试，再实现。
- 每完成一个可验证单元，运行对应检查；不以静态页面、截图或构建成功替代真实接口链路。
- 遇到源码与方案不同，以真实源码为依据，记录差异和选择；不得静默改变系统边界。
- 无环境完成的验证标注 NOT TESTED，外部依赖导致的阻塞标注 BLOCKED，不编造 PASS。

每阶段输出：
1. 实际修改文件和行为；
2. 接口、数据迁移和兼容性变化；
3. 执行过的命令及真实结果；
4. 未完成项、限制及下一阶段输入；
5. 若更改契约，同步更新契约和类型生成结果。

现在先执行我指定的阶段；如果我没有指定阶段，从 P0 开始。
```

## 4. 方案选择

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 在原前端增加 `/admin`，原后端增加角色分支 | 改动最少 | 登录、部署、依赖和数据库权限仍耦合 | 不满足本次目标 |
| 独立前后端、独立管理库，通过业务内部 API 集成 | 身份、构建和部署独立，业务规则仍只有一个所有者 | 需要处理跨服务失败、幂等和契约版本 | **首期采用** |
| 将用户、岗位、投递、认证全部拆为微服务 | 更细的服务边界 | 迁移面大，显著增加部署及一致性成本 | 不在本次范围 |

独立系统仍存在业务 API 契约依赖。这是明确且可版本化的依赖，并不承诺“零耦合”。首期不要求拆 Git 仓库；使用同一仓库有利于联调，但每个应用必须能在只复制自身目录和必要契约产物的条件下独立构建。

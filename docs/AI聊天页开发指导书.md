## 1. 要实现什么

用户进入现有黑白手绘走廊后，点击截图中央的小人，镜头平滑靠近并重新构图，在小人旁边展开纸张风格的聊天界面。用户输入问题后，由现有 FastAPI 后端调用 DeepSeek，答案逐步显示。关闭聊天后，镜头回到点击前的位置，继续探索走廊。

推荐第一版采用“原场景内的聊天模式”，而不是跳转到一个与原网站脱节的普通聊天网站。保留同一个 Canvas、走廊、小人和美术资源；聊天文本与输入框使用 DOM 层，避免把长文本和输入法塞进 3D 纹理。

这里的“摄像机变化”指 Three.js 虚拟镜头，不需要访问用户的真实摄像头。

第一版包含：点击入口、镜头进入和返回、中文多轮聊天、流式回答、停止生成、失败重试、清空会话、移动端适配。

第一版不包含：语音、口型同步、真实摄像头、自动修改个人档案、聊天记录数据库、多用户历史同步。后续可按需增加。

### 1.1 最高优先级：不点击，不改变原体验

用户补充要求：现有样式和动画不要动；不点击小人时，仍能像现在一样继续浏览房间。本节优先于下文任何可能扩大改动范围的建议。

- 聊天是可选附加功能，不是进入房间的前置步骤。不自动打开，不强制对话，不在首次进入、滚动靠近、悬停或经过小人时触发。
- 未点击时，入口动画、人物挥手与躲避、走廊滚动、鼠标视差、门、房间、地图和传送保持原行为与参数。原贴图、材质、灯光、字体、布局与动画速度均不修改。
- 新样式仅作用于聊天组件自身，使用独立类名前缀；不改全局设计变量、现有组件样式或全局 Canvas 尺寸。新增中文字体回退也仅限聊天 UI。
- `closed` 状态不写入镜头、不加控制锁、不暂停动画，不渲染拦截点击或滚动的透明遮罩，不发聊天请求。聊天服务异常也不能影响原房间浏览。
- 只有明确点击或键盘激活人物聊天入口后，才能临时接管镜头和暂停与聊天冲突的导航输入。手机拖动经过人物不算点击，须区分点击与滚动手势。
- 聊天退出完成后恢复原控制与动画行为；不重置房间浏览进度，不要求用户刷新页面。
- 不改写原人物动画算法。聊天专用的人物位移控制只能在选中实例且聊天活跃期间临时生效，退出后解除；原挥手帧速保持不变。

## 3. 页面与镜头设计

### 3.1 桌面端

保留全屏手绘走廊。进入聊天后，小人位于画面左侧约三分之一处，显示上半身或大半身；右侧是浅灰白纸张聊天区。画面仍能辨认走廊，不用重度模糊或深色遮罩。

聊天区建议宽度 400～560px，并受可用空间限制。标题使用“AI 就业助手”；正文使用清晰的中文系统字体，手写字体只用于短标题。使用纸纹、黑色细线、轻微不规则边缘和克制的阴影。不要新增紫蓝渐变、发光机器人、玻璃拟态或大型彩色按钮。

消息用段落和细分隔线组织，不需要多层卡片嵌套。关闭、发送、停止和清空使用一致的图标按钮，配可访问名称与悬停提示。项目尚未配置通用图标库时，可增添 `lucide-react`，不要为这几个按钮引入整套 UI 框架。

复用 `/textures/paper-texture.webp` 和 `/textures/corridor/avatar_anim/`，不要替换原小人。

### 3.2 移动端

上方保留人物与场景，下方展示纸张聊天区；不要机械缩小桌面左右分栏。建议以 768px 作为初始布局切换点，再按截图实测调整。

面板高度随实际可视区变化，处理 `100dvh`、安全区和软键盘。键盘展开时优先保证消息末尾和输入框可见，可缩小人物区域。按钮触控目标至少 44px，正文建议 16px，长链接和代码块不得撑破页面。

### 3.3 进入与退出动画

建议初始时序，可在实测时微调：

| 阶段 | 期望行为 |
| --- | --- |
| 点击瞬间 | 同步加锁，记录目标人物与原镜头，阻止重复触发 |
| 0～0.9 秒 | 镜头缓动靠近，并轻微平移构图 |
| 约 0.5 秒起 | 纸张 UI 淡入并小幅展开 |
| 动画结束 | 获得输入焦点，允许发送 |
| 关闭 | 取消当前请求、收起 UI，约 0.7 秒返回原镜头 |
| 返回结束 | 释放镜头控制，恢复滚动、视差和人物原行为 |

用户开启减少动态效果时，使用短淡入淡出或直接切换，避免长距离镜头移动。

## 4. 镜头实现的关键约束

### 4.1 一个镜头，同一时刻一个控制者

新增状态机：

```text
closed -> entering -> open -> exiting -> closed
```

网络状态与镜头状态分开：

```text
idle -> connecting -> streaming -> complete / error / cancelled
```

聊天镜头控制器放在 Canvas 内，获取真实 Three.js camera。进入前调用现有 `setCameraOverride(true)`，返回完成后才调用 `setCameraOverride(false)`。

仅接管 `useFrame` 不足以阻止滚轮事件修改内部目标位置。聊天期间也要禁用走廊滚动、触摸与视差输入；恢复时注意现有 Hook 的重新启用逻辑会清理镜头 Tween，必须等返回动画结束。

聊天期间禁用门、画框检查和传送入口；不要让别的组件在聊天中途释放 override。地图跳转先完成退出聊天，再执行原导航流程。同步 ref 锁负责挡住同一帧内重复点击，React 状态负责渲染。

### 4.2 不要写死截图对应的镜头坐标

当前人物在走廊段内的局部坐标为 `[0, -0.61, -0.3]`，但父级还叠加了段落位移。每段都会重复出现人物，不能用这一组局部坐标作为世界坐标。

点击时记录 `segmentIndex`，通过对象的 `getWorldPosition()` 和世界包围盒获取人物实际位置与尺寸；根据包围盒高度确定胸口或脸部观察点。

保存镜头 `position.clone()`、`quaternion.clone()`、FOV，以及需要保留的镜头参数。若后续代码给镜头添加父变换，计算与恢复必须明确使用相同坐标空间。

由人物尺寸、纵向 FOV 和宽高比求基础距离：

```text
基础距离 = 目标可见高度 / (2 * tan(纵向 FOV / 2))
```

角度计算使用弧度，并进一步校验横向取景。根据聊天面板实际占用的屏幕区域，迭代投影检查人物脸部位置，而不是只修改 `lookAt` 猜结果。可用轻微平移、观察点偏移完成构图，不做围绕平面小人的大幅侧向旋转。

用一个 GSAP timeline 插值位置与 quaternion；避免多个 Tween 同时修改 Euler 旋转和 `lookAt`。如果动画改变 FOV，每帧同步更新投影矩阵。

### 4.3 原有小人躲避必须处理

`Avatar.jsx` 会在相机接近时改变人物 X 坐标。聊天镜头若直接靠近，人物可能一边被对准、一边向侧面躲开。

仅在点击后进入聊天时，临时冻结所选人物的实际躲避偏移，聊天结束再平滑恢复原逻辑。不要直接清零偏移造成跳动。现有挥手帧动画及帧速保持原样，不新增骨骼动画；未点击时躲避逻辑完全照常运行。

透明贴图的矩形平面不等于人物轮廓。点击实现需要有限的身体命中区域，或基于 UV 的透明像素判定；不要让人物旁的大块透明区域也拦截走廊点击。

同时提供 DOM 可聚焦入口，让键盘和屏幕阅读器用户也能进入聊天。

### 4.4 走廊段生命周期

聊天期间将目标 `segmentIndex` 纳入 `activeSegments`，可见性包装器也必须保留目标人物所在段。退出后恢复原动态生成规则。

只给被选中人物设置聊天状态，不要同时暂停所有走廊人物。动画、监听器与异步回调在卸载时清理，旧完成回调不得关闭新打开的聊天。

## 6. DeepSeek 密钥如何接

### 6.1 正确链路

```text
浏览器聊天 UI
    -> 本项目 POST /api/chat/stream
    -> FastAPI 读取服务端环境变量
    -> DeepSeek Chat Completions
    -> 后端转成项目 SSE 事件
    -> 浏览器逐步显示
```

不要在前端直接请求 DeepSeek。密钥不得放入 `VITE_*`、前端源码、浏览器存储、Git、聊天提示词或演示截图。真实密钥只由你填写到后端本地配置或部署平台的服务端 Secret 中，不需要交给 AI 开发工具。

### 6.2 模型名必须更新核对

仓库目前默认 `deepseek-chat`。本次查阅的官方文档列出 `deepseek-flash` 与 `deepseek-v4-pro`，示例使用 `deepseek-flash`。不要照抄仓库旧模型名作为新部署保证。

本方案建议聊天先使用 `deepseek-flash`，但上线时再次核对账号可用模型。接入沿用兼容 SDK，基础地址为 `https://api.deepseek.com`。聊天初版显式关闭思考模式，先保证自然对话的响应体验。

依据：DeepSeek 官方《Your First API Call》及《Chat Completions API》，2026-09-15 查询。文末列出来源地址。

### 6.3 本地配置示例

在 DeepSeek 开放平台创建 API Key，并确认账号余额及可用模型。然后在 `backend/.env` 中填写：

```dotenv
APP_ENV=development
APP_DEBUG=true
DATABASE_URL=sqlite:///./ai_job_analysis.db
CORS_ORIGINS=http://localhost:5173
DEEPSEEK_API_KEY=your_deepseek_api_key_here
DEEPSEEK_BASE_URL=https://api.deepseek.com
DEEPSEEK_MODEL=deepseek-flash
AI_TIMEOUT=90
AI_MAX_RETRIES=3
AI_TEMPERATURE=0.7
AI_MAX_TOKENS=1500
```

将占位值替换为自己的密钥。这里的数据库名只是新环境示例，已有本地数据库配置应保留。仓库 `.env.example` 是生产 MySQL 示例，不能原样照搬后就期待本地 SQLite 启动成功。

注意：`DEEPSEEK_MODEL` 和 `AI_MAX_TOKENS` 是现有全局配置，修改会影响其他 AI 功能。若需要保持画像、简历和成长模块行为不变，应由开发者新增聊天专用配置，如 `CHAT_MODEL` 与 `CHAT_MAX_TOKENS`，在 `Settings` 中明确读取并传到新方法，不能只写环境变量却不接代码。

检查 `.env` 已被 Git 忽略。重启后端后查看 `/api/health`；`ai_mode=live` 只说明程序选择了真实客户端，并不证明密钥有效、余额充足或模型可调用，必须再发一条真实测试消息。

### 6.4 聊天专用流式方法的调用轮廓

以下是待实现的方法轮廓，不是当前代码可以直接粘贴运行的完整补丁：

```python
stream = await async_client.chat.completions.create(
    model=chat_model,
    messages=validated_messages,
    stream=True,
    max_tokens=1500,
    extra_body={"thinking": {"type": "disabled"}},

```

使用现有兼容 SDK 的异步客户端能力；新增方法例如 `chat_stream_async`，避免贸然把旧同步方法改成不兼容接口。对输出读取 `delta.content`，处理结束原因与 usage，并在取消、断开连接或异常时关闭上游流。

官方接口支持流式输出、思考模式开关与结束原因；具体字段以实施时文档和安装的 SDK 为准。第一版只显示最终回答文本，不展示推理字段。

## 7. 聊天接口与多轮上下文

### 7.1 第一版接口

新增 `POST /api/chat/stream`，请求示例：

```json
{
  "request_id": "client-generated-uuid",
  "messages": [
    {"role": "user", "content": "我想找 Java 后端实习，该怎么准备？"},
    {"role": "assistant", "content": "你目前做过哪些项目？"},
    {"role": "user", "content": "做过一个 Spring Boot 校园项目。"}
  ]
}
```

第一版采用无持久化会话：每次上传受限历史，服务端重新拼装系统提示词。`request_id` 用于请求关联和前端隔离，不是认证凭据，也不能自动保证计费幂等。

建议起始限制：用户单条消息不超过 2000 字符，最多 20 条历史消息，内容总长度不超过 20000 字符，同时做 Token 预算。超过限制返回明确错误，不能无限增长。

只接受 `user`、`assistant` 角色；第一条和最后一条为 user，检查交替顺序。后端添加自己的 system 消息，客户端不能覆盖。客户端带来的 assistant 历史同样是不可信文本，不能据此授权、取数或执行操作。

普通会话不必绑定用户 ID。个人档案增强放第二阶段：取得用户同意后，通过已认证身份由服务端读取最小必要资料，不允许前端随便传一个 user_id 读取他人信息。

### 7.2 项目 SSE 契约

复用现有 `start`、`chunk`、`complete`、`error` 名称，新增字段保持兼容。每帧以空行结尾，data 使用 JSON 序列化。

```text
event: start
data: {"request_id":"abc","message":"正在回答","mode":"live"}

event: chunk
data: {"request_id":"abc","content":"可以先从"}

event: chunk
data: {"request_id":"abc","content":"项目表达开始。"}

event: complete
data: {"request_id":"abc","raw_text":"可以先从项目表达开始。","finish_reason":"stop"}

```

错误示例：

```text
event: error
data: {"request_id":"abc","code":"AI_UNAVAILABLE","message":"AI 暂时无法回答，请稍后重试","retryable":true}

```

发送响应头之前的参数、认证、限流失败使用对应 HTTP 状态。开始流以后发生错误，发送 error 事件并终止，不再发送成功 complete。

没有收到 complete 或 error 就断流，前端应标记“回答中断”，不能当成成功。输出达到限制时，利用 finish_reason 提示回答未完整生成。

### 7.3 消息行为

发送后立即展示用户消息和一条空助手消息，只往这条助手消息追加内容。生成中只能有一个请求，发送按钮变成停止按钮。

关闭面板、清空或停止时 abort；通过 request_id 校验忽略旧请求迟到的数据。停止后的部分答案保留并标记“已停止”，不默认放入后续完整对话历史。

重试同一条问题时，移除失败的助手占位，不重复追加用户消息。Enter 发送、Shift+Enter 换行；中文输入法组合期间不得因 Enter 误发送。

只有用户接近消息底部时才自动滚到底部；用户向上阅读时不要抢滚动。初版可纯文本显示；若加入 Markdown，必须禁用原始 HTML，并过滤危险链接协议。

## 8. 现有代码必须留意的问题

这些是静态阅读发现的接入风险，尚未运行验证：

1. 现有 `chat_stream()` 使用同步 SDK，而现有异步生成器直接遍历它。新聊天不能照抄成阻塞事件循环的实现，建议使用聊天专用异步客户端与异步迭代。
2. 现有流式方法把异常转成普通文本 yield。聊天路径必须改为抛出结构化异常，否则“失败”会被界面当成成功答案。
3. 现有 Mock 返回分析类 JSON，不适合作为自然聊天回复。新增聊天专用 Mock，并由服务端返回 mode；界面标记模拟模式，不能伪装成真实 DeepSeek。
4. 现有 SSE 消费工具没有 AbortSignal，读取阶段异常、异常 EOF、CRLF 和尾部缓冲也需要补测试。用标准解析器或明确实现并验证增量解析，不能假设一个网络块就是一个完整事件。
5. 现有用量统计中的价格是硬编码旧估算，不能用于真实账单承诺；流式路径也未记录用量。新聊天需要统计服务返回的 usage，计价可配置，并以平台账单为准。
6. `TokenUsageTracker.to_dict()` 持有非可重入锁时又调用获取同一锁的方法，存在自锁风险。接入用量展示前应修复并加超时回归测试，不能直接依赖 `/api/usage` 做上线监控。
7. 代码里存在限流和预算配置项，不等于新路由已实际执行限制。必须核对中间件注册与聊天服务中的预算检查。
8. 当前读取范围内尚未形成完整登录认证闭环。公开上线付费聊天不能仅靠 CORS 或前端按钮防滥用；需受控访问、身份验证或网关保护、限流、并发控制和总预算。

共享模块的修复应保持旧调用方兼容，并运行画像、简历和成长模块回归测试。

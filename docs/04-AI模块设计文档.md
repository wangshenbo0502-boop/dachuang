## 1. 模块定位与边界

AI 模块负责所有大模型调用，是四个 AI 业务功能（就业画像 / 岗位匹配精排 / 简历优化 / 成长规划）的公共底层。

**强制边界**（摘自 01 第 9.2 节，违反即返工）：

1. 所有 LLM 调用必须经 `DeepSeekClient.instance()` 单例，禁止业务层自建 OpenAI 客户端。
2. AI 获取用户数据只能通过 `UserService.get_user_context()`（进程内）或 `GET /api/users/{id}/context`，禁止直查 User 相关 ORM。
3. System Prompt 一律外置在 `knowledge/prompts/*.md`，通过 `SystemPrompts` 加载；改 Prompt 不改代码、不重启。
4. JSON 输出一律用 `chat_json()`（双层容错），禁止裸 `json.loads`。
5. AI 增强类调用失败允许静默降级（保留非 AI 结果），核心分析调用失败向上抛异常。

## 2. 架构与数据流

```
app/services/*_service.py（业务编排）
        │  messages = [system_prompt, user_prompt]
        ▼
app/ai/prompts.py ──── 读取 ────► knowledge/prompts/*.md（外置Prompt）
        │
        ▼
app/ai/deepseek_client.py（DeepSeekClient 单例）
   ├── Mock 模式：DEEPSEEK_API_KEY 未配置 → 动态模拟数据，不出网
   ├── Live 模式：OpenAI 兼容 SDK → https://api.deepseek.com（deepseek-chat）
   ├── 重试：限流/网络错误指数退避，最多 AI_MAX_RETRIES 次
   └── TokenUsageTracker（线程安全）：用量/成本/预算 → GET /api/usage
        │
        ▼
chat_json() → 业务解析并落库（analysis/resume/growth/job_match 记录表）
chat_stream() → app/api/streaming.py → SSE（text/event-stream）→ 前端打字机
```

## 4. DeepSeekClient 接口（`app/ai/deepseek_client.py`）

| 方法 | 签名要点 | 用途 |
|------|---------|------|
| `instance()` / `reset_instance()` | 类方法；`reset` 供测试或改配置后重建 | 单例管理 |
| `chat(messages, temperature=None, max_tokens=None, response_format=None) -> str` | 带重试与 Token 统计 | 普通文本调用 |
| `chat_json(messages, temperature=0.3, max_tokens=None) -> dict` | 自动注入"纯 JSON 输出"系统指令 + `response_format={"type":"json_object"}` | **业务统一入口** |
| `chat_stream(messages, temperature=None, max_tokens=None) -> Generator[str]` | 逐片段 yield；Mock 模式下每 10 字符/20ms 模拟流式 | SSE |
| `load_prompt(filename)` 静态方法 | 从 `knowledge/prompts/` 读 md，缺失返回 "" | Prompt 外置 |
| `is_mock_mode` | 属性 | 响应中透出为 `is_mock` |
| `get_usage_stats()` 类方法 | 用量字典（见第 6 章） | `/api/usage` |

### 4.1 重试与错误分类

| 错误 | 重试 | 退避 | 最终行为 |
|------|------|------|---------|
| `RateLimitError`（上游限流） | 是 | `(2^attempt)×2 + [0,1)s` 随机指数退避 | 抛 `AIServiceError(TYPE_RETRY_EXHAUSTED)` |
| `APITimeoutError` / `APIConnectionError` | 是 | `1 + attempt` 秒线性 | 同上 |
| `APIError`（其他 API 错误） | 否 | — | 抛 `AIServiceError(TYPE_API_ERROR)` |
| 其他异常 | 否 | — | 抛 `AIServiceError(TYPE_UNKNOWN)` |

`AIServiceError` 定义类型常量：`api_error / retry_exhausted / parse_error / unknown`。
**已知问题**（见 01 第 13 章）：该异常未映射到统一错误码 3001-3004，当前冒泡后表现为 `HTTP 500 / code=1`。

### 4.2 JSON 解析容错（`_parse_json`）

1. 剥离 ```json 代码围栏 → 直接 `json.loads`；
2. 失败则正则截取首个 `{` 到最后一个 `}` 再试；
3. 仍失败抛 `AIServiceError(TYPE_PARSE_ERROR)`（响应前 300 字符随错误消息记录）。

## 5. Mock 模式（无 Key 开发）

| 项 | 说明 |
|----|------|
| 触发条件 | `DEEPSEEK_API_KEY` 为空或等于占位值 `your_deepseek_api_key_here` |
| 判定方式 | `GET /api/health` 返回 `ai_mode: "mock"`；AI 接口响应 `is_mock: true` |
| 数据生成 | 按最后一条用户消息中的关键词（画像/简历/成长/岗位）路由到对应动态 Mock 生成器，会**提取输入中的技能名**生成贴合的演示数据（非完全硬编码） |
| 覆盖范围 | `chat` / `chat_json` / `chat_stream` 全部生效；岗位匹配的 AI 精排自动跳过（仅关键词粗排） |
| 用途 | 前端联调、自动化测试（01 第 11 章）、离线演示 |

Mock 结果结构**与真实 Prompt 要求的 JSON 契约完全一致**，因此切换 live 模式前端无需改动。

## 6. Token 用量与成本控制

`TokenUsageTracker`（类级单例，线程安全 `threading.Lock`）：

- 统计口径：每日 prompt/completion tokens、调用次数、成本估算；**跨天自动清零**（按本地日期）。
- 成本公式（`deepseek-chat` 参考价）：`输入 $0.14/1M tokens`、`输出 $0.28/1M tokens`；估算值，以 DeepSeek 官方账单为准。
- 查询接口：`GET /api/usage`（字段见 [02 第 3.3 节](./02-API接口文档.md)），返回 `is_over_budget` / `is_near_limit` 两个预算标记。
- 局限：**进程内存统计**，重启清零、多进程部署时各自计数（`规划/待实现` Redis 持久化）。预算当前仅用于展示，不自动熔断调用。

## 7. Prompt 工程

### 7.1 双层结构

| 层 | 位置 | 内容 |
|----|------|------|
| System Prompt（外置） | `knowledge/prompts/system_{profile_analyst,resume_optimizer,growth_planner,job_matcher}.md` | 角色设定 + 输出 JSON 契约 + 质量要求 |
| User Prompt（代码内模板） | `app/ai/prompts.py` 四个 `build_user_prompt()` | 按模板拼装学生数据与任务指令 |

加载规则：`SystemPrompts.get(name, fallback)` —— 优先读外置 md；文件缺失/为空时代码内 fallback 生效（一句角色简述）。**修改外置 md 后无需重启，下次调用生效。**

### 7.2 用户数据格式化函数

`_format_skills / _format_projects / _format_competitions / _format_internships` 将结构化数据转为 Markdown 列表文本注入 User Prompt。**注意**：同步画像接口当前注入 skills+projects（+target_job）；竞赛/实习格式化函数已具备，Prompt 模板支持，但部分调用路径（流式接口、简历/成长同步接口）尚未传入竞赛/实习数据——属已知差距，补齐时同步本文档。

### 7.3 输出 JSON 契约

四个业务分别要求 AI 返回固定结构（字段与 [02 第 6-8 章](./02-API接口文档.md) 的 `result` 一致、与 [03 第 4 章](./03-数据库设计文档.md) 数据字典一致），由 Service 层 `chat_json` 获取后再映射落库。修改契约的顺序：**先改 Prompt md → 再改 Schema → 再改落库映射 → 同步 02/03/04 文档**。

### 7.4 Prompt 编写规范

新增或修改 System Prompt（`knowledge/prompts/system_*.md`）必须包含**四要素**：

| 要素 | 内容 | 示例（画像 Prompt） |
|------|------|-------------------|
| ① 角色设定 | 一句话定义 AI 身份与专业背景 | "你是一位资深的校园招聘就业顾问…" |
| ② 任务描述 | 明确输入是什么、要做什么判断 | "基于以下学生资料，评估其就业竞争力…" |
| ③ 输出 JSON 契约 | 完整字段名、类型、取值范围、枚举值 | `"comprehensive_score": 0-100 整数` |
| ④ 质量约束 | 中文输出、禁止编造、客观中立等 | "评分必须有依据，不足处如实指出" |

硬性规则：

1. **输出必须是结构化 JSON**——禁止要求/接受大段自然语言作为接口结果（错误示范：`{"answer": "你的能力不错…"}`）；
2. 字段名与 02 文档契约**逐字一致**（含下划线、单复数）；
3. 枚举值与 [03 第 4 章](./03-数据库设计文档.md) 数据字典一致（如 `importance`：必须/加分）；
4. 修改 Prompt 属于兼容变更（输出契约不变时），但**改变了输出字段即属于破坏性变更**，须走 [02 第 12.2 节](./02-API接口文档.md) 变更流程；
5. Prompt 文件头部建议以 HTML 注释标注版本与修改日期（`规划/待实现`：版本化追踪，见第 11 章验收标准与第 12 章规划清单）。

## 8. 四个 AI 业务流程

所有流程的共同骨架：**解析输入（user_id 或内联）→ 构建 Prompt → 调用 → 解析 → 落库/流式返回**。

### 8.1 就业画像分析（`AnalysisService`）

| 项 | 值 |
|----|-----|
| 输入 | `ProfileAnalysisRequest`（user_id 或内联资料，target_job 可选） |
| Prompt | `system_profile_analyst.md` + 画像用户模板 |
| 调用 | `chat_json(temperature=0.3)` |
| 结果字段 | profile_summary / technical_direction / core_advantages / current_level / recommended_directions / areas_to_improve / comprehensive_score / skill_assessment |
| 落库 | `profile_analyses`（含输入快照 + raw_result） |

### 8.2 简历优化（`ResumeService`）

调用 `chat_json(temperature=0.4)`；`target_job` 必填；可选 `original_resume` 原文。结果：optimized_projects / optimized_skills / overall_suggestions / personal_summary / resume_score → `resume_optimizations`。

### 8.3 成长规划（`GrowthService`）

调用 `chat_json(temperature=0.4)`；可选 `profile_analysis`（此前画像结果）作为附加上下文。结果：current_situation / ability_gaps / learning_roadmap / recommended_projects / recommended_resources / interview_prep_tips / expected_timeline → `growth_plans`。

### 8.4 岗位匹配 AI 精排（`JobMatchService._ai_enhance_matches`）

两阶段匹配中的第二阶段：

```
① 技能标准化：normalize_skill()（同义词表，见 05 第 6 章）
② 粗排：用户技能拼接 → KnowledgeService.search(category="jobs", top_k=50)
   → 与岗位 tags 逐项比对（标准化匹配 + 子串回退）→ score = 命中数/要求数×100
③ 精排（仅 live 模式且结果非空）：对 Top-K 逐岗位调用
   chat_json(temperature=0.3)，Prompt 含岗位正文前 500 字与技能要求
④ 融合：AI 分数上限为 粗排分+20（防 AI 虚高）；补充 match_reason /
   learning_suggestions / interview_focus；missing_skills 以 AI 结果为准
⑤ 失败降级：单个岗位精排失败 → 保留该岗位粗排结果（静默，唯一允许吞异常处）
```

结果落库 `job_match_records`（有匹配结果时）。知识检索细节见 [05 第 6-7 章](./05-RAG知识库设计文档.md)。

## 9. SSE 流式设计（`app/api/streaming.py`）

- 三个端点：`/api/stream/analysis|resume|growth`，请求体与同步接口一致；**不落库**。
- `_stream_generator`：依次发送 `start` → 多个 `chunk`（增量文本）→ `complete`（完整 JSON 解析结果或 `raw_text`）；异常时发 `error` 事件（HTTP 仍 200，错误在事件内）。事件格式见 [02 第 9 章](./02-API接口文档.md)。
- `chunk` 拼接结果 = 一次完整 JSON 文本；前端优先使用 `complete.result`。
- 流式与同步接口的 Prompt 构建逻辑一致，但流式路径**未落库**、未做历史查询——两条路径的数据一致性以同步接口为准。

## 10. 异常处理与降级总表

| 场景 | 行为 |
|------|------|
| 未配置 API Key | 全链路 Mock，业务接口正常返回（`is_mock=true`） |
| 上游限流/网络抖动 | 指数退避重试（≤`AI_MAX_RETRIES`），耗尽抛 `AIServiceError` |
| AI 返回非 JSON | 两层容错解析；仍失败抛 `AIServiceError(TYPE_PARSE_ERROR)` |
| 岗位匹配精排失败 | 静默降级为关键词粗排结果 |
| 核心分析调用失败 | 异常冒泡 → 全局处理器（当前 HTTP 500 / code=1，错误码映射为待修复项） |
| SSE 中途出错 | 发送 `error` 事件，连接结束 |

## 11. AI 功能验收标准

一个 AI 功能（或 Prompt 修改）要标记为"完成"，必须逐项满足：

| # | 验收项 | 标准 |
|---|--------|------|
| 1 | 输出格式稳定 | 连续 3 次调用，返回均能解析为合法 JSON 且字段与契约一致（`chat_json` 不抛 `TYPE_PARSE_ERROR`） |
| 2 | Prompt 可追踪 | 外置 md 生效（删除文件时 fallback 提示在日志可见）；`规划/待实现`：文件头版本注释 |
| 3 | Mock/Live 一致 | Mock 模式返回结构与 live 契约完全一致（前端切换无感知） |
| 4 | 异常可处理 | 上游超时/限流/非 JSON 输出三类场景有对应行为（见第 10 章总表），不出现未捕获异常 |
| 5 | 落库正确 | 结果快照与 `raw_result` 均正确写入对应记录表（同步接口） |
| 6 | 成本可见 | `GET /api/usage` 能反映该功能的 Token 消耗（live 模式） |
| 7 | 测试覆盖 | Mock 模式下有 TestClient 集成用例且通过（[01 第 11.2 节](./01-项目开发说明书.md)） |

验证方式：Swagger 走通"创建用户 → 触发 AI 功能 → 查历史记录"完整路径；回归命令见 [01 第 12.3 节](./01-项目开发说明书.md)。
